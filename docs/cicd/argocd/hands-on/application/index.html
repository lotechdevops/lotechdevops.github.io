Criando uma Application

Fundamentos​

Uma Application liga uma pasta do Git (origem) a um namespace do cluster (destino). Neste lab você vai ver, com um app simples, os comportamentos que definem o GitOps:

ComportamentoO que você vai comprovar
Sync manualO Argo CD só aplica quando você manda
DriftMudança manual no cluster vira OutOfSync
Self-healCom selfHeal, o Argo CD desfaz a mudança manual
Deploy por Gitgit push altera o cluster, sem kubectl
PruneApagar do Git apaga do cluster
Rollbackgit revert volta a versão
Pré-requisitos
  • Lab 4 concluído (Project homelab criado).
  • ARGOCD_OPTS definido no terminal.

Prática​

1. Criar os manifestos da aplicaçãoc​

Usamos o whoami (responde com o nome do pod), com versão fixa da imagem.

cd ~/gitops/gitops-homelab
mkdir -p apps/whoami
# apps/whoami/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: whoami
spec:
  replicas: 1
  selector:
    matchLabels:
      app: whoami
  template:
    metadata:
      labels:
        app: whoami
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.10.3
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
            limits:
              memory: 64Mi
# apps/whoami/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: whoami
spec:
  selector:
    app: whoami
  ports:
    - port: 80
      targetPort: 80
git add apps/whoami
git commit -m "Adiciona o app whoami"
git push
Verifique a tag da imagem

v1.12.0 é a versão que usei como exemplo. Confira que a tag existe em https://hub.docker.com/r/traefik/whoami/tags e mantenha sempre uma versão fixa, nunca latest.

2. Criar a Application (sync manual)​

Começamos sem sincronização automática, para ver o comportamento padrão.

# applications/whoami.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: whoami
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: homelab
  source:
    repoURL: git@github.com:lotechdevops/gitops-homelab.git
    targetRevision: main
    path: apps/whoami
  destination:
    server: https://kubernetes.default.svc
    namespace: demo
  syncPolicy:
    syncOptions:
      - CreateNamespace=true
CampoSignificado
project: homelabProject do Lab 4 (restringe repositório, destino e recursos)
targetRevision: mainBranch lido
path: apps/whoamiPasta com os manifestos
finalizersAo apagar a Application, os recursos dela também são apagados
CreateNamespace=trueCria o namespace demo
kubectl apply -f applications/whoami.yaml
git add applications/whoami.yaml && git commit -m "Adiciona a Application whoami" && git push
application.argoproj.io/whoami created

5. Provocar drift (ainda com sync manual)​

Altere o cluster por fora do Git:

kubectl scale deployment whoami -n demo --replicas=3
deployment.apps/whoami scaled
argocd app get whoami --refresh | grep -E "Sync Status|Health Status"
argocd app diff whoami
Sync Status:        OutOfSync from main (3f2a1c9)
Health Status:      Healthy

===== apps/Deployment demo/whoami ======
155c155
<   replicas: 3
---
>   replicas: 1

O Argo CD detectou o drift. Sem selfHeal, ele só avisa: o cluster segue com 3 réplicas.

kubectl get deploy whoami -n demo
NAME     READY   UP-TO-DATE   AVAILABLE   AGE
whoami   3/3     3            3            2m

(No diff, < é o cluster e > é o Git.)

6. Ligar sync automático com self-heal e prune​

Edite o applications/whoami.yaml e acrescente automated em syncPolicy:

  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
kubectl apply -f applications/whoami.yaml
git add applications/whoami.yaml && git commit -m "whoami: sync automático" && git push

Assim que a política é aplicada, o Argo CD corrige o drift sozinho:

kubectl get deploy whoami -n demo
NAME     READY   UP-TO-DATE   AVAILABLE   AGE
whoami   1/1     1            1            4m

As 3 réplicas voltaram a 1, como no Git.

7. Self-heal em ação​

Tente alterar de novo:

kubectl scale deployment whoami -n demo --replicas=5
kubectl get deploy whoami -n demo -w
NAME     READY   UP-TO-DATE   AVAILABLE   AGE
whoami   1/1     1            1            5m
whoami   1/5     1            1            5m
whoami   1/1     1            1            5m

Em poucos segundos o Argo CD desfaz a mudança. Para o Argo CD, o Git manda.

kubectl get events -n argocd --field-selector involvedObject.name=whoami --sort-by='.lastTimestamp' | tail -3

8. Deploy pelo Git​

O jeito certo de mudar: editar o Git. Altere as réplicas para 2:

sed -i 's/replicas: 1/replicas: 2/' apps/whoami/deployment.yaml
git commit -am "whoami: 2 réplicas"
git push

O Argo CD verifica o Git a cada 3 minutos (sem webhook). Para não esperar, force um refresh:

argocd app get whoami --refresh | grep -E "Sync Status"
kubectl get deploy whoami -n demo
Sync Status:        Synced to main (9b1e4a7)
NAME     READY   UP-TO-DATE   AVAILABLE   AGE
whoami   2/2     2            2            7m

Sem kubectl: o git push foi o deploy.

9. Histórico e rollback​

argocd app history whoami
ID  DATE                           REVISION
0   2026-11-01 11:50:12 -0300 -03  main (3f2a1c9)
1   2026-11-01 11:57:40 -0300 -03  main (9b1e4a7)

Agora tente o rollback do Argo CD:

argocd app rollback whoami 0
FATA[0000] rpc error: code = FailedPrecondition desc = rollback cannot be initiated when auto-sync is enabled

Com sync automático ligado, argocd app rollback não funciona: o Argo CD reaplicaria o Git logo em seguida. O rollback correto é pelo Git:

git revert --no-edit HEAD
git push
argocd app get whoami --refresh | grep "Sync Status"
kubectl get deploy whoami -n demo
Sync Status:        Synced to main (c4d8f21)
NAME     READY   UP-TO-DATE   AVAILABLE   AGE
whoami   1/1     1            1            9m

Voltou a 1 réplica, e o rollback ficou registrado no histórico do Git.

10. Prune: apagar do Git apaga do cluster​

Adicione um ConfigMap, sincronize, e remova:

cat > apps/whoami/configmap.yaml <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: whoami-config
data:
  ambiente: homelab
EOF
git add apps/whoami/configmap.yaml && git commit -m "whoami: configmap" && git push
argocd app get whoami --refresh >/dev/null
kubectl get configmap -n demo whoami-config
NAME            DATA   AGE
whoami-config   1      10s

Agora apague do Git:

git rm apps/whoami/configmap.yaml
git commit -m "whoami: remove configmap" && git push
argocd app get whoami --refresh >/dev/null
kubectl get configmap -n demo whoami-config
Error from server (NotFound): configmaps "whoami-config" not found

Com prune: true, o recurso saiu do cluster. Sem prune, ele ficaria "órfão".

11. Limpeza​

Apagar a Application (com o finalizer) apaga também os recursos dela:

argocd app delete whoami --yes
kubectl get all -n demo
application 'whoami' deleted
No resources found in namespace demo.

O namespace demo continua existindo (o Argo CD não apaga namespaces criados via CreateNamespace):

kubectl delete namespace demo
Não apague o arquivo do Git antes

Se você adotar o padrão app-of-apps (página de Conceitos) com uma Application raiz apontando para applications/, um applications/whoami.yaml esquecido no repositório recria o whoami. Remova o arquivo do Git junto: git rm applications/whoami.yaml.

Resumo​

  • Application = project + source (repo/branch/path) + destination + syncPolicy.
  • Sem automated, o Argo CD só mostra OutOfSync; o sync é manual.
  • Drift = cluster diferente do Git. argocd app diff mostra a diferença.
  • Self-heal desfaz alterações manuais; prune apaga do cluster o que saiu do Git.
  • Deploy = git push. Detecção: 3 minutos, ou argocd app get --refresh / webhook.
  • argocd app rollback não funciona com auto-sync. Use git revert.
  • O finalizer resources-finalizer.argocd.argoproj.io apaga os recursos junto com a Application.
  • Namespace criado com CreateNamespace não é apagado com a Application.
  • Imagem sempre com versão fixa.
