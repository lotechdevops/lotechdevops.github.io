Exposição do Argo CD

Fundamentos​

No Lab 1 o acesso era por port-forward. Aqui o Argo CD ganha um endereço próprio, com HTTPS válido, usando a infraestrutura que já está no cluster:

Navegador ─► (Cloudflare Access ─► Cloudflare Tunnel) ─► Traefik (10.10.20.200) ─► argocd-server
                    opcional, Parte B                    Ingress + TLS (Parte A)
ParteO que entregaDepende de
A. Ingress + TLShttps://argocd.devopsr66.com na rede localMetalLB, Traefik e cert-manager (ClusterIssuer letsencrypt-prod)
B. Cloudflare Tunnel + AccessAcesso de fora da rede, com login, sem abrir portasParte A e um Tunnel já criado

Por que o TLS termina no Traefik​

O chart foi instalado com server.insecure: true. Assim o argocd-server fala HTTP dentro do cluster, e o Traefik apresenta o certificado. Sem isso, o Argo CD redireciona HTTP para HTTPS e entra em loop de redirecionamento.

A CLI e o Ingress​

A CLI usa gRPC, e atrás de um proxy ela precisa do modo gRPC-web (--grpc-web). Com o Cloudflare Access na frente, o login da CLI também seria barrado pela página de login do Access. Por isso, neste lab:

  • Interface web: pelo domínio (Access protege).
  • CLI: continua pelo ARGOCD_OPTS com port-forward do Lab 1.
Pré-requisitos
  • Lab 1 concluído (Argo CD com server.insecure: true e global.domain: argocd.devopsr66.com).
  • Traefik com EXTERNAL-IP 10.10.20.200 e ClusterIssuer letsencrypt-prod funcionando.
  • A máquina que acessa precisa de rota para 10.10.20.0/24.
  • Parte B: um Tunnel já criado e conectado no cluster.

Prática​

Parte A: Ingress com TLS​

1. Conferir os pré-requisitos​

kubectl get svc traefik -n traefik
kubectl get clusterissuer letsencrypt-prod
kubectl get ingressclass
NAME      TYPE           CLUSTER-IP       EXTERNAL-IP    PORT(S)                      AGE
traefik   LoadBalancer   10.108.214.119   10.10.20.200   80:32505/TCP,443:31540/TCP   18h

NAME               READY   AGE
letsencrypt-prod   True    34h

NAME      CONTROLLER                      PARAMETERS   AGE
traefik   traefik.io/ingress-controller   <none>       18h

O ClusterIssuer precisa estar READY=True, e a IngressClass chama-se traefik.

2. Ativar o Ingress no values.yaml​

Edite o values.yaml do Lab 1 (~/gitops/argocd/values.yaml) e deixe assim:

global:
  domain: argocd.devopsr66.com

configs:
  params:
    server.insecure: true

server:
  ingress:
    enabled: true
    ingressClassName: traefik
    annotations:
      cert-manager.io/cluster-issuer: letsencrypt-prod
      traefik.ingress.kubernetes.io/router.entrypoints: websecure
      traefik.ingress.kubernetes.io/router.tls: "true"
    tls: true

O que cada parte faz:

CampoEfeito
ingressClassName: traefikQuem atende este Ingress
cert-manager.io/cluster-issuerPede o certificado ao cert-manager
router.entrypoints: websecureAtende só HTTPS (porta 443)
tls: trueO chart cria a seção tls do Ingress, com o Secret argocd-server-tls
Confira as chaves na sua versão

Os nomes das chaves podem mudar entre versões do chart. Veja o que a sua versão aceita:

helm show values argo/argo-cd --version 10.11.6 | grep -n -A12 "ingress:" | head -50

3. Aplicar com helm upgrade​

Use a mesma versão do Lab 1 (upgrade de versão é outra decisão):

helm upgrade argocd argo/argo-cd \
  --namespace argocd \
  --version 10.11.6 \
  -f ~/gitops/argocd/values.yaml
Release "argocd" has been upgraded. Happy Helming!
NAME: argocd
LAST DEPLOYED: Sun Nov  1 10:53:21 2026
NAMESPACE: argocd
STATUS: deployed
REVISION: 2

4. Acompanhar o certificado​

kubectl get ingress -n argocd
kubectl get certificate -n argocd -w
NAME            CLASS     HOSTS                  ADDRESS        PORTS     AGE
argocd-server   traefik   argocd.devopsr66.com   10.10.20.200   80, 443   28s

NAME                READY   SECRET              AGE
argocd-server-tls   False   argocd-server-tls   30s
argocd-server-tls   True    argocd-server-tls   58s

O DNS-01 leva de 1 a 2 minutos. Se ficar False, veja a seção de troubleshooting.

kubectl get secret argocd-server-tls -n argocd
NAME                TYPE                DATA   AGE
argocd-server-tls   kubernetes.io/tls   2      12s

5. Resolver o nome na sua máquina​

Como o domínio ainda não aponta para o IP interno, aponte pelo /etc/hosts:

echo "10.10.20.200 argocd.devopsr66.com" | sudo tee -a /etc/hosts
getent hosts argocd.devopsr66.com
10.10.20.200    argocd.devopsr66.com
Lembre de remover depois

Se o domínio passar a resolver pelo Cloudflare (Parte B), apague essa linha do /etc/hosts. Uma entrada antiga faz o curl e o navegador ignorarem o Cloudflare e o Access.

6. Testar​

curl -sI https://argocd.devopsr66.com | head -5
HTTP/2 200 
accept-ranges: bytes
content-security-policy: frame-ancestors 'self';
content-type: text/html; charset=utf-8
date: Sun, 01 Nov 2026 13:56:11 GMT

Sem -k: o certificado é válido (Let's Encrypt). Abra https://argocd.devopsr66.com no navegador e entre com o admin.

echo | openssl s_client -connect 10.10.20.200:443 -servername argocd.devopsr66.com 2>/dev/null \
  | openssl x509 -noout -issuer -dates
issuer=C = US, O = Let's Encrypt, CN = R11
notBefore=Nov  1 14:08:00 2026 GMT
notAfter=Jan 30 14:07:59 2027 GMT

(O nome do emissor intermediário pode variar.)

Parte B (opcional): Cloudflare Tunnel e Access​

Reaproveita o Tunnel que já existe. Os detalhes de cada tela estão nas páginas de Cloudflare Tunnel e Cloudflare Access; aqui só o que é específico do Argo CD.

7. Rota no Tunnel​

No painel Zero Trust, em Networks > Tunnels, abra o seu Tunnel, depois Routes > Add route > Published application:

CampoValor
Hostnameargocd.devopsr66.com
Service URLhttps://traefik.traefik.svc.cluster.local
Origin Server Nameargocd.devopsr66.com

O Service URL precisa do prefixo https://. O Origin Server Name faz o cloudflared validar o certificado do Traefik pelo nome certo. Mantenha "Disable TLS certificate verification" desligado.

8. Proteger com Access​

  1. Policy: crie (ou reutilize) uma policy Allow só para o seu e-mail.
  2. Application: Access Controls > Applications > Add > Self-hosted, com o subdomínio idêntico ao da rota (argocd) e o domínio devopsr66.com. Associe a policy.
Confira a grafia do subdomínio

Um erro de digitação (já aconteceu com whaomi) faz o Access não cobrir o host, e o site fica aberto sem login. O teste do passo 10 detecta isso.

9. Remover o /etc/hosts e testar a resolução​

sudo sed -i '/argocd.devopsr66.com/d' /etc/hosts
getent hosts argocd.devopsr66.com
104.21.xx.xx    argocd.devopsr66.com

O IP deve ser do Cloudflare, não 10.10.20.200.

10. Provar que o Access está barrando​

curl -sI https://argocd.devopsr66.com | grep -i -E "^HTTP|^server|^location"
HTTP/2 302
server: cloudflare
location: https://<seu-time>.cloudflareaccess.com/cdn-cgi/access/login/argocd.devopsr66.com?...
  • 302 para cloudflareaccess.com: o Access está protegendo.
  • 200 com server: cloudflare: o Access não cobre o host. Revise o subdomínio da Application.

No navegador, o login do Access aparece primeiro, e depois a tela de login do Argo CD (duas camadas de proteção).

11. Webhooks do Git (nota para depois)​

O Access bloqueia qualquer requisição sem login, incluindo o webhook do GitHub que vamos usar para sincronização imediata. Quando chegarmos lá, será necessária uma policy Bypass limitada ao caminho /api/webhook, ou então o fluxo continuará só com o refresh de 3 minutos.

Resumo​

  • Ingress com ingressClassName: traefik e annotation cert-manager.io/cluster-issuer gera o certificado sozinho.
  • O TLS termina no Traefik; o argocd-server roda em HTTP (server.insecure: true). Sem isso, o loop de redirecionamento é certo.
  • Atualize com helm upgrade ... --version <a mesma> -f values.yaml, sempre pelo arquivo.
  • /etc/hosts serve para testar localmente, mas remova antes de testar o Cloudflare.
  • Tunnel: Service URL https://traefik.traefik.svc.cluster.local e Origin Server Name igual ao host.
  • Access: o teste correto é o curl -sI devolver 302, não 200.
  • A CLI continua pelo port-forward (ARGOCD_OPTS); atrás de proxy ela exigiria --grpc-web.
  • O webhook do Git precisará de um Bypass no Access.
