Lab 8 - ApplicationSet

Fundamentos​

Um ApplicationSet é um "molde" que gera Applications. Em vez de manter um YAML de Application por ambiente ou por aplicação, você escreve um template e uma fonte de dados (generator), e o controller cria, atualiza e remove as Applications sozinho.

Generator (lista de itens) ──► Template (Application com {{variáveis}}) ──► N Applications

Os generators deste lab​

GeneratorFonte dos itensNeste lab
ListUma lista escrita no próprio ApplicationSetdev e prod do mesmo app
Git (diretórios)Pastas do repositórioUma pasta nova em catalogo/ vira uma Application

Existem outros (Cluster, Pull Request, Matrix, Merge), descritos na página de Conceitos.

Três cuidados antes de começar​

  1. O ApplicationSet é dono das Applications que gera. Se você editar uma Application gerada à mão, o controller desfaz a mudança. A edição certa é no template.
  2. Apagar o ApplicationSet apaga as Applications geradas, e (com o finalizer de cascade) também os recursos delas. A proteção é o preserveResourcesOnDeletion, que vamos usar.
  3. Nomes não podem colidir com Applications que já existem. Por isso este lab usa nomes novos (whoami-dev, whoami-prod), sem mexer no whoami do Lab 5.
Pré-requisitos
  • Labs 1 a 5 concluídos (Project homelab e repositório conectado). O Lab 7 (notificações) é opcional.
  • Login da CLI funcionando.
  • O Project homelab permite os namespaces demo e demo-*, e os recursos Deployment e Service.

Prática​

Parte A: generator List (dev e prod)​

1. Criar os manifestos com Kustomize​

Uma base comum e um overlay por ambiente, que só muda o número de réplicas:

cd ~/gitops/gitops-homelab
mkdir -p apps/whoami-envs/base apps/whoami-envs/overlays/dev apps/whoami-envs/overlays/prod
# apps/whoami-envs/base/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: whoami
spec:
  replicas: 1
  selector:
    matchLabels:
      app: whoami
  template:
    metadata:
      labels:
        app: whoami
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.10.3
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
            limits:
              memory: 64Mi
# apps/whoami-envs/base/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: whoami
spec:
  selector:
    app: whoami
  ports:
    - port: 80
      targetPort: 80
# apps/whoami-envs/base/kustomization.yaml
resources:
  - deployment.yaml
  - service.yaml
# apps/whoami-envs/overlays/dev/kustomization.yaml
resources:
  - ../../base
replicas:
  - name: whoami
    count: 1
# apps/whoami-envs/overlays/prod/kustomization.yaml
resources:
  - ../../base
replicas:
  - name: whoami
    count: 2

Confira localmente (se tiver o kubectl, ele já traz o Kustomize):

kubectl kustomize apps/whoami-envs/overlays/prod | grep -E "replicas|name: whoami"
  name: whoami
  name: whoami
  replicas: 2
git add apps/whoami-envs
git commit -m "Adiciona whoami por ambiente (kustomize)"
git push

2. Criar o ApplicationSet​

# applications/whoami-envs-appset.yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: whoami-envs
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]

  # Protege os recursos se o ApplicationSet for apagado
  syncPolicy:
    preserveResourcesOnDeletion: true

  generators:
    - list:
        elements:
          - env: dev
          - env: prod

  template:
    metadata:
      name: 'whoami-{{.env}}'
    spec:
      project: homelab
      source:
        repoURL: git@github.com:lotechdevops/gitops-homelab.git
        targetRevision: main
        path: 'apps/whoami-envs/overlays/{{.env}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: 'demo-{{.env}}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true

O que cada parte faz:

CampoFunção
goTemplate: trueUsa a sintaxe Go ({{.env}}) nas variáveis
missingkey=errorFalha se o template usar uma variável que não existe, em vez de gerar vazio
generators.listCada item (env: dev, env: prod) vira uma Application
templateO molde da Application; {{.env}} é substituído a cada item
preserveResourcesOnDeletionApagar o ApplicationSet não apaga os recursos no cluster

O {{.env}} forma os nomes whoami-dev/whoami-prod e os namespaces demo-dev/demo-prod, ambos permitidos pelo Project (demo-*).

3. Aplicar​

kubectl apply -f applications/whoami-envs-appset.yaml
git add applications/whoami-envs-appset.yaml && git commit -m "Adiciona o ApplicationSet whoami-envs" && git push
applicationset.argoproj.io/whoami-envs created

kubectl get deploy -n demo-dev

dev com 1 réplica e prod com 2: é a diferença dos overlays.

5. Provar que o ApplicationSet manda nas Applications​

Edite à mão uma Application gerada:

kubectl patch app whoami-dev -n argocd --type merge \
  -p '{"spec":{"source":{"targetRevision":"HEAD"}}}'
sleep 5
kubectl get app whoami-dev -n argocd -o jsonpath='{.spec.source.targetRevision}'; echo
main

O controller desfez a mudança: o valor voltou ao do template. Para alterar de verdade, mude o ApplicationSet.

6. Adicionar um ambiente: um item na lista​

Acrescente staging à lista do ApplicationSet:

        elements:
          - env: dev
          - env: staging
          - env: prod

Crie o overlay correspondente e aplique:

mkdir -p apps/whoami-envs/overlays/staging
cat > apps/whoami-envs/overlays/staging/kustomization.yaml <<'EOF'
resources:
  - ../../base
replicas:
  - name: whoami
    count: 1
EOF
kubectl apply -f applications/whoami-envs-appset.yaml
git add -A && git commit -m "whoami-envs: adiciona staging" && git push
argocd app list | grep whoami
argocd/whoami-dev      ... demo-dev      homelab  Synced  Healthy
argocd/whoami-prod     ... demo-prod     homelab  Synced  Healthy
argocd/whoami-staging  ... demo-staging  homelab  Synced  Healthy

Um item na lista, uma Application nova.

Parte B: generator Git (pasta nova vira Application)​

7. Criar a pasta do catálogo​

Cada subpasta de catalogo/ será uma aplicação. Vamos começar com uma, hello:

mkdir -p catalogo/hello
cat > catalogo/hello/deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
spec:
  replicas: 1
  selector:
    matchLabels:
      app: hello
  template:
    metadata:
      labels:
        app: hello
    spec:
      containers:
        - name: hello
          image: traefik/whoami:v1.10.3
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
            limits:
              memory: 64Mi
EOF
git add catalogo && git commit -m "catalogo: app hello" && git push
Use uma pasta separada de apps/

O generator vai varrer catalogo/*. Não aponte para apps/*: ele também pegaria apps/whoami, que já é gerenciado pela Application do Lab 5, e geraria uma Application com o mesmo nome em conflito.

8. Criar o ApplicationSet do catálogo​

# applications/catalogo-appset.yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: catalogo
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]

  syncPolicy:
    preserveResourcesOnDeletion: true

  generators:
    - git:
        repoURL: git@github.com:lotechdevops/gitops-homelab.git
        revision: main
        directories:
          - path: catalogo/*

  template:
    metadata:
      name: 'catalogo-{{.path.basename}}'
    spec:
      project: homelab
      source:
        repoURL: git@github.com:lotechdevops/gitops-homelab.git
        targetRevision: main
        path: '{{.path.path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: 'demo-{{.path.basename}}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true

As variáveis do generator Git: {{.path.path}} (o caminho, catalogo/hello) e {{.path.basename}} (o nome da pasta, hello).

kubectl apply -f applications/catalogo-appset.yaml
git add applications/catalogo-appset.yaml && git commit -m "Adiciona o ApplicationSet catalogo" && git push
argocd app list | grep catalogo
argocd/catalogo-hello  https://kubernetes.default.svc  demo-hello  homelab  Synced  Healthy  Auto-Prune

9. Uma pasta nova vira uma Application, sem mexer no Argo CD​

cp -r catalogo/hello catalogo/hello2
sed -i 's/hello/hello2/g' catalogo/hello2/deployment.yaml
git add catalogo && git commit -m "catalogo: app hello2" && git push

O generator Git consulta o repositório a cada 3 minutos (ou imediatamente com webhook). Para não esperar, force a leitura reiniciando o refresh do ApplicationSet:

kubectl annotate applicationset catalogo -n argocd argocd.argoproj.io/application-set-refresh=true --overwrite
sleep 10
argocd app list | grep catalogo
argocd/catalogo-hello   ... demo-hello   homelab  Synced  Healthy
argocd/catalogo-hello2  ... demo-hello2  homelab  Synced  Healthy

Sem kubectl apply, sem YAML de Application: só uma pasta nova no Git.

Remover a pasta tem o efeito inverso, graças ao prune e ao finalizer da geração (a Application some, e os recursos dela só são apagados se a política permitir; veja a próxima seção).

Parte C: proteger contra apagar tudo​

10. Provar o preserveResourcesOnDeletion​

Os dois ApplicationSets têm preserveResourcesOnDeletion: true. Apague o do catálogo:

kubectl delete applicationset catalogo -n argocd
sleep 5
argocd app list | grep catalogo
kubectl get deploy -n demo-hello
(nenhuma Application catalogo-*)
NAME    READY   UP-TO-DATE   AVAILABLE   AGE
hello   1/1     1            1           6m

As Applications sumiram, mas os recursos continuam rodando no cluster. Sem essa opção, apagar o ApplicationSet derrubaria os recursos junto.

Isso vale para o ApplicationSet inteiro

Apagar um ApplicationSet por engano, sem preserveResourcesOnDeletion, derruba todas as aplicações geradas. Deixe sempre ligado em ambientes importantes.

11. Limpeza​

Os recursos ficaram órfãos de propósito. Remova-os, junto com o ApplicationSet restante:

kubectl delete applicationset whoami-envs -n argocd
kubectl delete namespace demo-dev demo-staging demo-prod demo-hello demo-hello2
git rm -r --quiet catalogo apps/whoami-envs applications/whoami-envs-appset.yaml applications/catalogo-appset.yaml
git commit -m "Limpeza do lab ApplicationSet" && git push
applicationset.argoproj.io "whoami-envs" deleted
namespace "demo-dev" deleted
...
Por que o git rm?

Os YAMLs de applications/ são só dos labs. Se ficarem no repositório, qualquer ferramenta que leia essa pasta (como um app-of-apps no futuro) recria os recursos. Por isso a limpeza inclui o git rm.

Resumo​

  • ApplicationSet = template + generator → várias Applications, geradas e mantidas pelo controller.
  • List: itens fixos (ambientes). Git (diretórios): cada pasta vira uma Application.
  • Variáveis com goTemplate: true: {{.env}}, {{.path.basename}}, {{.path.path}}. Use missingkey=error.
  • O ApplicationSet é dono das Applications: edição manual nelas é desfeita.
  • Apagar o ApplicationSet apaga as Applications; preserveResourcesOnDeletion: true mantém os recursos.
  • O generator Git consulta o repositório a cada 3 minutos (ou por webhook).
  • Não deixe o generator Git varrer pastas já gerenciadas por outra Application.
  • Kustomize por ambiente (base + overlays/<env>) combina bem com o generator List.
