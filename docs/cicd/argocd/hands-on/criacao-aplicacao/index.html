Criação da Application no ArgoCD

Objetivo​

Nesta etapa, vamos criar uma Application dentro do ArgoCD, o recurso que liga o repositório Git ao cluster Kubernetes e faz o deploy automático dos manifests.

A Application é o coração do GitOps, pois ela monitora um caminho dentro do seu repositório e garante que o estado real do cluster esteja sempre igual ao estado declarado no Git.

Configuração​

1. Criando uma Application via ArgoCD UI​

  1. No painel do ArgoCD, acesse o menu lateral esquerdo -> Applications.
  2. Clique em NEW APP

2. Aba "General" - Identidade e política de sincronização​

Nesta etapa, definimos o nome da aplicação, o Project ao qual ela pertence e o comportamento de sincronização da aplicação.

  • Application Name -> Nome lógico da aplicação no ArgoCD (ex: nginx-dev).

  • Project -> Vincula a aplicação ao Project criado anteriormente. (ex: dev).

  • Sync Policy -> Define como a sincronização será feita.

    • Manual -> O ArgoCD apenas detecta mudanças, mas o operador precisa clicar em "Sync" para aplicá-las.
    • Automatic -> O ArgoCD aplica as mudanças detectadas sem intervenção do operador.

    Ao selecionar Automatic, surgem três opções adicionais que controlam o comportamento do GitOps:

    • Enable Auto-Sync -> Aplica automaticamente toda mudança detectada no Git.
    • Prune Resource -> Remove recursos que foram deletados do repositório Git.
    • Self-Heal -> Restaura automaticamente qualquer alteração feita manualmente no cluster.

  • Sync Options -> Essas opções refinam o comportamento do deploy e ajudam a lidar com casos específicos.

    • Auto-Create Namespace -> Cria automaticamente o namespace, caso ele não exista.
    • Service-Side Apply -> Usa o modo --server-side do kubectl, aplicando alterações diretamente no cluster.
    • Prune Last -> Deleta recursos antigos após aplicar os novos, evitando downtime em atualizações.
    • Skip Schema Validation -> Ignora a validação de schema dos manifests durante a aplicação.
    • Respect Ignore Differences -> Respeita regras de exclusão definidas na Application (ignoreDifferences), impedindo sincronização de campos ignorados.
    • Apply out of sync only -> Aplica apenas os recursos que estão fora de sincronismo, em vez de reaplicar todos.

  • Prune Propagation Policy -> Controla como o Kubernetes vai deletar recursos durante o processo de prune (remoção de objetos que foram apagados do Git).

    • foreground -> Espera todos os recursos dependentes serem removidos antes de deletar o recurso pai.
      • Ex: Aguarda os Pods terminarem antes de encerrar o Deployment.
    • background -> Deleta o recurso pai imediatamente e deixa o Kubernetes remover os filhos em segundo plano.
      • Ex: Deleta o Deployment imediatamente, e os Pods morrem logo depois.
    • orphan -> Remove apenas o recurso pai e mantém os filhos no cluster.
      • Ex: Deleta só o Deployment, mas os Pods continuam rodando (sem controle).

  • Replace -> Essa opção altera a forma como o ArgoCD atualiza os recursos no cluster:

    • Padrão -> O ArgoCD usa o comando: kubectl apply.
      • Atualiza apenas os campos alterados
    • Com Replace habilitado -> Ele usa o comando: kubectl replace, que substitui o recurso inteiro.
      • Deleta e recria o recurso do zero.

  • Retry -> Controla como o ArgoCD lida com falhas de sincronização. O bloco de configuração Retry pode ser ajustado via YAML ou interface, com os seguintes parâmetros:

    • Limit -> Número máximo de tentativas antes de desistir. (ex: 5)
    • Duration -> Tempo base entre as tentativas. (ex: 5s)
    • Factor -> Multiplicador exponencial para cada tentativa subsequente (ex: 2)
    • Max Duration -> Tempo máximo de espera entre tentativas (ex: 3m)

3. Aba "SOURCE" - Origem dos manifests​

Aqui definimos de onde o ArgoCD buscará os arquivos YAML.

  • Repository URL -> Repositório conectado via SSH. (ex: git@github.com:lotechdevops/infra.git)
  • Revision -> Branch que o ArgoCD irá monitorar. (ex: main)
  • Path -> Caminho dentro do repositório onde estão os manifests. (ex: apps/dev/nginx)
    • Esse path corresponde à estrutura do seu repositório Git. 
      infra/
          └── apps/
              └── dev/
                  └── nginx/
                      └── deployment.yaml

4. Aba "DESTINATION" - Onde será aplicado​

Aqui definimos o cluster e namespace de destino:

  • Cluster URL -> URL do cluster Kubernetes. (ex: https://kubernetes.default.svc)
  • Namespace -> Namespace de destino. (ex: dev)

5. Aba "DIRECTORY" - Estrutura de leitura​

Essa aba define como o ArgoCD vai interpretar os arquivos YAML dentro do caminho (path) especificado no repositório Git.

Ela é especialmente útil quando você quer aplicar filtros, variáveis ou controle sobre a forma como os manifests são processados.

  • Directory Recurse ->

    • Função: Faz o ArgoCD percorrer recursivamente as subpastas dentro do diretório definido no campo Path da aba "Source".
    • Padrão: Desativado (procura apenas YAMLs na pasta raiz do path).
    • Quando usar: Quando seu repositório tem manifests espalhados em subdiretórios (por exemplo: deployments, services, configmaps dentro de apps/dev/nginx).
    • Exemplo:
          apps/
            └── dev/
                └── nginx/
                    ├── deployment/
                    │   └── deployment.yaml
                    ├── service/
                    │   └── service.yaml
                    └── configmap/
                    └── nginx-config.yaml

Se essa opção estiver desmarcada, o ArgoCD só aplicará YAMLs do diretório nginx/.

  • Top-Level Arguments ->

    • Função: Permite inserir parâmetros personalizados que o ArgoCD repassa ao renderizador do diretório (como kustomize ou helm template).
    • Quando usar:
      • Se o diretório usa Kustomize (kustomization.yaml), você pode passar argumentos adicionais, como: --load-restrictor=LoadRestrictionsNone.
      • Se for Helm, pode definir parâmetros extras de renderização.
      • Em YAML puro, raramente é necessário.

  • External Variables ->

    • Função: Permite definir variáveis externas que podem ser usadas dentro dos manifests. Elas são substituídas durante a renderização antes da aplicação no cluster.
    • Quando usar:
      • Quando seus YAMLs têm placeholders, como ${DOMAIN} ou ${IMAGE_TAG}, e você quer injetar valores diferentes por ambiente.
      • Quando quer compartilhar uma Application entre projects, mudando apenas as variáveis.
    • Exemplo:
        External Variables:
        - name: DOMAIN
          value: devopsr66.com
        - name: IMAGE_TAG
          value: 1.27.1

    O ArgoCD substituirá automaticamente essas variáveis no momento da renderização. Mas atenção: O YAML precisa referenciá-las no formato ${VARIAVEL}.

  • Include ->

    • Função: Permite incluir apenas determinados arquivos ou pastas durante a renderização. É uma espécie de "filtro positivo".
    • Quando usar:
      • Quando seu diretório contém arquivos de configuração que não devem ser aplicados no cluster (ex.: README, scripts, templates).
      • Quando quer limitar a sincronização apenas a certos manifests.
      • Exemplo:
          INCLUDE:
              - deployment/*.yaml
              - service/*.yaml

  • Exclude ->

    • Função: Faz o oposto do Include: exclui arquivos ou subpastas da sincronização.
    • Quando usar:
      • Quando há arquivos YAML de exemplo, backup ou testes no mesmo diretório.
      • Quando deseja que o ArgoCD ignore manifests que não fazem parte do deploy atual.
    • Exemplo: 
          EXCLUDE:
              - README.md
              - old/
              - *.bak.yaml

Criação do Application via YAML​

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-dev
  namespace: argocd
spec:
  project: dev
  source:
    repoURL: https://github.com/lotechdevops/infra.git
    targetRevision: main
    path: apps/dev/nginx
  destination:
    server: https://kubernetes.default.svc
    namespace: dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
