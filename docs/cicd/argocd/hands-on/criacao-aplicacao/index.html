Criação da Application no ArgoCD

Objetivo​

Nesta etapa, vamos criar uma Application no ArgoCD para fazer o deploy do kube-prometheus-stack no namespace observabilidade.

A Application será criada no Project prometheus que configuramos anteriormente e utilizará um Helm Chat com values customizados armazenados no Git.

Pré-requisitos

  • Project prometheus criado
  • Namespace observabilidade existente no cluster
  • Repositório Git com os manifestos configurado

Passo 1: Preparar o namespace de destino​

Antes de criar a Application, certifique-se de que o namespace existe:

kubectl create namespace observabilidade

Ou habilite a criação automática na Application (veremos adiante).

Passo 2: Criar o arquivo da Application​

Crie o arquivo prometheus-application.yaml:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: prometheus
  namespace: argocd
spec:
  project: prometheus
  
  # Múltiplos sources: Helm Chart oficial + Values do Git
  sources:
    # Source 1: Helm Chart oficial do Prometheus
    - repoURL: https://prometheus-community.github.io/helm-charts
      chart: kube-prometheus-stack
      targetRevision: 79.5.0
      helm:
        releaseName: prometheus
        valueFiles:
          - $values/apps/values/prometheus/values.yaml
        skipCrds: false
    
    # Source 2: Repositório Git com os values customizados
    - repoURL: git@github.com:lotechdevops/apps-argocd.git
      targetRevision: main
      ref: values
  
  # Destino no cluster
  destination:
    server: https://kubernetes.default.svc
    namespace: observabilidade
  
  # Política de sincronização
  syncPolicy:
    automated:
      enabled: true
      prune: true
      selfHeal: true
    retry:
      limit: 5
      backoff:
        duration: "5s"
        factor: 2
        maxDuration: "3m"
    syncOptions:
      - CreateNamespace=true
      - PruneLast=true
      - ServerSideApply=true

Passo 3: Aplicar a Application​

kubectl apply -f prometheus-application.yaml

Passo 4: Verificar a criação​

Via kubectl

kubectl get application prometheus -n argocd

Saída esperada:

Via ArgoCD CLI

argocd app get prometheus

Passo 5: Acompanhar a sincronização​

Visualizar logs da sincronização

argocd app logs prometheus --follow

Visualizar recursos criados

kubectl get all -n observabilidade

Ver detalhes no ArgoCD UI

  1. Acesse o ArgoCD UI
  2. Clique na Application prometheus
  3. Visualize o grafo de recursos criados

Entendendo múltpilos sources​

Esta application usa uma configuração avançada com dois sources:

Source 1: Helm Chart oficial

- repoURL: https://prometheus-community.github.io/helm-charts
  chart: kube-prometheus-stack
  targetRevision: 79.5.0
  helm:
    releaseName: prometheus
    valueFiles:
      - $values/apps/values/prometheus/values.yaml
    skipCrds: false

Campos importantes:

  • repoURL: Repositório Helm oficial do prometheus
  • chart: Nome do chart a ser instalado
  • targetRevision: Versão específica do chart (fixada para estabilidade)
  • helm.releaseName: Nome da release do Helm no cluster
  • ValuesFiles: Referência ao arquivo de values customizados usando $values
  • skipCrds: false = instala os CRDs necessários

Source 2: Values customizados no Git

- repoURL: git@github.com:lotechdevops/apps-argocd.git
  targetRevision: main
  ref: values

Campos importantes:

  • ref: values: Define um alias $values que pode ser referenciado no source 1
  • Permite manter os values customizados versionados no Git
  • Facilita auditoria e rollback de configurações

Como o ArgoCD processa

  1. ArgoCD clona o repositório Git (source 2)
  2. Busca o Helm Chart oficial (source 1)
  3. Aplica os values de $values/apps/values/prometheus/values.yaml sobre os valores padrão
  4. Renderiza os templates e aplica no cluster

Por que usar múltiplos sources?

  • Separação de responsabilidades: Chart oficial + configurações customizadas
  • Versionamento: Values no Git permitem rastreabilidade completa
  • Facilidade de upgrade: Atualiza o chart sem perder customizações
  • Reutilização: Mesmos values para diferentes ambientes
  • Segurança: Chart oficial mantido pela comunidade, apenas values customizados

Estrutura do repositório​

apps-argocd/
├── apps/
│   └── values/
│       └── prometheus/
│           └── values.yaml    ← Customizações do Prometheus
└── apps/
    └── applications/
        └── prometheus.yaml     ← Application manifest

Alternativa: Criação via ArgoCD UI​

Passo 1: Acessar criação da Application​

  1. No painel do ArgoCD, acesse o menu lateral esquerdo -> Applications
  2. Clique em NEW APP

Passo 2: Aba General​

Nesta etapa, definimos o nome da aplicação, o Projeto ao qual ela pertence e o comportamento de sincronização

Campos básicos:

Application Name

  • Nome lógico da aplicação no ArgoCD

Project

  • Vincula a aplicação ao Project criado anteriormente

Sync Policy

  • Manual: O ArgoCD apenas detecta mudanças, mas o operador precisa clicar em "Sync" para aplicá-las.
  • Automatic: O ArgoCD aplica as mudanças detectadas sem intervenção do operador.

Ao selecionar Automatic, surgem três opções adicionais:

  • Enable Auto-Sync: Aplica automaticamente toda mudança detectada no Git
  • Prune resources: Remove recursos que foram deletados do repositório Git
  • Self-Heal: Restaura automaticamente qualquer alteração feita manualmente no cluster

Sync Options

Essas opções refinam o comportamento do deploy:

  • Auto-Create Namespace:

    • Cria automaticamente o namespace, caso ele não exista
    • Equivalente a: CreateNamespace=true

  • Server-Side Apply:

    • Usa o modo --server-side do kubectl
    • Aplica alterações diretamente no cluster
    • Melho0r para recursos grandes e CRDs

  • Prune Last:

    • Deleta recursos antigos após aplicar os novos
    • Evita downtime em atualizações
    • Equivalente a: PruneLast=true

  • Skip Schema Validation:

    • Ignora a validação de schema dos manifestos durante a aplicação
    • Use quando o schema validation causar problemas

  • Respect Ignore Differences:

    • Respeita regras de exclusão definidas na Application (ignoreDifferences)
    • Impede sincronização de campos ignorados

  • Apply Out of Sync Only:

    • Aplica apenas os recursos que estão fora de sincronismo, em vez de reaplicar todos

  • Prune Propagation Policy:

    • Controla como o Kubernetes vai deletar recursos durante o processo de prune:

      • foreground

        • Espera todos os recursos dependentes serem removidos antes de deletar o recurso pai

      • background

        • Deleta o recurso pai imediatamente e deixa o Kubernetes remover os filhos em segundo plano

      • orphan

        • Remove apenas o recurso pai e mantém os filhos no cluster

  • Replace:

    • Essa opção altera a forma como o ArgoCD atualiza os recursos no cluster:

      • Padrão

        • O ArgoCD usa o comando: kubectl apply
        • Atualiza apenas os campos alterados

      • Com Replace habilitado

        • Ele usa o comando kubectl replace
        • Substitui o recurso inteiro
        • Deleta e recria o recurso do zero

  • Retry:

    • Controla como o ArgoCD lida com falhas de sincronização:

      • Limit

        • Número máximo de tentativas antes de desistir

      • Duration

        • Tempo base entre as tentativas

      • Factor

        • Multiplicador exponencial para cada tentativa subsequente

      • Max Duration

        • Tempo máximo de espera entre tentativas

Passo 3: Aba Source​

Aqui definimos de onde o ArgoCD buscará os arquivos

  • Repository URL

    • Repositório conectado via SSH ou HTTPS
    • Exemplo SSH: git@github.com:lotechdevops/apps-argocd.git
    • Exemplo HTTPS: https://github.com/lotechdevops/apps-argocd.git

  • Revision

    • Branch que o ArgoCD irá monitorar

  • Path

    • Caminho dentro do repositório onde estão os manifestos

Passo 4: Aba Destination​

Aqui definimos o cluster e namespace de destino:

  • Cluster URL

    • URL do cluster Kubernetes
    • Para o cluster local: https://kubernetes.default.svc
    • Para clusters externos: URL do API server

  • Namespace

    • Namespace de destino

Passo 5: Aba Directory​

Esta aba aparece quando você está usando YAMLs diretos (não Helm Charts)

Essa aba define como o ArgoCD vai interpretar os arquivos YAML dentro do caminho especificado

  • Directory Recurse

    • Função: Faz o ArgoCD percorrer recursivamente as subpastas dentro do diretório definido no Path.
    • Padrão: Desativado (procura apenas YAMLs na pasta raiz do path)
    • Quando usar: Quando seu repositório tem manifestos espalhados em subdiretórios

  • Top-Level Arguments

    • Função: Permite inserir parâmetros personalizados que o ArgoCD repassa ao renderizador do diretório.
    • Quando usar:
      • Se o diretório usa Kustomize (kustomization.yaml), você pode passar argumentos como --load-restrictor=LoadRestrictionsNone
      • Se for Helm, pode definir parâmetros extras de renderização
      • Em YAML puro, raramente é necessário

  • External Variables

    • Função: Permite definir variáveis externas que podem ser usadas dentro dos manifestos.
    • Quando usar:
      • Quando seus YAMLs têm placeholders como ${DOMAIN} ou ${IMAGE_TAG}
      • Quando quer compartilhar uma Application entre ambientes, mudando apenas as variáveis.

    O ArgoCD substituirá automaticamente essas variáveis no momento da renderização

  • Include

    • Função: Permite incluir apenas determinados arquivos ou pastas durante a renderização.
    • Quando usar:
      • Quando seu diretório contém arquivos que não devem ser aplicados no cluster.
      • Quando quer limitar a sincronização apenas a certos manifestos

  • Exclude

    • Função: Faz o oposto do Include - exlui arquivos ou subpastas da sincronização.
    • Quando usar:
      • Quando há arquivos YAML de exemplo, backup ou testes no mesmo diretório
      • Quando deseja que o ArgoCD ignore manifestos que não fazem parte do deploy atual

Passo 6: Criar a Application​

Após preencher todos os campos, clique em CREATE

Comandos úteis​

  • Ver status da application
argocd app get prometheus
  • Forçar sincronização
argocd app sync prometheus
  • Ver diferenças (Git vs Cluster)
argocd app diff prometheus
  • Ver histórico de sincronizações
argocd app history prometheus
  • Fazer rollback
argocd app rollback prometheus <revision-id>
  • Ver logs da application
argocd app logs prometheus --follow
  • Ver parâmetros Helm usados
argocd app get prometheus --show-params
  • Pausar sincronização automática
argocd app set prometheus --sync-policy none
  • Reativar sincronização automática
argocd app set prometheus --sync-policy automated
  • Deletar application
argocd app delete prometheus

Próximos passos​

Agora que a Application está criada e funcionando:

  1. Monitore a sincronização no ArgoCD UI
  2. Teste fazer mudanças no Git e veja aplicar automaticamente
  3. Configure alertas para problemas de sincronização
