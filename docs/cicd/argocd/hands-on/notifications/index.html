Lab 7 - Notificações no Telegram

Fundamentos​

O Notifications Controller observa as Applications e envia mensagens quando algo acontece. Ele é configurado com quatro peças:

PeçaO que éOnde fica
ServicePara onde enviar (Telegram, Slack, e-mail...) e como autenticarargocd-notifications-cm (service.telegram)
TemplateO texto da mensagemargocd-notifications-cm (template.*)
TriggerQuando enviar (uma condição sobre a Application) e qual template usarargocd-notifications-cm (trigger.*)
SubscriptionQuem recebe: uma annotation na Application (ou assinatura padrão)Annotation na Application
Application muda de estado ─► Trigger (a condição é verdadeira?) ─► Template (monta o texto) ─► Service (Telegram) ─► você
                                          ▲
                              Subscription (annotation) diz para onde

Os nomes de trigger e template só existem se você os definir (ou instalar o catálogo oficial). Uma annotation que assina um trigger inexistente (como on-sync-succeeded, sem tê-lo definido) é ignorada sem erro. Por isso definimos os nossos aqui.

Segredo do bot​

O token do bot do Telegram dá controle total do bot, então é um segredo. Vamos entregá-lo como SealedSecret (Lab 6), e não no values.yaml.

Pré-requisitos
  • Labs 1 a 6 concluídos (Sealed Secrets funcionando, Application whoami com sync automático).
  • Uma conta no Telegram.
  • Login da CLI funcionando.

Prática​

1. Criar o bot no Telegram​

  1. No Telegram, abra uma conversa com @BotFather.
  2. Envie /newbot e siga as perguntas (nome e usuário do bot; o usuário termina em bot).
  3. O BotFather devolve o token (formato 123456789:AA...). Copie.
O token é uma credencial

Quem tem o token controla o bot. Não cole em chats, nem no Git. Se vazar, no BotFather use /revoke para gerar outro.

Guarde o token em uma variável sem deixar no histórico do terminal:

read -rs TELEGRAM_TOKEN
# cole o token e pressione Enter (nada aparece na tela)
echo "${#TELEGRAM_TOKEN} caracteres"
46 caracteres

2. Criar um grupo e descobrir o ID​

Use um grupo, não a conversa privada

O Argo CD aceita como destino o usuário de um canal público ou o ID negativo de um canal/grupo. Com o ID positivo da sua conversa privada com o bot, o curl direto funciona, mas o controller falha com Bad Request: chat not found. Por isso, use um grupo.

  1. No Telegram, crie um grupo (por exemplo, "Alertas_ArgoCD") e adicione o seu bot.
  2. No grupo, envie um comando para o bot, mencionando-o (em grupos, o bot só recebe comandos e menções): /start@SEU_BOT.
  3. Consulte as mensagens recebidas:
curl -s "https://api.telegram.org/bot${TELEGRAM_TOKEN}/getUpdates?timeout=0&offset=-1" | python3 -m json.tool | grep -B1 -A4 '"chat"'
"chat": {
    "id": -4512345678,
    "title": "Alertas_ArgoCD",
    "type": "group"

O id é negativo (-4512345678): é o chat ID do grupo. Ele não é segredo. Se o grupo virar supergrupo, o ID passa a ter o formato -100...; use sempre o que o getUpdates mostrar.

CHAT_ID=-4512345678   # troque pelo seu

3. Testar o bot fora do Argo CD​

Antes de mexer no cluster, confirme que o token e o chat ID funcionam (a mensagem deve chegar no grupo):

curl -s -X POST "https://api.telegram.org/bot${TELEGRAM_TOKEN}/sendMessage" \
  -d chat_id="${CHAT_ID}" \
  -d text="Teste do bot do homelab"
{"ok":true,"result":{"message_id":12,...,"text":"Teste do bot do homelab"}}

A mensagem deve chegar no Telegram. Se não chegar, resolva aqui antes de continuar (veja o troubleshooting).

4. Configurar o serviço, os triggers e os templates​

Acrescente ao ~/gitops/argocd/values.yaml (o mesmo dos Labs 1 e 2):

notifications:
  # O segredo vem de um SealedSecret (passo 6): o chart não cria o Secret
  secret:
    create: false

  # URL usada nos links das mensagens
  context:
    argocdUrl: https://argocd.devopsr66.com

  notifiers:
    service.telegram: |
      token: $telegram-token

  triggers:
    trigger.on-sync-succeeded: |
      - description: Sincronização concluída com sucesso
        send: [app-sync-succeeded]
        when: app.status.operationState != nil and app.status.operationState.phase in ['Succeeded']
        oncePer: app.status.operationState.syncResult.revision

    trigger.on-sync-failed: |
      - description: Sincronização falhou
        send: [app-sync-failed]
        when: app.status.operationState != nil and app.status.operationState.phase in ['Error', 'Failed']
        oncePer: app.status.operationState.finishedAt

    trigger.on-health-degraded: |
      - description: Aplicação ficou Degraded
        send: [app-health-degraded]
        when: app.status.health.status == 'Degraded'

  templates:
    template.app-sync-succeeded: |
      message: |
        ✅ {{.app.metadata.name}}: sincronizada com sucesso
        Revisão: {{.app.status.sync.revision}}
        {{.context.argocdUrl}}/applications/{{.app.metadata.name}}

    template.app-sync-failed: |
      message: |
        ❌ {{.app.metadata.name}}: o sync FALHOU
        Erro: {{.app.status.operationState.message}}
        {{.context.argocdUrl}}/applications/{{.app.metadata.name}}

    template.app-health-degraded: |
      message: |
        ⚠️ {{.app.metadata.name}}: saúde Degraded
        {{.context.argocdUrl}}/applications/{{.app.metadata.name}}

O que cada parte faz:

ItemExplicação
$telegram-tokenLê a chave telegram-token do Secret argocd-notifications-secret
when:Condição sobre a Application, em expressão
oncePer:Evita repetir a mesma notificação para o mesmo valor (uma vez por revisão, por exemplo)
{{.context.argocdUrl}}Vem de notifications.context; sem ele, o link sai vazio
Confira as chaves na sua versão do chart

As chaves (notifications.notifiers, .triggers, .templates, .context, .secret.create) são as que eu conheço do chart. Veja o que a sua versão aceita:

helm show values argo/argo-cd --version <SUA_VERSÃO> | grep -n -A6 -E "^notifications:|^  (notifiers|triggers|templates|context|secret):"

5. Aplicar com Helm​

Use a mesma versão do chart dos labs anteriores:

helm upgrade argocd argo/argo-cd \
  --namespace argocd \
  --version <SUA_VERSÃO> \
  -f ~/gitops/argocd/values.yaml
Release "argocd" has been upgraded. Happy Helming!
STATUS: deployed
REVISION: 3

Como secret.create agora é false, o Helm remove o Secret vazio que ele tinha criado. É o esperado. O controller de notificações reclama da falta do Secret até o próximo passo.

6. Entregar o token como SealedSecret​

Faça isto no mesmo terminal onde você deu o read -rs TELEGRAM_TOKEN. Se a variável estiver vazia, o kubectl create secret não reclama e sela um valor vazio, o que causa Not Found nas notificações:

cd ~/gitops/gitops-homelab
mkdir -p infra/secrets

[ -n "$TELEGRAM_TOKEN" ] || { echo "token vazio, abortando"; false; } && \
kubectl create secret generic argocd-notifications-secret \
  --namespace argocd \
  --from-literal=telegram-token="${TELEGRAM_TOKEN}" \
  --dry-run=client -o yaml \
  | kubeseal --format yaml > infra/secrets/argocd-notifications-secret.yaml

kubectl apply -f infra/secrets/argocd-notifications-secret.yaml
sealedsecret.bitnami.com/argocd-notifications-secret created
kubectl get secret argocd-notifications-secret -n argocd
kubectl get secret argocd-notifications-secret -n argocd \
  -o jsonpath='{.data.telegram-token}' | base64 -d | wc -c
unset TELEGRAM_TOKEN
NAME                          TYPE     DATA   AGE
argocd-notifications-secret   Opaque   1      5s
46

O número é o tamanho do token (não deve ser 0).

O arquivo cifrado pode ir para o Git:

git add infra/secrets/argocd-notifications-secret.yaml
git commit -m "Adiciona o token das notificações (SealedSecret)"
git push

Reinicie o controller para ele ler o Secret:

kubectl rollout restart deployment argocd-notifications-controller -n argocd
kubectl logs -n argocd deploy/argocd-notifications-controller --tail=5
time="..." level=info msg="Starting controller"
...

Não deve haver erros de secret not found.

7. Assinar a Application​

A subscription é uma annotation no formato notifications.argoproj.io/subscribe.<trigger>.<serviço>: <destino>. Edite applications/whoami.yaml:

metadata:
  name: whoami
  namespace: argocd
  annotations:
    notifications.argoproj.io/subscribe.on-sync-succeeded.telegram: "-4512345678"
    notifications.argoproj.io/subscribe.on-sync-failed.telegram: "-4512345678"
    notifications.argoproj.io/subscribe.on-health-degraded.telegram: "-4512345678"

Troque -4512345678 pelo ID do seu grupo (negativo, entre aspas). Aplique e versione:

kubectl apply -f applications/whoami.yaml
git add applications/whoami.yaml && git commit -m "whoami: assina notificações no Telegram" && git push

8. Testar o sucesso​

Mude algo e faça o deploy pelo Git:

sed -i 's/replicas: 1/replicas: 2/' apps/whoami/deployment.yaml
git commit -am "whoami: 2 réplicas (teste de notificação)" && git push
argocd app get whoami --refresh | grep "Sync Status"

Em instantes chega no Telegram:

✅ whoami: sincronizada com sucesso
Revisão: 9b1e4a7c...
https://argocd.devopsr66.com/applications/whoami

9. Testar a falha​

Provoque um erro de sync: uma porta inválida em um Service (o schema aceita, mas o servidor recusa):

sed -i 's/port: 80$/port: 70000/' apps/whoami/service.yaml
git commit -am "whoami: porta inválida (teste de falha)" && git push
argocd app get whoami --refresh | grep -E "Sync Status|Message"

A mensagem de falha:

❌ whoami: o sync FALHOU
Erro: one or more objects failed to apply, reason: Service "whoami" is invalid: spec.ports[0].port: Invalid value: 70000: must be between 1 and 65535, inclusive
https://argocd.devopsr66.com/applications/whoami

Conserte voltando o commit:

git revert --no-edit HEAD
git push

O sync seguinte volta a dar sucesso e você recebe a mensagem ✅ de novo.

10. (Opcional, não verificado) Testar pela CLI​

Dá para disparar um template à mão, útil para ajustar o texto:

argocd admin notifications template notify app-sync-succeeded whoami \
  --recipient telegram:-4512345678 -n argocd
notification sent

(Esse comando fala direto com o cluster, usando o seu kubectl.)

Passo não verificado

Este comando pode falhar mesmo com a configuração correta (já retornou chat not found com token e chat ID válidos, confirmados por curl). Se falhar, ignore e valide pelo caminho real: um commit novo (passos 8 e 9) e o log do controller.

11. (Opcional) Assinar todas as Applications​

Em vez de uma annotation por Application, defina assinaturas padrão no values.yaml:

notifications:
  subscriptions:
    - recipients:
        - telegram:-4512345678
      triggers:
        - on-sync-failed
        - on-health-degraded

Assim todas as Applications avisam em caso de falha, sem precisar da annotation. Deixe on-sync-succeeded de fora para evitar barulho.

Para ver o que o controller está fazendo:

kubectl logs -n argocd deploy/argocd-notifications-controller --tail=30

Resumo​

  • Notificações = service (destino) + template (texto) + trigger (quando) + subscription (annotation).
  • Triggers e templates precisam ser definidos: assinar um nome que não existe é ignorado sem erro.
  • Telegram: bot no @BotFather (token) + ID de um grupo (negativo) via getUpdates. O ID positivo de conversa privada não funciona no controller.
  • O token é segredo: vai no argocd-notifications-secret (via SealedSecret), nunca no values.yaml.
  • Annotation: notifications.argoproj.io/subscribe.<trigger>.telegram: "<chat_id>".
  • oncePer evita notificação repetida; {{.context.argocdUrl}} exige notifications.context.
  • Teste de sucesso = um deploy; teste de falha = um erro de apply (porta inválida), consertado com git revert.
  • argocd admin notifications template notify dispara um template à mão.
