Criando um Project

Fundamentos​

Toda Application pertence a um Project (AppProject). O Project é a fronteira de segurança do Argo CD: define de onde uma Application pode ler, onde pode implantar e o que pode criar.

O que o Project controla​

CampoControla
sourceReposDe quais repositórios as Applications podem ler
destinationsEm quais clusters e namespaces podem implantar
clusterResourceWhitelistQuais recursos de cluster podem criar (ex: Namespace)
namespaceResourceWhitelistQuais recursos de namespace podem criar
rolesRoles e tokens próprios do Project

O Project default​

O Project precisa existir antes das Applications, então aplicamos à mão com kubectl. (Um Project também pode ser gerenciado pelo próprio Argo CD, com o padrão app-of-apps descrito na página de Conceitos.)

Lista de permissão: o que vale​

Sem clusterResourceWhitelist o Project não permite nenhum recurso de cluster, nem Namespace. E uma lista vazia em namespaceResourceWhitelist bloqueia tudo. O que não for liberado é negado, e é por isso que a lista deve ser mínima e crescer conforme a necessidade.

Pré-requisitos
  • Lab 3 concluído (repositório gitops-homelab conectado, STATUS: Successful).
  • ARGOCD_OPTS definido no terminal.

Prática​

1. Definir o Project​

Vamos criar o Project homelab, para as aplicações de demonstração. Os nomes de namespace permitidos seguem o padrão demo e demo-*.

No repositório:

cd ~/gitops/gitops-homelab
mkdir -p infra/projects
# infra/projects/homelab.yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: homelab
  namespace: argocd
spec:
  description: Aplicações de demonstração do homelab

  # De onde as Applications podem ler
  sourceRepos:
    - git@github.com:lotechdevops/gitops-homelab.git

  # Onde podem implantar
  destinations:
    - server: https://kubernetes.default.svc
      namespace: demo
    - server: https://kubernetes.default.svc
      namespace: 'demo-*'

  # Recursos de cluster permitidos (só Namespace, para o CreateNamespace)
  clusterResourceWhitelist:
    - group: ''
      kind: Namespace

  # Recursos de namespace permitidos
  namespaceResourceWhitelist:
    - group: ''
      kind: ConfigMap
    - group: ''
      kind: Service
    - group: ''
      kind: ServiceAccount
    - group: apps
      kind: Deployment
    - group: networking.k8s.io
      kind: Ingress

O que isso diz, em português: "as Applications deste Project só leem do gitops-homelab, só implantam nos namespaces demo* do cluster local, e só podem criar Namespace, ConfigMap, Service, ServiceAccount, Deployment e Ingress."

2. Aplicar o Project​

O Project precisa existir antes das Applications, então aplicamos à mão agora. No Lab 9 (app-of-apps) o Argo CD passa a gerenciá-lo.

kubectl apply -f infra/projects/homelab.yaml
appproject.argoproj.io/homelab created

4. Testar o bloqueio: repositório não autorizado​

Tentamos criar uma Application que lê de um repositório fora da lista:

argocd app create teste-repo \
  --project homelab \
  --repo https://github.com/argoproj/argocd-example-apps.git \
  --path guestbook \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace demo
{"level":"fatal","msg":"rpc error: code = InvalidArgument desc = application spec for teste-repo is invalid: InvalidSpecError: application repo https://github.com/argoproj/argocd-example-apps.git is not permitted in project 'homelab'","time":"2026-11-01T11:40:18-03:00"}

O Project recusou a Application antes de criá-la.

5. Testar o bloqueio: namespace não autorizado​

Agora com o repositório certo, mas com um namespace de sistema:

argocd app create teste-ns \
  --project homelab \
  --repo git@github.com:lotechdevops/gitops-homelab.git \
  --path apps \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace kube-system
{"level":"fatal","msg":"rpc error: code = InvalidArgument desc = application spec for teste-ns is invalid: InvalidSpecError: application destination server 'https://kubernetes.default.svc' and namespace 'kube-system' do not match any of the allowed destinations in project 'homelab'","time":"2026-11-01T11:40:53-03:00"}

Isso é a proteção em ação: uma Application deste Project não consegue mexer em kube-system.

6. Confirmar que nada foi criado​

argocd app list
NAME  CLUSTER  NAMESPACE  PROJECT  STATUS  HEALTH  SYNCPOLICY  CONDITIONS  REPO  PATH  TARGET

As duas tentativas foram rejeitadas, então não sobrou nada para limpar.

7. Versionar o Project no Git​

git add infra/projects/homelab.yaml
git commit -m "Adiciona o AppProject homelab"
git push
[main 7d4c2e1] Adiciona o AppProject homelab
 1 file changed, 38 insertions(+)

8. (Opcional) Role de Project para automação​

Útil quando um pipeline de CI precisar sincronizar só as Applications deste Project (o conceito está na página de RBAC):

# acrescente em spec: do homelab.yaml
  roles:
    - name: ci-deploy
      description: Pipeline pode sincronizar as Applications do homelab
      policies:
        - p, proj:homelab:ci-deploy, applications, get, homelab/*, allow
        - p, proj:homelab:ci-deploy, applications, sync, homelab/*, allow
kubectl apply -f infra/projects/homelab.yaml
argocd proj role list homelab
ROLE-NAME  DESCRIPTION
ci-deploy  Pipeline pode sincronizar as Applications do homelab

O token só é gerado quando existir um pipeline que precise dele (argocd proj role create-token homelab ci-deploy).

9. (Opcional) Restringir o Project default​

Para que ninguém crie uma Application "solta" no default, você pode tirar as permissões dele. Faça depois de ter outro Project funcionando, e confira se o upgrade do Helm não o recria com as permissões originais.

kubectl patch appproject default -n argocd --type merge -p '
spec:
  sourceRepos: []
  destinations: []
  clusterResourceWhitelist: []
'

Se algo quebrar, desfaça com:

kubectl patch appproject default -n argocd --type merge -p '
spec:
  sourceRepos: ["*"]
  destinations: [{server: "*", namespace: "*"}]
  clusterResourceWhitelist: [{group: "*", kind: "*"}]
'

Troubleshooting​

SintomaCausa provávelComo resolver
repo ... is not permitted in projectO repoURL não está em sourceRepos (compara a string exata)Use a URL idêntica à do Project (SSH git@..., não HTTPS)
destination ... do not match any of the allowed destinationsNamespace ou cluster fora de destinationsAjuste o namespace da Application ou o Project
resource ... is not permitted in project no syncTipo de recurso fora das whitelistsAdicione o group/kind do erro à lista certa
namespaces "demo" is forbidden / não cria o namespaceFalta Namespace em clusterResourceWhitelistMantenha Namespace liberado quando usar CreateNamespace=true
project homelab not found ao criar a ApplicationO Project não foi aplicadokubectl apply -f infra/projects/homelab.yaml
Aplicação sem Project cai no defaultEsqueceu o --project / spec.projectSempre informe o Project

Resumo​

  • O Project é a fronteira de segurança: repositórios, destinos e recursos permitidos.
  • O Project default é totalmente aberto: evite usá-lo em produção.
  • Listas de permissão: o que não está liberado é negado. Comece mínimo e adicione conforme os erros pedirem.
  • sourceRepos compara a URL exata do repositório (SSH ≠ HTTPS).
  • clusterResourceWhitelist com Namespace é necessário para CreateNamespace=true.
  • O Project é rejeitado na criação da Application, antes de qualquer deploy.
  • Roles de Project + tokens = automação com escopo mínimo.
  • O Project é versionado em infra/projects/; aqui é aplicado com kubectl, mas pode ser gerenciado pelo próprio Argo CD (app-of-apps, na página de Conceitos).
