Lab 6 - Secrets na prática com Sealed Secrets

Fundamentos​

No GitOps, tudo vai para o Git, mas um Secret do Kubernetes é só base64, que qualquer pessoa decodifica. A solução deste lab é o Sealed Secrets:

Secret (texto puro, só na sua máquina)
   │  kubeseal (chave PÚBLICA do cluster)
   ▼
SealedSecret (cifrado) ──► Git ──► Argo CD ──► cluster
                                                  │  controller (chave PRIVADA)
                                                  ▼
                                            Secret real
  • O SealedSecret pode ir para o Git: só o controller do seu cluster consegue decifrá-lo.
  • Por padrão ele fica preso ao nome e ao namespace do Secret (escopo estrito).
  • A chave privada vive no cluster. Perdê-la significa perder os segredos do Git, então o backup dela é parte do lab.
Por que Sealed Secrets neste lab

É a opção mais simples para um homelab, sem cofre externo. É a escolha que fiz para a trilha (veja a página de Gerenciamento de Secrets); se você preferir o External Secrets Operator, este lab muda. A comparação está na página de teoria.

Pré-requisitos
  • Labs 1 a 5 concluídos.
  • A Application whoami do Lab 5 (se você a apagou na limpeza, recrie com kubectl apply -f applications/whoami.yaml; o arquivo precisa estar no repositório). Use sync automático.
  • Login da CLI funcionando (por domínio ou ARGOCD_OPTS).

Prática​

1. Instalar o controller​

helm repo add sealed-secrets https://bitnami.github.io/sealed-secrets
helm repo update
helm search repo sealed-secrets/sealed-secrets
NAME                              CHART VERSION  APP VERSION  DESCRIPTION
sealed-secrets/sealed-secrets     2.x.x          0.xx.x       Helm chart for the sealed-secrets controller.

Anote a CHART VERSION e o APP VERSION do seu resultado (os números acima são genéricos) e instale com a versão fixa:

helm install sealed-secrets sealed-secrets/sealed-secrets \
  --namespace kube-system \
  --version <CHART_VERSION> \
  --set-string fullnameOverride=sealed-secrets-controller
NAME: sealed-secrets
NAMESPACE: kube-system
STATUS: deployed

O fullnameOverride=sealed-secrets-controller e o namespace kube-system são o que o kubeseal espera por padrão. Sem eles, seria preciso informar --controller-name e --controller-namespace em todo comando.

kubectl get pods -n kube-system -l app.kubernetes.io/name=sealed-secrets
NAME                                        READY   STATUS    RESTARTS   AGE
sealed-secrets-controller-fcdf47bb5-n4df7   1/1     Running   0          33s

2. Instalar a CLI kubeseal​

Use a versão compatível com o controller (APP VERSION do passo 1):

KUBESEAL_VERSION=<APP_VERSION sem o "v">
curl -sSL -o kubeseal.tar.gz \
  "https://github.com/bitnami/sealed-secrets/releases/download/v${KUBESEAL_VERSION}/kubeseal-${KUBESEAL_VERSION}-linux-amd64.tar.gz"
tar -xzf kubeseal.tar.gz kubeseal
sudo install -m 755 kubeseal /usr/local/bin/kubeseal
rm kubeseal kubeseal.tar.gz
kubeseal --version
kubeseal version: 0.xx.x

3. Fazer backup da chave privada (obrigatório)​

kubectl get secret -n kube-system \
  -l sealedsecrets.bitnami.com/sealed-secrets-key \
  -o yaml > ~/sealed-secrets-key-backup.yaml
chmod 600 ~/sealed-secrets-key-backup.yaml
ls -l ~/sealed-secrets-key-backup.yaml
-rw------- 1 neto neto 2874 Nov 11 23:05 /home/neto/sealed-secrets-key-backup.yaml
Este arquivo é a chave de tudo

Guarde-o fora do Git e fora do cluster (gerenciador de senhas ou um volume cifrado). Quem o tiver decifra todos os seus SealedSecrets. Sem ele, ao recriar o cluster, os segredos do Git não podem ser decifrados.

4. Criar e cifrar um segredo​

O SealedSecret fica preso ao nome e ao namespace, então informe ambos. Primeiro o Secret em texto puro sem salvar em arquivo, passando direto para o kubeseal:

cd ~/gitops/gitops-homelab

kubectl create secret generic db-credentials \
  --namespace demo \
  --from-literal=username=app \
  --from-literal=password='S3nh4-De-Teste-123' \
  --dry-run=client -o yaml \
  | kubeseal --format yaml > apps/whoami/sealedsecret.yaml
cat apps/whoami/sealedsecret.yaml
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  creationTimestamp: null
  name: db-credentials
  namespace: demo
spec:
  encryptedData:
    password: AgBy3i4OJSWK+PiTySYZZA9rO43cGDEq...
    username: AgCk7n2mQ1xT8vLpZ...
  template:
    metadata:
      creationTimestamp: null
      name: db-credentials
      namespace: demo

Os valores estão cifrados. Este arquivo pode ir para o Git.

Cifrar sem acesso ao cluster

Se estiver sem acesso ao cluster, baixe o certificado público uma vez (kubeseal --fetch-cert > pub-cert.pem) e depois use kubeseal --cert pub-cert.pem. O certificado é público e pode ser versionado.

5. Liberar o tipo no Project​

O Project homelab (Lab 4) só permite alguns recursos. O SealedSecret é de outro grupo (bitnami.com) e vai ser bloqueado. Acrescente em infra/projects/homelab.yaml, dentro de namespaceResourceWhitelist:

    - group: bitnami.com
      kind: SealedSecret
kubectl apply -f infra/projects/homelab.yaml
appproject.argoproj.io/homelab configured

6. Entregar pelo Git​

Faça o Deployment do whoami ler o segredo como variável de ambiente. Em apps/whoami/deployment.yaml, dentro do container, acrescente:

          env:
            - name: DB_USER
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: username
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password
git add apps/whoami infra/projects/homelab.yaml
git commit -m "whoami: segredo via SealedSecret"
git push
argocd app get whoami --refresh | grep -E "Sync Status|Health Status"
Sync Status:        Synced to main (e5a2b90)
Health Status:      Healthy

7. Verificar​

O controller decifrou o SealedSecret e criou o Secret:

kubectl get sealedsecret,secret -n demo
NAME                                    STATUS   SYNCED   AGE
sealedsecret.bitnami.com/db-credentials          True     30s

NAME                    TYPE     DATA   AGE
secret/db-credentials   Opaque   2      30s
kubectl get secret db-credentials -n demo -o jsonpath='{.data.password}' | base64 -d; echo
kubectl describe pod -n demo -l app=whoami | grep -A2 DB_PASSWORD
S3nh4-De-Teste-123

      DB_PASSWORD:  <set to the key 'password' in secret 'db-credentials'>  Optional: false

No Git existe só o texto cifrado. No cluster, o Secret real foi criado pelo controller e não está no repositório.

8. Provar que o escopo protege​

Copie o SealedSecret para outro namespace e tente aplicar:

kubectl create namespace demo-outro
sed 's/namespace: demo/namespace: demo-outro/' apps/whoami/sealedsecret.yaml | kubectl apply -f -
kubectl get sealedsecret db-credentials -n demo-outro
kubectl describe sealedsecret db-credentials -n demo-outro | tail -5
sealedsecret.bitnami.com/db-credentials created

NAME             STATUS   SYNCED   AGE
db-credentials            False    10s

Warning  ErrUnsealFailed  ... Failed to unseal: no key could decrypt secret (password, username)

O objeto é criado, mas o controller não consegue decifrar, porque o nome/namespace não batem com o que foi cifrado. Limpe:

kubectl delete namespace demo-outro

9. (Opcional) Proteger a credencial do repositório do Lab 3​

O Secret do repositório contém a chave privada SSH e ainda está só no cluster. Dá para cifrá-lo com o mesmo método, para recriar o cluster a partir do Git:

mkdir -p infra/secrets
kubectl create secret generic repo-gitops-homelab \
  --namespace argocd \
  --from-literal=type=git \
  --from-literal=name=gitops-homelab \
  --from-literal=url=git@github.com:lotechdevops/gitops-homelab.git \
  --from-file=sshPrivateKey=$HOME/.ssh/argocd_gitops_homelab \
  --dry-run=client -o yaml \
  | kubectl label --local -f - argocd.argoproj.io/secret-type=repository -o yaml \
  | kubeseal --format yaml > infra/secrets/repo-gitops-homelab.yaml

Dois cuidados antes de aplicar:

  1. Label e annotation: o Secret gerado precisa do label argocd.argoproj.io/secret-type: repository. Confira que ele aparece em spec.template.metadata.labels do arquivo gerado; se não aparecer, adicione à mão.
  2. Secret que já existe: como o repositório já foi conectado pela CLI, o controller recusa assumir um Secret existente. Para isso, acrescente em spec.template.metadata.annotations: sealedsecrets.bitnami.com/managed: "true".

Só então kubectl apply -f infra/secrets/repo-gitops-homelab.yaml, e confirme com argocd repo list que o status continua Successful. Esta parte eu não testei no seu cluster: faça por último e com o backup da chave em mãos.

kubeseal: cannot fetch certificate / no endpoints availableController não está rodando ou o nome/namespace diferemkubectl get pods -n kube-system -l app.kubernetes.io/name=sealed-secrets; use --controller-name/--controller-namespace se mudou
Sync falha com resource bitnami.com:SealedSecret is not permitted in projectTipo fora do ProjectPasso 5
SealedSecret com SYNCED: False e no key could decrypt secretCifrado para outro nome, namespace ou clusterCifre de novo com o nome e namespace corretos, para este cluster

Cluster recriado e os segredos não abremChave privada nova, diferente da usada para cifrarRestaure o backup do passo 3 antes de aplicar os SealedSecrets

Restaurar a chave em um cluster novo​

kubectl apply -f ~/sealed-secrets-key-backup.yaml
kubectl rollout restart deployment sealed-secrets-controller -n kube-system

O controller passa a usar a chave restaurada e decifra os SealedSecret do Git.

Resumo​

  • Base64 não é cifra. SealedSecret (cifrado) pode ir para o Git; o Secret só existe no cluster.
  • kubeseal cifra com a chave pública; o controller decifra com a privada.
  • Backup da chave privada logo após instalar, fora do Git. Sem ela, os segredos do Git se perdem.
  • O escopo padrão é estrito: preso ao nome e ao namespace do Secret.
  • O Project precisa liberar bitnami.com/SealedSecret.
  • Variáveis de ambiente só mudam com restart do pod.
  • Pipeline: kubectl create secret --dry-run | kubeseal > arquivo.yaml e git push. O texto puro nunca é salvo em arquivo.
  • Recriar o cluster = restaurar a chave e deixar o Argo CD aplicar o Git.
