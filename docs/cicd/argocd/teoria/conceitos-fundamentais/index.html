Conceitos Fundamentais do Argo CD

Para trabalhar bem com o Argo CD, é preciso conhecer os seus conceitos centrais. Eles definem como a ferramenta organiza e controla as aplicações dentro do Kubernetes.

Application​

O Application é o recurso central do Argo CD. Ele representa uma aplicação gerenciada e reúne tudo que o Argo CD precisa para sincronizá-la:

  • Origem (source): repositório Git/Helm, versão (targetRevision) e caminho (path).
  • Destino (destination): cluster e namespace.
  • Projeto (project): a que Project ela pertence.
  • Política de sincronização (syncPolicy): manual ou automática.

O Application é o contrato entre o Git e o Kubernetes: diz "o que instalar, onde e como".

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    targetRevision: HEAD
    path: guestbook
  destination:
    server: https://kubernetes.default.svc
    namespace: guestbook
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
kubernetes.default.svc

É o endereço do próprio cluster onde o Argo CD roda. Para clusters externos, você registra o cluster no Argo CD e usa a URL dele.

Project​

O Project (AppProject) organiza e isola conjuntos de Applications. Ele aplica governança quando há vários times e aplicações.

Com um Project você define:

  • Quais repositórios podem ser usados (sourceRepos).
  • Quais clusters e namespaces podem receber deploys (destinations).
  • Quais tipos de recursos podem ser criados (listas de permissão).
  • Roles de acesso próprias do Project.

Exemplo: o Project time-backend só aceita manifestos do repositório do time e só implanta nos namespaces backend-*.

apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: time-backend
  namespace: argocd
spec:
  description: Projeto do time de backend
  sourceRepos:
    - 'https://github.com/empresa/backend-*'
  destinations:
    - namespace: 'backend-*'
      server: https://kubernetes.default.svc
  clusterResourceWhitelist:
    - group: ''
      kind: Namespace
  namespaceResourceWhitelist:
    - group: 'apps'
      kind: Deployment
    - group: ''
      kind: Service
Evite * nas listas

group: '*' e kind: '*' liberam qualquer recurso e desfazem o isolamento que o Project oferece. Liste só o que a aplicação realmente cria. Toda Application sem Project definido cai no Project default, que é permissivo: crie Projects próprios.

Repository​

O Argo CD precisa saber onde buscar os manifestos. Isso é configurado em Repositories:

TipoExemplo
GitGitHub, GitLab, Bitbucket
HelmArtifact Hub, repositórios de charts privados
OCICharts Helm em registries OCI

Autenticação suportada: SSH (chave privada), HTTPS (usuário e token), GitHub App e credenciais de nuvem.

Os repositórios (e suas credenciais) ficam guardados como Secrets no namespace do Argo CD. Para repositórios privados, prefira credenciais de somente leitura (como deploy key).

Refresh e Sync: duas coisas diferentes​

OperaçãoO que faz
RefreshCompara o Git com o cluster e atualiza o status. Não muda nada no cluster
SyncAplica no cluster o que está no Git

O Argo CD faz um refresh periódico (padrão: a cada 3 minutos). O sync pode ser manual ou automático.

Sync Status​

Indica se o cluster está em conformidade com o Git:

StatusSignificado
SyncedO cluster está igual ao Git
OutOfSyncHá diferenças entre o Git e o cluster
UnknownNão foi possível determinar (erro de comunicação ou de renderização)

Health Status​

Indica se a aplicação está funcionando:

StatusSignificado
HealthyTodos os recursos estão saudáveis
ProgressingRecursos sendo criados ou atualizados
DegradedAlgum recurso com problema (ex: pods em crash)
SuspendedIntencionalmente pausada
MissingRecursos esperados não existem no cluster
UnknownNão foi possível determinar

Sync × Health​

┌─────────────────────────────────────────┐
│ Sync Status:   Synced                   │  Git == Cluster
│ Health Status: Degraded                 │  pods em crash
└─────────────────────────────────────────┘

A aplicação está "como descrito no Git",
mas NÃO está funcionando corretamente.

Synced significa apenas "igual ao Git", e não "funcionando". Olhe sempre os dois status.

Sync: aplicando o estado desejado​

O sync é o coração do Argo CD: leva o cluster ao estado descrito no Git.

Política de sincronização (syncPolicy)​

ModoComo configurarComportamento
Manual(sem automated)Você dispara o sync (UI ou argocd app sync)
Automáticoautomated: {}Aplica sozinho quando o Git muda
+ Self-healautomated.selfHeal: trueTambém desfaz mudanças manuais feitas no cluster
+ Pruneautomated.prune: trueTambém remove recursos apagados do Git
syncPolicy:
  automated:
    prune: true
    selfHeal: true

Opções de sync (syncOptions)​

São ajustes de como o sync é feito, e ficam dentro de syncPolicy:

OpçãoO que fazQuando usar
CreateNamespace=trueCria o namespace de destino se não existirQuase sempre
ServerSideApply=trueAplica no servidor (server-side apply)CRDs e recursos grandes: evita o erro de anotação grande demais (ex: kube-prometheus-stack)
PruneLast=trueRemove recursos antigos depois de aplicar os novosReduz risco durante atualizações
Replace=trueUsa kubectl replace em vez de applyRecursos que não aceitam apply (use com cuidado)
ApplyOutOfSyncOnly=trueAplica só os recursos que estão fora de syncAplicações muito grandes
RespectIgnoreDifferences=trueRespeita as regras de ignoreDifferences também no syncJunto com ignoreDifferences
Validate=falsePula a validação de schemaÚltimo recurso

Retry​

Se o sync falhar, o Argo CD pode tentar de novo, com espera crescente:

syncPolicy:
  retry:
    limit: 5
    backoff:
      duration: 5s
      factor: 2
      maxDuration: 3m

Drift e self-heal​

Drift é quando o estado real do cluster diverge do estado declarado no Git. Acontece, por exemplo, quando alguém:

  • Roda kubectl edit ou kubectl scale direto no cluster.
  • Altera recursos por um painel.
  • Um operador externo modifica o recurso.

O Argo CD compara continuamente o desejado (Git) com o real (cluster):

Mesmo estado   → Synced
Estado diferente → OutOfSync  → (com self-heal) o Argo CD desfaz a mudança manual

Sem selfHeal, o Argo CD só avisa (OutOfSync). Com selfHeal: true, ele reverte a mudança manual. Você vai ver isso funcionando no laboratório de Application.

Prune: removendo o que saiu do Git​

Se você remove um recurso do Git, o que acontece no cluster?

ConfiguraçãoResultado
Sem pruneO recurso continua existindo no cluster (fica "órfão")
Com prune: trueO Argo CD remove o recurso do cluster
Prune em produção

Prune automático apaga recursos de verdade. Use com cuidado, e considere PruneLast=true. Um erro de caminho ou de branch que "esvazie" o repositório pode levar o Argo CD a apagar a aplicação inteira.

Sync waves​

Sync waves controlam a ordem em que os recursos são aplicados no sync. Servem quando um recurso depende de outro:

  • ConfigMaps e Secrets antes dos Deployments.
  • CRDs antes dos recursos que as usam.
  • Migrações de banco antes da aplicação subir.

Use a annotation argocd.argoproj.io/sync-wave:

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  annotations:
    argocd.argoproj.io/sync-wave: "0"   # primeiro
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
  annotations:
    argocd.argoproj.io/sync-wave: "1"   # depois

Regras:

  1. A wave padrão é 0.
  2. Das menores (inclusive negativas) para as maiores.
  3. O Argo CD só avança para a próxima wave quando a anterior estiver saudável.
  4. Dentro da mesma wave, a ordem segue o tipo de recurso.

Resource hooks​

Hooks são recursos que executam em momentos específicos do sync:

HookQuando executa
PreSyncAntes do sync começar
SyncJunto com a aplicação, durante o sync
PostSyncDepois que tudo foi aplicado e está saudável
SyncFailSe o sync falhar
PostDeleteDepois que a Application é removida (versões recentes)
SkipO recurso é ignorado pelo Argo CD

Exemplo: um Job que roda antes da atualização e é apagado se der certo.

apiVersion: batch/v1
kind: Job
metadata:
  name: database-migration
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      containers:
        - name: migrate
          image: minha-org/migrate:1.4.2   # use uma versão fixa, nunca "latest"
          command: ["./migrate.sh"]
      restartPolicy: Never

Política de remoção do hook:

PolicyComportamento
HookSucceededApaga o hook se deu certo
HookFailedApaga o hook se falhou
BeforeHookCreationApaga o hook anterior antes de criar um novo

App-of-Apps​

O App-of-Apps é um padrão em que uma Application gerencia outras Applications. Em vez de criar uma por uma, você cria uma Application "raiz" que aponta para uma pasta com as demais.

cluster-apps (Application raiz)
├── metallb      (Application)
├── traefik      (Application)
├── cert-manager (Application)
├── prometheus   (Application)
└── minha-app    (Application)
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cluster-apps
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/empresa/gitops
    path: applications        # pasta com um YAML de Application por app
    targetRevision: HEAD
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

Benefícios:

  • Gerencia infraestrutura e aplicações de forma centralizada, tudo pelo Git.
  • Recria um cluster do zero aplicando uma única Application (bootstrap).
  • Simplifica a adição de novas aplicações: um commit com um novo YAML.

ApplicationSet​

O ApplicationSet gera várias Applications a partir de um único manifesto, com um template e uma fonte de dados (generator).

Em vez de manter app-dev.yaml, app-staging.yaml e app-prod.yaml, você escreve um ApplicationSet que gera os três.

Generators​

GeneratorDe onde vem a listaUso típico
ListUma lista fixa no próprio manifestoConjunto pequeno e explícito de apps ou ambientes
Git (diretórios)Pastas do repositórioUma pasta = uma aplicação
Git (arquivos)Arquivos de configuração no repositórioParâmetros por aplicação
ClusterClusters registrados no Argo CDMesma aplicação em vários clusters
Pull RequestPRs abertosAmbientes temporários de preview
Matrix / MergeCombinação de generatorsAmbientes × clusters
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: multi-env
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]
  generators:
    - list:
        elements:
          - env: dev
          - env: prod
  template:
    metadata:
      name: 'app-{{.env}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/empresa/app
        targetRevision: main
        path: 'environments/{{.env}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: 'app-{{.env}}'

Gera as Applications app-dev e app-prod. Os generators são aplicados no laboratório de ApplicationSet.

Cuidado ao apagar um ApplicationSet

Apagar o ApplicationSet apaga as Applications que ele gerou, e, se elas tiverem o finalizer de cascade (próxima seção), também os recursos no cluster. Para proteger, use syncPolicy.preserveResourcesOnDeletion: true no ApplicationSet.

Finalizers​

Finalizers são um mecanismo do Kubernetes que impede a exclusão de um recurso até que certas condições sejam cumpridas.

Ao apagar uma Application, o Argo CD pode:

  1. Remover só a Application (os recursos no cluster continuam existindo).
  2. Remover a Application e os recursos que ela criou (cascade delete).

O segundo comportamento é ativado pelo finalizer:

metadata:
  finalizers:
    - resources-finalizer.argocd.argoproj.io

Com ele, ao apagar a Application, o Argo CD primeiro remove os recursos e só então remove a Application.

Application "presa" em Deleting​

Costuma ser causada por um recurso com finalizer próprio que não termina, ou por dependências circulares. Como último recurso, remova o finalizer à mão:

kubectl patch app minha-app -n argocd \
  -p '{"metadata":{"finalizers":[]}}' --type merge

Isso deixa os recursos órfãos no cluster: depois, remova-os manualmente.

Ignorando diferenças esperadas​

Algumas diferenças entre Git e cluster são normais e não devem virar OutOfSync. Use ignoreDifferences:

spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas   # ignora o número de réplicas

Casos comuns:

  • HPA altera as réplicas automaticamente.
  • Webhooks mutantes adicionam annotations e labels.
  • Secrets gerenciados por fora (por exemplo, por um operador).

Combine com RespectIgnoreDifferences=true nas opções de sync, para o campo também ser respeitado durante o sync.

Resumo​

  • Application = o contrato Git ↔ Kubernetes (origem, destino, política).
  • Project = isolamento e governança (repositórios, destinos e recursos permitidos). Evite *.
  • Repository = onde estão os manifestos (Git, Helm, OCI), com credenciais de leitura.
  • Refresh compara; Sync aplica.
  • Synced ≠ Healthy: olhe os dois status.
  • automated + selfHeal corrige drift; prune remove o que saiu do Git (cuidado).
  • ServerSideApply=true para CRDs e recursos grandes.
  • Sync waves ordenam; hooks rodam em momentos do sync.
  • App-of-Apps = uma Application gerencia outras (bootstrap do cluster).
  • ApplicationSet = gera Applications em escala; apagá-lo apaga as geradas.
  • Finalizer = cascade delete; Application presa → remover finalizer (deixa órfãos).
