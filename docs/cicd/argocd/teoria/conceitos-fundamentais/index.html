Conceitos Fundamentais do ArgoCD

Para trabalhar bem com o ArgoCD, é importante conhecer os seus conceitos centrais.

Eles definem como a ferramenta organiza e controla aplicações dentro do Kubernetes.

Application​

O Application é o recurso central do ArgoCD.

Ele representa uma aplicação Kubernetes gerenciada pelo ArgoCD e contém todas as informações necessárias para que o sistema faça a sincronização:

  • Repositório Git (origem dos manifestos ou Helm Charts).
  • Caminho dentro do repositório onde os manifestos estão armazenados.
  • Cluster de destino onde a aplicação deve ser instalada.
  • Namespace de destino no Kubernetes.
  • Política de sincronização (manual, automática, com ou sem autocorreção).

Em termos simples: o Application é o contrato entre o Git e o Kubernetes, dizendo "o que instalar, onde instalar e como instalar".

Exemplo de Application​

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    targetRevision: HEAD
    path: guestbook
  destination:
    server: https://kubernetes.default.svc
    namespace: guestbook
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

Project​

O Project é uma forma de organizar e isolar conjuntos de Applications.

Ele ajuda a aplicar governança em ambientes com múltiplos times e aplicações.

Com um Project, é possível definir:

  • Quais repositórios Git podem ser usados.
  • Quais clusters podem receber deploys.
  • Quais namespaces estão liberados.
  • Quais políticas de sincronização são permitidas.

Exemplo: um Project chamado time-financeiro pode permitir apenas deploys vindos do repositório git@github.com:empresa/financeiro.git para o cluster de homologação.

Exemplo de Project​

apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: time-backend
  namespace: argocd
spec:
  description: Projeto do time de backend
  sourceRepos:
  - 'https://github.com/empresa/backend-*'
  destinations:
  - namespace: 'backend-*'
    server: https://kubernetes.default.svc
  clusterResourceWhitelist:
  - group: ''
    kind: Namespace
  namespaceResourceWhitelist:
  - group: 'apps'
    kind: Deployment
  - group: ''
    kind: Service

Repository​

O ArgoCD precisa saber onde buscar os manifestos.

Isso é configurado através dos Repositories, que podem ser:

  • Repositórios Git (GitHub, GitLab, Bitbucket, etc).
  • Helm Repositories (ex: Artifact Hub ou repositórios privados).
  • OCI Repositories (Helm charts em registries OCI).

Tipos de autenticação suportados​

  • SSH (chave privada)
  • HTTPS (usuário/senha ou token)
  • GitHub App
  • Google Cloud Source Repository

Sync Status​

O Sync Status (sincronização) indica se o estado do cluster está em conformidade com o Git.

Estados possíveis​

| Status     | Significado                                                   |
| ---------- | ------------------------------------------------------------- |
| Synced     | Cluster está igual ao Git                                     |
| OutOfSync  | Há diferenças entre Git e cluster                             |
| Unknown    | Não foi possível determinar o status (erro de comunicação)    |

Importante: Synced não significa que a aplicação está funcionando, apenas que está conforme o Git.

Health Status​

O Health Status indica se a aplicação está funcionando corretamente.

Estados possíveis​

| Status      | Significado                                                    |
| ----------- | -------------------------------------------------------------- |
| Healthy     | Todos os recursos estão funcionando corretamente               |
| Progressing | Recursos estão sendo criados/atualizados                       |
| Degraded    | Alguns recursos têm problemas (pods crashando, por exemplo)    |
| Suspended   | Aplicação está intencionalmente suspensa                       |
| Missing     | Recursos esperados não existem no cluster                      |
| Unknown     | Não foi possível determinar o status                           |

Diferença entre Sync e Health​

┌─────────────────────────────────────────┐
│ Sync Status: Synced                     │  ✅ Git == Cluster
│ Health Status: Degraded                 │  ❌ Pods crashando
└─────────────────────────────────────────┘

A aplicação está "como descrito no Git",
mas NÃO está funcionando corretamente!

Sync (Sincronização)​

O conceito de Sync é o coração do ArgoCD.

Ele garante que o estado real do cluster corresponde ao estado desejado descrito no Git.

Modos de sincronização​

Manual​

  • O usuário precisa clicar ou rodar comando para aplicar a atualização.
  • Maior controle, mas requer intervenção humana.

Automática​

syncPolicy:
  automated: {}
  • O ArgoCD aplica mudanças assim que detecta alterações no Git.

Automática com Self-Heal​

syncPolicy:
  automated:
    selfHeal: true
  • Além de aplicar mudanças do Git, o ArgoCD corrige qualquer alteração manual feita no cluster.

Automática com Prune​

syncPolicy:
  automated:
    prune: true
  • Remove recursos que foram deletados do Git

Drift Detection​

Drift significa que o estado atual do cluster divergiu do estado declarado no Git.

Isso pode acontecer quando:

  • Alguém aplica um kubectl edit diretamente no cluster
  • Um operador externo modifica recrusos.
  • Mudanças manuais via dashboard do Kubernetes

Como o ArgoCD detecta drift​

O ArgoCD compara continuamente:

  1. Estado desejado (o que está no Git)
  2. Estado real (o que está no cluster)

Se houver diferença, o ArgoCD marca como OutOfSync.

Self-Heal​

Com SelfHeal: true, o ArgoCD automaticamente reverte mudanças manuais, garantindo que o cluster sempre reflita o Git.

Prune (Remoção de recursos)​

Quando você remove um recurso do Git, o que acontece no cluster?

Sem Prune​

O recurso continua existindo no cluster (orphaned resource).

Com Prune​

syncPolicy:
  automated:
    prune: true
  • O ArgoCD remove automaticamente recursos que não estão mais no Git.

Cuidado: Prune automático pode ser perigoso em produção, Use com cautela.

Sync Waves​

Sync Waves controlam a ordem de aplicação dos recursos durante uma sincronização.

Por que usar​

Alguns recursos dependem de outros:

  • ConfigMaps/Secrets devem existir antes dos Deployments.
  • CRDs devem ser instalados antes dos CRs
  • Migrations devem rodar antes da aplicação subir

Como funciona​

Use a annotation argocd.argoproj.io/sync-wave:

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  annotations:
    argocd.argoproj.io/sync-wave: "0"  # Aplica primeiro
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
  annotations:
    argocd.argoproj.io/sync-wave: "1"  # Aplica depois

Ordem de execução​

  1. ArgoCD ordena recursos por wave (menor para maior)
  2. Wave padrão é 0.
  3. Waves negativas são aplicadas primeiro
  4. Dentro da mesma wave, a ordem é baseada no tipo de recurso
Wave -1 → Wave 0 → Wave 1 → Wave 2 → ...

Resource Hooks​

Hooks são recursos especiais que executam em momentos específicos do ciclo de sincronização.

Tipos de Hooks​

| Hook      | Quando executa                                   |
| --------- | ------------------------------------------------ |
| PreSync   | Antes da sincronização começar                   |
| Sync      | Durante a sincronização normal                   |
| PostSync  | Após todos os recursos serem aplicados com sucesso |
| SyncFail  | Se a sincronização falhar                        |
| Skip      | Recurso é ignorado pelo ArgoCD                   |

Exemplo: Migration Job​

apiVersion: batch/v1
kind: Job
metadata:
  name: database-migration
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      containers:
      - name: migrate
        image: migrate-tool:latest
        command: ["./migrate.sh"]
      restartPolicy: Never

Este Job roda antes da aplicação ser atualizada e é deletado após sucesso.

Hook Delete Policy​

| Policy          | Comportamento                               |
| --------------- | ------------------------------------------- |
| HookSucceeded   | Deleta o hook se ele for bem-sucedido       |
| HookFailed      | Deleta o hook se ele falhar                 |
| BeforeHookCreation | Deleta hooks anteriores antes de criar novos |

App-of-Apps Pattern​

O App-of-Apps é um padrão comum no ArgoCD, usado em ambientes grandes.

Em vez de criar Applications manualmente um por um, você cria um Application principal que referencia outros Applications secundários.

Estrutura​

app-of-apps (Application)
├── ingress-nginx (Application)
├── prometheus (Application)
├── app-backend (Application)
└── app-frontend (Application)

Exemplo​

# app-of-apps.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cluster-apps
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/empresa/gitops
    path: applications
    targetRevision: HEAD
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

Benefícios​

  • Facilita a orquestração de múltiplas aplicações
  • Permite gerenciar infraestrutura + apps de negócios de forma centralizada.
  • Simplifica bootstrap de novos clusters.

ApplicationSet​

O ApplicationSet é um recurso avançado do ArgoCD que permite gerar dinamicamente várias aplicações a partir de uma único manifesto declarativo.

Em vez de criar manualmente um Application para cada ambiente, cluster ou serviço, o ApplicationSet automatiza esse processo com base em um modelo (template) e uma fonte de dados (generator).

Por que usar ApplicationSet​

Em vez de criar manualmente:

app-dev.yaml
app-staging.yaml
app-prod.yaml

Você cria um único ApplicationSet que gera os três automaticamente.

Generators​

List Generator​

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: multi-env
spec:
  generators:
  - list:
      elements:
      - env: dev
        cluster: https://dev-cluster
      - env: staging
        cluster: https://staging-cluster
      - env: prod
        cluster: https://prod-cluster
  template:
    metadata:
      name: 'app-{{env}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/empresa/app
        path: 'environments/{{env}}'
      destination:
        server: '{{cluster}}'
        namespace: 'app-{{env}}'

Gera: app-dev, app-staging e app-prod

Git Generator​

Varre diretórios dentro do repositório Git.

generators:
- git:
    repoURL: https://github.com/empresa/apps
    revision: HEAD
    directories:
    - path: apps/*

Se existirem pastas apps/front, apps/backend, apps/api, o ApplicationSet cria uma Application para cada.

Cluster Generator​

Cria aplicações para cada registro no ArgoCD:

generators:
- clusters: {}

Pull Request Generator​

Cria ambientes temporários para cada PR aberto:

generators:
- pullRequest:
    github:
      owner: empresa
      repo: app

Matrix Generator​

Combina múltiplos generators:

generators:
- matrix:
    generators:
    - list:
        elements:
        - env: dev
        - env: prod
    - clusters:
        selector:
          matchLabels:
            region: us-east

Finalizers​

Finalizers são mecanismos do Kubernetes que impedem a deleção de um recurso até que certas condições sejam atendidas.

Finalizer do ArgoCD​

Quando você deleta uma Application, o ArgoCD pode:

  1. Apenas remover a Application (recursos no cluster continuam existindo).
  2. Remover a Application E os recursos no cluster (cascade delete).

Cascade Delete​

metadata:
  finalizers:
  - resources-finalizer.argocd.argoproj.io

Com este finalizer, quando a Application é deletada, o ArgoCD:

  1. Remove todos os recursos que ela gerencia no Cluster.
  2. Só então remove a própria Application.

Problema Comum: Application "stuck"​

Se uma Application fica presa em "Deleting"m geralmente é porque:

  • Algum recurso no cluster está com finalizer próprio.
  • Há dependências circulares.

Solução: Remover manualmente o finalizer.

kubectl patch app myapp -n argocd -p '{"metadata":{"finalizers":[]}}' --type merge

Diff Customization​

O ArgoCD compara (diff) o estado desejado (Git) com o estado real (cluster).

Às vexes, certas diferenças são esperadas e devem ser ignoradas.

Ignorar diferenças​

spec:
  ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers:
    - /spec/replicas  # Ignora diferenças no número de réplicas

Por que ignorar diferenças​

  • HPA (Horizontal Pod Autoscaler) altera replicas automaticamente.
  • Mutating Webhooks adicionam annotations/labes.
  • Secrets são gerenciadas externamente.

Compare Options​

metadata:
  annotations:
    argocd.argoproj.io/compare-options: IgnoreExtraneous

Conclusão​

Os conceitos fundamentais do ArgoCD são a base para entender como a ferramenta funciona:

  • Application: conecta Git ao Kubernetes
  • Project: organiza e aplica governança
  • Repository: define onde estão os manifestos
  • Sync Status: indica se está conforme o Git
  • Health Status: indica se está funcionando
  • Sync: garante alinhamento Git -> Cluster
  • Drift Detection: identifica mudanças manuais
  • Sync Waves: controla ordem de aplicações
  • Hooks: executa tarefas em momentos específicos
  • App-of-Apps: orquestra múltiplas aplicações
  • ApplicationSet: automação em escala

Com esses conceitos dominados, você está pronto para a Arquitetura do ArgoCD, que veremos no próximo capítulo.
