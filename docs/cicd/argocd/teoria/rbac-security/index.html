RBAC e Controle de Acesso

Visão geral​

O RBAC (Role-Based Access Control) do Argo CD controla:

  • Quem pode acessar o Argo CD (autenticação).
  • O que cada pessoa pode fazer (autorização).
  • Onde (em quais Projects e Applications) as ações valem.

Isso é essencial quando há vários times e aplicações.

Autenticação (quem é você?)  ──►  Autorização (o que você pode fazer?)
  usuário local / SSO                RBAC: roles + policies + Projects

Autenticação​

Usuários locais​

Contas criadas no próprio Argo CD. Existe sempre a conta admin. Outras contas são declaradas no ConfigMap argocd-cm:

# argocd-cm
data:
  accounts.alice: login       # pode entrar na UI/CLI
  accounts.cicd: apiKey       # só gera token de API (automação)
  admin.enabled: "false"      # desativa o admin (após configurar o SSO)

Depois de declarada, a conta recebe a senha com a CLI:

argocd account update-password --account alice \
  --current-password <SENHA_DO_ADMIN> --new-password <NOVA_SENHA>

argocd account list
A CLI não cria usuários

O argocd account update-password define a senha de uma conta que já foi declarada. Sem a linha accounts.alice no argocd-cm, a conta não existe.

Use quando: laboratório, poucos usuários, contas de automação, ou como plano B se o SSO falhar.

SSO (login único)​

Integra o Argo CD ao provedor de identidade da organização, de duas formas:

  • Via Dex (conector pronto para GitHub, GitLab, Google, Microsoft, LDAP/AD, SAML).
  • Via OIDC direto com o provedor (Okta, Keycloak, Azure AD, Google...).

Exemplo com GitHub pelo Dex:

# argocd-cm
data:
  url: https://argocd.devopsr66.com
  dex.config: |
    connectors:
      - type: github
        id: github
        name: GitHub
        config:
          clientID: $dex.github.clientID
          clientSecret: $dex.github.clientSecret
          orgs:
            - name: minha-organizacao

O url precisa ser o endereço real de acesso, pois o fluxo de login redireciona para ele. Os valores com $ vêm de um Secret (nunca coloque o clientSecret direto no ConfigMap).

Use quando: ambientes com vários usuários, onde são importantes auditoria, offboarding e identidade centralizada. Em produção, prefira SSO a usuários locais.

Autorização (RBAC)​

O Argo CD usa um modelo de roles e policies, e os Projects funcionam como a fronteira.

Roles padrão​

RoleO que permite
role:adminAcesso total
role:readonlyApenas visualização

Formato de uma policy​

p, <sujeito>, <recurso>, <ação>, <objeto>, <efeito>
g, <usuário-ou-grupo>, <role>
CampoSignificadoExemplo
sujeitoRole que recebe a permissãorole:backend-dev
recursoTipo de recursoapplications, projects, repositories
açãoOperaçãoget, create, update, delete, sync, override, action
objetoAlvo no formato projeto/aplicaçãobackend/*, */*
efeitoallow ou denyallow

A linha g associa um usuário ou grupo a uma role.

Objetos no formato projeto/aplicação

Para applications, o objeto é sempre <projeto>/<aplicação>. Por isso backend/* significa "todas as Applications do Project backend", e */*, "todas as Applications de todos os Projects". Um deny com * isolado pode não casar como você espera.

Recursos e ações​

RecursoDescrição
applicationsApplications
applicationsetsApplicationSets
projectsAppProjects
repositoriesRepositórios
clustersClusters registrados
accountsContas
certificates, gpgkeysCertificados TLS e chaves GPG
logsLogs das aplicações
execTerminal nos Pods
AçãoDescrição
getVisualizar
createCriar
updateModificar
deleteRemover
syncSincronizar
overrideSobrescrever parâmetros no sync
actionExecutar resource actions

Configuração do RBAC​

As policies ficam no ConfigMap argocd-rbac-cm:

apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: argocd
data:
  # Role aplicada a quem não casou com nenhuma regra (menor privilégio)
  policy.default: role:readonly

  # Usado com SSO: quais "claims" trazem os grupos
  scopes: '[groups]'

  policy.csv: |
    # DevOps: gerencia todas as Applications e repositórios
    p, role:devops, applications, *, */*, allow
    p, role:devops, repositories, *, *, allow
    p, role:devops, clusters, get, *, allow
    g, minha-organizacao:devops, role:devops

    # Backend: só vê e sincroniza as Applications do Project "backend"
    p, role:backend-dev, applications, get, backend/*, allow
    p, role:backend-dev, applications, sync, backend/*, allow
    g, minha-organizacao:backend-team, role:backend-dev

    # Automação (CI/CD): sincroniza, sem poder apagar
    p, role:cicd, applications, get, */*, allow
    p, role:cicd, applications, sync, */*, allow
    p, role:cicd, applications, delete, */*, deny
    g, cicd, role:cicd
  • Com SSO do GitHub, os grupos aparecem como organização:time (por exemplo, minha-organizacao:backend-team).
  • Os nomes de usuário (como cicd) vêm das contas declaradas no argocd-cm.
  • Se uma regra deny e uma allow se aplicam ao mesmo alvo, o deny prevalece.

Para testar uma policy sem aplicá-la:

argocd admin settings rbac can role:backend-dev sync applications 'backend/minha-app' \
  --policy-file policy.csv

Roles e tokens do Project​

Além do RBAC global, cada Project pode ter roles próprias, ideais para automação com escopo reduzido:

apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: backend
  namespace: argocd
spec:
  roles:
    - name: ci-deploy
      description: Pipeline de deploy do backend
      policies:
        - p, proj:backend:ci-deploy, applications, sync, backend/*, allow

Depois, gere um token para essa role (e guarde-o no cofre do pipeline):

argocd proj role create-token backend ci-deploy

O token só consegue o que a role permite, no Project dela. Isso é melhor do que colocar as credenciais de uma pessoa no pipeline.

Multi-tenancy​

Para isolar times, combine três camadas:

CamadaO que isola
NamespacesOnde os recursos de cada time vivem
ProjectsQue repositórios, destinos e recursos cada time pode usar
RBACQuem pode ver e operar cada Project
Time Backend:  namespaces backend-*  │  Project: backend  │  RBAC: backend-team → role:backend-dev
Time Frontend: namespaces frontend-* │  Project: frontend │  RBAC: frontend-team → role:frontend-dev

Existe também a opção de instâncias separadas do Argo CD por time. Ela dá isolamento total, mas custa mais para operar (várias UIs, mais recursos), e só compensa em casos específicos.

Auditoria e logs​

O Argo CD registra o que acontece:

# Eventos do Kubernetes no namespace do Argo CD
kubectl get events -n argocd --sort-by='.lastTimestamp'

# Histórico de sincronizações de uma aplicação
argocd app history minha-app
  • Os logs do argocd-server registram as requisições à API (quem fez o quê).
  • Para logs em JSON, ajuste o argocd-cmd-params-cm (server.log.format: "json").
  • Para análise centralizada, envie os logs para o seu sistema de observabilidade (por exemplo, Loki). Em clusters com containerd, o coletor deve usar o parser cri.

Boas práticas​

1. Menor privilégio​

# Muito permissivo
p, role:dev, applications, *, */*, allow

# Específico
p, role:dev, applications, get, meuprojeto/*, allow
p, role:dev, applications, sync, meuprojeto/*, allow

2. Um Project por time (e por ambiente, quando necessário)​

backend-dev   → devs podem modificar
backend-prod  → só SRE/Operações

3. Contas de serviço para automação​

Nunca coloque credenciais pessoais em pipelines. Use uma conta de API (apiKey) ou um token de role de Project, com permissões mínimas.

4. Rotacione tokens​

argocd account generate-token --account cicd
# atualize o token no cofre de segredos do pipeline

5. SSO em produção, e desative o admin​

Centraliza a identidade, facilita o offboarding e melhora a auditoria. Depois que o SSO estiver funcionando, defina admin.enabled: "false". Antes disso, troque a senha do admin e apague o argocd-initial-admin-secret.

6. Revise periodicamente​

Reveja as policies, remova usuários inativos e confira as permissões das contas de automação.

Resumo​

  • Autenticação: usuários locais (declarados no argocd-cm) ou SSO (Dex/OIDC). Em produção, prefira SSO.
  • Autorização: roles + policies no argocd-rbac-cm. Formato: p, sujeito, recurso, ação, projeto/app, efeito.
  • policy.default: role:readonly = menor privilégio para quem não casou com nenhuma regra.
  • deny prevalece sobre allow.
  • Roles de Project + tokens = automação com escopo mínimo.
  • Multi-tenancy = namespaces + Projects + RBAC.
  • Boas práticas: desative o admin após o SSO, não use credenciais pessoais no CI, rotacione tokens.
  • A CLI não cria usuários: a conta precisa estar declarada no argocd-cm.
