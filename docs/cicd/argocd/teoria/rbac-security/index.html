RBAC e Controle de Acesso

Visão Geral​

O RBAC (Role-Based Access Control) do ArgoCD permite controlar:

  • Quem pode acessar o ArgoCD
  • O que cada usuário pode fazer
  • Onde as ações podem ser executadas

Isso é essencial em ambientes com múltiplos times e aplicações.

Modelo de Autenticação​

Autenticação Local​

Usuários criados diretamente no ArgoCD.

# Criar usuário
argocd account update-password --account alice --new-password abc123

# Listar usuários
argocd account list

Use quando:

  • Ambientes de desenvolvimento/teste
  • Poucos usuários
  • Não há SSO disponível

SSO (Single Sign-On)​

Integração com provedores corporativos via Dex ou OICD.

Provedores suportados:

  • GitHub
  • GitLab
  • Google
  • Microsoft Azure AD
  • Okta
  • LDAP/Active Directory
  • SAML

Configuração exemplo (GitHub):

# argocd-cm ConfigMap
data:
  url: https://argocd.example.com
  dex.config: |
    connectors:
    - type: github
      id: github
      name: GitHub
      config:
        clientID: $github-client-id
        clientSecret: $github-client-secret
        orgs:
        - name: my-organization
          teams:
          - backend-team
          - frontend-team

Use quando:

  • Ambientes corporativos
  • Múltiplos usuários
  • Compliance e auditoria

Modelo de Autorização (RBAC)​

O ArgoCD usa um modelo de RBAC baseado em:

  • Roles (papéis/funções)
  • Policies (regras de permissão)
  • Projects (boundary de recursos)

Roles Padrão​

RoleDescrição
adminAcesso total ao ArgoCD
readonlyApenas visualização

Estrutura de uma Policy​

p, <subject>, <resource>, <action>, <object>, <effect>

Onde:

  • subject: usuário, grupo ou role
  • resource: tipo de recurso (applications, projects, repositories)
  • action: operação (get, create, update, delete, sync, override)
  • object: recurso específico ou wildcard
  • effect: allow ou deny

Configuração do RBAC​

argocd-rabc-cm ConfigMap​

apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: argocd
data:
  policy.default: role:readonly  # Policy padrão para usuários não mapeados
  
  policy.csv: |
    # Admin completo
    p, role:admin, *, *, *, allow
    
    # DevOps team - pode gerenciar todas as apps
    p, role:devops, applications, *, */*, allow
    p, role:devops, repositories, *, *, allow
    p, role:devops, clusters, get, *, allow
    g, devops-team, role:devops
    
    # Backend team - apenas apps do projeto backend
    p, role:backend-dev, applications, get, backend/*, allow
    p, role:backend-dev, applications, sync, backend/*, allow
    g, backend-team, role:backend-dev
    
    # Frontend team - apenas apps do projeto frontend  
    p, role:frontend-dev, applications, get, frontend/*, allow
    p, role:frontend-dev, applications, sync, frontend/*, allow
    g, frontend-team, role:frontend-dev
    
    # Read-only para todos
    p, role:readonly, applications, get, */*, allow
    p, role:readonly, projects, get, *, allow

Mapeamento de Grupos SSO​

policy.csv: |
  g, my-github-org:backend-team, role:backend-dev
  g, my-github-org:frontend-team, role:frontend-dev
  g, alice@example.com, role:admin

Exemplos de Policies​

Exemplo 1: Developer com acesso limitado​

# Pode visualizar e sincronizar apps do seu projeto
p, role:developer, applications, get, myproject/*, allow
p, role:developer, applications, sync, myproject/*, allow

# Pode ver projetos
p, role:developer, projects, get, myproject, allow

# NÃO pode deletar ou modificar configurações
p, role:developer, applications, delete, *, deny
p, role:developer, applications, update, *, deny

Exemplo 2: SRE/Operations​

# Acesso total a aplicações
p, role:sre, applications, *, */*, allow

# Pode gerenciar clusters e repositórios
p, role:sre, clusters, *, *, allow
p, role:sre, repositories, *, *, allow

# Pode gerenciar projetos
p, role:sre, projects, *, *, allow

# NÃO pode modificar configurações globais do ArgoCD
p, role:sre, accounts, *, *, deny

Exemplo 3: Read-only com auditoria​

# Visualização completa
p, role:auditor, applications, get, */*, allow
p, role:auditor, projects, get, *, allow
p, role:auditor, clusters, get, *, allow
p, role:auditor, repositories, get, *, allow

# Ver logs de eventos
p, role:auditor, logs, get, */*, allow

# NENHUMA ação de modificação
p, role:auditor, *, create, *, deny
p, role:auditor, *, update, *, deny
p, role:auditor, *, delete, *, deny
p, role:auditor, *, sync, *, deny

Exemplo 4: CI/CD Service Account​

# Service account para pipelines CI/CD
# Pode criar e sincronizar apps
p, role:cicd, applications, create, */*, allow
p, role:cicd, applications, get, */*, allow
p, role:cicd, applications, sync, */*, allow
p, role:cicd, applications, update, */*, allow

# NÃO pode deletar
p, role:cicd, applications, delete, *, deny

# Mapear service account
g, cicd-bot, role:cicd

Actions Disponíveis​

ActionDescrição
getVisualizar recurso
createCriar novo recurso
updateModificar recurso existente
deleteRemover recurso
syncSincronizar aplicação
overrideSobrescrever parâmetros durante sync
actionExecutar resource actions

Resources Disponíveis​

ResourceDescrição
applicationsApplications do ArgoCD
projectsAppProjects
repositoriesRepositórios Git/Helm

accountsContas de usuários
certificatesCertificados TLS
gpgkeysChaves GPG para verificação

execExec em pods

Multi-tenancy​

Estratégia 1: Namespaces Dedicados​

Cada item tem:

  • Namespace exclusivo
  • Project do ArgoCD
  • RBAC isolado
Time Backend:
├── Namespace: backend-prod
├── Project: backend
└── RBAC: backend-team → role:backend-dev

Time Frontend:
├── Namespace: frontend-prod
├── Project: frontend
└── RBAC: frontend-team → role:frontend-dev

Estratégia 2: Instâncias Separadas do ArgoCD​

Cada time tem sua própria instalação do ArgoCD:

argocd-backend    (namespace: argocd-backend)
argocd-frontend   (namespace: argocd-frontend)
argocd-platform   (namespace: argocd-platform)

Vantagens:

  • Isolamento completo
  • Configurações independentes
  • Escalabilidade

Desvantagens:

  • Mais complexo de gerenciar
  • Múltiplas UIs
  • Overhead de recursos

Estratégia 3: Cluster-scoped vs Namespaced​

Cluster-scoped (padrão):

# ArgoCD gerencia recursos em qualquer namespace
kubectl create namespace argocd
kubectl apply -n argocd -f install.yaml

Namespaced (isolado):

# ArgoCD gerencia apenas um namespace específico
kubectl create namespace team-a-argocd
kubectl apply -n team-a-argocd -f install-namespace.yaml

Auditoria e Logs​

Events​

O ArgoCD registra todos os eventos:

# Ver eventos de uma aplicação
argocd app list-events myapp

# Via kubectl
kubectl get events -n argocd --sort-by='.lastTimestamp'

Audit Logs​

Habilite audit logs no API Server:

# argocd-cmd-params-cm ConfigMap
data:
  server.log.level: "debug"
  server.log.format: "json"

Logs incluem:

  • Quem fez a ação
  • Quando foi feito
  • O que foi modificado
  • Resultado da ação

Integração com SIEM​

Exporte logs para sistemas de análises

# Fluent Bit, Fluentd, etc
apiVersion: v1
kind: ConfigMap
metadata:
  name: fluent-bit-config
data:
  fluent-bit.conf: |
    [INPUT]
        Name tail
        Path /var/log/containers/argocd-server*.log
        Parser docker
    
    [OUTPUT]
        Name es
        Match *
        Host elasticsearch.logging.svc

Boas Práticas​

1. Princípio do Menor Privilégio​

Dê apenas as permissões necessárias:

# ❌ Muito permissivo
p, role:dev, applications, *, */*, allow

# ✅ Específico
p, role:dev, applications, get, myproject/*, allow
p, role:dev, applications, sync, myproject/*, allow

2. Use Projects para Isolamento​

Cada time deve ter seu próprio Project

├── project: backend
├── project: frontend
├── project: platform
└── project: data

3. Separe Ambientes​

├── project: backend-dev
├── project: backend-staging
└── project: backend-prod

Com RBAC diferente para cada ambiente:

  • Dev: developers podem modificar
  • Prod: apenas SRE/Ops

4. Service Accounts para Automação​

Nunce use credenciais pessoais em pipelines:

# ❌ Não faça
ARGOCD_USER=alice
ARGOCD_PASSWORD=...

# ✅ Use service account
ARGOCD_TOKEN=${{ secrets.ARGOCD_SA_TOKEN }}

5. Rotação de Tokens​

# Rotacionar token do service account
argocd account generate-token --account cicd-bot
# Atualizar em secrets do CI/CD

6. Auditoria Regular​

  • Revise periodicamente policies
  • Remova usuários inativos
  • Valide permissões de service accounts

7. SSO quando possível​

Evite usuários locais em produção:

  • Centraliza gestão de identidades
  • Facilita offboarding
  • Melhora auditoria

8. Namespaces como Boundary​

Use namespaces do Kubernetes como limite de isolamento:

destinations:
- namespace: 'backend-*'  # Apenas namespaces backend-*
  server: https://kubernetes.default.svc

Conclusão​

RBAC e controle de acesso são fundamentais para usar o ArgoCD com segurança em ambientes corporativos.

Principais pontos:

  • Use SSO para autenticação
  • Configure RBAC granular com policies
  • Isole times com Projects
  • Aplique least privilege
  • Mantenha auditoria habilitada
  • Use service accounts para automação
