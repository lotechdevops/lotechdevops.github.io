Arquitetura do ArgoCD

Visão Geral​

O ArgoCD é composto por uma arquitetura modular, onde cada componente executa uma função específica.
Todos os componentes rodam como pods dentro do Kubernetes, garantindo escalabilidade, observabilidade e fácil atualização.

O objetivo dessa arquitetura é manter o estado do cluster sincronizado com o estado desejado armazenado no Git, de forma contínua, segura e auditável.

Componentes Principais​

ArgoCD API Server​

  • É o cérebro central do ArgoCD.
  • Expõe uma API REST, a interface web (UI) e o acesso da CLI (argocd).
  • Cuida da autenticação, autorização e do gerenciamento das Applications.
  • Todos os comandos executados pelo usuário passam pelo API Server.
  • Serve a interface gRPC para a CLI.

Responsabilidades:

  • Validação e autorização de requisições
  • Gerenciamento de Applications, Projects e Repositories.
  • Integração com Dex para SS0
  • Webhook receiver para eventos do Git

Ele é o ponto de entrada para o ArgoCD, conectando usuários, automações e a UI.

Repository Server​

  • É responsável por clonar e preocessar repositórios Git.
  • Gera os manifestos Kubernetes a partir de diferentes formatos?
    • YAML puro
    • Helm Charts
    • Kustomize
    • Jsonnet
    • Custom Config Management Plugins
  • Faz cache dos repositórios para melhorar a performance e reduzir chamados ao Git.
  • Trabalha de forma isolada, permitindo escalabilidade horizontal.
  • Mantém cópias locais dos repositórios em disco.

Fluxo de trabalho:

  1. Recebe requisição para processar um repositório
  2. Clona ou atualiza o repositório (se já existir em cache)
  3. Executa o processamento (Helm template, Kustomize build, etc)
  4. Retorna os manifestos YAML resultantes
  5. Mantém cache para acelerar futuras requisições

Ciclo de reconciliação:

  1. Lista todas as Applications
  2. Para cada Application:
    • Busca estado desejado do Repository Server
    • Busca estado atual do cluster via Kubernetes API
    • Compara os dois estados
    • Se detectar diferença:
      • Marca como OutOfSync
      • Aplica mudanças (se auto-sync estiver habilitado)
    • Avalia Health Status dos recursos

Configurações importantes:

  • Intervalo de reconcilização (padrão: 3 minutos)
  • Timeout de sincronização
  • Retry policy

É o componente que efetivamente faz o GitOps acontecer.

ApplicationSet Controller​

  • É o componente responsável pelo recurso ApplicationSet.
  • Permite gerar Applications dinamicamente com base em templates e fontes de dados.
  • Ideal para ambientes multi-cluster, multi-ambiente ou com muitos microserviços.
  • Suporta diferentes "geradores" (generators):
    • List Generator (lista estática de parâmetros)
    • Cluster Generator (gera apps para cada cluster registrado)
    • Git Generator (lê pastas ou arquivos no repositório)
    • Matrix/Combination Generator (combina múltiplas fontes)
    • Pull Request Generator (cria apps para cada PR aberto)
    • SCM Provider Generator (GitHub/GitLab organizations)

Funcionamento:

  1. Observa objetos ApplicationSet
  2. Executa os generators definidos
  3. Gera lista de parâmetros
  4. Renderiza template para cada conjunto de parâmetros
  5. Cria/atualiza/deleta Applications conforme necessário

O ApplicationSet Controller traz automação e escalabilidade, eliminando a necessidade de criar centenas de Applications manualmente.

Notifications Controller​

  • É o subsistema de alertas e notificações do ArgoCD
  • Envia mensagens automáticas quando ocorrem eventos como:
  • Totalmente configurável via ConfigMap e CRDs.

Eventos suportados:

  • Sincronização bem-sucedidas ou com falha
  • Mudanças no status da aplicação (degraded, Health, etc)
  • Ações manuais executadas por usuários
  • Detecção de drift
  • Health degradation

Canais de integração:

  • Slack
  • Microsoft Teams
  • Email (SMTP)
  • Webhook genérico
  • Opsgenie
  • PagerDuty
  • Grafana OnCall entre outros.

Estrutura de configuração:

# ConfigMap
notifications:
  templates:
    template.app-deployed: |
      message: Application {{.app.metadata.name}} deployed
  triggers:
    trigger.on-deployed: |
      - when: app.status.operationState.phase == 'Succeeded'
        send: [app-deployed]
  services:
    slack:
      token: $slack-token

Esse componente é essencial em ambientes corporativos e SRE, onde o time precisa ser notificado imediatamente sobre problemas.

Dex (ou outro provedor de autenticação)​

  • Cuida da autenticação (login) no ArgoCD.
  • Implementa OpenID Connect (OIDC)
  • Suporta SSO (Single Sign-On) e integração com:
    • LDAP / Active Directory
    • OAuth2 / OIDC
    • SAML
    • GitHub
    • GitLab
    • Google
    • Microsoft Azure AD
    • Okta

Configuração típica:

dex.config: |
  connectors:
  - type: github
    id: github
    name: GitHub
    config:
      clientID: $github-client-id
      clientSecret: $github-client-secret
      orgs:
      - name: my-organization

Alternaticas ao Dex:

  • Keycloak
  • Auth0

Facilita o uso de credenciais corporativas sem precisar criar usuários locais.

Redis​

  • Atua como cache em memória para o ArgoCD.
  • Armazena dados temporários para melhorar o desempenho.
  • Não guarda dados permanentes (tudo é reconstruído em caso de reinício).

O que é armazenado:

  • Cache de repositórios Git
  • Informações de sessão
  • Cache de manifestos processados
  • Estado temporário de sincronização

Modos de deployment:

  • Standalone (desenvolvimento/teste)
  • HA com Sentinel (produção)
  • Cluster mode (alta escala)

CLI (argocd)​

  • Ferramenta de linha de comando para interagir com o ArgoCD via API Server.
  • Permite criar, listar e sincronizar Applications diretamente do terminal.
  • Útil em pipelines CI/CD, scripts de automação e tarefas administrativas.

Comandos principais:

# Login
argocd login argocd.example.com

# Criar application
argocd app create myapp --repo https://github.com/... --path ./

# Sincronizar
argocd app sync myapp

# Ver status
argocd app get myapp

# Deletar
argocd app delete myapp

Fluxo de Funcionamento Detalhado​

1. Criação de Application​

[Usuário] → [CLI/UI] → [API Server]
                            ↓
                      [Validação RBAC]
                            ↓
                      [Salva no Kubernetes]
                            ↓
                      [Application CRD criado]

2. Reconciliação​

[Application Controller] → [Detecta nova Application]
         ↓
[Solicita manifests] → [Repository Server]
                              ↓
                        [Clona Git repo]
                              ↓
                        [Processa manifests]
                              ↓
                        [Retorna YAML]
         ↓
[Compara com cluster] → [Kubernetes API]
         ↓
[Identifica diferenças]
         ↓
[Aplica recursos (se auto-sync)]
         ↓
[Atualiza status] → [API Server] → [UI/CLI]
         ↓
[Envia notificações] → [Notifications Controller]

3. Webhook do Git​

[Git Push] → [Webhook] → [API Server]
                              ↓
                        [Marca app para refresh]
                              ↓
                        [Application Controller]
                              ↓
                        [Inicia reconciliação]

Padrões de Deployment​

Deployment Básico (Não-HA)​

┌──────────────────────────────────────┐
│          argocd-server (1 pod)       │
├──────────────────────────────────────┤
│    argocd-repo-server (1 pod)        │
├──────────────────────────────────────┤
│ argocd-application-controller (1 pod)│
├──────────────────────────────────────┤
│     argocd-dex-server (1 pod)        │
├──────────────────────────────────────┤
│        redis (1 pod)                 │
└──────────────────────────────────────┘

Use quando:

  • Ambiente de desenvolvimento/teste
  • Pequena quantidade de aplicações (menor que 50)
  • Downtime tolerável

High Availability (HA)​

┌────────────────────────────────────────────────┐
│   argocd-server (3+ pods com LoadBalancer)     │
├────────────────────────────────────────────────┤
│   argocd-repo-server (2+ pods)                 │
├────────────────────────────────────────────────┤
│   argocd-application-controller (1 pod) *      │
├────────────────────────────────────────────────┤
│   argocd-dex-server (2+ pods)                  │
├────────────────────────────────────────────────┤
│   redis-ha (3+ pods com Sentinel)              │
└────────────────────────────────────────────────┘

**Application Controller não pode ter múltiplas réplicas (evita race conditions), mas pode ter standby**

Use quando:

  • Ambiente de produção
  • SLA exigente
  • Muitas aplicações (100+)

Resiliência e Escalabilidade​

Escalabilidade Horizontal​

  • API Server (múltiplas réplicas atrás de LoadBalancer)
  • Repository Server (múltiplas réplicas)
  • Notifications Controller (múltiplas réplicas)
  • ApplicationSet Controller (múltiplas réplicas)
  • Dex (múltiplas réplicas)
  • Application Controller (apenas 1 active, pode ter standby)
  • Redis (múltiplas réplicas)

Limites de Escala​

Application Controller:

  • ~1000 Applications por instância
  • ~2000 recursos Kubernetes por Application
  • Reconciliação a cada 3 minutos (configurável)

Repository Server:

  • Cache de repositórios em disco
  • Processar ~50 repositórios simultaneamente
  • Escale horizontalmente conforme necessário

Recomendações:

Pequeno (< 100 apps):    recursos padrão
Médio (100-500 apps):    2x recursos, 2+ repo-servers
Grande (500-1000 apps):  4x recursos, 4+ repo-servers
Muito grande (> 1000):   considere múltiplas instâncias do ArgoCD

Segurança​

Network Policies​

# Permitir apenas comunicação necessária
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: argocd-server
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: argocd-server
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app.kubernetes.io/name: argocd-dex-server
    ports:
    - protocol: TCP
      port: 8080

RBAC​

O ArgoCD precisa de permissões no cluster:

  • cluster-scoped: para gerenciar CRDs, ClusterRoles, etc
  • Namespace-scoped: para gerenciar Deployments, Services, etc

Recomendação: Use Projects do ArgoCD para limitar o que cada Application pode fazer.

Secrets Management​

Integrações suportadas:

  • Sealed Secrets (criptografia assimétrica)
  • External Secrets Operator (sincroniza de vaults externos)
  • Hashicorp Vault (via Vault Agent ou CSI)
  • SOPS (criptografia de arquivos YAML)
  • ArgoCD Vault Plugin (AVP) (plugin oficial)

Integrações​

Monitoramento​

Prometheus:

# ServiceMonitor para Prometheus Operator
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: argocd-metrics
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: argocd-server-metrics
  endpoints:
  - port: metrics

Métricas importantes:

  • argocd_app_info - Informações das aplicações
  • argocd_app_sync_total - Total de sincronizações
  • argocd_app_health_status - Status de saúde
  • argocd_cluster_api_resource_objects - Objetos no cluster

Grafana:

  • Dashboards oficial do ArgoCD
  • Métricas de performance
  • Status de aplicações

CI/CD Integration​

GitHub Actions:

- name: Sync ArgoCD App
  run: |

GitLab CI:

deploy:
  script:
    - argocd app sync myapp

Conclusão​

A arquitetura do ArgoCD é formada por componentes independentes, mas altamente integrados:

  • O API Server centraliza o acesso e autenticação
  • O Repository Server processa e interpreta os manifestos do Git
  • O Application Controller garante a reconciliação contínua
  • O ApplicationSet Controller automatiza a criação de Applications
  • O Notifications Controller alerta sobre eventos importantes
  • O Dex autentica os usuários via SSO
  • O Redis acelera as operações com cache

Essa modularidade permite que o ArgoCD seja usado desde ambientes pequenos on-premises até plataformas corporativas complexas com múltiplos clusters e centenas de aplicações.

A arquitetura é cloud-native, escalável e resiliente, alinhada com as melhores práticas de Kubernetes.
