Arquitetura do Argo CD

Visão geral​

O Argo CD tem uma arquitetura modular: cada componente cumpre uma função e roda como Pod dentro do Kubernetes. O objetivo é manter o estado do cluster sincronizado com o estado desejado no Git, de forma contínua, segura e auditável.

                       ┌────────── Argo CD (namespace argocd) ──────────┐
 Usuário ─► UI / CLI ─►│ API Server ──► Application Controller ──────────┼─► Kubernetes API
                       │      │                  │                        │   (cluster destino)
 Webhook Git ─────────►│      │                  ▼                        │
                       │      │            Repo Server ──► Git / Helm     │
                       │      ▼                  ▲                        │
                       │    Redis (cache) ───────┘                        │
                       │  Dex (SSO)   ApplicationSet / Notifications      │
                       └──────────────────────────────────────────────────┘
Onde fica o estado do Argo CD?

O Argo CD não tem banco de dados. Applications, Projects e configurações são recursos do Kubernetes (CRDs, ConfigMaps e Secrets no namespace argocd), guardados no etcd. O Redis é só cache e pode ser perdido sem prejuízo. Isso importa para o backup: basta salvar esses recursos.

Componentes principais​

ComponenteFunção
API ServerPorta de entrada: UI, CLI e API; autenticação e autorização
Repository ServerClona o Git e gera os manifestos
Application ControllerReconcilia: compara o Git com o cluster e sincroniza
ApplicationSet ControllerGera Applications a partir de templates
Notifications ControllerEnvia alertas sobre eventos das Applications
DexSSO (login único), opcional
RedisCache

API Server (argocd-server)​

É o ponto de entrada do Argo CD. Expõe a interface web, a API e atende a CLI (argocd).

Responsabilidades:

  • Autenticar (usuários locais ou SSO) e autorizar (RBAC) cada requisição.
  • Gerenciar Applications, Projects e Repositories.
  • Receber webhooks do Git, que antecipam a detecção de mudanças.
  • Integrar com o Dex para SSO.

Todo comando do usuário (UI ou CLI) passa por ele.

Repository Server (argocd-repo-server)​

Responsável por clonar e processar os repositórios.

  • Gera os manifestos Kubernetes a partir de vários formatos: YAML puro, Helm, Kustomize, Jsonnet e plugins (CMP).
  • Mantém cache local dos repositórios e dos manifestos gerados, reduzindo chamadas ao Git.
  • Trabalha de forma isolada e pode ser escalado horizontalmente.

Fluxo:

  1. Recebe um pedido para processar um repositório.
  2. Clona ou atualiza o repositório (usa o cache se já existir).
  3. Executa o processamento (helm template, kustomize build...).
  4. Devolve os manifestos YAML resultantes.

Application Controller (argocd-application-controller)​

É o coração do GitOps: o componente que realmente reconcilia o cluster com o Git.

Ciclo de reconciliação:

  1. Para cada Application, pede ao Repository Server o estado desejado (manifestos do Git).
  2. Lê o estado atual do cluster pela API do Kubernetes.
  3. Compara os dois.
  4. Se houver diferença:
    • Marca a Application como OutOfSync.
    • Aplica as mudanças, se a sincronização automática estiver habilitada.
  5. Avalia o Health dos recursos.
  6. Atualiza o status e dispara eventos (que o Notifications usa).

Configurações importantes:

  • Intervalo de refresh: padrão de 3 minutos (timeout.reconciliation).
  • Timeouts e política de retry do sync.
Escala

O Application Controller roda como StatefulSet e escala por sharding: cada réplica cuida de um conjunto de clusters. Para um único cluster (como um homelab), uma réplica é suficiente.

ApplicationSet Controller​

Cuida do recurso ApplicationSet: gera Applications dinamicamente a partir de templates e fontes de dados (generators).

Funcionamento:

  1. Observa os objetos ApplicationSet.
  2. Executa os generators (List, Git, Cluster, Pull Request, Matrix...).
  3. Gera um conjunto de parâmetros para cada item.
  4. Renderiza o template para cada conjunto.
  5. Cria, atualiza ou remove as Applications conforme necessário.

Os generators e a forma de usá-los estão em Conceitos Fundamentais e no laboratório de ApplicationSet.

Notifications Controller​

É o subsistema de alertas. Observa as Applications e envia mensagens quando ocorrem eventos, como:

  • Sincronização concluída ou com falha.
  • Mudança de status (Degraded, OutOfSync...).
  • Ação manual de um usuário.

A configuração é feita por ConfigMap (templates, triggers e serviços) e por annotations nas Applications. Canais: Slack, Microsoft Teams, e-mail, webhook, PagerDuty, Opsgenie e outros. O passo a passo está no laboratório de Notificações.

Dex (opcional)​

Cuida do login único (SSO) no Argo CD, usando OpenID Connect (OIDC). Conecta o Argo CD a provedores de identidade, como GitHub, GitLab, Google, Microsoft, Okta, LDAP/AD e SAML.

Alternativas: usar um OIDC direto do provedor (sem o Dex) ou outro serviço de identidade, como Keycloak.

Usuários e permissões são tratados em RBAC e Controle de Acesso.

Redis​

Cache em memória do Argo CD: guarda manifestos gerados, estado de aplicações e dados temporários. Não guarda dados permanentes: se for reiniciado, tudo é reconstruído.

Modos de instalação: simples (laboratório) ou HA com Sentinel (produção).

CLI (argocd)​

Ferramenta de linha de comando que conversa com o API Server. Serve para criar, listar e sincronizar Applications no terminal, em scripts e em pipelines.

argocd login argocd.devopsr66.com   # autenticar
argocd app list                     # listar aplicações
argocd app get minha-app            # ver o status
argocd app sync minha-app           # sincronizar
Versão da CLI

Use uma CLI com a mesma versão do servidor Argo CD, para evitar incompatibilidades.

Fluxos principais​

1. Criar uma Application​

[Usuário] ─► [UI / CLI] ─► [API Server]
                               ├─ valida a permissão (RBAC)
                               └─ cria o recurso Application no Kubernetes

2. Reconciliar​

[Application Controller] detecta a Application
     ├─ pede os manifestos ─► [Repository Server] ─► clona o Git e gera o YAML
     ├─ lê o estado atual ──► [Kubernetes API]
     ├─ compara (diff)
     ├─ se houver diferença: OutOfSync (+ aplica, se auto-sync)
     └─ atualiza o status ──► visível na UI/CLI e usado pelas notificações

3. Webhook do Git​

[git push] ─► [Webhook] ─► [API Server] ─► marca a Application para refresh
                                         └─► o Controller reconcilia na hora

Sem webhook, o Argo CD só percebe a mudança no próximo refresh (até 3 minutos).

Modelos de instalação​

Não-HAHA (alta disponibilidade)
UsoLaboratório, desenvolvimento, poucas aplicaçõesProdução, SLA exigente
argocd-server1 réplicaVárias réplicas
argocd-repo-server1 réplicaVárias réplicas
ApplicationSet Controller1 réplicaVárias réplicas
Application Controller1 réplica1 (ou mais, com sharding)
RedisSimplesredis-ha com Sentinel
Confira as réplicas na documentação oficial

O número exato de réplicas do modo HA muda entre versões. Consulte o manifesto/chart da versão que você instalar. O ponto principal é que API Server, Repository Server e Redis ganham redundância, e o Application Controller escala por sharding, não por réplicas idênticas.

Para um cluster pequeno ou um homelab, a instalação não-HA é suficiente. A decisão de HA vale quando uma indisponibilidade do Argo CD já causaria prejuízo.

Segurança e integrações (resumo)​

Os detalhes ficam nas páginas e laboratórios específicos:

  • Secrets: como guardar credenciais com segurança no GitOps (página Gerenciamento de Secrets).
  • Acesso: SSO, RBAC e Projects (página RBAC e Controle de Acesso).
  • Rede: as instalações oficiais já incluem NetworkPolicies para os componentes.
  • Monitoramento: cada componente expõe métricas Prometheus. Dá para coletá-las com um ServiceMonitor e montar painéis no Grafana.
  • Integração com CI: o pipeline pode acionar o Argo CD pela CLI/API, ou apenas atualizar a versão no repositório de configuração e deixar o Argo CD sincronizar.

Resumo​

  • Componentes: API Server, Repository Server, Application Controller, ApplicationSet Controller, Notifications Controller, Dex e Redis.
  • O Application Controller é quem reconcilia: compara Git × cluster e sincroniza. Refresh padrão: 3 minutos.
  • O Repository Server gera os manifestos (Helm, Kustomize, YAML).
  • O estado do Argo CD vive em recursos do Kubernetes; o Redis é só cache.
  • Webhook do Git antecipa a detecção de mudanças.
  • Não-HA para laboratório; HA para produção.
  • O controller escala por sharding de clusters.
