O que é GitOps

Conceito​

O GitOps é uma prática de operações orientadas a Git.

Ele propõe que o estado desejado de aplicações e infraestrutura seja descrito em repositórios Git e que um agente automatizado (como o ArgoCD) seja responsável por aplicar e manter esse estado em produção.

Em outras palavras: tudo que define seu sistema deve estar versionado no Git, e o cluster nunca deve ser alterado manualmente.

Princípios do GitOps​

O GitOps se apoia em quatro princípios fundamentais:

  1. Estado desejado declarativo

    • Toda a configuração é descrita em arquivos (YAML, Helm, Kustomize), que definem o que deve existir no cluster.

  2. Git como única fonte de verdade

    • O repositório Git é o ponto central onde estão armazenados todos os manifestos.
    • Se algo não está no Git, não existe oficialmente.

  3. Automação e sincronização contínua

    • Um agente (ex: ArgoCD) monitora o Git e reconcilia constantemente o estado real com o estado desejado.

  4. Auditoria e rastreabilidade total

    • Cada mudança passa por commit e pull request, garantindo histórico completo de quem alterou, o que foi alterado e quando.

Benefícios do GitOps​

  • Consistência entre ambientes: fácil replicar staging e produção a partir do mesmo repositório.
  • Segurança e governança: ninguém altera manualmente o cluster, reduzindo riscos.
  • Auditoria detalhada: o Git mostra todo o histórico de mudanças.
  • Rollback simples: voltar para um estado anterior é apenas reverter um commit.
  • Colaboração facilitada: todos os times trabalham a partir do mesmo repositório.
  • Escalabilidade: ideal para gerenciar dezenas ou centenas de microserviços.
  • Disaster Recovery: o Git é o backup natural do seu ambiente.
  • Conformidade e compliance: atende requisitos de auditoria em ambientes regulados.

Fluxo de Trabalho GitOps​

Um ciclo GitOps típico funciona assim:

  1. 0 desenvolvedor altera um manifesto ou Helm Chart no repositório Git.
  2. A alteração passa por revisão e aprovação via Pull Request.
  3. Após o merge, o estado desejado é atualizado no Git.
  4. O agente GitOps (como o ArgoCD) detecta a mudança e aplica no cluster.
  5. O cluster passa a refletir exatamente o que está descrito no Git.
  6. Se houver mudanças manuais, o agente identifica o drift e pode corrigir automaticamente.

GitOps x CI/CD Tradicional​

É comum confundir GitOps com pipelines CI/CD, mas eles têm funções diferentes:

CI (Continuos Integration)​

  • Foca em build, testes e validações.
  • Exemplo: compilar código, rodar testes unitários, gerar imagem Docker.
  • Ferramentas comuns: Jenkins, GitHub Actions, GitLab CI.

CD Tradicional (Push-based)​

  • Pipeline empurra mudanças para o ambiente.
  • Requer credenciais de acesso ao cluster no CI/CD.
  • Menos seguro (credenciais expostas).
[Git] → [CI Pipeline] → [kubectl apply] → [Kubernetes Cluster]
         ↑ possui credenciais do cluster

GitOps (Pull-based CD)​

  • Agente dentro do cluster puxa mudanças do Git.
  • Não expõe credenciais do cluster.
  • Mais seguro e auditável.
  • Exemplo: garantir que o cluster esteja rodando a versão da aplicação definida no Git.
  • Ferramentas comuns: ArgoCD, FluxCD.
[Git] ← [ArgoCD dentro do cluster] → [Kubernetes Cluster]
         ↑ monitora continuamente

O ponto-chave é: CI prepara o pacote, GitOps garante que o pacote esteja rodando corretamente no ambiente.

Estratégias de Repositório​

Mono-repo​

Um único repositório contém todos os manifestos de todas as aplicações.

Vantagens:

  • Simples de gerenciar
  • Fácil visualização de todas as apps
  • Ideal para times pequenos

Desvantagens:

  • Pode crescer muito
  • Difícil controlar permissões granulares
  • Commits afetam muitas aplicações

Multi-repo​

Cada aplicação tem seu próprio repositório.

Vantagens:

  • Isolamento completo entre apps
  • Controle de acesso granular
  • Escalável para grandes organizações

Desvantagens:

  • Mais completo de gerenciar
  • Múltiplos repositórios para sincronizar

Hybrid (Recomendado)​

Repositórios separados para:

  • App code (código da aplicação).
  • App config (manifestos Kubernetes)
  • Infraestrutura (recursos compartilhados)

Vantagens:

  • Separação de concerns
  • Diferentes ciclos de vida
  • Diferentes permissões por tipo

Environment Promotion​

Como promover mudanças entre ambientes (dev -> staging -> prod)?

Opção 1: Branches​

git/
├── branches/dev
├── branches/staging
└── branches/prod

Promoção via merge ou cherry-pick.

Opção 2: Diretórios​

git/
├── environments/dev/
├── environments/staging/
└── environments/prod/

Promoção via cópia de arquivos ou PR.

Opção 3: Repositórios separados​

app-dev/
app-staging/
app-prod/

Promoção via tag e atualização de valores.

Casos de Uso​

  • Times distribuídos que precisam garantir consistência entre múltiplos ambientes (dev, stage e prod).
  • Ambientes regulados (bancos, saúde, telecom) que exigem auditoria e rastreabilidade.
  • Escalabilidade de microserviços, onde cada equipe gerencia suas próprias aplicações.
  • Resiliência: rollback imediato revertendo um commit no Git.
  • Governança corporativa: centralizar políticas e configurações no Git, aplicadas de forma automática.
  • Multi-cloud/Hybrid cloud: gerenciar múltiplos clusters de forma unificada.

Exemplos Práticos​

Atualizar uma aplicação​

# 1. Editar values.yaml
image:
  tag: v1.2.3  # nova versão

# 2. Commit e push
git add values.yaml
git commit -m "Update app to v1.2.3"
git push

# 3. ArgoCD detecta e aplica automaticamente

Rollback rápido​

# Reverter commit
git revert HEAD
git push

# ArgoCD restaura a versão anterior em minutos

Clonar ambientes​

# Mesmo repositório, diferentes Applications no ArgoCD
# Production aponta para /prod
# Staging aponta para /staging

Conclusão​

O GitOps é uma forma moderna e confiável de gerenciar aplicações em Kubernetes.

Ele combina os benefícios do controle de versão do Git com a automação de entrega contínua, garantindo ambientes mais seguros, auditáveis e previsíveis.
