O que é GitOps

Conceito​

GitOps é uma prática de operações orientada a Git.

O estado desejado de aplicações e infraestrutura é descrito em repositórios Git, e um agente automatizado (como o Argo CD) aplica e mantém esse estado no ambiente.

Em outras palavras: tudo que define o sistema fica versionado no Git, e o cluster não deve ser alterado manualmente.

Os quatro princípios​

O GitOps se apoia em quatro princípios (definidos pelo projeto OpenGitOps):

#PrincípioNa prática
1DeclarativoO sistema é descrito pelo estado desejado (YAML, Helm, Kustomize), não por uma sequência de comandos
2Versionado e imutávelO estado desejado vive no Git, com histórico completo. Se não está no Git, não existe oficialmente
3Puxado automaticamenteUm agente busca o estado desejado da fonte, sem que alguém precise empurrá-lo
4Reconciliado continuamenteO agente compara o estado real com o desejado o tempo todo e corrige as diferenças

Benefícios​

  • Consistência entre ambientes: staging e produção partem do mesmo repositório.
  • Segurança: ninguém altera o cluster à mão, e o agente roda dentro do ambiente, sem expor credenciais ao pipeline.
  • Auditoria: o Git mostra quem mudou o quê, quando e por quê.
  • Rollback simples: voltar é reverter um commit.
  • Recuperação de desastre: com o Git, o ambiente pode ser recriado.
  • Colaboração: todos trabalham pelo mesmo fluxo de pull request.

O ciclo de trabalho​

1. Alguém altera um manifesto (ou values do Helm) em um branch
2. Abre um Pull Request, que passa por revisão
3. Após o merge, o estado desejado no Git muda
4. O agente (Argo CD) detecta a mudança
5. Aplica no cluster
6. Se alguém alterar o cluster à mão, o agente vê o drift e pode corrigi-lo
Quanto tempo leva para o Argo CD notar?

Por padrão, o Argo CD consulta o Git a cada 3 minutos. Com um webhook do GitHub, a detecção é praticamente imediata. Por isso "o rollback acontece em minutos" é o comportamento padrão, e não uma garantia.

GitOps e CI/CD​

GitOps não substitui o CI: ele cuida do CD. O CI constrói e publica a imagem, e o GitOps garante que o cluster rode o que está descrito no Git.

A diferença entre o modelo push (o pipeline empurra a mudança) e o pull (um agente dentro do ambiente busca a mudança), com os prós e contras de cada um, está em CI/CD: visão geral. O GitOps usa o modelo pull.

Estratégias de repositório​

Onde ficam os manifestos?

EstratégiaComo éQuando usarCuidado
Mono-repoUm repositório com tudoTimes pequenos, homelabCresce muito; permissões pouco granulares
Multi-repoUm repositório por aplicaçãoOrganizações grandesMais repositórios para gerenciar
HíbridoSepara código, configuração e infraestruturaRecomendado a partir de uma certa escalaExige disciplina

Por que separar o código da aplicação da configuração (manifestos)?

  • Um commit de configuração não dispara o build do código (evita ciclos de CI desnecessários).
  • Os dois têm ciclos de vida e permissões diferentes.
  • O histórico de deploys fica limpo, sem misturar com commits de código.

Promoção entre ambientes​

Como levar uma mudança de dev para staging e produção?

OpçãoComoObservação
BranchesUm branch por ambiente (dev, staging, prod)Promoção por merge. Branches de longa duração tendem a divergir
DiretóriosUma pasta por ambiente (environments/dev, staging, prod)Tudo visível em um só lugar. Promoção por PR copiando/alterando valores
Repositórios separadosUm repositório por ambienteIsolamento máximo, mas mais trabalho

Uma escolha comum é diretórios (com Kustomize ou Helm values por ambiente): fica fácil comparar ambientes com diff e revisar a promoção em um PR.

gitops/
└── environments/
    ├── dev/      ← values.yaml do dev
    ├── staging/  ← values.yaml do staging
    └── prod/     ← values.yaml de produção

Exemplos do dia a dia​

Atualizar uma aplicação

# 1. Edite o values.yaml com a nova versão
#    image:
#      tag: 1.2.3

# 2. Commit e push
git add values.yaml
git commit -m "Atualiza app para 1.2.3"
git push

# 3. O Argo CD detecta e aplica (em até 3 min, ou na hora com webhook)

Rollback

git revert HEAD
git push

# O Argo CD restaura a versão anterior
Rollback é por Git

Com sincronização automática ligada, o caminho correto de rollback é reverter o commit. O comando argocd app rollback não funciona com auto-sync habilitado (veja o laboratório de Application).

Casos de uso​

  • Times distribuídos que precisam de consistência entre ambientes.
  • Ambientes regulados (bancos, saúde, telecom), que exigem auditoria.
  • Muitos microserviços, cada equipe cuidando das suas aplicações.
  • Multi-cluster e multi-cloud, gerenciados de forma unificada.
  • Recuperação rápida, pois o ambiente se reconstrói a partir do Git.

Resumo​

  • GitOps = o estado desejado fica no Git, e um agente reconcilia o ambiente com ele.
  • Quatro princípios: declarativo, versionado e imutável, puxado automaticamente, reconciliado continuamente.
  • GitOps cuida do CD; o CI continua fazendo build e testes.
  • Detecção padrão: a cada 3 minutos (webhook deixa imediato).
  • Separe o repositório de código do de configuração.
  • Promoção entre ambientes: diretórios costumam ser o caminho mais simples.
  • Rollback = git revert.
