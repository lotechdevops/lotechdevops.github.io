Gerenciamento de Secrets no GitOps

O problema​

No GitOps, tudo fica versionado no Git. Mas e as senhas, tokens e certificados?

Nunca faça isto:

apiVersion: v1
kind: Secret
metadata:
  name: database
data:
  password: c3VwZXJzZWNyZXQ=   # base64 NÃO é criptografia!

O base64 é só uma codificação: qualquer pessoa decodifica em um comando. Commitar um Secret assim no Git é uma falha grave de segurança:

  • Quem tem acesso ao repositório vê o segredo.
  • O histórico do Git guarda o valor para sempre, mesmo depois de apagá-lo.
  • Logs de CI e ferramentas de revisão podem expô-lo.
  • Trocar a credencial vira uma operação trabalhosa.
Apagar o commit não resolve

Se um segredo já foi para o Git, considere-o comprometido: troque a credencial (revogue o token, mude a senha). Reescrever o histórico não basta, pois cópias e clones continuam existindo.

As duas famílias de solução​

O Argo CD documenta duas abordagens para segredos:

AbordagemComo funcionaExemplos
Operador no clusterUm controller cria o Secret dentro do cluster. O Git guarda só algo cifrado ou uma referênciaSealed Secrets, External Secrets Operator
Plugin de manifestoO Argo CD injeta o valor no manifesto ao renderizarArgo CD Vault Plugin, SOPS/KSOPS
Qual a recomendação do Argo CD?

A documentação do Argo CD recomenda a abordagem de operador. Nos plugins de manifesto, o valor do segredo passa pelo Repository Server e fica no cache do Argo CD, o que amplia a superfície de ataque. Por isso, neste material o foco é nos operadores.

Sealed Secrets​

O Sealed Secrets deixa você cifrar um Secret antes de commitar. Só o controller dentro do cluster consegue decifrar.

Como funciona​

Secret normal ──► kubeseal (chave PÚBLICA) ──► SealedSecret ──► Git
                                                      │
                                       Argo CD aplica no cluster
                                                      ▼
                          Controller (chave PRIVADA) ──► Secret real
  1. Você cria o Secret normalmente (sem commitar).
  2. O kubeseal cifra com a chave pública do cluster, gerando um SealedSecret.
  3. O SealedSecret (seguro) vai para o Git.
  4. O Argo CD aplica o SealedSecret no cluster.
  5. O controller decifra com a chave privada e cria o Secret.

Pontos importantes​

  • O SealedSecret fica atrelado ao nome e ao namespace do Secret (escopo estrito, o padrão): não dá para reaproveitá-lo em outro lugar.
  • O valor cifrado é por cluster: ele só decifra no cluster que o gerou.
  • A chave privada do controller é o ponto crítico: faça backup dela. Sem ela, os SealedSecret do Git não podem ser decifrados ao recriar o cluster.
VantagensDesvantagens
Simples, sem infraestrutura externaRotação de chaves exige cuidado
Funciona bem com Argo CDBackup da chave privada é obrigatório
Os segredos ficam no Git, auditáveisSegredo preso ao cluster

External Secrets Operator (ESO)​

O ESO sincroniza segredos de um cofre externo para Secrets do Kubernetes. No Git ficam apenas as referências (o ExternalSecret), nunca o valor.

[Cofre: Vault / AWS / GCP / Azure / ...] ◄── [External Secrets Operator] ──► [Secret do Kubernetes]
                                                       ▲
                                    [ExternalSecret no Git: só a referência]

Dois recursos principais:

RecursoO que define
SecretStore / ClusterSecretStoreOnde buscar (qual cofre e como autenticar)
ExternalSecretO que buscar, e qual Secret criar no cluster

O ESO renova o Secret periodicamente (refreshInterval), o que facilita a rotação.

VantagensDesvantagens
Segredos centralizadosExige um cofre externo
Rotação automáticaMais peças para operar
Muitos backends suportadosDependência de um serviço externo
Versão da API

O apiVersion dos recursos do ESO muda entre versões. Use sempre o da versão que você instalou (kubectl explain externalsecret mostra o que o cluster suporta).

SOPS​

O SOPS cifra arquivos (YAML, JSON) usando age, GPG ou KMS de nuvem. Ele cifra só os valores, e as chaves continuam legíveis, o que facilita o diff no Git.

  • Funciona bem para quem já usa KMS de uma nuvem ou age.
  • No Argo CD, a integração é feita por plugin (CMP em sidecar) ou pelo KSOPS. Por ser abordagem de plugin, tem o ponto de atenção do cache descrito acima.
  • A configuração antiga por configManagementPlugins no argocd-cm foi removida das versões recentes: use o modelo de sidecar.

HashiCorp Vault​

O Vault é uma solução completa de segredos: armazenamento, segredos dinâmicos (credenciais geradas sob demanda), rotação, auditoria e controle de acesso granular.

Dá para usá-lo de duas formas no Kubernetes:

  • Via ESO, que lê do Vault e cria Secrets (recomendado com Argo CD).
  • Via Vault Agent Injector, que injeta os segredos nos Pods por sidecar.

Tem alta capacidade, mas é complexo de operar e pede infraestrutura dedicada.

E o Argo CD Vault Plugin (AVP)?

O AVP é um projeto do argoproj-labs (não faz parte do núcleo do Argo CD). É um plugin de manifesto, então vale a ressalva do cache. Hoje, usar o ESO com o Vault costuma ser preferido.

Comparação​

CritérioSealed SecretsESOSOPSVault
ComplexidadeBaixaMédiaMédiaAlta

Segredo fica no GitSim, cifradoNão (só referência)Sim, cifradoNão
Rotação automáticaManualSimManualSim

Qual escolher​

CenárioRecomendação
Homelab / time pequeno, sem cofreSealed Secrets: simples e sem dependência externa
Já existe um cofre (Vault, AWS, GCP...)External Secrets Operator
Enterprise, segredos dinâmicos e auditoriaVault (preferencialmente com o ESO)
Já usa KMS ou age para arquivosSOPS (com atenção ao cache do plugin)

Neste material, no cluster de laboratório, usamos o Sealed Secrets.

Segredos do próprio Argo CD​

O Argo CD também tem segredos que precisam de proteção:

SegredoOnde fica
Credenciais de repositórios privadosSecrets no namespace argocd
Token do Slack (notificações)argocd-notifications-secret
Credenciais de clusters externosSecrets no namespace argocd
Segredo do SSO (client secret)argocd-secret ou Secret referenciado

Se esses Secrets forem para o Git (o ideal em GitOps), protegê-los com a mesma solução que você escolheu (por exemplo, SealedSecret).

Boas práticas​

  1. Nunca commite segredos em texto puro ou base64.
  2. Menor escopo: cada aplicação com os seus Secrets, sem compartilhar.
  3. Rotacione credenciais regularmente, e tenha o processo documentado.
  4. Faça backup da infraestrutura de segredos (a chave privada do Sealed Secrets, o storage do Vault).
  5. Teste a recuperação: simule perder o cluster e recriá-lo a partir do Git.
  6. RBAC mínimo: restrinja quem pode ler Secrets no cluster.
  7. Auditoria: acompanhe acessos aos segredos e a mudanças.
  8. Se vazou, troque: um segredo que já foi para o Git deve ser considerado comprometido.

Resumo​

  • Base64 não é criptografia. Nunca commite Secret em texto puro ou base64.
  • Duas famílias: operador no cluster (Sealed Secrets, ESO), recomendada pelo Argo CD, e plugin de manifesto (SOPS, AVP), com o valor passando pelo cache.
  • Sealed Secrets: cifra com chave pública, só o cluster decifra. Faça backup da chave privada.
  • ESO: o Git guarda só a referência; o valor vem de um cofre externo.
  • No lab usamos Sealed Secrets (sem cofre externo).
  • Segredos que vazaram para o Git: troque a credencial.
  • Os segredos do próprio Argo CD (repositórios, Slack, SSO) também precisam de proteção.
