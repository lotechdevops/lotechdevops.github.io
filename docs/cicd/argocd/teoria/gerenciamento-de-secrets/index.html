Gerenciamento de Secrets

O Problema​

No GitOps, tudo deve estar versionado no Git. Mas e as senhas, tokens e certificados?

NUNCA faça isso:

apiVersion: v1
kind: Secret
metadata:
  name: database
data:
  password: c3VwZXJzZWNyZXQ=  # base64 não é criptografia!

Commitar secrets em plain text (ou base64) no Git é uma falha grave de segurança:

  • Qualquer pessoa com acesso ao repo vê os secrets
  • Histórico do Git mantém secrets antigos para sempre
  • Logs de CI/CD podem expor secrets
  • Dificulta rotação de credenciais

Soluções Principais​

Existem várias abordagens para gerenciar secrets no GitOps:

| Solução                      | Complexidade | Descrição                                    |
| ---------------------------- | ------------ | -------------------------------------------- |
| Sealed Secrets               | Baixa        | Criptografia assimétrica no Git              |
| External Secrets Operator    | Média        | Sincroniza de vaults externos                |
| SOPS                         | Média        | Criptografia de arquivos YAML                |
| HashiCorp Vault              | Alta         | Vault enterprise-grade                       |
| ArgoCD Vault Plugin (AVP)    | Média        | Plugin oficial do ArgoCD para Vault          |

Sealed Secrets​

Sealed Secrets permite criptografar secrets antes de commitar no Git.

Como funciona​

  1. Você cria um secret normal
  2. O kubeseal criptografa usando uma chave pública
  3. Você commita o SealedSecret no Git
  4. O Sealed Secrets Controller descriptografa no cluster usando a chave privada

Instalação​

# Instalar o controller no cluster
kubectl apply -f https://github.com/bitnami-labs/sealed-secrets/releases/download/v0.24.0/controller.yaml

# Instalar CLI
brew install kubeseal

Uso básico​

# Criar secret normal
kubectl create secret generic mysecret \
  --from-literal=password=supersecret \
  --dry-run=client -o yaml > mysecret.yaml

# Criptografar
kubeseal -f mysecret.yaml -w mysealedsecret.yaml

# Commitar no Git
git add mysealedsecret.yaml
git commit -m "Add encrypted secret"

SealedSecret no Git​

apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: mysecret
  namespace: default
spec:
  encryptedData:
    password: AgBqX2UwM3R... # Seguro para commitar

Vantagens​

  • Simples de implementar
  • Secrets ficam no Git (auditável)
  • Funciona nativamente com ArgoCD

Desvantagens​

  • Rotação de chaves é complexa
  • Backup de chave privada é crítico
  • Secrets ficam acoplados ao cluster específico

External Secrets Operator (ESO)​

ESO sincroniza secrets de sistemas externos para o Kubernetes.

Arquitetura​

[Vault/AWS/GCP] ←→ [External Secrets Operator] → [Kubernetes Secret]
                         ↑
                    [ExternalSecret CRD no Git]

Backends suportados​

  • AWS Secrets Manager
  • AWS Parameter Store
  • Azure Key Vault
  • Google Secret Manager
  • HashiCorp Vault
  • 1Password
  • Doppler
  • E muitos outros

Instalação​

helm repo add external-secrets https://charts.external-secrets.io
helm install external-secrets external-secrets/external-secrets -n external-secrets-system --create-namespace

Configuração​

1. Criar SecretStore (aponta para o backend):

apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: vault-backend
  namespace: default
spec:
  provider:
    vault:
      server: "https://vault.example.com"
      path: "secret"
      version: "v2"
      auth:
        kubernetes:
          mountPath: "kubernetes"
          role: "myapp"

2. Criar ExternalSecret (define qual secret buscar):

apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: database-credentials
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: SecretStore
  target:
    name: database-secret  # Nome do Secret que será criado
    creationPolicy: Owner
  data:
  - secretKey: password
    remoteRef:
      key: database/prod
      property: password

3. ESO cria o Secret automaticamente:

# Criado automaticamente pelo ESO
apiVersion: v1
kind: Secret
metadata:
  name: database-secret
data:
  password: <valor do Vault>

Vantagens​

  • Secrets centralizados
  • Rotação automática
  • Suporte a múltiplos backends
  • Auditoria no vault externo

Desvantagens​

  • Requer infraestrutura adicional (Vault, AWS, etc)
  • Mais complexo de configurar
  • Dependência de serviço externo

SOPS (Secrets Operations)​

SOPS criptografa arquivos YAML inteiros usando KMS (AWS, GCP, Azure) ou GPG.

Como funciona​

  1. Vocẽ define um arquivo YAML com secrets
  2. SOPS criptografa apenas os valores (não as chaves)
  3. Você commita o arquivo criptografado no Git
  4. No cluster, SOPS descriptografa antes de aplicar

Instalação​

# Instalar SOPS
brew install sops

# Configurar KMS (exemplo AWS)
export SOPS_KMS_ARN="arn:aws:kms:us-east-1:123456789:key/abc-123"

Uso​

Arquivo original:

apiVersion: v1
kind: Secret
metadata:
  name: mysecret
stringData:
  password: supersecret
  api_key: abc123xyz

Criptografar:

sops --encrypt --kms $SOPS_KMS_ARN secret.yaml > secret.enc.yaml

Arquivo criptografado:

apiVersion: v1
kind: Secret
metadata:
  name: mysecret
stringData:
  password: ENC[AES256_GCM,data:xK8...,tag:Q==]
  api_key: ENC[AES256_GCM,data:mN2...,tag:P==]
sops:
  kms:
  - arn: arn:aws:kms:...

Descriptografar:

sops --decrypt secret.enc.yaml | kubectl apply -f -

Integração com ArgoCD​

Use o ArgoCD SOPS Plugin:

# argocd-cm ConfigMap
configManagementPlugins: |
  - name: sops
    generate:
      command: ["sh", "-c"]
      args: ["sops -d *.yaml"]

Vantagens​

  • Criptografia robusta (KMS)
  • Formato legível (vê as chaves, não os valores)
  • Integra com ArgoCD

Desvantagens​

  • Requer KMS (AWS/GCP/Azure)
  • Toda mudança requer encrypt/decrypt
  • Configuração manual no ArgoCD

HashiCorp Vault​

Vault é uma solução enterprise-grafe para gerenciamento de secrets.

Funcionalidades​

  • Armazenamento seguro de secrets
  • Dynamic secrets (gera credenciais sob demanda)
  • Rotação automática
  • Auditoria completa
  • Controle de acesso granular
  • Encryption as a Service

Arquitetura com Kubernetes​

[Application] → [Vault Agent Sidecar] → [Vault Server]
                        ↓
                [Inject secrets em arquivos]

Vault Agent Injector​

1. Instalar Vault:

helm repo add hashicorp https://helm.releases.hashicorp.com
helm install vault hashicorp/vault

2. Configurar Kubernetes auth:

vault auth enable kubernetes
vault write auth/kubernetes/config \
  kubernetes_host="https://kubernetes.default.svc"

3. Criar policy:

vault policy write myapp - <<EOF
path "secret/data/myapp/*" {
  capabilities = ["read"]
}
EOF

**4. Criar role:**

```bash
vault write auth/kubernetes/role/myapp \
  bound_service_account_names=myapp \
  bound_service_account_namespaces=default \
  policies=myapp \
  ttl=24h
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    metadata:
      annotations:
        vault.hashicorp.com/agent-inject: "true"
        vault.hashicorp.com/role: "myapp"
        vault.hashicorp.com/agent-inject-secret-db: "secret/data/myapp/db"
        vault.hashicorp.com/agent-inject-template-db: |
          {{- with secret "secret/data/myapp/db" -}}
          export DB_PASSWORD="{{ .Data.data.password }}"
          {{- end }}
    spec:
      serviceAccountName: myapp
      containers:
      - name: app
        image: myapp:latest

O Vault Agent injeta os secrets em /vault/secrets/db.

Vantagens​

  • Enterprise-grade
  • Dynamic secrets
  • Auditoria completa
  • Rotação automática

Desvantagens​

  • Complexo de configurar e operar
  • Requer infraestrutura dedicada
  • Custo (versão Enterprise)

ArgoCD Vault Plugin (AVP)​

AVP é um plugin oficial do ArgoCD para integração com Vault.

Como funciona​

  1. ArgoCD processa manifestos com placeholders
  2. AVP substitui placeholders por valores do Vault
  3. ArgoCD aplica os manifestos com valores reais

Instalação​

Adicione o plugin ao argocd-repo-server:

apiVersion: v1
kind: ConfigMap
metadata:
  name: cmp-plugin
data:
  avp.yaml: |
    apiVersion: argoproj.io/v1alpha1
    kind: ConfigManagementPlugin
    metadata:
      name: argocd-vault-plugin
    spec:
      generate:
        command: ["argocd-vault-plugin"]
        args: ["generate", "./"]

Uso​

Manifesto com placeholders:

apiVersion: v1
kind: Secret
metadata:
  name: database
stringData:
  password: <path:secret/data/database#password>
  username: <path:secret/data/database#username>

ArgoCD Application:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: myapp
spec:
  source:
    plugin:
      name: argocd-vault-plugin

AVP substitui <path:...> pelos valores reais do Vault.

Vantagens​

  • Integração nativa com ArgoCD
  • Syntax simples
  • Suporta múltiplos backends

Desvantagens​

  • Requer configuração do plugin
  • Placeholders não são YAML válido

Recomendações​

Para Startups/Times Pequenos​

Sealed Secrets

  • Simples , sem infraestrutura adicional
  • Suficiente para a maioria dos casos

Para Empresas em Crescimento​

External Secrets Operator

  • Escalável, múltiplos backends
  • Boa relação custo/benefício

Para Empresas Enterprise​

HashiCorp Vault + AVP

  • Dynamic Secrets
  • Compliance e auditoria robusta
  • Rotação automática

Para Multi-cloud​

SOPS com KMS do cloud provider

  • Aproveita KMS nativo (AWS/GCP/Azure)
  • Portável entre clouds

Boas práticas​

  1. Nunca commite secrets em plain text

    • Use qualquer uma das soluções acima

  2. Minimize o escopo dos secrets

    • Cada app deve ter seus próprios secrets
    • Não compartilhe secrets entre apps

  3. Rotacione regularmente

    • Configure rotação automática quando possível
    • Tenha processo manual documentado

  4. Auditoria

    • Monitore acessos a secrets
    • Alertas para acessos anormais

  5. Backup da infraestrutura de secrets

    • Sealed Secrets: backup da chave privada
    • Vault: backup do storage backend

  6. Teste o disaster recovery

    • Simule perda dos secrets
    • Documente processo de recuperação

  7. Use namespaces para isolamento

    • Secrets em um namespace não devem vazar para outros

  8. Least privilege

    • ServiceAccounts só devem acessar os secrets necessários

Conclusão​

Gerenciamento de secrets é crítico no GitOps.

Escolha a solução adequada ao seu contexto:

  • Simples? -> Sealed Secrets
  • Escalável? -> External Secrets Operator
  • Enterprise? -> Vault + AVP

O importante é NUNCA commitar secrets em plain text no Git.
