CI/CD

O que é CI/CD​

CI/CD é um conjunto de práticas que automatiza o caminho de uma mudança de código até a produção: do git push até a aplicação rodando para o usuário.

Sem automação, cada entrega depende de passos manuais (compilar, testar, copiar arquivos, reiniciar serviços). Isso é lento, repetitivo e sujeito a erro humano. Com CI/CD, o mesmo caminho acontece sempre do mesmo jeito, a cada mudança, sem depender de quem está de plantão.

A ideia central: entregar mudanças pequenas, com frequência e com segurança. Mudanças pequenas são mais fáceis de testar, de revisar e de desfazer.

CI, Entrega Contínua e Implantação Contínua​

A sigla junta três práticas diferentes:

PráticaSiglaO que automatizaQuem aprova a ida para produção
Integração ContínuaCICompilar, testar e validar cada mudança assim que ela entra no repositório—
Entrega ContínuaCDDeixar o artefato sempre pronto para produção (testado, empacotado e implantado em ambientes de teste)Uma pessoa, com um clique
Implantação ContínuaCDLevar a mudança até a produção sozinha, se passar em todas as verificaçõesNinguém: é automático

A diferença entre as duas últimas é só a aprovação final. A Entrega Contínua mantém uma decisão humana antes da produção, e a Implantação Contínua remove essa decisão e confia nos testes automatizados.

Onde começar

A maioria das equipes começa por CI (testes automáticos a cada commit) e Entrega Contínua (com aprovação manual). A Implantação Contínua exige uma suíte de testes e um monitoramento maduros, pois não há um humano para barrar um problema.

O fluxo, de ponta a ponta​

 Código         Integração (CI)                Entrega (CD)
┌───────┐   ┌───────────────────────┐   ┌────────────────────────────┐
│ commit│──►│ build → testes → scan │──►│ artefato → homologação → produção │
└───────┘   └───────────────────────┘   └────────────────────────────┘
    ▲                  │ falhou?                      │ falhou?
    └──────────────────┴── feedback rápido ◄─────────┘

Duas regras valem para todo o fluxo:

  • Feedback rápido: se algo quebrar, quem fez a mudança precisa saber em minutos, não em dias.
  • Falhou, parou: uma etapa que falha interrompe o pipeline. Nada quebrado avança para a próxima fase.

As etapas de um pipeline​

Cada projeto monta o seu pipeline, mas as etapas costumam ser estas:

EtapaObjetivoExemplos do que roda
CheckoutBaixar o código da mudançagit clone, git checkout
BuildCompilar ou empacotar a aplicaçãonpm ci && npm run build, docker build
TestesGarantir que nada quebroutestes unitários, de integração, lint
Análise de qualidade e segurançaAchar problemas antes da produçãoanálise estática (SAST), varredura de dependências e de imagens
Publicação do artefatoGuardar o resultado do build em um repositórioenviar a imagem para um registry
Implantação em homologaçãoTestar em um ambiente parecido com produçãoaplicar manifestos, rodar testes de ponta a ponta
AprovaçãoDecisão humana (só na Entrega Contínua)clique de aprovação
Implantação em produçãoColocar a mudança no aratualizar a versão da aplicação
Verificação pós-deployConfirmar que está saudávelhealth checks, métricas, alertas
Pipeline como código

O pipeline é descrito em um arquivo versionado junto com o código (geralmente YAML). Assim ele passa por revisão, tem histórico e pode ser reproduzido. Evite configurar pipelines apenas por cliques em uma interface: ninguém sabe o que mudou nem como recriar.

Artefatos e versionamento​

O artefato é o resultado do build: um pacote, um binário ou, no caso de containers, uma imagem. Ele é o que realmente vai para produção.

Três regras evitam dor de cabeça:

  • Construa uma vez, implante em vários ambientes. O mesmo artefato que passou nos testes é o que vai para produção. Reconstruir a cada ambiente cria diferenças que ninguém testou.
  • Artefatos são imutáveis. Uma versão publicada nunca é alterada.
  • Versione de forma rastreável. Use o hash do commit ou uma versão semântica (1.4.2) como tag. Evite latest: você não sabe qual código ela contém, e um rollback vira adivinhação.
Ruim:   minha-app:latest
Bom:    minha-app:1.4.2
Bom:    minha-app:a3f9c21   (hash curto do commit)

Estratégias de entrega​

Como a nova versão chega aos usuários muda o risco da entrega:

EstratégiaComo funcionaVantagemCuidado
Rolling updateTroca as instâncias aos poucosSimples, sem paradaDuas versões convivem por um tempo
Blue/GreenSobe a versão nova ao lado da antiga e troca o tráfego de uma vezRollback instantâneo (volta o tráfego)Dobra a infraestrutura durante a troca
CanaryEnvia uma pequena parte do tráfego para a nova versão e amplia aos poucosLimita o estrago de um problemaExige métricas boas para decidir
RecreateDerruba a versão antiga e sobe a novaSimplesHá indisponibilidade

Vale combinar com feature flags: o código novo vai para produção desligado e é ativado depois, separando o deploy (colocar o código no ar) do release (liberar a funcionalidade aos usuários).

Push × Pull: duas formas de implantar​

Existem dois modelos para levar a mudança ao ambiente:

ModeloComo funcionaObservação
PushO pipeline empurra a mudança para o ambiente, com credenciais de acesso ao destinoSimples, mas o pipeline precisa de acesso privilegiado à produção
Pull (GitOps)Um agente dentro do ambiente observa o repositório e puxa o estado desejadoO ambiente não expõe credenciais para fora, e o repositório vira a fonte da verdade

No GitOps, o repositório Git descreve como o ambiente deve estar, e um agente reconcilia o ambiente real com esse estado. Uma mudança é um commit; um rollback é um revert. Isso dá auditoria e histórico de graça.

Segurança no pipeline (DevSecOps)​

O pipeline tem acesso a código, segredos e produção, então ele próprio é um alvo. Segurança precisa estar dentro dele, e não depois:

  • Segredos fora do código. Nunca coloque senhas ou tokens no repositório. Use o cofre de segredos da ferramenta de CI ou um gerenciador externo.
  • Privilégio mínimo. Cada etapa recebe só as permissões de que precisa, e credenciais de curta duração são melhores que chaves permanentes.
  • Varredura de dependências e imagens. Verifique vulnerabilidades conhecidas antes de publicar.
  • Análise estática do código (SAST) para pegar falhas comuns ainda no commit.
  • Cadeia de suprimentos. Fixe versões de dependências e imagens, gere um inventário de componentes (SBOM) e, em ambientes maduros, assine os artefatos.
  • Proteja a branch principal. Exija revisão e que o pipeline passe antes do merge.
Cuidado com segredos em logs

Pipelines imprimem muita coisa. Um echo ou um env descuidado pode jogar uma senha no log, e logs de CI costumam ser visíveis para muita gente. Marque segredos como mascarados e evite imprimir variáveis de ambiente.

Como medir: as métricas DORA​

Como saber se o seu processo de entrega é bom? As quatro métricas DORA são o padrão da indústria:

MétricaO que medeQuanto melhor
Frequência de implantaçãoCom que frequência você entrega em produçãoMais frequente
Tempo de entrega (lead time)Do commit até estar em produçãoMenor
Taxa de falha de mudançasQuantas entregas causam problema em produçãoMenor
Tempo de recuperaçãoQuanto demora para restaurar o serviço após uma falhaMenor

Repare que velocidade e estabilidade andam juntas: equipes que entregam mais vezes, em mudanças menores, tendem a falhar menos e se recuperar mais rápido.

Boas práticas​

  • Commits pequenos e frequentes. Integre ao menos uma vez ao dia, para evitar conflitos gigantes.
  • Pipeline rápido. Se demora mais de ~10 minutos, as pessoas deixam de esperar o resultado. Paralelize testes e use cache.
  • Mantenha a branch principal sempre implantável.
  • Teste na proporção certa: muitos testes unitários (rápidos), alguns de integração e poucos de ponta a ponta (lentos).
  • Ambientes parecidos com produção para os testes, para evitar o "na minha máquina funciona".
  • Tenha um plano de rollback testado, e não só escrito.
  • Observabilidade: sem métricas e logs, você implanta no escuro e não sabe se a entrega deu certo.
  • Trate o pipeline como código de produção: revisão, versionamento e testes também valem para ele.

Panorama de ferramentas​

As ferramentas mudam, mas os conceitos acima valem para todas. Um mapa por categoria:

CategoriaFunçãoExemplos
Servidor de CI / pipelineExecutar build, testes e etapas do pipelineJenkins, GitHub Actions, GitLab CI, CircleCI
Registry de artefatosGuardar imagens e pacotesDocker Hub, GitHub Container Registry, Harbor
Entrega / GitOpsImplantar e reconciliar o ambiente a partir do GitArgo CD, Flux
SegurançaVarrer código, dependências e imagensTrivy, SonarQube, Snyk
Gestão de segredosGuardar e entregar credenciais com segurançaHashiCorp Vault, External Secrets, cofres das plataformas
ObservabilidadeMedir e alertar depois do deployPrometheus, Grafana, Loki

Escolher ferramenta vem depois de entender o fluxo. Uma boa prática com a ferramenta errada ainda funciona, mas ferramenta boa sem prática só automatiza o caos.

Resumo​

  • CI = integrar e testar cada mudança, automaticamente.
  • Entrega Contínua = sempre pronto para produção, com aprovação humana. Implantação Contínua = vai para produção sem aprovação.
  • Pipeline falhou, parou. O feedback precisa ser rápido.
  • Construa uma vez, implante em vários ambientes. Artefato imutável e versionado (nunca latest).
  • Pipeline como código, versionado junto com a aplicação.
  • Estratégias: rolling, blue/green, canary, recreate. Feature flags separam deploy de release.
  • Push (pipeline empurra) × Pull/GitOps (agente no ambiente puxa do Git).
  • Segurança dentro do pipeline: segredos fora do código, privilégio mínimo, varredura de dependências e imagens.
  • DORA: frequência de implantação, tempo de entrega, taxa de falha e tempo de recuperação.
