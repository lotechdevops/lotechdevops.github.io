Protocolos e Portas no Kubernetes

Por que entender as portas do Kubernetes?​

O Kubernetes é um sistema distribuído. Isso significa que diversos componentes precisam se comunicar entre si por meio de protocolos e portas específicas.

Saber quais portas precisam estar abertas é essencial para:

  • Configurar corretamente firewalls e grupos de segurança em nuvem.
  • Permitir a comunicação entre Control Plane e Workers.
  • Garantir acesso seguro de usuários externos ao cluster (kubectl, dashboards, ingress).
  • Fazer troubleshooting em problemas de rede e conectividade.

Em ambientes corportativos, onde firewalls e ACLs (Access Control List) são rigorosos, conhecer essas portas é fundamental para o funcionamento saudável do cluster.

Portas do Control Plane​

O Control Plane é responsável por orquestrar todo o cluster.

A comunicação com ele ocorre principalmente através do API Server, mas outros componentes também expõem portas de uso interno.

| Componente                | Porta       | Protocolo | Função |
|----------------------------|-------------|-----------|--------|
| **kube-apiserver**         | 6443        | TCP       | Endpoint principal da API Kubernetes. Todos os comandos `kubectl` e comunicações externas passam por aqui. |
| **etcd**                   | 2379–2380   | TCP       | Armazena o estado do cluster. Usado para comunicação cliente e replicação entre nós etcd. |
| **kube-scheduler**         | 10251       | TCP       | Porta usada para métricas e diagnósticos do scheduler. |
| **kube-controller-manager**| 10252       | TCP       | Porta usada para métricas e diagnósticos dos controladores. |

Portas dos Workers (Nós)​

Os workers são responsáveis por rodar os contêineres (via Pods). Eles precisam se comunicar com o Control Plane e também com outros nós.

| Componente      | Porta         | Protocolo | Função |
|-----------------|---------------|-----------|--------|
| **Kubelet**     | 10250         | TCP       | Comunicação entre o Control Plane e os nós (execução e monitoramento de Pods). |
| **kube-proxy**  | Dinâmico      | TCP/UDP   | Mantém as regras de rede e garante que os serviços funcionem corretamente. |
| **NodePort**    | 30000–32767   | TCP/UDP   | Faixa usada para expor serviços para fora do cluster sem precisar de load balancer. |

Resumo​

  • O API Server (6443/TCP) é a porta crítica, sem ele, não há comunicação com o cluster.
  • O etcd (2379-2380/TCP) armazena o estado do cluster e deve estar sempre acessível e seguro.
  • O kubelet (10250/TCP) garante a comunicação do Control Plane com os nós.
  • Serviços expostos via NodePort usam a faixa 3000-32767.
  • Aplicações acessadas externamente normalmente utilizam um Ingress (80/443).
