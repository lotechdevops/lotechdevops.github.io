Probes no Kubernetes: liveness, readiness e startup

O que são as Probes?​

As Probes no Kubernetes são mecanismos de verificação de saúde dos containers. Elas permitem que o Kubernetes entenda se um container está funcionando corretamente, se está pronto para receber tráfego e até se conseguiu iniciar de forma adequada.

Existem três tipos principais de probes:

  • LivenessProbe
  • ReadinessProbe
  • StartupProbe

LivenessProbe​

A LivenessProbe é a probe de verificação de integridade. Ela verifica se o processo dentro do Pod continua em execução de forma saudável. Caso o teste falhe, o Kubernetes reinicia o container.

Exemplo de Configuração no Manifesto:

livenessProbe:
    tcpSocket:
        port: 80 
    initialDelaySeconds: 10 
    periodSeconds: 10
    timeoutSeconds: 5 
    failureThreshold: 3

Explicação dos campos:

  • tcpSocket: -> Método de verificação baseado em conexão TCP.
  • port: -> Porta TCP usada na verificação.
  • initialDelaySeconds: -> Quantos segundos esperar antes da primeira verificação.
  • periodSeconds: -> Intervalo em segundos entre cada verificação.
  • timeoutSeconds: -> Tempo máximo de espera por uma resposta antes de considerar a verificação como falha.
  • failureThreshold: -> Número de falhas consecutivas antes de reiniciar o container.

ReadinessProbe​

A ReadinessProbe é responsável por verificar se o container está pronto para receber tráfego. Enquanto a probe não tiver sucesso, o Pod não será incluído nos endpoints dos Services, garantindo que ele não receba requisições externas antes da hora.

Isso é especialmente útil quando a aplicação demora para inicializar ou depende de outros serviços antes de estar pronto para atender tráfego.

Exemplo de Configuração no Manifesto:

readinessProbe:
  httpGet:
    path: /
    port: 80
  initialDelaySeconds: 10
  periodSeconds: 10
  timeoutSeconds: 5
  successThreshold: 2
  failureThreshold: 3

Explicação dos campos:

  • httpGet: -> Método de verificação baseado em requisições HTTP.
  • path: -> Caminho da aplicação que será testado.
  • port: -> Porta onde a aplicação responde às requisições HTTP.
  • initalDelaySeconds: -> Quantos segundos esperar antes de executar a primeira verificação.
  • periodSeconds: -> Intervalo em segundos entre cada verificação.
  • timeoutSeconds: -> Tempo máximo de espera por resposta antes de considerar a verificação como falha.
  • successThreshold: -> Número mínimo de verificações bem-sucedidas antes de considerar o container pronto.
  • failureThreshold: -> Número de falhas consecutivas antes de considerar o container não pronto.

StartupProbe​

A StartupProbe é usada para verificar se o container foi inicializado corretamente. Ela é ideal para aplicações que demoram a subir, evitando que falhem em verificações de liveness ou readiness enquanto ainda estão inicializando.

Enquanto a StartupProbe não tiver sucesso, o Kubernetes não executa as verificações de liveness e readiness, garantindo que a aplicação tenha tempo suficiente para ficar pronta antes de começar a ser monitorada.

Exemplo de Configuração no Manifesto:

startupProbe:
  httpGet:
    path: /
    port: 80
  initialDelaySeconds: 10
  periodSeconds: 10
  timeoutSeconds: 5
  successThreshold: 1
  failureThreshold: 30

Explicação dos campos:

  • httpGet: -> Método de verificação baseado em requisições HTTP.
  • path: -> Caminho da aplicação que será testado.
  • port: -> Porta onde a aplicação responde às requisições HTTP.
  • initialDelaySeconds: -> Quantos segundos esperar antes de executar a primeira verificação.
  • periodSeconds: -> Intervalo em segundos entre cada verificação.
  • timeoutSeconds: -> Tempo máximo de espera por resposta antes de considerar a verificação como falha.
  • successThreshold: -> Númermo mínimo de verificações bem-sucedidas para considerar a inicialização concluída.
  • failureThresolhd: -> Número de falhas consecutivas antes de considerar que o container não conseguiu inicializar. Geralmente se usa um valor alto, para dar bastante tempo à aplicação antes de falhar.
