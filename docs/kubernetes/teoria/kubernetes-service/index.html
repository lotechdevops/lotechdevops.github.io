Services no Kubernetes: expondo aplicações

O que é um Service?​

Um Service (Serviço) no Kubernetes é uma abstração de rede que define um conjunto lógico de Pods e uma política de acesso a eles.

Ele permite que um ou mais Pods sejam acessados de forma estável e consistente, mesmo que os Pods sejam reiniciados, escalados ou realocados para outros nós no cluster.

Os Services são definidos por meio da API do Kubernetes, geralmente utilizando um manifesto YAML.

Sem um Service, os Pods só podem ser acessados diretamente por seus IPs, que são efêmeros e mudam a cada recriação. O Service resolve esse problema oferecendo um ponto e acesso fixo.

Existem quatro tipos principais de Services no Kubernetes:

1. ClusterIP Service 2. NodePort Service 3. LoadBalancer Service 4. ExternalName Service

Como os Services funcionam​

IPs efêmeros e o problema​

No Kubernetes, cada Pod possui um IP próprio, porém:

  • Esse IP muda sempre que o Pod é recriado.
  • Aplicações que dependem de comunicar com esse Pod diretamente quebram quando ele morre e renasce com outro IP.

É ai que entra o Service

O papel do Service​

Um Service atua como uma ponte estável entre os consumidores (ex: outros Pods, usuários externos) e um conjunto de Pods dinâmicos selecionados por labels.

Ele fornece:

  • Um IP virtual fixo (ClusterIP).
  • Um DNS interno (service-name>.<namespace>.svc.cluster.local)
  • E realiza o load balancing automático entre os Pods associados.

Seleção do Service​

Todo Service usa label selectors para descobrir quais Pods ele deve representar.

selector:
  app: backend

Esse seletor faz com que o Service descubra todos os Pods com app=backend e redireciona o tráfego para eles, de forma transparente.

Rotemaneto via kube-proxy​

O Kubernetes usa um componente chamado kube-proxy para configurar regras de roteamento no nível de rede dos nós do cluster:

  • Ele intercepta o tráfego enviado para o IP do service.
  • E redireciona esse tráfego para um dos Pods do conjunto (de forma balanceada).

Internamente, pode usar iptables ou IPVS para isso, dependendo da configuração do cluster.

Funcionamento resumido​

  1. Você define um Service com um seletor de labels
  2. O Kubernetes identifica os Pods correspondentes
  3. O Service recebe um IP virtual fixo e um nome DNS interno
  4. O kube-proxy roteia o tráfego recebido para os Pods corretos
  5. Quando um POd morre ou nasce, o Service se atualiza automaticamente
  6. O consumidor (outro Pod, usuário externo, etc) continua se comunicando normalmente com o Service, sem se preocupar com a instabilidade dos IPs dos Pods.

Tipos de Services​

1. ClusterIP​

O tipo ClusterIP é a opção padrão ao se criar um Service no Kubernetes. Ele é utilizado para expor um conjunto de Pods internamente dentro do cluster, permitindo que outros componentes, como outros Pods ou serviços, se comuniquem com eles de forma estável e confiável. Cada vez que um Service do tipo ClusterIP é criado, o Kubernetes atribui a ele um endereço IP virtual interno que funciona como ponto fixo de entrada para acessar os Pods associados. Esse IP não é acessível de fora do cluster, sendo restrito à comunicação interna entre os recursos do Kubernetes.

O Service atua como uma espécie de "balancer interno". Por emio de seletores de rótulo (labels), ele identifica os Pods-alvo e automaticamente realiza o balanceamento de carga entre eles, distribuindo o tráfego de maneira uniforme. Mesmo que os Pods sejam reiniciados, substituídos ou movidos para outros Nós, O IP virtual do Service continua o mesmo, garantindo estabilidade na comunicação

Esse comportamento é especialmente útil em arquiteturas de microserviços, onde os componentes precisam se comunicar constantemente. Em vez de cada serviço tentar descobrir o IP dinâmico dos Pods, ele apenas se comunica com o ClusterIP fixo, enquanto o Kubernetes garante o tráfego chegue aos Pods corretos.

O tipo ClusterIP é amplamente utilizado para expor APIs privadas, serviços internos, camadas de backend e outros elementos que não precisam (ou não devem) ser acessados de fora do cluster.

Exemplo de manifesto YAML com ClusterIP Service​

apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: my-app
  ports:
  - port: 80
    protocol: TCP
    targetPort: 8080
  type: ClusterIP

2. NodePort​

O tipo NodePort é uma das formas de expor um serviço Kubernetes para fora do cluster, permitindo que ele seja acessado externamente por meio de uma porta específica em todos os nós do cluster.

Por padrão, o serviços do Kubernetes são acessíveis apenas internamente, através do tipo ClusterIP. No entanto, em muitos cenários, como testes, desenvolvimento ou ambientes sem balanceador de carga, é necessário disponibilizar um serviço para acesso externo. É ai que entra o tipo NodePort.

Quando você cria um Service do tipo NodePort, o Kubernetes reserva uma porta entre 3000 e 32767 em cada nó do cluster. Qualquer requisição enviada ao IP externo de um desses nós, utilizando essa porta, será encaminhada para o Service, que por sua vez redireciona para os Pods corretos através do balanceamento interno.

Por exemplo, ao definir um nodePort: 3000, qualquer requisição feita para http://<ip-do-nó>:3000 será encaminhada ao Service, que direcionará o tráfego para os Pods do seu app. Internamente, o Service pode estar exposto em outra porta (port: 8000) e repassando para a porta real em que o container escuta (targetPort: 80).

Exemplo de manifesto YAML com NodePort Service​

apiVersion: v1
kind: Service
metadata:
  name: my-nodeport-service
spec:
  type: NodePort
  selector:
    app: your-app-label
  ports:
    - protocol: TCP
      port: 8080         # Porta exposta no serviço internamente
      targetPort: 80     # Porta onde o container escuta
      nodePort: 30000    # Porta externa exposta em todos os nós do cluster

É importante ressaltar que, embora o NodePort seja simples de configurar, ele possui limitações importantes para ambientes de produção. Ele não fornece recursos como balanceamento de carga entre nós, escalabilidade elástica ou gerenciamento de SSL/TLS, sendo mais indicado para ambientes de desenvolvimento, testes ou soluções caseiras. Para soluções mais robustas e seguras, é recomendado o uso de LoadBalancer ou Ingress Controller, dependendo do seu provedor de nuvem e requisitos de arquitetura.

3. LoadBalancer​

O tipo LoadBalancer no Kubernetes é usado para expor um serviço diretamente à Internet, utilizando um balanceador de carga externo provisionando automaticamente pelo provedor de nuvem (como AWS, GCP ou Azure). Ele é ideal para aplicações que precisam ser acessadas publicamente e com alta disponibilidade.

De forma geral, um LoadBalancer atua como um componentes de rede que distribui uniformemente o tráfego de entrada entre os Pods de um serviço, evitando sobrecarga em instâncias individuais e garantindo escalabilidade, confiabilidade e performance.

Como funciona um LoadBalancer no Kubernetes​

1. Definição do Service:

  • Você cria um Service do tipo LoadBalancer com as portas de entrada e um selector para identificar os Pods que receberão o tráfego.

2. Provisionamento automático:

  • O Kubernetes interage com a API do provedor de nuvem e solicita o provisionamento de um balanceador de carga externo.

3. Atribuição de IP público:

  • O provedor atribui um IP externo público ao serviço, o qual servirá como ponto de acesso para usuários e sistemas externos.

4. Distribuição de tráfego:

  • O tráfego recebido pelo IP público é distribuído automaticamente para os Pods do serviço, com base em algoritmos como round-robin ou afinidade de sessão.

5. Health Checks:

  • O balanceador de carga realiza verificações periódicas de integridade (health checks) nos Pods. Caso um Pod esteja inoperante, ele será temporariamente removido da rotação de tráfego.

Tipos de LoadBalancers em nuvem​

Dependendo do seu provedor de nuvem, o Kubernetes pode provisionar dois tipos de balanceadores:

  • LoadBalancer Externo: Expõe o serviço à Internet pública. Muito comum para aplicações web, APIs públicas e frontends.
  • LoadBalancer Interno: Disponível em alguns provedores, esse tipo de LoadBalancer é criado dentro da rede privada (VPC), ideal para serviços que devem ser acessados apenas internamente por outros sistemas ou microserviços.

Exemplo de manifesto YAML com LoadBalancer Service​

apiVersion: v1
kind: Service
metadata:
  name: my-loadbalancer-service
spec:
  selector:
    app: my-app
  ports:
    - protocol: TCP
      port: 80          # Porta pública exposta no LoadBalancer
      targetPort: 8080  # Porta onde o container escuta dentro do Pod
  type: LoadBalancer

Neste exemplo, assim que o manifesto for aplicado, o Kubernetes solicitará ao provedor de nuvem a criação de um LoadBalancer. O tráfego que chegar ao IP público na porta 80 será redirecionado para os Pods que têm o rótulo app: my-app, onde o serviço real está escutando na porta 8080.

4. ExternalName​

O ExternalName é um tipo essencial de Service no Kubernetes que não cria um proxy de rede nem expõe Pods, mas sim mapeia um nome de serviço interno para um nome DNS externo.

Esse tipo de serviço é útil quando você quer que aplicações dentro do cluster acessem um serviço externo (fora do cluster) como se ele forsse um serviço Kubernetes.

Como ele funciona​

  • O Kubernetes cria uma entrada DNS interno (external-service.default.svc.cluster.local) que, quando acessada, resolve diretamente para o nome DNS externo especificado.
  • Não há IP atribuído, nem balanceamento de carga interno. Ele atua puramente como um alias DNS.
  • Pode ser usado para acessar APIs, bancos de dados externos, serviços legados, etc.

Exemplo de manifesto YAML com ExternalName Service​

apiVersion: v1
kind: Service
metadata:
  name: external-service
spec:
  type: ExternalName
  externalName: api.exemplo-externo.com

Neste exemplo, quando um Pod dentro do cluster tentar acessar external-service.default.svc.cluster.local, a requisição será redirecionada para api.examplo-externo.com.

Observações importantes​

  • Sem pods ou selectors: esse tipo de serviço não usa o campo selector e não se conecta a Pods, pois o destino é externo ao cluster.
  • Requisições DNS: o Kubernetes retorna um registro CNAME apontando para o externalName, e a resolução acontece fora do cluster.
  • Portas não são definidas: como não há proxy nem rede, os campos de porta não são usados.
