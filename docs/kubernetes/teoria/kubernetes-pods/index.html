Pods no Kubernetes: conceito e funcionamento

O que é um Pod?​

Os Pods são as menores unidades de computação que você pode criar e gerenciar no Kubernetes.

Um Pod é um grupo de um ou mais contêineres que compartilham:

  • Armazenamento (volumes)
  • Rede (mesmo endereço IP e portas)
  • Especificações de execução

O conteúdo de um Pod é sempre colocado e agendado em conjunto, rodando em um mesmo contexto compartilhado.

Em outras palavras, um Pod é como um "host lógico" dentro do cluster, onde podem rodar contêineres que precisam trabalhar juntos.

Isso é análoga, fora de nuvem, a múltiplos aplicativos rodando numa mesma VM ou servidor físico.

Pods com múltiplos contêineres​

Embora o padrão seja um contêiner por Pod, também é possível criar Pods que executam múltiplos contêineres fortemente acoplados.

Eles compartilham rede e volumes, formando uma única unidade coesa de serviço.

Exemplo:

  • Um contêiner servindo arquivos de um volume compartilhado.
  • Um contêiner auxiliar (sidecar) que atualiza esses arquivos em background.

Essa abordagem é poderosa, mas considerada avançada. Só use quando seus contêineres precisarem realmente estar colocalizados.

Init Containers e Ephemeral Containers​

Além dos contêineres principais, um Pod também pode incluir:

  • Init Containers: executados durante a inicialização, antes dos contêineres de aplicativo.
  • Ephemeral Containers: contêineres temporários, usados para depuração em Pods já em execução.

Esses recursos tornam os Pods mais flexíveis e adequados para cenários de preparação ou troubleshooting.

Recursos de carga de trabalho e Pods​

Normalmente, você não cria Pods diretamente.

Em vez disso, utiliza recursos de carga de trabalho (workload Resources), que gerenciam Pods para você:

  • Deployments -> gerencia réplicas de Pods e atualizações.
  • StatefulSet -> gerencia Pods com estado persistentes e identidades estável.
  • DaemonSet -> garante que um Pod rode em todos (ou em alguns) nós.
  • Job / CronJon -> cria Pods para tarefas batch ou agendadas.

Esses recursos usam PodTemplates, que são modelos de Pods dentro de seus manifestos.

Compartilhamento de recursos nos Pods​

Rede​

  • Cada Pod recebe um IP exclusivo dentro do cluster.
  • Todos os contêineres dentro do Pod compartilham esse IP e o mesmo espaço de portas.
  • Contêineres do mesmo Pod podem se comunicar via localhost.

Armazenamento​

  • Pods podem montar volumes compartilhados.
  • Isso permite persistência de dados mesmo que um contêiner seja reiniciado.

Ciclo de vida dos Pods​

Um pod pode estar em diferentes fases:

  • Pending -> definido, mas ainda não agendado.
  • Running -> contêineres em execução.
  • Succeeded -> terminou com sucesso.
  • Failed -> terminou com erro.
  • Unknown -> estado não pôde ser determinado.

Reiniciar um contêiner não é o mesmo que reiniciar um Pod.

Se um Pod falhar, ele é recriado do zero pelo Kubernetes (ou pelo controlador que o gerencia).

Resumo​

  • O Pod é a menor unidade de execução no Kubernetes.
  • Ele encapsula contêineres, rede e volumes compartilhados.
  • Pode conter um contêiner único ou múltiplos fortemente acoplados.
  • É efêmero: quando falha, outro Pod é criado no lugar.
  • Normalmente é gerenciado por controladores como Deployments, StatefulSet e DaemonSet.

Exemplo de manifesto de um único Pod​

Antes de entrar em detalhes mais avançados, veja um exemplo simples de Pod rodando um contêiner Nginx:

apiVersion: v1
kind: Pod
metadata:
  name: meu-primeiro-pod
spec:
  containers:
  - name: nginx
    image: nginx:1.14.2
    ports:
    - containerPort: 80

Exemplo de manifesto de um Pod com múltiplos contêineres​

apiVersion: v1
kind: Pod
metadata:
  name: meu-primeiro-pod
spec:
  containers:
  - name: nginx
    image: nginx:1.14.2
    ports:
    - containerPort: 80
  - name: mysql
    image: mysql:5.7
    ports:
    - containerPort: 3306

Explicando o manifesto de um Pod

  • apiVersion: v1
    • Define qual versão da API Kubernets será usada para criar esse objeto.
  • kind: Pod
    • Indica o tipo de objeto que estamos criando. Nesse caso, é um Pod.
  • metadata:
    • Contém informações adicionais sobre o objeto, como:
      • name -> nome único do Pod no cluster.
      • Outros campos possíveis: labels, annotations, etc.
  • spec:
    • Define a especificação desejada para o Pod.
    • É aqui que você descreve os contêineres, volumes e demais configurações.
  • containers:
    • Lista de contêineres que farão parte do Pod.
    • Cada item da lista representa um contêiner a ser executado.
      • name: Nome de identificação do contêiner dentro do Pod. (Precisa ser único por Pod).
      • image: Imagem do contêiner a ser executado.
        • Aqui usamos a imagem oficial do Nginx, versão 1.14.2.
      • ports: Lista das portas que o contêiner expõe.
        • containerPort: expõe a porta 80 do contêiner, usada pelo Nginx para servir páginas web.

Resumindo:

  • apiVersion + kind -> dizem o que está sendo criado.
  • metadata -> diz como identificar esse objeto no cluster.
  • spec -> define como o objeto deve funcionar.
  • containers -> descreve os contêineres dentro do Pod (imagem, nome, portas, etc).

Exemplo de PodTemplate​

apiVersion: batch/v1
kind: Job
metadata:
  name: hello
spec:
  template:
    spec:
      containers:
      - name: hello
        image: busybox
        command: ['sh', '-c', 'echo "Hello, Kubernetes!" && sleep 3600']
      restartPolicy: OnFailure

Aqui o PodTemplate dentro do Jobdefine o Pod que será criado e gerenciado automaticamente.
