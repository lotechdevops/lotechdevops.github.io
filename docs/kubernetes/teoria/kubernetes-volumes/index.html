Volumes no Kubernetes

O que são os Volumes no Kubernetes?​

No Kubernetes, os Volumes são utilizados para armazenar dados persistentes que precisam sobreviver à reinicialização dos containers ou à exclusão de Pods. Eles resolvem uma limitação importante dos containers: o fato de que tudo que é gravado dentro do container desaparece quando ele é reiniciado ou destruído.

Diferente do armazenamento efêmero interno ao container, os volumes do Kubernetes são montados em diretórios acessíveis pelo(s) container(s) de um Pod e oferecem maior durabilidade e flexibilidade.

Como os Volumes funcionam?​

Quando um Pod é criado, você pode definir um ou mais volumes que serão montados em seus containers. Esses volumes têm escopo do Pod, ou seja, vivem enquanto o Pod vive, e podem ser compartilhados entre múltiplos containers dentro do mesmo Pod.

Ao contrário dos containers Docker nativos, onde volumes são locais e não gerenciados diretamente pelo orquestrador, o Kubernetes oferece um modelo extensível de volumes, incluindo integração com soluções de rede, NFS, volumes persistentes e provedores de nuvem.

Tipos de Volumes​

O Kubernetes suporta diversos tipos de volumes. Aqui estão os mais comuns utilizados:

1. emptyDir

  • Criado quando o Pod é iniciado e existe enquanto o Pod está em execução.
  • É útil para armazenar arquivos temporários ou para compartilhamento entre containers.

2. hostPath

  • Monta um diretório do host (nó) diretamente no container.
  • Útil para diagnósticos ou acesso direto ao sistema de arquivos do nó, mas pode ser perigoso se mal configurado.

3. configMap/secret

  • Monta dados de configuração como arquivos.
  • Útil para separar configuração de código da aplicação.

4. persistentVolumeClaim (PVC)

  • Permite montar volumes que pesistem além da vida útil do Pod.
  • Usado para garantir persistência real de dados, mesmo se o Pod for deletado ou recriado.

PV, PVC e StorageClass​

No Kubernetes, o armazenamento persistente é gerenciado por meio de três objetos principais:

  • PersistentVolume (PV)
  • PersistentVolumeClaim (PVC)
  • StorageClass

Esse objetos permitem que o Kubernetes trate o armazenamento como um recurso desacoplado, tal como CPU ou memória.

PersistentVolume (PV)​

Um PersistentVolume é um objeto do Kubernetes que represnta um recurso de armazenamento físico no cluster. Ele pode ser, por exemplo, um disco local de um nó, um volume de rede (como NFS) ou até mesmo um disco gerenciado em nuvem, como o AWS EBS, Google Persistent Disk, Azure Disk, entre outros.

O principal objetivo do PV é fornecer armazenamento durável: os dados armazenados permanecem disponíveis mesmo que o Pod seja reiniciando ou movido para outro nó do cluster.

Tipos de armazenamento utilizados como PV​

Os volumes utilizados em um PV podem ser classificados em duas categorias principais:

Armazenamento Local

  • hostPath: Usa o diretório local do nó do cluster como volume. É simples e útil para testes e desenvolvimento local, mas não é recomendado para produção, pois o volume só está acessível no nó específico.

Armazenamento em Rede

  • nfs (Network File System): Compartilha arquivos entre múltiplos nós via rede.
  • iscsi: Protocolo para armazenamento de blocos via IP, comum em ambientes com SAN.
  • cephRBD: Soluções distribuída e altamente escalável (Ceph) que provê volumes em blocos.
  • glusterfs: Sistema de arquivos distribuído, ideal para volumes compartilhados.
  • csi: Interface padrão para plugins de armazenamento de terceiros (mais moderna e recomendada para drivers recentes).

Exemplos de tipos de volume suportado​

  • awsElasticBlockStore
  • azureDisk
  • azureFile
  • cephFS
  • rbd
  • csi
  • cinder
  • fc
  • glusterfs
  • hostPath
  • iscsi
  • nfs
  • vsphereVolume
  • vsphereVirtualDisk

Exemplo de manifesto de um PV​

apiVersion: v1
kind: PersistentVolume
metadata:
  name: primeiroPV
spec:
  storageClassName: ""
  capacity:
    storage: 1Gi
  accessModes:
    - ReadWriteOnce
  hostPath:
    path: "/volume"

Campos Importantes:

capacity:
    storage: 1Gi
  • Define o tamanho do volume.
volumeMode: FileSystem
  • Define se o volume será exposto como um sistem arquivos (FileSystem) ou como um bloco (Block).
accessModes:
    - ReadWriteOnce # leitura/escrita por um nó
    - ReadOnlyMany # leitura por vários nós
    - ReadWriteMany # leitura/escrita por vários nós
persistentVolumeReclaimPolicy: Retain
  • Retain -> O volume permanece no cluster, precisa de limpeza manual.
  • Recycle -> O volume é removido do cluster.
  • Delete -> Apaga o volume (recomendado com EBS, GCE, Azure).
  • hostPath -> Monta o um diretório ou arquivo local do nó.
hostPath:
    path: /volume
    type: DirectoryOrCreate
  • O tipo DirectoryOrCreate cria o diretório se ele não existir.
  • O tipo FileOrCreate cria um arquivo vazio, se necessário.

PersistentVolumeClaim (PVC)​

Enquanto o PersistentVolume (PV) representa o recurso de armazenamento disponível no cluster, o PersistentVolumeClaim (PVC) é a solicitação desse recurso feita por um usuário ou aplicação.

O PVC permite que você solicite dinamicamente espaço de armazenamento para seu Pod, sem precisar conhecer os detalhes físicos do volume, como tipo, localização ou driver de provisionamento.

Como o PVC funciona?​

  1. O administrador do cluster disponibiliza um ou mais PersistentVolumes.
  2. O desenvolvedor (ou aplicativo) cria um PersistentVolumeClaim, especificando a capacidade necessária, modo de acesso e (opcionalmente) uma StorageClass.
  3. O Kubernetes tenta vincular automaticamente o PVC a um PV que atenda aos requisitos especificados.
  4. Uma vez vinculado, o Pod que usar esse PVC pode montar o volume e utilizá-lo.

Exemplo de manifesto de um PVC​

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: primeiroPVC
spec:
  storageClassName: ""
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi

Este exemplo solicita um volume de 1 GB, com acesso de leitura e escrita por apenas um nó.

Campos Importantes:

acessModes:
    - ReadWriteOnce # leitura/escrita por um nó
    - ReadOnlyMany # leitura por vários nós
    - ReadWriteMany # leitura/escrita por vários nós
  • Define o tipo de acesso necessário ao volume.
resources:
    requests:
        storage: 1Gi
  • Tamanho do volume desejado
storageClassName: ""
  • Especifica a classe de armazenamento a ser utilizada.
  • Se não for definida e a StorageClass padrão (default) estiver habilitada, ela será usada automaticamente.

Vinculando um PVC a um Pod​

Após o PVC estar disponível (e vinculado a um PV), você pode usá-lo em um Pod como volume:

apiVersion: v1
kind: Pod
metadata:
  name: pod-com-pvc
spec:
  containers:
    - name: app
      image: nginx
      volumeMounts:
        - name: meu-volume
          mountPath: /usr/share/nginx/html
  volumes:
    - name: meu-volume
      persistentVolumeClaim:
        claimName: primeiroPVC

Neste exemplo, o volume solicitado no PVC será montado no caminho /usr/share/nginx/html dentro do container.

StorageClass​

A StorageClass é um recurso do Kubernetes que permite definir diferentes classes de armazenamento, descrevendo como o armazenamento persistente deve ser provisionado dinamicamente no cluster. Ela atua como uma camada de abstração sobre os sistemas de armazenamento, permitindo que aplicações solicitem volumes sem conhecer os detalhes da infraestrutura subjacente, como o tipo de disco, performance, replicação ou sistema de arquivos.

Quando um usuário ou aplicação cria um PersistentVolumeClaim (PVC) e especifica uma StorageClass, o Kubernetes entende como deve provisionar o volume com base nas definições dessa classe.

Isso traz flexibilidade e padronização, pois:

  • Permite definir políticas de armazenamento reutilizáveis.
  • Permite múltiplas classes com diferentes características (por exemplo: SSD, HDD, replicado, criptografado).
  • Facilita o provisionamento dinâmico de volumes, ou seja, sem necessidade de criação manual de PVs.

Exemplo de um manifesto de um StorageClass​

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-storage
provisioner: example.com/provisioner
parameters:
  type: fast

Neste exemplo:

  • O nome da StorageClass é fast-storage
  • O campo provisioner define qual plugin de provisionamento dinâmico será usado, como kubernetes.io/aws-ebs, kubernetes.io/gce-pd ou csi.amazon.com (no caso do CSI da AWS).
  • O campo parameters define configurações específicas para o provisionador. No caso acima, type: fast é apenas ilustrativo, o valor real dependerá da integração com seu backend de armazenamento.

Algumas StorageClass comuns (por provedores)​

| Provedor   | Provisioner                          | Observações                     |
| ---------- | ------------------------------------ | ------------------------------- |
| AWS        | `kubernetes.io/aws-ebs`              | Depreciado, substituído por CSI |
| AWS (CSI)  | `ebs.csi.aws.com`                    | Recomendado                     |
| GCP        | `kubernetes.io/gce-pd`               |                                 |
| Azure      | `kubernetes.io/azure-disk`           |                                 |
| NFS CSI    | `nfs.csi.k8s.io`                     | Para volumes baseados em NFS    |
| Local Path | `k8s.io/minikube-hostpath` ou custom | Usado para labs locais          |

StorageClass padrão​

Você pode definir uma StorageClass como padrão com o seguinte annotation:

metadata:
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"

Dessa forma, qualquer PVC criado sem especificar explicitamente um storageClassName usará essa classe automaticamente.
