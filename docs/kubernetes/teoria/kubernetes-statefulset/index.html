StatefulSet no Kubernetes: aplicações com estado

O que é um StatefulSet?​

Os StatefulSet são uma funcionalidade do Kubernetes que gerencia o Deployment e o scaling de um conjunto de Pods, fornecendo garantias sobre a ordem de Deployment e a singularidade desses Pods.

Diferente dos Deployments e ReplicaSets que são considerados stateless (sem estado), os statefulsets são utilizados quando você precisa de mais garantias sobre o Deployment e scaling. Eles garantem que os nomes e endereços dos Pods sejam consistentes e estáveis ao longo do tempo.

Quando usar StatefulSets?​

Os StatefulSets são úteis para aplicações que necessitam de um ou mais dos seguintes:

  • Identidade de rede estável e única.
  • Armazenamento persistente estável.
  • Ordem de Deployment e scaling garantida.
  • Ordem de rolling updates e rollbacks garantida.
  • Algumas aplicações que se encaixem nesses requisitos são bancos de dados, sistemas de filas e quaisquer aplicativos que necessitam de persistência de dados ou identidades de rede estável

Como funciona o StatefulSet?​

Os StatefulSets funcionam criando uma série de Pods replicados. Cada réplica é uma instância da mesma aplicação que é criada a partir do mesmo spec, mas pode ser diferenciada por seu índice e hostname.

Ao contrário dos Deployments e ReplicaSets, onde as réplicas são intercambiáveis, cada Pod em um StatefulSet tem um índice persistente e um hostname que se vinculam a sua indentidade.

Por exemplo: se um StatefulSet tiver um nome app e um spec de três réplicas, ele criará três Pods: app-0, app-1 e app-2. A ordem dos índices é garantida. O Pod app-1 não será iniciado até que o Pod app-0 esteja disponível e pronto.

A mesma garantia de ordem é aplicada ao scaling e aos updates.

O StatefulSet e os volumes persistentes​

Um aspecto chave dos StatefulSets é a integração com Volumes Persistentes. Quando um Pod é recriado, ele se reconecta ao mesmo Volume Persistente, garantindo a persistência dos dados entre as recriações dos Pods.

Por padrão, o Kubernetes cria um PersistentVolume para cada Pod em um StatefulSet, que é então vinculado a esse Pod para a vida útil do StatefulSet.

Isso é útil para aplicações que precisam de um armazenamento persistente e estável, como banco de dados.

O StatefulSet e o Headless Service​

Para entender a relação entre o StatefulSet e o Headless Service, é preciso primeiro entender o que é um Headless Service.

No Kubernetes, um serviço é uma abstração que define um conjunto lógico de Pods e uma maneira de acessá-los. Normalmente, um serviço tem um IP e encaminha o tráfego para os Pods. No entanto, um Headless Service é um tipo especial de serviço que não tem um IP próprio. Em vez disso, ele retorna diretamente os IPs dos Pods que estão associados a ele.

Agora, o que isso tem a ver com os StatefulSets?

Os StatefulSets e os Headless Service geralmente trabalham juntos no gerenciamento de aplicações stateful. O Headless Service é responsável por permitir a comunicação de rede entre os Pods em um StatefulSet, enquanto o gerencia o Deployment e o scaling desses Pods.

Aqui está como eles funcionam juntos:

Quando um StatefulSet é criado, ele geralmente é associado a um Headless Service. Ele é usado para controlar o domínio DNS dos Pods criados pelo StatefulSet. Cada Pod obtém um nome de host DNS que segue o formato: <pod-name>.<service-name>.<namespace>.svc.cluster.local. Isso permite que cada Pod seja alcançado individualmente.

Por exemplo, você tiver um StatefulSet chamado app com três replicas e um Headless Service chamado nginx, os Pods criados serão app-0, app-1, app-2 e eles terão os seguintes endereços de host DNS: app-0.nginx.default.svc.cluster.local, app-1.nginx.default.svc.cluster.local e app-2.nginx.default.svc.cluster.local

Essa combinação de StatefulSets com Headless Service permite q eaplicações stateful, como banco de dados, tenham uma indentidade de rede estável e previsível, facilitando a comunicação entre diferentes instâncias da mesma aplicação.

Exemplo de um manifesto de um StatefulSet​

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: app
spec:
  serviceName: "nginx"
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.21.6
        ports:
        - containerPort: 80
          name: app
        volumeMounts:
        - name: app
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
  - metadata:
      name: www
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: "standard"
      resources:
        requests:
          storage: 1Gi

Explicação dos campos principais

serviceName:
  • Nome do Headless Service usado como base para gerar o DNS dos pods.
replicas:
  • Quantos pods devem ser criados no StatefulSet.
selector.matchLabels:
  • Define quais pods pertencem a este StatefulSet (match com os labels)
template:
  • Modelo de pod a ser criado, assim como no Deployment
volumeMounts:
  • Onde o volume será montado dentro do container.
volumeClaimTemplates:
  • Cria um PVC exclusivo por pod com base nesse template. Cada app-0, app-1, etc., receberá seu próprio PVC.

Boas Práticas​

  • Sempre usar StorageClass adequado e com suporte à persistencia real.
  • Evitar usar StatefulSet para apps que não precisam de estado ou ordem de inicialização.
  • Usar Pod Anti-Affinity para distribuir réplicas entre diferentes nós (alta disponibilidade).
  • Em atualizações de imagem, o StatefulSet atualizará os pods um por um, respeitando a ordem.
