HPA - Horizontal Pod Autoscaler

Fundamentos​

O que é HPA​

No Kubernetes, o Horizontal Pod Autoscaler (HPA) é um mecanismo essencial que garante que as suas aplicações conseguem lidar com qualquer carga de trabalho, sem intervenção manual. Pense no HPA como um gerenciador de tráfego inteligente para sua aplicação.

Quando o tráfego (a carga) aumenta muito, ele detecta a necessidade e abre mais "faixas" (cria mais Pods) para evitar uma "congestionamento" (a aplicação ficar lenta ou cair). Quando a carga diminui, ele reduz as faixas desnecessárias para economizar recursos.

Escalonamento Horizontal vs Vertical

É fundamental entender a diferença:

  • Escalonamento Horizontal (HPA): Significa implantar mais Pods (réplicas) em resposta ao aumento de carga. É como adicionar mais caixas em um supermercado.

  • Escalonamento Vertical: Significa atribuir mais recursos (CPU ou Memória) aos Pods que já estão em execução. É como dar uma máquina de alta performance para a caixa existente.

O HPA atua sobre recursos de carga de trabalho como Deployments ou StatefulSets, mas não se aplica a objetos que não podem ser escalados, como DaemonSets.

Como Funciona o HPA: O Ciclo de Controle​

O HPA não é apenas um comando: é um recurso de API e um controlador que funciona dentro do Control Plane do Kubernetes.

O controlador HPA opera como um loop de controle que é executado periodicamente. O intervalo padrão é de 15 segundos.

1. O Loop do HPA

Durante cada ciclo (padrão de 15 segundos), o HPA segue estes passos:

  1. Consulta de Métricas: O controlador consulta a utilização de recursos (CPU, Memória, etc) através das APIs de Métricas (como metrics.k8s.io ou custom.metrics.k8s.io).

  2. Seleção de Pods: Encontra o recurso-alvo (scaleTargetRef) e seleciona os pods associados.

  3. Cálculo: Calcula o número de réplicas que são desejadas para atingir o valor alvo da métrica.

  4. Ação: Se necessário (e se o resultado do cálculo exceder a tolerância), ele ajusta o número de réplicas do recurso-alvo (Deployment ou StefulSet).

2. A Fórmula de Cálculo

O HPA usa uma fórmula de proporção simples para determinar quantos Pods são necessários:

desiredReplicas = ceil[currentReplicas × (currentMetricValue / desiredMetricValue)]

Explicando de forma simples:

O HPA divide o valor atual da métrica observada (por exemplo, 200m de uso de CPU) pelo valor alvo desejado (por exemplo, 100m de CPU).

  • Se a proporção for 2.0 (200m/100m), o número de réplicas irá dobrar
  • Se a proporção for 0.5 (50m/100m), o número de réplicas será reduzido pela metade.

Se a proporção estiver muito próxima de 1.0 (dentro da tolerância padrão de 0.1), o HPA não fará nenhuma ação, evitando flapping.

Para métricas de CPU, o HPA é cauteloso. Pods que estão not-yet-ready ou que não estão prontos são reservados ou tratados de forma conservadora no cálculo, para que a carga alta durante a inicialização não cause um scale-up desnecessário e excessivo.

Tipos de Métricas Suportadas​

O HPA oferece flexibilidade, permitindo o escalonamento com base em quatro tipos principais de métricas (na versão autoscaling/v2):

1. Resource Metrics (Métricas de Recurso)​

  • O que é: Uso de CPU ou Memória de todo o Pod. A utilização é calculada como uma porcentagem dos recursos que foram solicitados pelo Pod.
  • Exemplo: Manter a utilização média de CPU em 60%.
type: Resource
resource:
  name: cpu
  target:
    type: Utilization
    averageUtilization: 60

2. Container Resource Metrics​

  • O que é: Uso de recursos de um container individual dentro de um Pod. Útil quando um Pod tem vários containers, mas apenas um é o gargalo.
type: ContainerResource
containerResource:
  name: cpu
  container: application
  target:
    type: Utilization
    averageUtilization: 60

3. Custom Metrics (Métricas Personalizadas)​

  • O que é: Métricas específicadas da aplicação, como taxa de pedidos HTTP por segundo ou tamanho da fila de mensagens. Requer um adaptador de métricas personalizado (API custom.metrics.k8s.io);
  • Exemplo: Manter em média 1000 pedidos HTTP por segundo por Pod.
type: Pods
pods:
  metric:
    name: http_requests_per_second
  target:
    type: AverageValue
    averageValue: "1000"

4. Múltiplas Métricas​

  • O que é: Podes especificar várias métricas simultaneamente. O HPA calculará as réplicas necessárias para cada métrica e escolherá o maior valor de réplicas desejado. Isto garante que a aplicação está sempre dimensionada para a métrica que está a ser o maior bottleneck.

Comportamento de Escalonamento Configurável (Anti-Flapping)​

No Kubernetes, o HPA, por padrão, age de forma bastante agressiva, especialmente no aumento da escala. No entanto, se as métricas da sua aplicação flutuarem muito, isso pode levar ao que chamamos de "flapping": o HPA está constantemente adicionando e removendo pods a cada 15 segundos, o que é ineficiente e estressante para o seu cluster.

Para evitar este problema, o HPA na versão autoscaling/v2 permite-te configurar o seu comportamento (campo behavior). Isto dá-te um controlo fino sobre as ações de scale up (aumentar) e scale down (diminuir).

A Chave: Janela de Estabilização (stabilizationWindowSeconds)

A Janela de Estabilização é o mecanismo de defesa do HPA contra o flapping. É um período de tempo que o HPA deve "esperar" antes de tomar uma decisão, garantindo que a tendência da métrica é estável e não apenas um pico momentâneo.

Para o Scale Down (Redução de Escala)

  • Padrão: 300 segundos (5 minutos)
  • Como funciona: O HPA só reduzirá o número de réplicas se o número de pods desejado tiver sido igual ou inferior ao valor atual durante todo o período da Janela de Estabilização.
  • Motivo: Isto evita que uma queda momentânea no tráfego faça com que os pods sejam terminados, apenas para serem criados novamente 30 segundos depois quando o tráfego volta.

Para o Scale Up (Aumento de Escala)

  • Padrão: 0 segundos
  • Como funciona: Por padrão, o aumetno de escala é imediato assim que o cálculo o exige, para garantir que a aplicação responde rapidamente a um pico de carga. No entanto, podes configurar uma janela de estabilização aqui também se a tua métrica for muito volátil e tu souberes que os picos são temporários.

Políticas de Escalonamento (policies)

Além da Janela de Estabilização, podes definir regras explícitas sobre a rapidez com que a escala pode mudar:

|Tipo de Política | Descrição                                                             |
|Percent          | Limita o scale a uma porcentagem do número atual de pods num período. |
|Pods             | Limita o scale a um número fixo de pods em um período.                |

O HPA pode ter múltiplas políticas. Por padrão, ele usa o selectPolicy: Max no scale up (escolhe a política que resulta no maior aumento de pods) e selectPolicy: Min no scale down (escolhe a política mais conservadora para reduzir a escala).

Usando autoscaling/v2, você pode configurar comportamentos separados via campo behavior:

behavior:
  scaleUp:
    stabilizationWindowSeconds: 0
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
    - type: Pods
      value: 4
      periodSeconds: 15
    selectPolicy: Max

  scaleDown:
    stabilizationWindowSeconds: 300
    policies:
    - type: Percent
      value: 50
      periodSeconds: 15
    - type: Pods
      value: 2
      periodSeconds: 60
    selectPolicy: Min

Prática: Testando o HPA no Cluster​

HPA na Prática: Implementação com Nginx​

Pré-requisitos​

  • Cluster Kubernetes rodando
  • kubectl configurado
  • Metrics Server instalado

1. Instalar Metrics Server​

O Metrics Server é essencial para o HPA funcionar, pois fornece as métricas de CPU e memória dos pods.

kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
Verificar instalação​

Verificar se o Metrics Server está rodando

kubectl get deployment metrics-server -n kube-system

Aguardar 1-2 minutos e testar

kubectl top nodes
kubectl top pods -A

Configuração para ambientes de desenvolvimento​

Se estiver usando um cluster local (minikube, kind, k3s), pode ser necessário adicionar a flag --kubelet-insecure-tls

kubectl edit deployment metrics-server -n kube-system

Adicionar aos args container: - --kubelet-insecure-tls

2. Criar o Deployment​

Vamos usar uma imagem nginx simples com recursos definidos

deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: nginx-hpa
  name: nginx-hpa
  namespace: default
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nginx-hpa
  template:
    metadata:
      labels:
        app: nginx-hpa
    spec:
      containers:
      - image: nginx
        name: nginx-hpa
        resources:
          limits:
            cpu: "500m"          # 500 millicores
            memory: 500Mi
          requests:
            cpu: "200m"          # 200 millicores (base para cálculo do HPA)
            memory: 250Mi

Campos importantes

CPU:

  • requests.cpu: "500m" - Base para o cálculo de utilização do HPA (500m = 50% de 1 CPU)
  • limits.cpu: "200m" - Limite máximo que o container pode usar Memória:
  • requests.memory: 500Mi - Quantidade mínima de memória garantida. Base para o cálculo de utilização do HPA
  • limits.memory: 250Mi - Limite máximo de memória. Se ultrapssar, o pod será terminado (OOMKilled)

Réplicas:

  • replicas: 1 - Valor inicial (O HPA vai ajustar automaticamente para minReplicas ou mais)

O HPA calcula a utilização como porcentagem do request

  • CPU a 50m = 50% de utilização (50m / 100m request)
  • Memória a 8Mi = 50% de utilização (8Mi / 16Mi request)

Aplique o deployment no cluster:

kubectl apply -f deployment.yaml
kubectl get pods -l app=nginx-hpa

3. Criar o Service​

service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: nginx
spec:
  selector:
    app: nginx-hpa
  ports:
  - port: 80
    targetPort: 80

Aplique o service no cluster:

kubectl apply -f service.yaml
kubectl get svc nginx

4. Configurar o HPA​

hpa.yaml:

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-hpa
  minReplicas: 3              # Mínimo de 3 pods sempre
  maxReplicas: 5              # Máximo de 5 pods
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50    # Escala quando CPU média > 50%
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 50    # Escala quando memória média > 50%
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60    # Aguarda 60s antes de confirmar
      policies:
      - type: Percent
        value: 100                      # Dobra o número de pods
        periodSeconds: 10               # A cada 10 segundos
    scaleDown:
      stabilizationWindowSeconds: 60    # Aguarda 60s antes de remover
      policies:
      - type: Percent
        value: 100                      # Remove até 100% dos pods
        periodSeconds: 10               # A cada 10 segundos
Explicação das Métricas​

type: Resource

  • Métricas de CPU/memória do pod inteiro
  • averageUtilization: 50= quando a média dos pods atingir 50% do request
Explicação do Behavior​

scaleUp:

  • stabilizationWindowSeconds: 60 = Aguarda 1 minuto confirmando que realmente precisa escalar
  • value: 100 com type: Percent = Pode dobrar o número de pods (aumentar 100%)

scaleDown:

  • stabilizationWindowSeconds: 60 = Aguarda 1 minuto antes de remover pods
  • Evita flapping (oscilação constante)

Aplique o hpa no cluster:

kubectl apply -f hpa.yaml

5. Verificar o HPA​

Ver status do HPA

kubectl get hpa

Saída esperada:

# NAME        REFERENCE              TARGETS                      MINPODS   MAXPODS   REPLICAS
# nginx-hpa   Deployment/nginx-hpa   <unknown>/50%, <unknown>/50%   3         5         1

Aguarde alguns segundos para as métricas aparecerem:

# NAME        REFERENCE              TARGETS         MINPODS   MAXPODS   REPLICAS
# nginx-hpa   Deployment/nginx-hpa   0%/50%, 0%/50%  3         5         3

Ver detalhes

kubectl describe hpa nginx-hpa

6. Testar o HPA​

Observar o escalonamento inicial​

Como configuramos minReplicas: 3, o HPA vai automaticamente criar 3 pods:

watch -n 2 'kubectl get hpa && echo "" && kubectl get pods -l app=nginx-hpa'

Gerar carga para testar scale up​

Com request.cpu: 200m e target de 50%, o HPA vai escalar quando a média de CPU passar de 100m (50% de 200m).

Método 1: Carga leve (testar escalonamento gradual)

Criar 3 pods gerando carga moderado

for i in {1..3}; do
  kubectl run load-test-$i --image=busybox --restart=Never -- /bin/sh -c "while true; do wget -q -O- http://nginx > /dev/null; sleep 0.05; done" &
done

Observe o comportamento:

Em outro terminal:

watch -n 2 'kubectl get hpa && echo "" && kubectl get pods -l app=nginx-hpa'

watch -n 2 'kubectl top pods -l app=nginx-hpa'

Você verá:

  • CPU dos pods começa a subir: ~6m -> ~15m -> ~20m

Método 2: Carga Pesada (forçar scale up rápido)

Criar 10 pods gerando carga agressiva

for i in {1..10}; do
  kubectl run heavy-load-$i --image=busybox --restart=Never -- /bin/sh -c "while true; do wget -q -O- http://nginx > /dev/null; done" &
done

Observe o comportamento:

Em outro terminal:

Você verá:

  • CPU dos pod sobe rapidamente: ~30m -> ~50m -> ~70m -> ~100m
  • Média ultrapassa 100m rapidamente
  • Após 60s, HPA escala de 3 -> 4

Parar o teste de carga​

Deletar todos os pods de teste

kubectl delete pod -l run --force --grace-period=0

Observe o comportamento:

  • CPU dos pods cai
  • HPA aguarda 60s
  • Após confirmar que a carga está baixa, começa a remover pods
  • Processo pode levar ~1 minutos devido ao stabilizationWindow

Troubleshooting​

CPU não sobe mesmo com carga​

Verificar se os pods estão recebendo requisições

kubectl logs -l app=nginx-hpa --tail=20
HPA não escala mesmo com CPU alta​

Verificar se passou do threshold

kubectl top pods -l app=ngix-hpa

Verificar eventos do HPA

kubectl describe hpa nginx-hpa

Sucesso! Seu HPA está configurado e testado!
