HPA - Horizontal Pod Autoscaler

Fundamentos​

O que é HPA​

No Kubernetes, o Horizontal Pod Autoscaler (HPA) é um mecanismo que garante que suas aplicações consigam lidar com variações de carga sem intervenção manual. Pense no HPA como um gerenciador de tráfego inteligente para sua aplicação.

Quando o tráfego aumenta, ele detecta a necessidade e abre mais "faixas" (cria mais Pods) para evitar congestionamento (a aplicação ficar lenta ou cair). Quando a carga diminui, ele reduz as faixas desnecessárias para econimizar recursos.

Escalonamento horizontal vs vertical

É fundamental entender a diferença:

  • Escalonamento horizontal (HPA): implanta mais Pods (réplicas) em resposta ao aumento de carga. É como abrir mais caixas em um supermercado.
  • Escalonamento vertical: atribui mais recursos (CPU ou memória) aos Pods que já estão em execução. É como dar uma máquina mais rápida para o caixa existente.

O HPA atua sobre recursos de carga de trabalho como Deployments ou StatefulSets, mas não se aplica a objetos que não podem ser escalados, como DaemonSets.

Como funciona o HPA: O ciclo de controle​

O HPA não é apenas um comando: é um recurso de API e um controlador que roda dentro do Control Plane do Kubernetes.

O controlador HPA opera como um loop de controle executado periodicamente. O intervalo padrão é de 15 segundos.

1. O loop do HPA

Durante cada ciclo (padrão de 15 segundos), o HPA segue estes passos:

  1. Consulta de métricas: o controlador consulta a utilização de recursos (CPU, memória, etc.) através das APIs de métricas (como metrics.k8s.io ou custom.metrics.k8s.io).
  2. Seleção de Pods: encontra o recurso-alvo (scaleTargetRef) e seleciona os Pods associados.
  3. Cálculo: calcula o número de réplicas desejados para atingir o valor alvo da métrica.
  4. Ação: se necessário (e se o resultado do cálculo exceder a tolerância), ajusta o número de réplicas de recurso-alvo (Deployment ou StatefulSet)

2. A fórmula de cálculo

O HPA usa uma fórmula de proporção simples para determinar quantos Pods são necessários:

desiredReplicas = ceil[currentReplicas × (currentMetricValue / desiredMetricValue)]

Explicando de forma simples:

O HPA divide o valor atual da métrica observada (por exemplo, 200m de uso de CPU) pelo valor alvo desejado (por exemplo, 100m de CPU).

  • Se a proporção for 2.0 (200m/100m), o número de réplicas dobra
  • Se a proporção for 0.5 (50m/100m), o número de réplicas é reduzido pela metade.

Se a proporção estiver muito próxima de 1.0 (dentro da tolerância padrão de 0.1), o HPA não faz nada, evitando flapping.

observação

Para métricas de CPU, o HPA é cauteloso. Pods que ainda não estão prontos (not-yet-ready) são tratados de forma conservadora no cálculo, para que a carga alta durante a inicialização não cause um scale up desnecessário.

Tipos de Métricas Suportadas​

O HPA permite escalonamento com base em quatro tipos principais de métricas (na versão autoscaling/v2):

1. Resource Metrics (métricas de recurso)​

  • O que é: uso de CPU ou memória de todo o Pod. A utilização é calculada como uma porcentagem dos recursos solicitados (requests) pelo Pod.

  • Exemplo: manter a utilização média de CPU em 60%.

type: Resource
resource:
  name: cpu
  target:
    type: Utilization
    averageUtilization: 60

2. Container Resource Metrics​

  • O que é: uso de recursos de um container individual dentro de um Pod. Útil quando um Pod tem vários containers, mas apenas um é o gargalo.
type: ContainerResource
containerResource:
  name: cpu
  container: application
  target:
    type: Utilization
    averageUtilization: 60

3. Custom Metrics (métricas personalizadas)​

  • O que é: Métricas específicadas da aplicação, como taxa de pedidos HTTP por segundo ou tamanho da fila de mensagens. Exige um adaptador de métricas personalizado (API custom.metrics.k8s.io).

  • Exemplo: Manter em média 1000 requisições HTTP por segundo por Pod.

type: Pods
pods:
  metric:
    name: http_requests_per_second
  target:
    type: AverageValue
    averageValue: "1000"

4. Múltiplas métricas​

  • O que é: você pode especificar várias métricas simultaneamente. O HPA calcula as réplicas necessárias para cada métrica e escolhe o maior valor. Isso garante que a aplicação esteja sempre dimensionada para a métrica que está sendo o maior gargalo.

Comportamento de escalonamento configurável (anti-flapping)​

Por padrão, o HPA age de forma bastante agressiva, especialmente no aumento de escala. Se as métricas da aplicação flutuam muito, isso pode levar ao flapping: o HPA adicionando o removendo Pods a cada 15 segundos, o que é ineficiente e estressa o cluster.

Para evitar isso, o HPA na versão autoscaling/v2 permite configurar o comportamento (campo behavior), dando controle fino sobre as ações de scale up (aumentar) e scale down (diminuir).

A chave: janela de estabilização (stabilizationWindowSeconds)

A janela de estabilização é a defesa do HPA contra o flapping. É um período que o HPA deve "esperar" antes de tomar uma decisão, garantindo que a tendência da métrica é estável e não apenas um pico momentâneo.

Para o scale down (redução de escala)

  • Padrão: 300 segundos (5 minutos)
  • Como funciona: o HPA só reduz o número de réplicas se o número de Pods desejado tiver sido igual ou inferior ao valor atual durante todo o período da janela de estabilização.
  • Motivo: evita que uma queda momentânea no tráfego faça os Pods serem terminados, apenas para serem recriados 30 segundos depois quando o tráfego volta.

Para o scale up (aumenta de escala)

  • Padrão: 0 segundos
  • Como funciona: por padrão, o aumento de escala é imediato assim que o cálculo o exige, garantindo que a aplicação responda rapidamente a um pico de carga. Você pode configurar uma janela de estabilização aqui também, se a métrica for muito volátil e você souber que os picos são temporários.

Políticas de escalonamento (policies)

Além da janela de estabilização, você pode definir regras explícitas sobre a rapidez com que a escala pode mudar:

Tipo de políticaDescrição
PercentLimita a mudança a uma porcentagem do número atual de Pods num período.
PodsLimita a mudança a um número fixo de Pods num período.

O HPA pode ter múltiplas políticas. Por padrão, usa selectPolicy: Maxno scale up (escolhe a política que resulta no maior aumento de Pods) e selectPolicy: Min no scale down (escolhe a política mais conservadora para reduzir).

Usando autoscaling/v2, é possível configurar comportamentos separados via campo behavior:

behavior:
  scaleUp:
    stabilizationWindowSeconds: 0
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
    - type: Pods
      value: 4
      periodSeconds: 15
    selectPolicy: Max

  scaleDown:
    stabilizationWindowSeconds: 300
    policies:
    - type: Percent
      value: 50
      periodSeconds: 15
    - type: Pods
      value: 2
      periodSeconds: 60
    selectPolicy: Min

Prática: testando o HPA no cluster​

Pré-requisitos​

  • Cluster Kubernetes rodando
  • kubectl configurado
  • Metrics Server instalado

1. Instalar o Metrics Server​

O Metrics Server é essencial para o HPA funcionar, pois fornece as métricas de CPU e memória dos Pods.

kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

Configuração para ambientes de testes​

Se estiver usando um cluster local (kubeadm em VMs, minikube, kind, k3s), pode ser necessário adicionar a flag --kubelet-insecure-tls, porque o kubelet usa certificado autoassinado.

kubectl edit deployment metrics-server -n kube-system

Adicionar aos args do container: - --kubelet-insecure-tls

    spec:
      containers:
      - args:
        - --cert-dir=/tmp
        - --secure-port=10250
        - --kubelet-preferred-address-types=InternalIP,ExternalIP,Hostname
        - --kubelet-use-node-status-port
        - --metric-resolution=15s
        - --kubelet-insecure-tls
aviso

Essa flag desabilita a verificação do certificado do kubelet. É aceitável em testes, mas não use em produção - lá o caminho correto é configurar certificados válidos para os kubelets.

2. Criar o Deployment​

Vamos usar uma imagem do nginx simples com recursos definidos

deployment-hpa.yaml

apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: nginx-hpa
  name: nginx-hpa
  namespace: nginx
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nginx-hpa
  template:
    metadata:
      labels:
        app: nginx-hpa
    spec:
      containers:
      - image: nginx
        name: nginx-hpa
        resources:
          requests:
            cpu: "200m"          # base para o cálculo do HPA
            memory: 250Mi        # base para o cálculo do HPA
          limits:
            cpu: "500m"          # teto de CPU do container
            memory: 500Mi        # teto de memória do container

Campos importantes

CPU:

  • requests.cpu: "200m" — quantidade de CPU garantida ao container. É esta a base do cálculo de utilização do HPA.
  • limits.cpu: "500m" — teto que o container pode usar. Ao atingir o limite, o container é throttled (desacelerado), não terminado.

Memória:

  • requests.memory: 250Mi — memória garantida ao container, e base do cálculo de utilização do HPA.
  • limits.memory: 500Mi — teto de memória. Se ultrapassar, o container é terminado por OOMKilled.

Réplicas:

  • replicas: 1 — valor inicial. O HPA vai ajustar automaticamente para minReplicas ou mais.
O HPA calcula a utilização como porcentagem do request, nunca do limit

Com request.cpu: 200me alvo de 50%:

  • CPU a 100m = 50% de utilização (100m / 200m) -> está exatamente no alvo
  • CPU a 200m = 100% de utilização (200m / 200m) -> escala

Com requests.memory: 250Mie alvo de 50%:

  • Memória a 125Mi = 50% de utilização (125Mi / 250Mi)

Por isso o request nunca deve ser um chute: ele é o denominador de toda decisão do HPA.

Aplique o deployment no cluster:

kubectl create -f deployment-hpa.yaml

Verifica os pods criados:

kubectl get pods -l app=nginx-hpa -n nginx
NAME                         READY   STATUS    RESTARTS   AGE
nginx-hpa-64bc976b69-q5tj9   1/1     Running   0          19s

3. Criar o Service​

service-nginx-hpa.yaml

apiVersion: v1
kind: Service
metadata:
  name: nginx
  namespace: nginx
spec:
  selector:
    app: nginx-hpa
  ports:
  - port: 80
    targetPort: 80

Aplique o service no cluster:

kubectl create -f service-nginx-hpa.yaml

Verifica o serviço criado:

kubectl get svc nginx -n nginx
NAME    TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
nginx   ClusterIP   10.98.150.202   <none>        80/TCP    113s

4. Configura o HPA​

hpa-nginx.yaml

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx-hpa
  namespace: nginx
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-hpa
  minReplicas: 3              # mínimo de 3 pods sempre
  maxReplicas: 5              # máximo de 5 pods
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50    # escala quando CPU média > 50% do request (100m)
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 50    # escala quando memória média > 50% do request (125Mi)
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60    # aguarda 60s antes de confirmar
      policies:
      - type: Percent
        value: 100                      # pode dobrar o número de pods
        periodSeconds: 10               # a cada 10 segundos
    scaleDown:
      stabilizationWindowSeconds: 60    # aguarda 60s antes de remover
      policies:
      - type: Percent
        value: 50                       # remove no máximo 50% dos pods por vez
        periodSeconds: 60               # a cada 60 segundos

Explicação das métricas​

type: Resource

  • Métricas de CPU/memória do Pod inteiro.
  • averageUtilization: 50 = a média entre os Pods atingiu 50% do request.
  • Com duas métricas declaradas, o HPA calcula as réplicas para cada uma e usa o maior resultado. Basta CPU ou memória passar do alvo para escalar.
Explicação do behavior​

scaleUp:

  • stabilizationWindowSeconds: 60 -> aguarda 1 minuto confirmando que realmente precisa escalar.
  • value: 100 com type: Percent -> pode dobrar o número de Pods (aumentar 100%) a cada 10s.

scaleDown:

  • stabilizationWindowSeconds: 60 -> aguarda 1 minuto antes de remover Pods.
  • value: 50 com periodSeconds: 60 -> remove no máximo metada dos Pods por minuto, de forma gradual.
Por que 50% no scale down, e não 100%

Com value: 100 no scale down, o HPA pode cair direto para minReplicas num único passo. Em ambiente de testes isso é só mais rápido de observar; em produção, uma redução gradual evita derrubar capacidade de uma vez se a queda de tráfego for temporária.

Aplique o HPA no cluster:

kubectl create -f hpa-nginx.yaml

6. Testar o HPA​

Observar o escalonamento inicial​

Como configuramos minReplicas: 3, o HPA cria 3 Pods automaticamente:

kubectl get hpa -n nginx && echo "" && kubectl get pods -l app=nginx-hpa -n nginx
NAME                         READY   STATUS    RESTARTS   AGE
nginx-hpa-64bc976b69-6knd5   1/1     Running   0          15m
nginx-hpa-64bc976b69-9sq6t   1/1     Running   0          15m
nginx-hpa-64bc976b69-q5tj9   1/1     Running   0          43m

Gerar carga para testar o scale up​

Com requests.cpu: 200m e alvo de 50%, o HPA escala quando a média de CPU passar de 100m.

Todos os Pods de teste recebem a label teste=carga, para poderem ser removidos depois sem afetar nada mais do namespace.

Método 1: carga leve (escalonamento gradual)

Cria 3 Pods gerando carga moderada:

for i in {1..3}; do
  kubectl run load-test-$i \
    --image=busybox \
    --restart=Never \
    --labels=teste=carga \
    -n nginx \
    -- /bin/sh -c "while true; do wget -q -O- http://nginx > /dev/null; sleep 0.05; done" &
done

Observe o comportamento em outro terminal:

kubectl get hpa -n nginx && echo "" && kubectl get pods -l app=nginx-hpa -n nginx

Você verá:

NAME        REFERENCE              TARGETS                       MINPODS   MAXPODS   REPLICAS   AGE
nginx-hpa   Deployment/nginx-hpa   cpu: 4%/50%, memory: 1%/50%   3         5         3          39m

NAME                         READY   STATUS    RESTARTS   AGE
nginx-hpa-64bc976b69-6knd5   1/1     Running   0          39m
nginx-hpa-64bc976b69-9sq6t   1/1     Running   0          39m
nginx-hpa-64bc976b69-q5tj9   1/1     Running   0          68m
  • A CPU dos Pods começa a subir: ~1m -> 6m
  • Média ainda fica abaixo de 100m, então o HPA mantém 3 réplicas

Método 2: carga pesada (forçar scale up)

Cria 20 Pods gerando carga agressiva (sem sleep entre as requisições):

for i in {1..20}; do
  kubectl run heavy-load-$i \
    --image=busybox \
    --restart=Never \
    --labels=teste=carga \
    -n nginx \
    -- /bin/sh -c "while true; do wget -q -O- http://nginx > /dev/null; done" &
done

Observe o comportamento em outro terminal:

kubectl get hpa -n nginx && echo "" && kubectl get pods -l app=nginx-hpa -n nginx

Você verá:

NAME        REFERENCE              TARGETS                        MINPODS   MAXPODS   REPLICAS   AGE
nginx-hpa   Deployment/nginx-hpa   cpu: 70%/50%, memory: 1%/50%   3         5         5          55m

NAME                         READY   STATUS    RESTARTS   AGE
nginx-hpa-64bc976b69-6knd5   1/1     Running   0          55m
nginx-hpa-64bc976b69-85mv8   1/1     Running   0          50s
nginx-hpa-64bc976b69-9sq6t   1/1     Running   0          55m
nginx-hpa-64bc976b69-nhjns   1/1     Running   0          50s
nginx-hpa-64bc976b69-q5tj9   1/1     Running   0          83m
  • A CPU dos Pods sobe rapidamente: ~20m -> ~50m -> ~70m
  • A média ultrapassa 100m
  • Após a janela de estabilização de 60s, o HPA escala de 3 -> 5

7. Parar o teste de carga​

Remove apenas os Pods de teste, pela label que definimos:

kubectl delete pod -l teste=carga --force --grace-period=0 -n nginx
cuidado

Evite kubectl delete pod -l run .... A label run é aplicada pelo kubectl run a qualquer Pod criado assim no namespace, então esse comando pode apagar Pods que não fazem parte do lab. Por isso usamos uma label própria (teste=carga).

Observe o comportamento:

  • A CPU dos Pods cai
  • 0 HPA aguarda os 60s da janela de estabilização
  • Depois de confirmar que a carga está baixa, começa a remover Pods até chegar em minReplicas: 3

8. Limpeza do lab de teste​

kubectl delete pod -l teste=carga --force --grace-period=0 --ignore-not-found -n nginx
kubectl delete hpa nginx-hpa --ignore-not-found -n nginx
kubectl delete svc nginx --ignore-not-found -n nginx
kubectl delete deployment nginx-hpa --ignore-not-found -n nginx

O Metrics Server pode ficar instalado - é útil para kubectl top no dia a dia. Se quiser remover:

kubectl delete -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

Pronto! Seu HPA está configurado e testado.
