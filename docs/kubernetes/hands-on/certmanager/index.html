Cert-Manager com Let's Encrypt e Cloudflare no Kubernetes: teoria e prática

Fundamentos​

O que é o cert-manager?​

O cert-manager é um controlador do Kubernetes que automatiza a emissão, a renovação e o armazenamento de certificados TLS. Ele conversa com Autoridades Certificadoras (CAs) como o Let's Encrypt e entrega o resultado como um Secret do Kubernetes, pronto para ser usado por qualquer Ingress.

Ele trabalha com CRDs (Custom Resource Definitions). Você declara o que quer, e o cert-manager faz o resto:

RecursoPara que serve
IssuerDefine quem emite os certificados, válido apenas no namespace onde foi criado
ClusterIssuerO mesmo que o Issuer, mas válido em todo o cluster
CertificateDeclara qual certificado você quer (domínios, nome do Secret, emissor)
CertificateRequestPedido interno de assinatura, gerado pelo cert-manager a partir do Certificate
OrderRepresenta o pedido junto à CA (protocolo ACME)
ChallengeRepresenta o desafio de validação do domínio

Você só cria o ClusterIssuer e o Certificate. Os outros três são criados sozinhos, e são eles que você inspeciona quando algo dá errado (veja a seção de troubleshooting).

O que é o Let's Encrypt?​

O Let's Encrypt é uma CA gratuita e automatizada. Ele usa o protocolo ACME para validar que você controla o domínio e emitir o certificado, sem nenhum processo manual.

Os certificados têm validade curta (hoje, 90 dias), e o Let's Encrypt já anunciou a redução gradual desse prazo nos próximos anos. Isso torna a renovação automática uma necessidade, não um luxo: ninguém consegue renovar à mão, com segurança, certificados que vencem a cada poucas semanas.

Os desafios de validação​

Antes de emitir, a CA precisa de uma prova de que o domínio é seu. Existem dois desafios que o cert-manager suporta:

HTTP-01DNS-01
Como validaServe um arquivo em http://dominio/.well-known/...Cria um registro TXT _acme-challenge no DNS
Cluster precisa estar acessível pela internetSim (porta 80)Não
Suporta certificado wildcard (*.dominio)NãoSim
Precisa de credencial do provedor DNSNãoSim
E o TLS-ALPN-01?

O Let's Encrypt também oferece esse desafio, mas o cert-manager não o suporta. Na prática, a escolha é sempre entre HTTP-01 e DNS-01.

Neste laboratório usamos DNS-01 com Cloudflare, por dois motivos: o cluster é um homelab que não está exposto diretamente à internet, e o DNS-01 permite emitir um certificado wildcard.

Como o fluxo funciona​

  1. Você cria o ClusterIssuer apontando para o Let's Encrypt e para o seu provedor DNS (Cloudflare)
  2. Você cria um Certificate pedindo os domínios desejados
  3. O cert-manager gera a chave privada e cria um CertificateRequest, depois um Order e um Challenge
  4. Pela API do Cloudflare, ele cria um registro TXT _acme-challenge.seudominio
  5. O Let's Encrypt consulta o DNS, encontra o registro e libera a emissão
  6. O cert-manager remove o registro TXT, grava o certificado no Secret e passa a monitorá-lo
  7. Antes do vencimento (por padrão, quando restam 30 dias), ele repete o processo sozinho

Atenção ao wildcard​

Um certificado para *.lab.devopsr66.com cobre app.lab.devopsr66.com, api.lab.devopsr66.com e qualquer outro subdomínio de um nível. Mas ele não cobre o próprio lab.devopsr66.com, nem x.y.lab.devopsr66.com. Por isso o certificado deste lab lista os dois nomes.

Staging × produção​

O Let's Encrypt tem dois ambientes:

AmbienteURL do servidor ACMECertificado confiávelLimites
Staginghttps://acme-staging-v02.api.letsencrypt.org/directoryNão (o navegador acusa erro)Muito folgados
Produçãohttps://acme-v02.api.letsencrypt.org/directorySimRígidos (ex: 5 certificados duplicados por semana)
Teste sempre no staging primeiro

Se você errar a configuração em produção e repetir a emissão várias vezes, bate no limite de requisições e fica bloqueado por dias. O staging faz exatamente o mesmo fluxo, sem risco. Valide tudo nele e só depois troque para produção. É o que fazemos neste lab.

Prática: emitindo certificados com Cloudflare​

O que você vai fazer​

  • Instalar o cert-manager com Helm
  • Criar um token de API no Cloudflare com permissão mínima
  • Criar ClusterIssuers (staging e produção) com o solver DNS-01 do Cloudflare
  • Emitir um certificado wildcard, primeiro no staging e depois em produção
  • Comprovar o certificado e usá-lo em um Ingress

Pré-requisitos​

  • Cluster Kubernetes funcional, com kubectl e Helm configurados
  • Um Ingress Controller instalado. Neste lab usamos o Traefik exposto pelo MetalLB, como no laboratório MetalLB, Traefik e Cloudflare Tunnel (o Ingress-NGINX foi aposentado em março de 2026 e não recebe mais correções)
  • Um domínio com a zona ativa no Cloudflare (os nameservers do domínio apontando para o Cloudflare)
  • Acesso ao painel do Cloudflare para criar um token de API

Etapa 1 — Instalar o cert-manager​

Descubra a versão mais recente do chart e fixe-a, para que a instalação seja reprodutível:

helm repo add jetstack https://charts.jetstack.io
helm repo update
helm search repo jetstack/cert-manager

Saída esperada:

NAME                    CHART VERSION   APP VERSION   DESCRIPTION
jetstack/cert-manager   v1.21.3         v1.21.3       A Helm chart for cert-manager

A coluna CHART VERSION é a que vai no --version. Neste lab usamos a v1.21.3; se você estiver lendo isto mais tarde e o helm search mostrar outra versão, pode usar a mais recente.

Crie o arquivo cert-manager-values.yaml:

crds:
  enabled: true

extraArgs:
  - --dns01-recursive-nameservers-only
  - --dns01-recursive-nameservers=1.1.1.1:53,1.0.0.1:53

O que esse arquivo faz:

  • crds.enabled: true → instala as CRDs junto com o chart. Substitui o antigo installCRDs=true, que está descontinuado
  • extraArgs → faz o cert-manager conferir a propagação do registro TXT diretamente nos DNS públicos do Cloudflare, em vez de usar o DNS do cluster ou do seu roteador. Em homelab, com DNS local ou cache (roteador, Pi-hole, CoreDNS), essa checagem costuma falhar sem esse ajuste

Instale:

helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --create-namespace \
  --version v1.21.3 \
  -f cert-manager-values.yaml

O --version fixa a versão do chart: quem repetir o lab daqui a meses instala exatamente o mesmo cert-manager, em vez de uma versão mais nova que pode ter mudado algum comportamento.

Verifique:

kubectl get pods -n cert-manager

Saída esperada:

NAME                                       READY   STATUS    RESTARTS   AGE
cert-manager-586ddf675-fxkxk               1/1     Running   0          39s
cert-manager-cainjector-59b6d9ff44-828nv   1/1     Running   0          40s
cert-manager-webhook-8449c649d5-qzfbp      1/1     Running   0          2m4s

São três componentes: o controller (faz o trabalho), o cainjector (injeta CAs nos webhooks) e o webhook (valida os recursos). Os três precisam estar Running antes de seguir.

Etapa 2 — Criar o token de API no Cloudflare​

O cert-manager precisa de uma credencial para criar e remover os registros TXT. Não use a Global API Key: ela dá acesso a toda a conta. Use um API Token com escopo mínimo.

No painel do Cloudflare:

  1. My Profile → API Tokens → Create Token
  2. Use o modelo Edit zone DNS (ou crie um personalizado)
  3. Permissões:
    • Zone → DNS → Edit
    • Zone → Zone → Read
  4. Em Zone Resources, selecione apenas a zona do seu domínio (devopsr66.com)
  5. Crie o token e copie o valor (ele só é exibido uma vez)

Crie o Secret no cluster sem deixar o token no histórico do shell:

read -rs CF_TOKEN

Cole o token (nada aparece na tela) e pressione Enter. Depois:

kubectl create secret generic cloudflare-api-token \
  --from-literal=api-token="$CF_TOKEN" \
  -n cert-manager

Valide o token antes de seguir (evita esperar um desafio falhar para descobrir um token errado):

curl -s -H "Authorization: Bearer $CF_TOKEN" \
  https://api.cloudflare.com/client/v4/user/tokens/verify

Saída esperada (trecho):

{"result":{"id":"...","status":"active"},"success":true,"errors":[],"messages":[...]}

Limpe a variável:

unset CF_TOKEN
O Secret precisa estar no namespace do cert-manager

Um ClusterIssuer só enxerga Secrets do namespace do próprio cert-manager (cert-manager). Se o Secret estiver em outro namespace, o emissor fica com erro de secret not found. E, como o namespace é criado pelo --create-namespace da Etapa 1, o Secret só pode ser criado depois da instalação.

Etapa 3 — Criar os ClusterIssuers​

Crie o arquivo clusterissuers.yaml com os dois ambientes:

apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-staging
spec:
  acme:
    server: https://acme-staging-v02.api.letsencrypt.org/directory
    email: voce@exemplo.com          # Substitua pelo seu e-mail
    privateKeySecretRef:
      name: letsencrypt-staging-account-key
    solvers:
      - dns01:
          cloudflare:
            apiTokenSecretRef:
              name: cloudflare-api-token
              key: api-token
---
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: voce@exemplo.com          # Substitua pelo seu e-mail
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
      - dns01:
          cloudflare:
            apiTokenSecretRef:
              name: cloudflare-api-token
              key: api-token

Entendendo o manifesto:

CampoFunção
serverEndereço ACME da CA (staging ou produção)
emailContato registrado na conta ACME. O Let's Encrypt avisa por aqui se algo vencer sem renovar
privateKeySecretRefSecret onde o cert-manager guarda a chave da conta ACME (criado por ele, não por você)
solvers[].dns01.cloudflareDiz que a validação será feita criando TXT no Cloudflare
apiTokenSecretRefAponta para o Secret criado na Etapa 2 e para a chave api-token dentro dele

Aplique:

kubectl apply -f clusterissuers.yaml

Verifique:

kubectl get clusterissuer

Saída esperada:

NAME                  READY   AGE
letsencrypt-prod      True    15s
letsencrypt-staging   True    15s

READY: True significa que a conta ACME foi registrada com sucesso na CA. Para ver os detalhes:

kubectl describe clusterissuer letsencrypt-staging

Saída esperada (trecho):

Status:
  Acme:
    Last Registered Email:  voce@exemplo.com
    Uri:                    https://acme-staging-v02.api.letsencrypt.org/acme/acct/...
  Conditions:
    Message:  The ACME account was registered with the ACME server
    Reason:   ACMEAccountRegistered
    Status:   True
    Type:     Ready

Etapa 4 — Emitir um certificado no staging​

Crie o namespace do lab:

kubectl create namespace lab-certmanager

Crie o arquivo certificate.yaml:

apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: lab-cert
  namespace: lab-certmanager
spec:
  secretName: lab-tls
  issuerRef:
    name: letsencrypt-staging
    kind: ClusterIssuer
  dnsNames:
    - lab.devopsr66.com
    - "*.lab.devopsr66.com"

Entendendo o manifesto:

CampoFunção
secretNameNome do Secret onde o certificado e a chave serão gravados
issuerRefQual emissor usar (por ora, o staging)
dnsNamesDomínios cobertos. Os dois nomes são necessários: o wildcard não cobre o domínio-base

O Secret é criado no mesmo namespace do Certificate, e é nesse namespace que o Ingress vai precisar estar.

kubectl apply -f certificate.yaml

Em outro terminal, acompanhe a emissão:

kubectl get certificate -n lab-certmanager -w

Saída esperada:

NAME       READY   SECRET    AGE
lab-cert   False   lab-tls   3s
lab-cert   True    lab-tls   52s

Enquanto está False, o desafio DNS está em andamento. Veja:

kubectl get challenges -n lab-certmanager

Saída esperada (durante a emissão):

NAME                              STATE     DOMAIN              AGE
lab-cert-1-1234567890-1234567890  pending   lab.devopsr66.com   10s
lab-cert-1-1234567890-9876543210  pending   lab.devopsr66.com   10s

São dois Challenges, porque o certificado tem dois nomes. Nesse intervalo, se você abrir DNS → Records no painel do Cloudflare, verá registros TXT _acme-challenge.lab aparecendo. Eles somem sozinhos assim que a validação termina.

Quando o certificado ficar READY: True, inspecione o histórico:

kubectl describe certificate lab-cert -n lab-certmanager

Saída esperada (trecho dos eventos):

Events:
  Type    Reason     Age   From                                       Message
  ----    ------     ----  ----                                       -------
  Normal  Issuing    62s   cert-manager-certificates-trigger          Issuing certificate as Secret does not exist
  Normal  Generated  62s   cert-manager-certificates-key-manager      Stored new private key in temporary Secret resource "lab-cert-xxxxx"
  Normal  Requested  62s   cert-manager-certificates-request-manager  Created new CertificateRequest resource "lab-cert-1"
  Normal  Issuing    10s   cert-manager-certificates-issuing          The certificate has been successfully issued

Essa sequência é o ciclo completo, em quatro eventos: gatilho, chave gerada, pedido criado, certificado emitido.

Etapa 5 — Comprovar o conteúdo do Secret​

Confirme que o Secret foi criado:

kubectl get secret lab-tls -n lab-certmanager

Saída esperada:

NAME      TYPE                DATA   AGE
lab-tls   kubernetes.io/tls   2      1m

O tipo kubernetes.io/tls é o que o Ingress espera, com duas chaves de dados. Para ver quais:

kubectl describe secret lab-tls -n lab-certmanager

Saída esperada (trecho):

Name:         lab-tls
Namespace:    lab-certmanager
Type:  kubernetes.io/tls

Data
====
tls.crt:  5867 bytes
tls.key:  1675 bytes

Agora leia o conteúdo real do certificado:

kubectl get secret lab-tls -n lab-certmanager -o jsonpath='{.data.tls\.crt}' \
  | base64 -d \
  | openssl x509 -noout -issuer -dates -ext subjectAltName

Saída esperada:

issuer=C = US, O = Let's Encrypt, CN = (STAGING) Dastardly Durum YR1
notBefore=Oct 31 02:21:01 2026 GMT
notAfter=Jan  3 02:21:00 2027 GMT
X509v3 Subject Alternative Name: 
    DNS:*.lab.devopsr66.com, DNS:lab.devopsr66.com

Três coisas para conferir aqui:

  • issuer com (STAGING) → o certificado veio do ambiente de testes (e por isso não é confiável para navegadores, como esperado)
  • notAfter − notBefore = 90 dias → a validade do Let's Encrypt
  • Os dois nomes em Subject Alternative Name → wildcard e domínio-base

Etapa 6 — Trocar para produção​

Com o staging funcionando, a configuração está validada. Edite o certificate.yaml, trocando apenas o emissor:

  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer

Aplique:

kubectl apply -f certificate.yaml

O cert-manager percebe que o emissor mudou e reemite o certificado. Acompanhe:

kubectl get certificate -n lab-certmanager -w

Saída esperada:

NAME       READY   SECRET    AGE
lab-cert   False   lab-tls   8m
lab-cert   True    lab-tls   8m52s

Dois detalhes para não se confundir:

  • O READY volta para False assim que você aplica: é o sinal de que a reemissão começou, e não de que algo deu errado. Ele só volta a True quando o novo certificado é emitido, o que leva alguns minutos (o desafio DNS-01 precisa propagar).
  • A coluna AGE é a idade do objeto Certificate, não do certificado emitido. Ela nunca reinicia na troca de emissor, então continuar mostrando 8m não significa que o certificado ainda é o de staging.

Para ver o que o cert-manager decidiu fazer, consulte os eventos:

kubectl describe certificate lab-cert -n lab-certmanager

Saída esperada (trecho dos eventos):

Events:
  Type    Reason     Age   From                                       Message
  ----    ------     ----  ----                                       -------
  Normal  Issuing    56s   cert-manager-certificates-trigger          Issuing certificate as Secret was previously issued by "ClusterIssuer.cert-manager.io/letsencrypt-staging"
  Normal  Generated  56s   cert-manager-certificates-key-manager      Stored new private key in temporary Secret resource "lab-cert-xxxxx"
  Normal  Requested  55s   cert-manager-certificates-request-manager  Created new CertificateRequest resource "lab-cert-2"
  Normal  Issuing    10s   cert-manager-certificates-issuing          The certificate has been successfully issued

A mensagem previously issued by ... letsencrypt-staging (motivo IncorrectIssuer) comprova que o cert-manager detectou a troca de emissor sozinho. Repare também que o CertificateRequest agora é o lab-cert-2, o segundo pedido deste Certificate.

Confirme que agora o emissor é o de produção:

kubectl get secret lab-tls -n lab-certmanager -o jsonpath='{.data.tls\.crt}' \
  | base64 -d \
  | openssl x509 -noout -issuer -dates

Saída esperada:

issuer=C = US, O = Let's Encrypt, CN = YR1
notBefore=Oct 31 02:50:08 2026 GMT
notAfter=Jan 29 02:50:07 2027 GMT

Sem o (STAGING): este é um certificado válido e confiável.

Etapa 7 — Usar o certificado em um Ingress​

Antes do Ingress, precisamos de uma aplicação para responder. Usaremos o whoami, a mesma do laboratório MetalLB, Traefik e Cloudflare Tunnel: ela devolve os dados da requisição. Crie o arquivo app.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: whoami
  namespace: lab-certmanager
spec:c
  replicas: 1
  selector:
    matchLabels:
      app: whoami
  template:
    metadata:
      labels:
        app: whoami
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.10.2
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: whoami
  namespace: lab-certmanager
spec:
  selector:
    app: whoami
  ports:
    - port: 80
      targetPort: 80

Crie o arquivo ingress.yaml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: whoami
  namespace: lab-certmanager
  annotations:
    traefik.ingress.kubernetes.io/router.entrypoints: websecure
spec:
  ingressClassName: traefik
  tls:
    - hosts:
        - lab.devopsr66.com
      secretName: lab-tls
  rules:
    - host: lab.devopsr66.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: whoami
                port:
                  number: 80

Entendendo o manifesto:

  • ingressClassName: traefik → define que o Traefik é o controller responsável por este Ingress
  • router.entrypoints: websecure → o Traefik atende esta rota somente em HTTPS (porta 443). Annotations com o prefixo traefik.ingress.kubernetes.io/ são específicas do Traefik
  • tls.secretName: lab-tls → o Secret emitido pelo cert-manager. Ele precisa estar no mesmo namespace do Ingress

Aplique os dois arquivos:

kubectl apply -f app.yaml
kubectl apply -f ingress.yaml

Descubra o IP que o MetalLB atribuiu ao Traefik, que é o ponto de entrada de todas as aplicações:

kubectl get svc traefik -n traefik

Saída esperada:

NAME      TYPE           CLUSTER-IP      EXTERNAL-IP       PORT(S)
traefik   LoadBalancer   10.96.205.174   10.10.20.200   80:30080/TCP,443:30443/TCP

O EXTERNAL-IP é o primeiro IP livre do pool do MetalLB (10.10.20.200-10.10.20.220). O seu pode ser outro, conforme o pool que você criou.

Confirme também que o Ingress foi aceito:

kubectl get ingress -n lab-certmanager

Saída esperada:

NAME     CLASS     HOSTS               ADDRESS   PORTS     AGE
whoami   traefik   lab.devopsr66.com             80, 443   30s

A coluna ADDRESS pode ficar vazia dependendo da configuração do chart do Traefik. Isso não impede o funcionamento: o IP de entrada é o EXTERNAL-IP do Service, mostrado acima.

Teste o certificado sem depender de DNS, usando --resolve para apontar o nome diretamente para esse IP:

curl -v --resolve lab.devopsr66.com:443:10.10.20.200 https://lab.devopsr66.com 2>&1 \
  | grep -E "subject:|issuer:|expire date|SSL certificate verify|HTTP/"
Rota para a rede do laboratório

O IP 10.10.20.200 está na rede 10.10.20.0/24. A máquina que executa o curl precisa ter rota para essa rede passando pelo host das VMs.

Saída esperada:

*  subject: CN=lab.devopsr66.com
*  expire date: Jan 27 22:25:09 2027 GMT
*  issuer: C=US; O=Let's Encrypt; CN=R12
*  SSL certificate verify ok.
< HTTP/2 200

SSL certificate verify ok é a prova final: o curl validou a cadeia de confiança sem nenhum -k (que ignoraria erros). O certificado foi emitido pelo Let's Encrypt, automaticamente, e entregue ao Ingress.

Quer acessar pelo navegador?

No Cloudflare, crie um registro A lab apontando para o IP do Ingress, no modo DNS only (nuvem cinza). Como o IP é privado, funciona apenas dentro da sua rede, o que é exatamente o cenário de um homelab.

Ingress com certificado automático

Existe um atalho: adicionar ao Ingress a anotação cert-manager.io/cluster-issuer: letsencrypt-prod. O cert-manager então cria o Certificate sozinho a partir do bloco tls do Ingress. Aqui criamos o Certificate à mão de propósito, para você ver cada recurso envolvido. Em uso real, a anotação costuma ser mais prática. Mas para certificados wildcard compartilhados por vários Ingress, manter um Certificate explícito, como fizemos, é melhor.

Troubleshooting​

Quando um certificado não fica Ready, siga a cadeia de recursos de cima para baixo. O erro quase sempre aparece em um dos níveis abaixo do Certificate:

kubectl describe certificate lab-cert -n lab-certmanager
kubectl describe certificaterequest -n lab-certmanager
kubectl describe order -n lab-certmanager
kubectl describe challenge -n lab-certmanager
SintomaCausa provávelComo resolver
Challenge parado em pending com propagation check failedO cert-manager não enxerga o TXT pelo DNS que está usandoConfira os extraArgs de DNS recursivo da Etapa 1
Erro 403 ou Authentication error do CloudflareToken sem permissão ou sem acesso à zonaRecrie o token com Zone:DNS:Edit e Zone:Zone:Read na zona correta
ClusterIssuer com secret not foundSecret fora do namespace cert-manager, ou nome/chave erradosConfira o nome e o key: api-token
Erro de CAAO domínio tem registro CAA que não autoriza o Let's EncryptAdicione um CAA para letsencrypt.org ou remova o CAA restritivo
too many certificates already issuedLimite de produção atingidoAguarde a janela expirar e use o staging para testes
Navegador acusa certificado inválidoCertificado de staging em usoTroque o issuerRef para letsencrypt-prod
Navegador mostra TRAEFIK DEFAULT CERTO Traefik não achou o Secret TLS: ele não existe no namespace do Ingress ou o secretName está erradoO Secret precisa estar no mesmo namespace do Ingress, com o mesmo nome do secretName
404 page not foundingressClassName incorreto, host diferente do usado na requisição, ou acesso por HTTP com a rota restrita a websecureConfira o ingressClassName: traefik, o host e use https://

Limpeza do laboratório​

kubectl delete namespace lab-certmanager

Isso remove o Certificate, o Secret, o Ingress, o Deployment e o Service. Os ClusterIssuers continuam existindo, e é essa a ideia: eles são reaproveitáveis em qualquer outro namespace.

Se quiser remover também o cert-manager:

helm uninstall cert-manager -n cert-manager
As CRDs permanecem

Por padrão, o helm uninstall não remove as CRDs do cert-manager, para proteger certificados existentes de uma remoção acidental. Se quiser removê-las de fato, apague-as manualmente com kubectl delete crd (isso apaga todos os Certificates do cluster).

Conclusão​

Com o cert-manager e o Let's Encrypt integrados via desafio DNS-01 no Cloudflare:

  • Certificados TLS são emitidos e renovados automaticamente, sem intervenção manual
  • O domínio é validado sem expor o cluster à internet, ideal para homelab
  • O certificado wildcard atende todos os subdomínios com um único Secret
  • O token do Cloudflare tem escopo mínimo: só edita DNS, só da zona necessária
  • Testar no staging antes da produção evita bloqueio por limite de requisições
  • Em caso de falha, a cadeia Certificate → CertificateRequest → Order → Challenge mostra exatamente onde parou
