LimitRange no Kubernetes: teoria e prática

Fundamentos​

O que é o LimitRange?​

O LimitRange define restrições e padrões de uso de recursos (CPU, memória e armazenamento) dentro de um namespace.

Ele evita o consumo excessivo ou mal configurado por parte dos Pods, promovendo uma alocação mais previsível dos recursos do cluster. Enquanto o ResourceQuota olha para a soma do namespace inteiro, o LimitRange olha para cada container individualmente.

O que ele faz​

1. Define valores padrão. Aplica automaticamente requests e limits em containers que não os especificam.

2. Impõe mínimos e máximos. Restringem o intervalo de valores aceitáveis que um container pdoe declarar.

3. Influencia a classe de QoS. Com todo Pod passa a ter requestse limits definidos, os Pods deixam de ser BestEffort e passam a ser classificados como Burstable ou Guaranteed.

Estrutura básica​

apiVersion: v1
kind: LimitRange
metadata:
  name: example-limit-range
  namespace: meu-namespace
spec:
  limits:
  - type: Container
    max:
      cpu: "1"
      memory: "1Gi"
    min:
      cpu: "100m"
      memory: "128Mi"
    default:
      cpu: "500m"
      memory: "512Mi"
    defaultRequest:
      cpu: "200m"
      memory: "256Mi"

Campos:

CampoO que fazAge sobre
minValor mínimo permitidoO request do container
maxValor máximo permitidoO limit do container
defaultValor aplicado como limit quando o container não declaralimits
defaultRequestValor aplicado como request quando o container não declararequests
maxLimitRequestRatioProporção máxima entre limit e request (ex: 2 impede um limit mais que 2× o request)Relação entre os dois
typeEscopo da regra: Container, Pod ou PersistentVolumeClaim—
A diferença entre min e max que confunde

min valida os requests, max valida os limits. Por isso, ao testar violações, um Pod que pede pouco falha no min (mensagem citando request), e um Pod que pede demais falha no max (mensagem citando limit). Você vai ver as duas mensagens na prática mais abaixo.

Tipos de escopo​

typeAplica a regra sobre
ContainerCada container individualmente. É o mais usado.
PodA soma de todos os containers do Pod
PersistentVolumeClaimO tamanho solicitado em cada PVC (min/max de storage)

LimitRange e QoS​

A classe de QoS define quem o Kubernetes mata primeiro quando um nó fica sem memória:

ClasseQuando acontecePrioridade de despejo
Guaranteedrequests iguais aos limits em todos os containersÚltimo a ser morto
BurstableTem requests definidos, mas diferentes dos limitsIntermediário
BestEffortNão tem requests nem limitsPrimeiro a ser morto

Como o LimitRange preenche os dois valores, ele elimina Pods BestEffort do namespace. Se default e defaultRequest tiverem valores diferentes (o caso mais comum), os Pods viram Burstable.

LimitRange e ResourceQuota juntos​

Os dois se completam:

  • O ResourceQuota com requests.cpu/limits.cpu definidos obriga todo Pod a declarar recursos - sem isso, o Pod é rejeitado.
  • O LimitRange injeta os valores padrão, fazendo o Pod atender a essa exigência automaticamente

Sem LimitRange, cada pessoa do time precisaria lembrar de declarar requests e limits em todo manifesto.

ResourceQuotaLimitRange
EscopoSoma de todo o namespaceCada container individualmente
Pergunta que responde"O namespace já usou demais?""Este container pediu um valor válido?"
Se não atenderRecurso é rejeitadoRecurso é rejeitado ou recebe o valor padrão

Pontos de atenção​

  • Só vale para Pods criados depois. Pods que já existiam quando o LimitRange foi aplicado não são alterados nem removidos.
  • Se o container declara só limits, o Kubernetes copia os limits para os requests — o defaultRequest do LimitRange não é usado nesse caso.
  • Vários LimitRanges no mesmo namespace são somados, e conflitos entre eles causam erro na criação do Pod. Prefira um único LimitRange por namespace.

Prática: aplicando LimitRange​

Objetivo​

Demonstrar, na práticam como usar o LimitRange para definir restrições de CPU e memória dentro de um namespace, garantindo que todos os Pods sigam limites controlados mesmo quando não especificam nada.

Pré-requisitos​

  1. Um cluster Kubernetes funcional
  2. kubectl configurado
  3. Conhecimento básico sobre Pods e recursos de CPU/memória

Etapa 1 - Criar o namespace do lab​

kubectl create namespace lab-limitrange

Etapa 2 — Criar o LimitRange​

Crie o arquivo limitrange.yaml:

apiVersion: v1
kind: LimitRange
metadata:
  name: default-cpu-mem-limit
  namespace: lab-limitrange
spec:
  limits:
  - default:
      cpu: 500m
      memory: 256Mi
    defaultRequest:
      cpu: 250m
      memory: 128Mi
    min:
      cpu: 100m
      memory: 64Mi
    max:
      cpu: 1
      memory: 512Mi
    type: Container

O que esse manifesto faz:

RegraCPUMemória
Limit padrão (default)500m256Mi
Request padrão (defaultRequest)250m128Mi
Mínimo aceito (min)100m64Mi
Máximo aceito (max)1512Mi

Aplique:

kubectl apply -f limitrange.yaml

Verifique:

kubectl describe limitrange default-cpu-mem-limit -n lab-limitrange

Saída esperada:

Name:       default-cpu-mem-limit
Namespace:  lab-limitrange
Type        Resource  Min   Max    Default Request  Default Limit  Max Limit/Request Ratio
----        --------  ---   ---    ---------------  -------------  -----------------------
Container   cpu       100m  1      250m             500m           -
Container   memory    64Mi  512Mi  128Mi            256Mi          -

Essa tabela é a forma mais rápida de conferir o LimitRange: cada coluna corresponde a um campo do manifesto.

Etapa 3 — Criar um Pod sem requests/limits definidos​

Crie o arquivo pod-sem-limites.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: test-lr-pod
  namespace: lab-limitrange
spec:
  containers:
  - name: test
    image: busybox
    command: ["sh", "-c", "sleep 3600"]

Repare que o manifesto não declara nenhum recurso.

Aplique:

kubectl apply -f pod-sem-limites.yaml

Veja quais recursos foram aplicados automaticamente:

kubectl get pod test-lr-pod -n lab-limitrange -o jsonpath="{.spec.containers[*].resources}"

Saída esperada:

{"limits":{"cpu":"500m","memory":"256Mi"},"requests":{"cpu":"250m","memory":"128Mi"}}

O LimitRange aplicou os valores padrão mesmo sem o manifesto ter especificado nada:

  • limits receberam os valores de default (500m / 256Mi)
  • requests receberam os valores de defaultRequest (250m / 128Mi)

Etapa 4 — Verificar a classe de QoS​

Como o Pod agora tem requests e limits (e eles são diferentes entre si), ele deixou de ser BestEffort:

kubectl get pod test-lr-pod -n lab-limitrange -o jsonpath="{.status.qosClass}"

Saída esperada:

Burstable

Sem o LimitRange, esse mesmo manifesto — sem nenhum recurso declarado — geraria um Pod BestEffort, o primeiro candidato a ser morto se o nó ficar sem memória. O LimitRange resolveu isso sem que ninguém precisasse editar o manifesto.

Etapa 5 — Testar o limite mínimo​

Crie o arquivo pod-abaixo-min.yaml, pedindo menos que o mínimo permitido:

apiVersion: v1
kind: Pod
metadata:
  name: pod-abaixo-min
  namespace: lab-limitrange
spec:
  containers:
  - name: test
    image: busybox
    command: ["sh", "-c", "sleep 3600"]
    resources:
      requests:
        cpu: 50m
        memory: 32Mi

Aplique:

kubectl apply -f pod-abaixo-min.yaml

Saída esperada:

Error from server (Forbidden): error when creating "pod-abaixo-min.yaml": pods "pod-abaixo-min" is forbidden: [minimum cpu usage per Container is 100m, but request is 50m, minimum memory usage per Container is 64Mi, but request is 32Mi]

O Pod foi rejeitado na criação. A mensagem cita explicitamente request, porque o min valida os requests — e lista as duas violações (CPU e memória) de uma vez.

Etapa 6 — Testar o limite máximo​

Crie o arquivo pod-acima-max.yaml, declarando limits acima do teto:

apiVersion: v1
kind: Pod
metadata:
  name: pod-acima-max
  namespace: lab-limitrange
spec:
  containers:
  - name: test
    image: busybox
    command: ["sh", "-c", "sleep 3600"]
    resources:
      limits:
        cpu: "2"
        memory: "1Gi"

Aplique:

kubectl apply -f pod-acima-max.yaml

Saída esperada:

Error from server (Forbidden): error when creating "pod-acima-max.yaml": pods "pod-acima-max" is forbidden: [maximum cpu usage per Container is 1, but limit is 2, maximum memory usage per Container is 512Mi, but limit is 1Gi]

Agora a mensagem cita limit, não request — confirmando na prática a diferença explicada nos fundamentos: min valida requests, max valida limits.

Confirme que nenhum dos dois Pods de teste foi criado:

kubectl get pods -n lab-limitrange

Saída esperada:

NAME          READY   STATUS    RESTARTS   AGE
test-lr-pod   1/1     Running   0          5m

Só o Pod da Etapa 3 existe. Os dois que violaram o LimitRange nunca chegaram a ser criados — foram barrados pela API antes de qualquer agendamento.

Limpeza do laboratório​

kubectl delete namespace lab-limitrange

Apagar o namespace remove de uma vez o LimitRange e todos os Pods criados aqui.

Conclusão​

Com o LimitRange aplicado:

  • Todos os Pods recebem valores padrão de CPU e memória, mesmo sem declarar nada
  • Pods com valores fora do intervalo (min / max) são rejeitados na criação
  • O namespace deixa de ter Pods BestEffort, melhorando o comportamento sob pressão de memória
  • Junto com o ResourceQuota, forma a dupla que torna o controle de recursos viável em ambientes compartilhados
