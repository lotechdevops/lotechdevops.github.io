NFS e StorageClass no Kubernetes: teoria e prática

Fundamentos​

O problema: dados que sobrevivem ao Pod​

O sistema de arquivos de um container some junto com o Pod. Para guardar dados que precisam persistir (bancos, uploads, arquivos de aplicação), o Kubernetes usa três objetos que trabalham juntos:

ObjetoO que éEscopoQuem cria
PersistentVolume (PV)O volume real: um pedaço de armazenamento (neste lab, uma pasta no NFS)ClusterAdmin, ou o provisionador (automático)
PersistentVolumeClaim (PVC)O pedido de armazenamento feito por uma aplicação: "quero 1Gi, com acesso de leitura e escrita compartilhado"NamespaceQuem desenvolve a aplicação
StorageClassA receita que diz como criar volumes automaticamente (qual provisionador usar, qual política de remoção)ClusterAdmin

O Pod nunca fala direto com o PV: ele usa o PVC, e o Kubernetes liga o PVC a um PV.

Provisionamento estático × dinâmico​

EstáticoDinâmico
Quem cria o PVO admin, à mão, antes do PVCO provisionador, automaticamente, quando o PVC é criado
Trabalho do adminUm PV para cada pedidoConfigura a StorageClass uma vez
Uso típicoPoucos volumes, casos especiaisPadrão em clusters reais

Este laboratório usa o dinâmico:

PVC (pedido) ──► StorageClass (receita) ──► Provisionador ──► cria pasta no NFS + PV ──► PVC "Bound"

O que é o NFS e por que usá-lo​

O NFS (Network File System) compartilha uma pasta de um servidor pela rede, e vários clientes a montam como se fosse local.

Vantagens:

  • Simples de montar, ótimo para laboratórios e homelab.
  • Suporta ReadWriteMany: vários Pods, em nós diferentes, leem e escrevem ao mesmo tempo no mesmo volume. Muitos storages em bloco (como discos de nuvem) não suportam isso.

Limitações para ter em mente:

  • O servidor NFS é um ponto único de falha: se ele cair, todos os volumes caem.
  • O desempenho depende da rede.
  • Não existe limite de tamanho real. O storage: 1Gi do PVC é só uma declaração, o NFS não impede que o Pod escreva mais que isso.
  • Não é indicado para bancos de dados com alta carga de I/O.

Modos de acesso (accessModes)​

ModoSiglaSignificado
ReadWriteOnceRWOLeitura e escrita por um nó
ReadOnlyManyROXSomente leitura por vários nós
ReadWriteManyRWXLeitura e escrita por vários nós
ReadWriteOncePodRWOPLeitura e escrita por um único Pod

O NFS suporta RWX, e é por isso que usamos ReadWriteMany na prática.

O provisionador NFS​

O Kubernetes não cria volumes NFS sozinho: ele precisa de um componente que saiba fazer isso. Aqui usamos o nfs-subdir-external-provisioner.

Provisionador externo, não driver CSI

O nfs-subdir-external-provisioner é um provisionador externo simples. Ele não é um driver CSI (o padrão moderno de plugins de armazenamento). Para o laboratório ele funciona bem, e existe também o CSI Driver NFS (csi-driver-nfs), que segue o padrão CSI e traz mais recursos. O conceito de StorageClass, PVC e PV é o mesmo nos dois.

Como ele funciona: para cada PVC, cria uma subpasta dentro do diretório exportado, com o nome <namespace>-<pvc>-<pv>, e cria o PV apontando para ela. Cada aplicação ganha a sua pasta, e todas dividem o mesmo servidor.

Política de remoção (reclaimPolicy)​

O que acontece com o dado quando o PVC é apagado:

PolíticaEfeito
DeleteO PV é removido junto com o PVC (o padrão deste provisionador)
RetainO PV e o dado são mantidos para recuperação manual

No nfs-subdir-external-provisioner, mesmo com Delete, o padrão é arquivar: a subpasta é renomeada para archived-... em vez de apagada. Você vai ver isso na limpeza.

StorageClass padrão

Neste lab marcamos a StorageClass como padrão (defaultClass=true). A partir daí, qualquer PVC sem storageClassName no cluster passa a usar o NFS. Em um cluster com várias aplicações, pense nisso antes de ativar, e mantenha apenas uma StorageClass padrão.

Prática: NFS com StorageClass dinâmica​

Objetivo​

Criar um servidor NFS em uma VM, integrá-lo ao Kubernetes com um provisionador e uma StorageClass, e comprovar que um Pod grava dados que persistem no servidor NFS e são compartilhados entre Pods.

Pré-requisitos​

  1. Um cluster Kubernetes funcional (1 control plane + 1 ou mais workers) e kubectl configurado
  2. helm instalado
  3. Uma VM Linux (ex: Ubuntu Server) para o servidor NFS, alcançável por todos os nós do cluster
  4. Acesso sudo no servidor NFS e em todos os nós
IPs usados neste lab

Os exemplos usam o servidor NFS em 10.10.20.30, na rede de laboratório 10.10.20.0/24. Troque pelo IP do seu servidor NFS, e use sempre um IP que todos os nós alcancem.

Etapa 1 — Criar o servidor NFS​

Na VM do servidor NFS, instale o pacote e crie o diretório que será compartilhado:

sudo apt update
sudo apt install -y nfs-kernel-server
sudo mkdir -p /mnt/nfs/data
sudo chown nobody:nogroup /mnt/nfs/data

Exporte o diretório, liberando apenas a rede do laboratório:

echo "/mnt/nfs/data 10.10.20.0/24(rw,sync,no_subtree_check,no_root_squash)" | sudo tee -a /etc/exports
sudo exportfs -rav
sudo systemctl restart nfs-kernel-server

Saída esperada do exportfs:

exporting 10.10.20.0/24:/mnt/nfs/data

Entendendo as opções do export:

OpçãoO que faz
10.10.20.0/24Só aceita clientes dessa rede. Evite * (qualquer origem), que abre o NFS para todos
rwLeitura e escrita
syncConfirma a gravação em disco antes de responder (mais seguro, um pouco mais lento)
no_subtree_checkDesativa uma verificação que costuma causar problemas e não traz ganho aqui
no_root_squashO root do cliente continua root no servidor
Cuidado com o no_root_squash

Ele é necessário para o provisionador criar as subpastas, mas permite que o root de um cliente tenha poderes de root na pasta exportada. Use somente em rede confiável, como a deste lab, e limite a origem como fizemos.

Verifique o que está sendo exportado:

sudo exportfs -v

Saída esperada:

/mnt/nfs/data   10.10.20.0/24(sync,wdelay,hide,no_subtree_check,sec=sys,rw,secure,no_root_squash,no_all_squash)

Etapa 2 — Testar o acesso a partir dos nós​

O kubelet monta o NFS no nó onde o Pod roda. Por isso, todos os nós (control plane e workers) precisam do cliente NFS. Em cada um:

sudo apt install -y nfs-common
showmount -e 10.10.20.30

Saída esperada:

Export list for 10.10.20.30:
/mnt/nfs/data 10.10.20.0/24
  • A lista mostra o diretório exportado e para quem ele está liberado.
  • Se o comando travar ou der RPC: Unable to receive, o nó não alcança o servidor (rede ou firewall).
  • Se a lista vier vazia ou der access denied, o IP do nó está fora da rede liberada no /etc/exports.
Não pule os outros nós

Instalar o nfs-common só em um worker é a causa mais comum de Pod preso em ContainerCreating: o Pod é agendado em um nó sem o cliente NFS e a montagem falha.

Etapa 3 — Instalar o provisionador NFS no cluster​

Adicione o repositório do Helm:

helm repo add nfs-subdir-external-provisioner https://kubernetes-sigs.github.io/nfs-subdir-external-provisioner/
helm repo update

Veja a versão disponível do chart (e fixe-a na instalação):

helm search repo nfs-subdir-external-provisioner

Saída esperada:

NAME                                                              CHART VERSION   APP VERSION   DESCRIPTION
nfs-subdir-external-provisioner/nfs-subdir-external-provisioner   4.0.18          4.0.2         nfs-subdir-external-provisioner is an automatic...

Crie um namespace dedicado e instale:

kubectl create namespace storage-nfs

helm install provisioner-nfs nfs-subdir-external-provisioner/nfs-subdir-external-provisioner \
  --namespace storage-nfs \
  --version 4.0.18 \
  --set nfs.server=10.10.20.30 \
  --set nfs.path=/mnt/nfs/data \
  --set storageClass.name=storage-nfs \
  --set storageClass.defaultClass=true

Entendendo os parâmetros:

ParâmetroO que defineValor no lab
nfs.serverIP do servidor NFS10.10.20.30
nfs.pathDiretório exportado pelo NFS/mnt/nfs/data
storageClass.nameNome da StorageClass criadastorage-nfs
storageClass.defaultClassTorna esta a StorageClass padrão do clustertrue
--versionFixa a versão do chart (instalação reproduzível)4.0.18

Saída esperada (trecho):

NAME: provisioner-nfs
NAMESPACE: storage-nfs
STATUS: deployed
REVISION: 1

Confirme que o Pod do provisionador subiu:

kubectl get pods -n storage-nfs

Saída esperada:

NAME                                                          READY   STATUS    RESTARTS   AGE
provisioner-nfs-nfs-subdir-external-provisioner-6d8c9b7f5-x2k4q   1/1     Running   0          30s

Confirme a StorageClass:

kubectl get storageclass

Saída esperada:

NAME                    PROVISIONER                                                      RECLAIMPOLICY   VOLUMEBINDINGMODE   ALLOWVOLUMEEXPANSION   AGE
storage-nfs (default)   cluster.local/provisioner-nfs-nfs-subdir-external-provisioner   Delete          Immediate           true                   30s
  • (default) ao lado do nome confirma que é a StorageClass padrão.
  • PROVISIONER mostra quem cria os volumes: o Pod que acabamos de instalar.
  • A StorageClass não pertence a um namespace, por isso o comando não leva -n.

Etapa 4 — Criar o PVC​

Crie um namespace para o teste e o arquivo pvc.yaml:

kubectl create namespace lab-nfs
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: meu-pvc
  namespace: lab-nfs
spec:
  accessModes:
    - ReadWriteMany
  storageClassName: storage-nfs
  resources:
    requests:
      storage: 1Gi

O PVC fica no namespace da aplicação (lab-nfs), separado do namespace do provisionador (storage-nfs).

Aplique e confira:

kubectl apply -f pvc.yaml
kubectl get pvc -n lab-nfs

Saída esperada:

persistentvolumeclaim/meu-pvc created

NAME      STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
meu-pvc   Bound    pvc-3f1c8e7a-5b2d-4c6e-9a41-7d2e8f0b1c93   1Gi        RWX            storage-nfs    5s
  • STATUS Bound significa que o PVC já foi ligado a um PV. Isso aconteceu sozinho, em segundos: provisionamento dinâmico.
  • Se ficar em Pending, o provisionador não está funcionando (veja a tabela de problemas).

Veja o PV que o provisionador criou:

kubectl get pv

Saída esperada:

NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM             STORAGECLASS   AGE
pvc-3f1c8e7a-5b2d-4c6e-9a41-7d2e8f0b1c93   1Gi        RWX            Delete           Bound    lab-nfs/meu-pvc   storage-nfs    10s

O PV foi criado sem você escrever nenhum manifesto de PV. O CLAIM mostra a quem ele pertence (lab-nfs/meu-pvc).

Agora olhe o servidor NFS. O provisionador criou uma subpasta para esse PVC:

ls /mnt/nfs/data

Saída esperada (no servidor NFS):

lab-nfs-meu-pvc-pvc-3f1c8e7a-5b2d-4c6e-9a41-7d2e8f0b1c93

O nome segue o formato <namespace>-<pvc>-<pv>.

Etapa 5 — Criar um Pod que usa o PVC​

Crie o arquivo pod.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: pod-com-nfs
  namespace: lab-nfs
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
    volumeMounts:
    - name: volume-nfs
      mountPath: /mnt/nfs
  volumes:
  - name: volume-nfs
    persistentVolumeClaim:
      claimName: meu-pvc
  • volumes declara o volume e o liga ao PVC pelo nome (claimName).
  • volumeMounts define onde ele aparece dentro do container (/mnt/nfs).

Aplique e confira:

kubectl apply -f pod.yaml
kubectl get pods -n lab-nfs

Saída esperada:

pod/pod-com-nfs created

NAME          READY   STATUS    RESTARTS   AGE
pod-com-nfs   1/1     Running   0          12s

Etapa 6 — Testar a gravação​

Grave um arquivo no volume, de dentro do container:

kubectl exec pod-com-nfs -n lab-nfs -- sh -c 'echo "Testando volume NFS" > /mnt/nfs/teste.txt'
kubectl exec pod-com-nfs -n lab-nfs -- ls -l /mnt/nfs

Saída esperada:

total 4
-rw-r--r--    1 root     root            20 Oct 31 20:40 teste.txt

Confira que o volume é realmente o NFS:

kubectl exec pod-com-nfs -n lab-nfs -- df -h /mnt/nfs

Saída esperada:

Filesystem                                                       Size  Used Available Use% Mounted on
10.10.20.30:/mnt/nfs/data/lab-nfs-meu-pvc-pvc-3f1c8e7a-...       30G   4G     24G  14% /mnt/nfs

O Filesystem mostra o IP:caminho do servidor NFS, a prova de que /mnt/nfs é uma montagem de rede, e não o disco do container. Repare que o tamanho exibido (30G) é o do disco do servidor, e não o 1Gi do PVC: o NFS não aplica limite de tamanho.

Agora confirme no servidor NFS que o arquivo chegou:

cat /mnt/nfs/data/lab-nfs-meu-pvc-*/teste.txt

Saída esperada (no servidor NFS):

Testando volume NFS

O arquivo criado dentro do Pod está fisicamente no servidor NFS.

Etapa 7 — Provar a persistência e o compartilhamento​

Persistência: apague o Pod e crie de novo. O arquivo deve continuar lá.

kubectl delete pod pod-com-nfs -n lab-nfs
kubectl apply -f pod.yaml
kubectl exec pod-com-nfs -n lab-nfs -- cat /mnt/nfs/teste.txt

Saída esperada:

pod "pod-com-nfs" deleted
pod/pod-com-nfs created

Testando volume NFS

O Pod é novo, mas o dado sobreviveu, porque vive no volume, e não no container.

Compartilhamento (RWX): crie um segundo Pod usando o mesmo PVC. Crie o arquivo pod-leitor.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: pod-leitor
  namespace: lab-nfs
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
    volumeMounts:
    - name: volume-nfs
      mountPath: /mnt/nfs
  volumes:
  - name: volume-nfs
    persistentVolumeClaim:
      claimName: meu-pvc

Aplique e leia o arquivo criado pelo primeiro Pod:

kubectl apply -f pod-leitor.yaml
kubectl exec pod-leitor -n lab-nfs -- cat /mnt/nfs/teste.txt

Saída esperada:

pod/pod-leitor created

Testando volume NFS

Dois Pods leem o mesmo arquivo. Se o kubectl get pods -n lab-nfs -o wide mostrar os dois em nós diferentes, melhor ainda: é o ReadWriteMany na prática.

Problemas comuns​

SintomaCausa provável
PVC em PendingO provisionador não está rodando ou a StorageClass está errada. Veja kubectl get pods -n storage-nfs e kubectl describe pvc meu-pvc -n lab-nfs
Pod preso em ContainerCreatingO nó onde ele foi agendado não tem nfs-common ou não alcança o servidor. Veja kubectl describe pod (evento MountVolume.SetUp failed)
mount.nfs: access denied by serverO IP do nó está fora da rede liberada no /etc/exports
showmount trava ou RPC: Unable to receiveRede ou firewall entre o nó e o servidor NFS
Permission denied ao gravarPermissão da pasta no servidor, ou falta do no_root_squash
PVC criado sem storageClassName não usa o NFSA StorageClass não está marcada como padrão (defaultClass=true)

Limpeza do laboratório​

Apague o namespace de teste (Pods e PVC):

kubectl delete namespace lab-nfs

Veja o que aconteceu com os dados no servidor NFS:

ls /mnt/nfs/data

Saída esperada (no servidor NFS):

archived-lab-nfs-meu-pvc-pvc-3f1c8e7a-5b2d-4c6e-9a41-7d2e8f0b1c93

O PV foi removido, mas a pasta foi arquivada (prefixo archived-), e não apagada. É uma proteção contra remoção acidental. Para liberar o espaço, apague a pasta manualmente no servidor.

Se quiser remover também o provisionador (e a StorageClass):

helm uninstall provisioner-nfs -n storage-nfs
kubectl delete namespace storage-nfs

Conclusão​

Com o NFS e a StorageClass dinâmica:

  • Basta criar um PVC e o volume aparece sozinho, sem escrever manifestos de PV
  • Os dados persistem além da vida do Pod
  • Vários Pods, em nós diferentes, compartilham o mesmo volume (ReadWriteMany)
  • O NFS é um ótimo ponto de partida para laboratório, mas é um ponto único de falha e não limita o tamanho dos volumes
