Expondo Aplicações com Cloudflare Tunnel

Visão Geral​

Nesta etapa, você vai publicar a aplicação na internet de forma segura, gratuita e sem IP público fixo, usando o Cloudflare Tunnel (agente cloudflared).

Essa abordagem é especialmente útil para:

  • Ambientes on-premises.
  • Clusters locais com CGNAT ou IP dinâmico.
  • Acesso externo sem abrir portas no roteador.

O que é o Cloudflare Tunnel​

O agente cloudflared cria uma conexão de dentro para fora com a Cloudflare. Usuários externos acessam o domínio na Cloudflare, e ela encaminha o tráfego pelo túnel até o seu cluster. Nenhuma porta de entrada precisa ser aberta.

Navegador ──► Cloudflare ══(túnel)══ cloudflared (Pods) ──► Traefik ──► Aplicação

O que será feito​

  1. Criar um Tunnel no painel Cloudflare Zero Trust.
  2. Implantar o cloudflared no cluster.
  3. Criar uma Published Application Route apontando para o Traefik.

Pré-requisitos​

  • Domínio gerenciado pela Cloudflare e acesso ao painel Zero Trust.
  • MetalLB, Traefik e o Ingress da etapa anterior funcionando.
  • Certificado TLS válido no Ingress (etapa 5).

1. Criar o Tunnel​

  1. Acesse o Zero Trust da Cloudflare.
  2. Vá em Networks → Tunnels.
  3. Clique em Create a tunnel, escolha um Nome e salve.
  4. Na tela seguinte (Setup Environment), não é preciso escolher sistema operacional nem arquitetura: o cloudflared vai rodar no Kubernetes, não nessa máquina.
  5. Em Install and Run, selecione Docker e localize o comando. O token é a string longa depois de --token. Copie somente o token (TUNNEL_TOKEN); ele será usado no Kubernetes.

Não execute o comando do painel. Ele serve só para você enxergar o token.

Trate o token como uma senha. Quem tem o token consegue conectar um cloudflared ao seu tunnel. Não o versione no Git.

Os menus da Cloudflare mudam

A interface do painel é reorganizada com frequência. Se algum menu tiver outro nome, procure por Tunnels (ou Cloudflare Tunnels) dentro de Networks.

2. Instalar o cloudflared no cluster​

2.1. Criar o namespace e a Secret com o token​

kubectl create namespace cloudflare-tunnel

kubectl -n cloudflare-tunnel create secret generic cloudflared \
  --from-literal=TUNNEL_TOKEN='<COLE_AQUI_O_TUNNEL_TOKEN>'

Saída esperada:

namespace/cloudflare-tunnel created
secret/cloudflared created

2.2. Criar o Deployment​

deploy-tunnel.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cloudflared
  namespace: cloudflare-tunnel
spec:
  replicas: 2
  selector:
    matchLabels:
      app: cloudflared
  template:
    metadata:
      labels:
        app: cloudflared
    spec:
      containers:
      - name: cloudflared
        image: cloudflare/cloudflared:<VERSAO>   # use uma tag fixa, não "latest"
        args: ["tunnel", "--no-autoupdate", "run"]
        env:
        - name: TUNNEL_TOKEN
          valueFrom:
            secretKeyRef:
              name: cloudflared
              key: TUNNEL_TOKEN
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            memory: 128Mi

Pontos de atenção

  • Substitua <VERSAO> por uma tag da página de releases do cloudflared. Evite latest: ele torna o laboratório não reproduzível e pode trazer mudanças inesperadas.
  • replicas: 2 -> duas réplicas do cloudflared conectam ao mesmo tunnel, dando alta disponibilidade.
  • --no-autoupdate -> a atualização é feita pela troca da tag da imagem, não dentro do Pod.

Aplique e verifique os Pods:

kubectl apply -f deploy-tunnel.yaml
kubectl -n cloudflare-tunnel get pods

Saída esperada:

deployment.apps/cloudflared created

NAME                           READY   STATUS    RESTARTS   AGE
cloudflared-66df6f45f9-k2tsh   1/1     Running   0          23s
cloudflared-66df6f45f9-q67fz   1/1     Running   0          23s

Confira os logs:

kubectl -n cloudflare-tunnel logs deploy/cloudflared | tail -n 20

Confira os logs:

kubectl -n cloudflare-tunnel logs deploy/cloudflared | tail -n 20

Saída esperada (trecho):

INF Registered tunnel connection connIndex=0 ... location=gru01 protocol=quic
INF Registered tunnel connection connIndex=1 ... location=gru02 protocol=quic
  • Os 2 Pods Running correspondem às 2 réplicas.
  • Registered tunnel connection confirma que o cloudflared conectou à Cloudflare. Os valores de location e protocol variam.
  • No painel, o tunnel deve aparecer como Healthy.

3. Criar a Published Application Route​

Com o tunnel Healthy, configure a rota de acesso:

  1. Em Networks → Tunnels, localize o tunnel e, na coluna Actions, clique no menu de três pontos (⋯) e depois em Configure.
  2. Na aba Routes, clique em Add route e depois em Add published application.
  3. Preencha:
    • Hostname:
      • Subdomain -> whoami
      • Domain -> seu domínio (ex: devopsr66.com)
      • Path -> deixe vazio
    • Service URL -> https://traefik.traefik.svc.cluster.local (veja as opções abaixo)
  4. Expanda Additional application settings → TLS e configure a verificação do certificado (veja abaixo). As demais seções (HTTP, Connection e Access) ficam com os valores padrão.
  5. Salve a rota (Save).
No campo URL, inclua o protocolo

O painel exige o formato completo, por exemplo https://traefik.traefik.svc.cluster.local. Sem o https://, a rota não é salva (erro Invalid service URL format).

Qual URL usar?​

OpçãoURLQuando usar
IP do MetalLB10.10.20.200Simples, mas o tunnel passa a depender do IP fixo do MetalLB.
DNS interno do Service (recomendado)traefik.traefik.svc.cluster.localFunciona porque o cloudflared roda dentro do cluster e resolve o DNS interno. Não depende do MetalLB.

Verificação do certificado (TLS)​

O cloudflared conecta ao Traefik por DNS interno ou IP, mas o certificado do Ingress foi emitido para whoami.devopsr66.com. Sem ajuste, a validação falha por incompatibilidade de nome.

Em Additional application settings → TLS, preencha:

  • Origin Server Name -> whoami.devopsr66.com
  • Disable TLS certificate verification -> deixe desligado

O Origin Server Name define o nome (SNI) que o cloudflared apresenta ao Traefik no handshake TLS. O Traefik devolve o certificado correto, a validação passa e a verificação continua ativa.

Os campos CA Pool e TLS Timeout ficam vazios: o CA Pool só é necessário para CA privada ou certificado autoassinado, e o certificado do Let's Encrypt já é confiável.

Evite desligar a validação

Ativar Disable TLS certificate verification faz o cloudflared aceitar qualquer certificado do origin. Use apenas para teste, nunca em produção.

4. Testar​

Remova do /etc/hosts a entrada criada na etapa 5. Assim, o teste passa pela Cloudflare e não direto pelo IP do MetalLB:

sudo sed -i '/whoami.devopsr66.com/d' /etc/hosts

Confirme que o nome agora resolve para a Cloudflare:

dig +short whoami.devopsr66.com

Saída esperada:

104.21.18.xx
172.67.181.xx

Esses são IPs da Cloudflare, não do seu cluster. A Cloudflare cria automaticamente o registro DNS (CNAME para o tunnel) ao salvar a rota, e é ela quem recebe a requisição.

Acesse a aplicação a partir da internet (ou de um celular fora do Wi-Fi):

curl -v https://whoami.devopsr66.com

Saída esperada (trechos):

< HTTP/2 200
< server: cloudflare
...
Hostname: whoami-7d9c5b8f4c-4xk2p
  • server: cloudflare mostra que a resposta passou pela Cloudflare.
  • Hostname é o Pod do whoami que atendeu, o mesmo caminho completo: Cloudflare → túnel → Traefik → Pod.

Problemas comuns​

SintomaCausa provável
Tunnel aparece como Down/InactivePods do cloudflared não iniciaram ou token inválido. Veja os logs.
Erro 502 / 1033 da CloudflareO cloudflared não alcança o origin. Teste de dentro do cluster: kubectl run -it --rm curl --image=curlimages/curl --restart=Never -- curl -vk https://traefik.traefik.svc.cluster.local. Um 404 page not found do Traefik já prova que o caminho de rede funciona.
Erro de certificado nos logs do cloudflaredFalta o Origin Server Name (ou, só em teste, Disable TLS certificate verification).
404 do TraefikO Host da requisição não bate com o Ingress. Confira o hostname da rota.
O curl ainda vai direto ao 10.10.20.200 (certificado correto, mas sem server: cloudflare)O /etc/hosts ainda tem a entrada antiga. O dig ignora esse arquivo, mas o curl não: confira com grep whoami /etc/hosts.

Para proteger a aplicação com autenticação, siga para a próxima etapa.
