Instalação e Configuração do MetalLB no Kubernetes

Objetivo desta seção​

Nesta etapa, você vai entender o papel do MetalLB e instalá-lo no cluster.

Diferente de clusters em nuvens públicas (EKS, GKE, AKS), ambientes on-premises não possuem um balanceador de carga nativo. Sem ele, um Service do tipo LoadBalancer fica para sempre com o EXTERNAL-IP em <pending>. O MetalLB resolve isso.

O que é o MetalLB?​

O MetalLB é um balanceador de carga para clusters que rodam fora da nuvem (bare-metal, datacenters próprios, laboratórios). Ele implementa o tipo LoadBalancer: quando você cria um Service desse tipo, o MetalLB escolhe um IP de uma faixa que você definiu e o anuncia na rede.

Como funciona​

O MetalLB tem dois componentes:

  • controller: atribui os IPs aos Services.
  • speaker: roda em cada nó (DaemonSet) e anuncia os IPs na rede.

E opera em dois modos:

  • Layer 2: um nó responde às requisições ARP do IP. Todo o tráfego daquele IP entra por esse nó e, se ele falhar, outro assume. É simples e não exige configuração no roteador.
  • BGP: anuncia os IPs a roteadores externos, permitindo distribuir o tráfego entre vários nós.

Neste laboratório usaremos o modo Layer 2.

Instalação​

1. Instalar o MetalLB com Helm​

helm repo add metallb https://metallb.github.io/metallb
helm repo update

helm install metallb metallb/metallb \
  --namespace metallb-system \
  --create-namespace

O --create-namespace cria o namespace metallb-system. Não é necessário criá-lo antes com kubectl create namespace.

2. Aguardar os Pods ficarem prontos​

kubectl get pods -n metallb-system
kubectl wait --namespace metallb-system \
  --for=condition=ready pod \
  --selector=app.kubernetes.io/name=metallb \
  --timeout=120s

Você deve ver o Pod metallb-controller e um Pod metallb-speaker por nó, todos Running.

Importante: aguarde os Pods ficarem prontos antes de criar o pool de IPs. Se você aplicar os recursos cedo demais, o webhook de validação do MetalLB ainda não estará no ar e o kubectl apply falhará.

Configurando o pool de IPs​

3. Criar o IPAddressPool​

Defina a faixa de IPs que o MetalLB poderá distribuir.

metallb-pool.yaml
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: metallb-pool
  namespace: metallb-system
spec:
  addresses:
    - 10.10.20.200-10.10.20.220

A faixa deve estar na rede em que o MetalLB vai anunciar os IPs (neste laboratório, a eth1, 10.10.20.0/24), fora do DHCP e sem usar IPs já ocupados (o gateway 10.10.20.1 e os IPs dos nós). Caso contrário, haverá conflito de IP.

4. Criar o L2Advertisement​

O L2Advertisement diz ao MetalLB para anunciar o pool via ARP.

metallb-l2.yaml
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: metallb-l2
  namespace: metallb-system
spec:
  ipAddressPools:
    - metallb-pool
  interfaces:
    - eth1
  • ipAddressPools -> pool que será anunciado (o nome criado no passo anterior).
  • interfaces -> restringe o anúncio ARP à interface eth1, a rede do pool. Sem esse campo, o MetalLB anuncia por todas as interfaces do nó. Se os seus nós tiverem uma única interface, pode omitir.

5. Aplicar e verificar​

kubectl apply -f metallb-pool.yaml
kubectl apply -f metallb-l2.yaml
kubectl get ipaddresspools -n metallb-system

Saída esperada:

NAME           AUTO ASSIGN   AVOID BUGGY IPS   ADDRESSES
metallb-pool   true          false             ["10.10.20.200-10.10.20.220"]
kubectl get l2advertisements -n metallb-system

Saída esperada:

NAME         IPADDRESSPOOLS     IPADDRESSPOOL SELECTORS   INTERFACES
metallb-l2   ["metallb-pool"]                             ["eth1"]

Testando o MetalLB (opcional)​

Crie um Service LoadBalancer de teste e veja se ele recebe um IP do pool:

kubectl create deployment teste-lb --image=nginx:1.27-alpine
kubectl expose deployment teste-lb --port=80 --type=LoadBalancer
kubectl get svc teste-lb

O EXTERNAL-IP deve ser um endereço da faixa 10.10.20.200-220. A partir de outra máquina da rede, curl http://<EXTERNAL-IP> deve responder. Depois, limpe o teste:

kubectl delete svc,deployment teste-lb

Problemas comuns​

SintomaCausa provável
EXTERNAL-IP fica em <pending>O IPAddressPool não foi criado, ou o L2Advertisement não referencia o pool.
kubectl apply falha com erro de webhookOs Pods do MetalLB ainda não estavam prontos. Aguarde e tente de novo.
IP atribuído, mas não respondeConflito com outro dispositivo da rede, ou kube-proxy em IPVS sem strictARP: true (veja os pré-requisitos).

Com o MetalLB funcionando, qualquer Service LoadBalancer do cluster recebe um IP real da rede. Na próxima etapa, o Traefik será exposto assim.
