Protegendo Aplicações com Cloudflare Access (Zero Trust)

Visão Geral​

Agora que a aplicação está exposta pelo Cloudflare Tunnel, vamos adicionar uma camada essencial de segurança: o Cloudflare Access.

Sem ele, qualquer pessoa que souber a URL acessa a aplicação. Com o Access, só quem passar pela autenticação chega ao tunnel, seguindo o modelo Zero Trust.

O que é o Cloudflare Access​

O Cloudflare Access é uma solução de segurança baseada em identidade, que controla o acesso a aplicações privadas ou públicas sem depender de VPN. Com ele é possível:

  • Exigir login por e-mail com código PIN temporário (One-Time PIN).
  • Integrar com Google, GitHub, Okta, Azure AD e outros provedores de identidade.
  • Aplicar MFA (autenticação multifator).
  • Auditar e registrar os acessos.

A autenticação acontece na borda da Cloudflare, antes de a requisição entrar no tunnel. Requisições não autenticadas nunca chegam ao seu cluster.

Navegador ──► Cloudflare (Access: login + policy) ══(túnel)══ cloudflared ──► Traefik ──► Aplicação
                      │
                      └─ sem autenticação válida: barrado aqui

Conceitos rápidos​

TermoO que é
ApplicationO que você quer proteger: um hostname (ex: whoami.devopsr66.com).
PolicyA regra de quem pode entrar: ação (Allow, Deny, Bypass) + condições (e-mail, país, grupo...).
Login methodComo a pessoa prova quem é: One-Time PIN, Google, GitHub etc.

A Application diz o que proteger, e a Policy diz quem passa.

Pré-requisitos​

  • Etapa 6 concluída: https://whoami.devopsr66.com abre a aplicação pelo Cloudflare Tunnel.
  • Acesso ao painel Zero Trust da Cloudflare.
  • Um e-mail que você consiga acessar, para receber o código PIN.

Antes de proteger, confirme que a aplicação está aberta (sem login):

curl -i https://whoami.devopsr66.com

Saída esperada (trecho):

HTTP/2 200
server: cloudflare
...
Hostname: whoami-7d9c5b8f4c-4xk2p

Esse é o estado "antes": qualquer pessoa com a URL recebe a resposta. Vamos mudar isso.

O que será feito​

  1. Criar uma Application no Cloudflare Zero Trust.
  2. Criar uma Access Policy (e-mail + PIN).
  3. Testar o acesso, nos casos positivo e negativo.

1. Criar uma Application​

  1. Acesse o Zero Trust da Cloudflare.
  2. No menu lateral, vá em Access → Applications.
  3. Clique em Add an application e selecione Self-hosted.
  4. Preencha:
    • Application name -> nome descritivo (ex: whoami).
    • Session duration -> quanto tempo o usuário permanece autenticado (ex: 24h).
  5. Em Add public hostname, configure:
    • Input method -> mantenha o padrão.
    • Subdomain -> whoami
    • Domain -> seu domínio (ex: devopsr66.com)
  6. Clique em Next para prosseguir.
O hostname precisa ser idêntico

O hostname da Application deve ser exatamente o mesmo da Published Application Route criada na etapa anterior (whoami.devopsr66.com). Se divergir, o Access não protege a rota e a aplicação continua aberta.

Os menus da Cloudflare mudam

O painel é reorganizado com frequência, e o assistente de criação pode juntar Application e Policy na mesma tela. Siga a ordem lógica (Application → Policy → associar) mesmo que os rótulos variem.

2. Criar uma Access Policy​

Uma policy define quem pode entrar.

  1. No menu Zero Trust -> Access controls, vá em Policies e clique em Add a policy.
  2. Preencha os campos obrigatórios (tabela abaixo).
  3. Clique em Save.

Campos obrigatórios​

CampoO que preencherExemplo
Policy nameNome descritivo, que diga o que a policy fazE-mail com PIN
ActionO que acontece com quem atende às regras (veja abaixo)Allow
Policy rules → IncludePelo menos uma regra: um Selector (ex: Emails) e um Valueusuario@exemplo.com

Sem nenhuma regra em Include, a policy não tem a quem se aplicar.

Actions disponíveis

  • Allow -> permite o acesso a quem atender às regras.
  • Deny -> bloqueia o acesso.
  • Bypass -> ignora a autenticação.

Como as regras se combinam​

BlocoLógicaQuando usar
IncludeOR: basta atender a uma regraDefinir quem pode entrar (ex: e-mail A ou e-mail B)
RequireAND: todas as regras precisam ser atendidasExigir uma condição extra (ex: e-mail autorizado e país Brasil)
ExcludeNOT: quem atender a uma regra é barradoAbrir uma exceção (ex: todo o domínio da empresa, menos um e-mail)

Campos opcionais úteis​

CampoPara que serveRecomendação
Policy session durationTempo até o usuário precisar autenticar de novoDefina de forma consciente: este valor substitui o da Application e o global. Se o painel sugerir 30 minutes, o 24h da Application é ignorado
Override global MFA settingsExige MFA para quem atende a esta policyAtive se o método de login oferecer MFA (ex: Google, Okta). Depende do provedor de identidade escolhido
Purpose justificationPede ao usuário um motivo a cada acessoÚtil para aplicações sensíveis, pois o motivo fica registrado na auditoria. Desnecessário para o whoami
Temporary authenticationExige aprovação de um aprovador para liberar o acessoPara acessos pontuais e críticos. Não é preciso neste lab

Connection settings: ignore neste lab​

O bloco Connection settings (clipboard e transferência de arquivos do RDP) só vale para aplicações de desktop remoto. Como o whoami é uma aplicação web, deixe os valores padrão.

Boas práticas​

  • Menor privilégio: liste e-mails específicos em vez de regras amplas, como um domínio inteiro, sempre que possível.
  • Combine regras: use Require para somar uma condição (país, MFA) ao Include. Uma policy só com e-mail é um fator só.
  • Use Exclude para exceções, em vez de criar uma policy nova para cada caso.
  • Evite Bypass e nunca o use com regras abrangentes: ele desliga a autenticação.
  • Sessão curta para aplicações sensíveis. Quanto mais crítica a aplicação, menor o tempo de sessão.
  • Nome que explique a intenção (Admins - e-mail + MFA), pois as policies são reutilizáveis entre aplicações e o nome vira o que você enxerga na auditoria.
  • Teste sempre o caminho negativo (e-mail não autorizado), como na etapa 3.

Por padrão, o login por One-Time PIN já vem disponível como método de autenticação. Para usar Google, GitHub ou outro provedor, configure-o antes em Settings → Authentication → Login methods.

2. Criar a Application e associar a policy​

Só a policy não protege nada: ela precisa ser associada a uma Application, que diz o que proteger (o hostname).

  1. No menu lateral, vá em Access controls → Applications.
  2. Clique em Add an application (ou Create new application, no canto superior direito).
  3. Na aba Self-hosted and private, abra a subaba Public DNS e clique em Continue with Self-hosted and private.
  4. Em Destinations → Public hostnames, preencha:
    • Subdomain -> whoami
    • Domain -> seu domínio (ex: devopsr66.com)
    • Path -> deixe vazio
  5. Em Access policies, use a caixa Add current policies e selecione a policy criada na seção 1 (E-mail com PIN).
  6. Em Authentication, mantenha os valores padrão.
  7. Em Details, informe o Name (ex: whoami) e confira a Session Duration (padrão 24 hours).
  8. Confira o bloco Preview: ele deve mostrar Sources, Policies e Destinations preenchidos (e não mais "No policies added" ou "No destinations assigned").
  9. Clique em Create.
O hostname precisa ser idêntico

O hostname da Application (whoami.devopsr66.com) deve ser exatamente o mesmo da Published Application Route criada na etapa anterior. Se divergir, o Access não protege a rota e a aplicação continua aberta.

O que são as outras opções da tela​

Você só precisa dos passos acima. O restante pode ficar como está:

Opção na telaO que éNeste lab
Create new policy (em Access policies)Cria uma policy nova ali mesmo, sem sair da ApplicationNão precisa: já criamos a policy na seção 1
Add private hostname / Add private IP / Add WorkersOutros tipos de destino: serviços em rede privada, IPs internos ou Cloudflare WorkersNão usar: nosso destino é um hostname público
Allow access through browser-based RDP, SSH, or VNC sessionsAcesso a terminais e desktops remotos pelo navegadorDeixe Off
Accept all available identity providersAceita todos os métodos de login configurados (One-Time PIN, Google etc.)Deixe ligado
Choose available identity providersRestringe a Application a provedores específicosSó use se quiser limitar o login a um provedor
Apply instant authenticationPula a tela de escolha do provedor quando só existe um métodoOpcional
Authenticate with Cloudflare One ClientLogin automático para quem usa o cliente WARP/Cloudflare OneDeixe desligado
Identity / MFA (abas de Authentication)Define os provedores e os requisitos de MFA da ApplicationMantenha o padrão
PreviewResumo do que está configurado: quem (Sources), qual policy e qual destinoUse para conferir antes de criar
Como o Access avalia as policies

As policies são negadas por padrão: se ninguém atender a nenhuma regra, o acesso é bloqueado. O Access avalia primeiro as policies Bypass e Service Auth e, depois, as demais em ordem, de cima para baixo.

Os menus da Cloudflare mudam

O painel é reorganizado com frequência. Se algum rótulo for diferente, siga a ordem lógica: Policy → Application → associação.

3. Testar o acesso​

3.1. Sem autenticação: deve ser barrado​

Repita o curl do início:

curl -i https://whoami.devopsr66.com

Saída esperada (trecho):

HTTP/2 302
location: https://<seu-time>.cloudflareaccess.com/cdn-cgi/access/login/whoami.devopsr66.com?...
  • Antes era 200 com o conteúdo da aplicação. Agora é 302, um redirecionamento para a tela de login da Cloudflare.
  • Nenhuma requisição chegou ao cluster: quem respondeu foi a borda da Cloudflare. Você pode confirmar que o Traefik não recebeu nada olhando os logs dele.
  • <seu-time> é o nome da sua organização (team name) no Zero Trust.

3.2. Com e-mail autorizado: deve entrar​

No navegador:

  1. Acesse https://whoami.devopsr66.com.
  2. Você verá a tela de login da Cloudflare Access.
  3. Informe o e-mail autorizado.
  4. Digite o código PIN recebido no e-mail.
  5. A aplicação é carregada.

Como a aplicação é o whoami, a resposta mostra os headers da requisição, incluindo os adicionados pelo Access:

Cf-Access-Authenticated-User-Email: usuario@exemplo.com
Cf-Access-Jwt-Assertion: eyJhbGciOi...
  • Cf-Access-Authenticated-User-Email traz o e-mail de quem se autenticou. Sua aplicação pode usá-lo para identificar o usuário, sem implementar login próprio.
  • Cf-Access-Jwt-Assertion é o token assinado pela Cloudflare que comprova a autenticação.

3.3. Com e-mail não autorizado: deve ser negado​

Tente o login com um e-mail que não está na policy. O PIN não é enviado (ou o acesso é negado), e a aplicação não abre. Esse é o caminho negativo, e ele precisa ser testado, pois prova que a policy realmente restringe.

Reforço opcional: validar o token no tunnel​

O Access barra o acesso na borda da Cloudflare, mas quem alcançar o origin por outro caminho (por exemplo, o IP 10.10.20.200 direto, dentro da rede do laboratório) não passa pelo Access.

Para uma camada extra (defesa em profundidade), a rota do tunnel oferece, em Additional application settings → Access, a opção de validar o JWT do Access no próprio tunnel. Com ela, o cloudflared recusa requisições que não tragam um token válido. Os campos de team name e AUD tag vêm da Application criada nesta etapa.

Problemas comuns​

SintomaCausa provável
A aplicação abre sem pedir login (curl retorna 200)A Application não foi criada, ou o hostname não bate com o da rota do tunnel.
Você é barrado mesmo com e-mail autorizadoA policy não está associada à Application, ou o e-mail está diferente do cadastrado na regra.
Não chega o e-mail com o PINVerifique a caixa de spam e se o e-mail está na regra da policy (o PIN só é enviado a e-mails permitidos).
O curl ainda retorna 200 mesmo com a Application criadaO /etc/hosts ainda aponta whoami.devopsr66.com para o 10.10.20.200, e a requisição vai direto ao Traefik, sem passar pela Cloudflare. Remova a linha.

Recursos avançados

O Cloudflare Access oferece muito mais do que e-mail + PIN:

  • Integração com provedores de identidade (Google Workspace, GitHub, Okta, Azure AD).
  • MFA.
  • Controle por país/localização do IP.
  • Permissão por grupos de usuários.
  • Bypass para IPs de redes confiáveis.
  • Políticas condicionais com lógica AND, OR e NOT.

Conclusão​

Ao final deste laboratório, sua aplicação é servida por um Ingress com TLS emitido pelo cert-manager, exposta sem abrir portas pelo Cloudflare Tunnel, e protegida por autenticação no Cloudflare Access.
