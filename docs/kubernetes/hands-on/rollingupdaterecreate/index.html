Estratégias de Deployment no Kubernetes: RollingUpdate e Recreate

Fundamentos​

Como um Deployment atualiza Pods​

Quando você altera o template do Pod de um Deployment (nova imagem, nova variável de ambiente, novos recursos), o Kubernetes precisa trocar os Pods antigos pelos novos. A forma como essa troca acontece é definida pela estratégia de atualização:

  • RollingUpdate — troca gradual, Pod a Pod. É a padrão: se você não declarar strategy, é ela que será usada.
  • Recreate — derruba todos os Pods antigos e só depois sobe os novos.

Por baixo, o mecanismo é o mesmo nas duas: o Deployment não atualiza Pods, ele cria um novo ReplicaSet. Cada versão do template corresponde a um ReplicaSet, e a estratégia só define como o número de Pods é transferido do ReplicaSet antigo para o novo.

Só o template dispara rollout

Mudar replicas não cria rollout (só escala o ReplicaSet atual). Mudar labels ou anotações do próprio Deployment também não. Apenas alterações dentro de spec.template geram uma nova revisão.

Estratégia RollingUpdate​

A RollingUpdate atualiza os Pods de forma gradual, em pequenos grupos, mantendo o serviço no ar durante todo o processo. O novo ReplicaSet sobe aos poucos enquanto o antigo desce na mesma medida. É a escolha natural para aplicações stateless em produção.

Exemplo de configuração:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: webserver
spec:
  replicas: 10
  selector:
    matchLabels:
      app: webserver
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 5
      maxUnavailable: 5
  template:
    metadata:
      labels:
        app: webserver
    spec:
      containers:
        - name: nginx
          image: nginx:1.25.3

Campos de controle:

CampoO que controlaPadrão
maxSurgeQuantos Pods a mais que replicas podem existir durante a atualização25%
maxUnavailableQuantos Pods a menos que replicas podem estar indisponíveis durante a atualização25%

No exemplo acima, com replicas: 10, maxSurge: 5 e maxUnavailable: 5:

  • Pode haver até 15 Pods ao mesmo tempo (10 + 5)
  • Devem existir pelo menos 5 Pods disponíveis o tempo todo (10 − 5)

Os dois campos aceitam número absoluto (2) ou percentual ("25%"). No caso de percentual, o Kubernetes arredonda maxSurge para cima e maxUnavailable para baixo.

Dois ajustes comuns:

ObjetivoConfiguraçãoEfeito
Nunca reduzir a capacidademaxUnavailable: 0 e maxSurge: 1Sobe um Pod novo, espera ficar pronto, só então derruba um antigo. Mais lento, mais seguro
Atualizar o mais rápido possívelmaxSurge: "100%"Sobe um conjunto completo de Pods novos antes de derrubar os antigos. Consome o dobro de recursos temporariamente
Combinação inválida

maxSurge: 0 e maxUnavailable: 0 ao mesmo tempo é rejeitado pela API: o Kubernetes não teria como progredir (não pode criar Pod extra nem derrubar nenhum). Pelo menos um dos dois precisa ser maior que zero.

O Pod só "conta" quando está Ready

O RollingUpdate decide o próximo passo olhando quantos Pods novos estão prontos. Sem uma readinessProbe, o Kubernetes considera o Pod pronto assim que o container inicia, e pode derrubar os antigos antes de a aplicação realmente conseguir responder. Em produção, toda atualização gradual deveria ter readiness configurada — veja a página sobre Probes.

Estratégia Recreate​

Ao contrário da RollingUpdate, a Recreate derruba todos os Pods atuais antes de iniciar qualquer Pod novo. Existe, portanto, uma janela em que nenhum Pod está disponível.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: webserver
spec:
  replicas: 10
  selector:
    matchLabels:
      app: webserver
  strategy:
    type: Recreate
  template:
    metadata:
      labels:
        app: webserver
    spec:
      containers:
        - name: nginx
          image: nginx:1.25.3

A Recreate só tem o campo type: não existem maxSurge nem maxUnavailable, porque nunca há Pods antigos e novos coexistindo.

Quando usar:

  • Volume ReadWriteOnce. É o motivo mais comum na prática. Um PVC com esse modo só pode ser montado por um nó por vez; com RollingUpdate, o Pod novo fica preso em ContainerCreating esperando o antigo soltar o volume — que só solta quando o novo ficar pronto. Impasse.
  • Versões incompatíveis não podem coexistir. Por exemplo, a versão nova altera o schema do banco de um jeito que quebra a versão antiga.
  • Instância única por natureza. Aplicações que só podem ter uma cópia rodando (um consumidor de fila sem coordenação, um agendador).

RollingUpdate × Recreate​

RollingUpdateRecreate
Disponibilidade durante a atualizaçãoMantidaInterrompida
Versões antiga e nova coexistemSimNão
Consumo temporário de recursosMaior (maxSurge)Menor
VelocidadeMais lentaMais rápida
Cuidado principalA aplicação precisa tolerar duas versões ao mesmo tempoHá downtime garantido

Campos que controlam o rollout​

Três campos do spec do Deployment (não da estratégia) ajustam o comportamento de qualquer atualização:

CampoPadrãoPara que serve
minReadySeconds0Tempo que um Pod precisa ficar Ready, sem falhar, para ser considerado disponível. Impede que um Pod que cai 3 segundos depois de subir seja contado como bom
progressDeadlineSeconds600Tempo máximo sem progresso antes de o rollout ser marcado como falho. É o que faz o rollout status desistir de esperar
revisionHistoryLimit10Quantos ReplicaSets antigos são mantidos. Define até onde o rollback consegue voltar
Rollout travado não volta sozinho

Quando o progressDeadlineSeconds estoura, o Kubernetes apenas marca o Deployment como ProgressDeadlineExceeded. Ele não faz rollback automático: os Pods novos defeituosos continuam lá e os antigos continuam atendendo (no caso da RollingUpdate). Quem decide voltar é você, com kubectl rollout undo.

Comandos de rollout​

ComandoO que faz
kubectl rollout status deployment <nome>Acompanha a atualização e informa sucesso ou falha
kubectl rollout history deployment <nome>Lista as revisões
kubectl rollout undo deployment <nome>Volta para a revisão anterior
kubectl rollout undo deployment <nome> --to-revision=NVolta para uma revisão específica
kubectl rollout pause deployment <nome>Pausa uma atualização em andamento
kubectl rollout resume deployment <nome>Retoma uma atualização pausada
kubectl rollout restart deployment <nome>Recria os Pods sem mudar a imagem (gera uma nova revisão)
Um truque do pause

Pausar permite acumular várias alterações no Deployment (imagem, recursos, variáveis) e aplicar tudo em um único rollout ao executar resume, em vez de um rollout por alteração.

Prática: atualizando e medindo a disponibilidade​

Neste laboratório você vai:

  • Subir um Deployment com RollingUpdate e atualizar a imagem
  • Ver o Kubernetes criando um novo ReplicaSet e esvaziando o antigo
  • Registrar o histórico de revisões e fazer rollback
  • Trocar para Recreate e medir o downtime com um cliente de teste

Pré-requisitos​

  1. Um cluster Kubernetes funcional
  2. kubectl configurado
  3. Dois terminais abertos (um para executar, outro para observar)

Etapa 1 — Criar o namespace​

kubectl create namespace lab-rollout

Etapa 2 — Criar o Deployment com RollingUpdate​

Crie o arquivo deployment-rolling.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: webserver
  namespace: lab-rollout
spec:
  replicas: 6
  minReadySeconds: 5
  revisionHistoryLimit: 5
  selector:
    matchLabels:
      app: webserver
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2
      maxUnavailable: 1
  template:
    metadata:
      labels:
        app: webserver
    spec:
      containers:
        - name: nginx
          image: nginx:1.25.3
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 2
          resources:
            requests:
              cpu: 50m
              memory: 32Mi

O que esse manifesto define:

  • replicas: 6 com maxSurge: 2 → no máximo 8 Pods ao mesmo tempo
  • maxUnavailable: 1 → no mínimo 5 Pods disponíveis o tempo todo
  • minReadySeconds: 5 e readinessProbe → cada Pod novo precisa ficar pronto por 5 segundos antes de o próximo passo acontecer. Isso deixa o rollout lento o bastante para você observá-lo
  • revisionHistoryLimit: 5 → o histórico guarda as 5 últimas revisões
  • Imagem com tag explícita (1.25.3). Com latest, reaplicar o manifesto não dispara rollout nenhum, porque o template não mudou

Crie também o Service, que será o ponto de acesso do nosso cliente de teste. Arquivo service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: webserver
  namespace: lab-rollout
spec:
  selector:
    app: webserver
  ports:
    - port: 80
      targetPort: 80

Aplique os dois:

kubectl apply -f deployment-rolling.yaml -f service.yaml

Aguarde o Deployment ficar pronto:

kubectl rollout status deployment webserver -n lab-rollout

Saída esperada:

deployment "webserver" successfully rolled out

Registre o motivo desta revisão. Sem isso, a coluna CHANGE-CAUSE do histórico ficaria <none>:

kubectl annotate deployment webserver -n lab-rollout \
  kubernetes.io/change-cause="Deploy inicial com nginx 1.25.3"

Etapa 3 — Iniciar o cliente de teste​

Este Pod fica em loop fazendo uma requisição ao Service a cada meio segundo e registrando OK ou FALHA. É ele que vai provar se houve ou não interrupção durante as atualizações.

kubectl run cliente \
  --image=busybox \
  --restart=Never \
  --labels=teste=cliente \
  -n lab-rollout \
  -- /bin/sh -c 'while true; do if wget -q -T 1 -O /dev/null http://webserver; then echo "$(date +%T) OK"; else echo "$(date +%T) FALHA"; fi; sleep 0.5; done'

Confirme que está funcionando:

kubectl logs cliente -n lab-rollout --tail=3

Saída esperada:

21:40:12 OK
21:40:13 OK
21:40:13 OK

Etapa 4 — Disparar o RollingUpdate​

No segundo terminal, deixe observando os ReplicaSets:

kubectl get rs -n lab-rollout -w

No primeiro terminal, troque a imagem:

kubectl set image deployment/webserver nginx=nginx:1.27.0 -n lab-rollout

E acompanhe o progresso:

kubectl rollout status deployment webserver -n lab-rollout

Saída esperada (trecho):

Waiting for deployment "webserver" rollout to finish: 2 out of 6 new replicas have been updated...
Waiting for deployment "webserver" rollout to finish: 4 out of 6 new replicas have been updated...
Waiting for deployment "webserver" rollout to finish: 5 of 6 updated replicas are available...
deployment "webserver" successfully rolled out

No terminal do -w, o mecanismo aparece nas linhas dos ReplicaSets:

NAME                  DESIRED   CURRENT   READY   AGE
webserver-6c5d7b9f4   6         6         6       4m
webserver-7f8b9d6c5   2         0         0       0s
webserver-7f8b9d6c5   2         2         0       0s
webserver-6c5d7b9f4   5         6         6       4m
webserver-7f8b9d6c5   3         2         2       6s
webserver-6c5d7b9f4   4         5         5       6s
...
webserver-7f8b9d6c5   6         6         6       32s
webserver-6c5d7b9f4   0         0         0       4m

Como ler essa saída:

  • Surgiu um segundo ReplicaSet (7f8b9d6c5): o Deployment não alterou os Pods existentes, ele criou uma nova "versão"
  • O novo vai de 2 → 3 → … → 6 enquanto o antigo desce de 6 → 5 → 4 → … → 0
  • Em nenhum momento a soma ultrapassa 8 (6 + maxSurge), nem fica abaixo de 5 disponíveis (6 − maxUnavailable)
  • O ReplicaSet antigo termina em 0, mas não é apagado: é ele que torna o rollback possível

Veja o estado final:

kubectl get rs -n lab-rollout

Saída esperada:

NAME                  DESIRED   CURRENT   READY   AGE
webserver-6c5d7b9f4   0         0         0       5m
webserver-7f8b9d6c5   6         6         6       1m

Agora a evidência mais importante: houve alguma interrupção para o cliente?

kubectl logs cliente -n lab-rollout | grep -c FALHA

Saída esperada:

0

Zero falhas. Os 6 Pods foram trocados e o Service nunca deixou de responder. É essa a garantia que a RollingUpdate oferece.

Etapa 5 — Registrar e consultar o histórico​

Anote o motivo da revisão 2:

kubectl annotate deployment webserver -n lab-rollout \
  kubernetes.io/change-cause="Atualização para nginx 1.27.0"

Consulte o histórico:

kubectl rollout history deployment webserver -n lab-rollout

Saída esperada:

deployment.apps/webserver
REVISION  CHANGE-CAUSE
1         Deploy inicial com nginx 1.25.3
2         Atualização para nginx 1.27.0
Por que anotar manualmente

A flag --record, que preenchia esse campo automaticamente, foi descontinuada. Hoje o caminho é anotar kubernetes.io/change-cause com kubectl annotate. Sem isso, toda revisão aparece como <none> e o histórico deixa de servir justamente na hora do rollback, quando você mais precisa saber o que cada versão tinha.

Para ver o conteúdo de uma revisão específica:

kubectl rollout history deployment webserver -n lab-rollout --revision=1

A saída mostra o template daquela revisão, incluindo a imagem nginx:1.25.3.

Etapa 6 — Fazer rollback​

Voltar para a versão anterior:

kubectl rollout undo deployment webserver -n lab-rollout

Saída esperada:

deployment.apps/webserver rolled back

Confirme qual imagem está rodando:

kubectl get deployment webserver -n lab-rollout -o jsonpath="{.spec.template.spec.containers[0].image}"

Saída esperada:

nginx:1.25.3

Veja como ficou o histórico:

kubectl rollout history deployment webserver -n lab-rollout

Saída esperada:

deployment.apps/webserver
REVISION  CHANGE-CAUSE
2         Atualização para nginx 1.27.0
3         Deploy inicial com nginx 1.25.3

Repare: a revisão 1 sumiu e apareceu a 3. O rollback não "desfaz" nada: ele reaproveita o ReplicaSet da revisão 1 e o promove a uma nova revisão. O histórico só anda para frente.

Etapa 7 — Trocar para Recreate e medir o downtime​

Agora vamos fazer a mesma atualização com Recreate e ver a diferença.

Crie o arquivo deployment-recreate.yaml. É o mesmo Deployment, mudando apenas a estratégia (a imagem continua 1.25.3, então aplicar este arquivo não dispara rollout):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: webserver
  namespace: lab-rollout
spec:
  replicas: 6
  minReadySeconds: 5
  revisionHistoryLimit: 5
  selector:
    matchLabels:
      app: webserver
  strategy:
    type: Recreate
  template:
    metadata:
      labels:
        app: webserver
    spec:
      containers:
        - name: nginx
          image: nginx:1.25.3
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 2
          resources:
            requests:
              cpu: 50m
              memory: 32Mi

Aplique:

kubectl apply -f deployment-recreate.yaml
Trocando a estratégia por patch ou edit

Se em vez de apply você alterar o type para Recreate com kubectl edit ou kubectl patch, precisa remover o bloco rollingUpdate na mesma operação, senão a API rejeita com may not be specified when strategy type is 'Recreate'. Com apply isso é resolvido sozinho, porque o manifesto novo simplesmente não contém o bloco.

Confirme a estratégia ativa:

kubectl get deployment webserver -n lab-rollout -o jsonpath="{.spec.strategy}"

Saída esperada:

{"type":"Recreate"}

No segundo terminal, observe os Pods:

kubectl get pods -n lab-rollout -l app=webserver -w

No primeiro terminal, dispare a atualização:

kubectl set image deployment/webserver nginx=nginx:1.27.0 -n lab-rollout

No terminal do -w, o comportamento é bem diferente:

NAME                         READY   STATUS        RESTARTS   AGE
webserver-6c5d7b9f4-4kx2p    1/1     Terminating   0          3m
webserver-6c5d7b9f4-9bn7t    1/1     Terminating   0          3m
webserver-6c5d7b9f4-m2xqw    1/1     Terminating   0          3m
webserver-6c5d7b9f4-r8vhz    1/1     Terminating   0          3m
webserver-6c5d7b9f4-t5jlc    1/1     Terminating   0          3m
webserver-6c5d7b9f4-z6pnd    1/1     Terminating   0          3m
webserver-7f8b9d6c5-2hfxk    0/1     Pending       0          0s
webserver-7f8b9d6c5-8wqtn    0/1     ContainerCreating   0    0s
...
webserver-7f8b9d6c5-2hfxk    1/1     Running       0          9s

Primeiro todos os Pods antigos entram em Terminating; só depois os novos começam a aparecer. É esse intervalo que vira downtime.

Quando o rollout terminar, conte as falhas do cliente nos últimos minutos:

kubectl logs cliente -n lab-rollout --since=3m | grep -c FALHA

Saída esperada (o número varia de execução para execução):

14

E veja o momento exato da interrupção:

kubectl logs cliente -n lab-rollout --since=3m | grep -B2 -A2 FALHA | head -12

Saída esperada (trecho):

21:52:07 OK
21:52:07 OK
21:52:08 FALHA
21:52:08 FALHA
21:52:09 FALHA
...

Comparação final:

EstratégiaFalhas do cliente durante a atualização
RollingUpdate (Etapa 4)0
Recreate (Etapa 7)> 0

É a prova direta, em texto, da diferença entre as duas: a RollingUpdate mantém o serviço no ar, a Recreate abre uma janela de indisponibilidade.

Limpeza do laboratório​

kubectl delete namespace lab-rollout

Apagar o namespace remove o Deployment, os ReplicaSets, o Service e o Pod cliente de uma vez.

Conclusão​

  • O Deployment atualiza criando um novo ReplicaSet; a estratégia define apenas como os Pods migram de um para o outro
  • A RollingUpdate mantém o serviço disponível. Seu comportamento é controlado por maxSurge e maxUnavailable (padrão 25% cada) e depende de uma readinessProbe para saber quando avançar
  • A Recreate tem downtime garantido, mas é a escolha certa quando versões não podem coexistir ou quando o volume é ReadWriteOnce
  • Anote kubernetes.io/change-cause a cada mudança para o histórico ser útil no rollback
  • O rollback promove um ReplicaSet antigo a uma nova revisão; o histórico só anda para frente
  • A forma mais direta de comprovar a diferença entre as estratégias é medir: um cliente em loop contra o Service, contando as falhas
