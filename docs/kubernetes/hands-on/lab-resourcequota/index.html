ResourceQuota no Kubernetes: teoria e prática

Fundamentos​

O que é o ResourceQuota?​

O ResourceQuota é o recurso que controla e limita o consumo dentro de um namespace. Ele garante que aplicações ou equipes compartilhem o cluster de forma equilibrada, evitando que uma única aplicação consuma mais do que deveria.

Com ele você define tetos para CPU, memória, armazenamento e também para a quantidade de objetos criados no namespace - Pods, Services, Secrets, ConfigMaps e PersistentVolumeClaims.

É especialmente útil em ambientes compartilhados por vários times, porque traz previsibilidade de recursos, controle de custo e isolamento entre workloads.

Tipos de recursos suportados​

Recursos computacionais

ChaveO que limita
requests.cpuSoma dos requests de CPU de todos os Pods do namespace
requests.memorySoma dos requests de memória
limits.cpuSoma dos limits de CPU
limits.memorySoma dos limits de memória
requests.ephemeral-storageSoma dos requests de disco efêmero
limits.ephemeral-storageSoma dos limits de disco efêmero

Recursos de armazenamento

ChaveO que limita
requests.storageSoma do storage solicitado por todos os PVCs
persistentvolumeclaimsQuantidade de PVCs no namespace
<storageclass>.storageclass.storage.k8s.io/requests.storageStorage solicitado em uma StorageClass específica
<storageclass>.storageclass.storage.k8s.io/persistentvolumeclaimsQuantidade de PVCs em uma StorageClass específica

Contagem de objetos

ChaveO que limita
podsQuantidade de Pods
servicesQuantidade de Services
secretsQuantidade de Secrets
configmapsQuantidade de ConfigMaps
count/<recurso>.<grupo>Forma genérica, funciona para qualquer recurso (ex: count/deployments.apps, count/ingresses.networking.k8s.io)

Como o ResourceQuota interage com requests e limits​

O ResourceQuota impõe limites agregados no nível do namespace, enquanto requestse limits são declarados em cada container.

Se a soma dos requests ou limits de todos os Pods ultrapasar a cota, novos Pods não são criados até que o consumo volte para dentro do teto.

A regra que confunde quase todo mundo na primeira vez:

Atenção

Quando a quota define requests.cpu ou limits.cpu (ou os equivalentes de memória), todo Pod do namespace passa a ser obrigado a declarar esses valores. Um Pod sem requests/limits é rejeitado na criação, com erro de must specify limits.cpu.

É aqui que entra o LimitRange: ele injeta valores padrão nos Pods que não declararam nada, fazendo com que eles atendam à exigência da quota automaticamente.

ResourceQuotaLimitRange
EscopoSoma de todo o namespaceCada container individualmente
Pergunta que responde"O namespace já usou demais?""Este container pediu um valor válido?"
Se não atenderRecurso é rejeitadoRecurso é rejeitado ou recebe o valor padrão

Ou seja: LimitRange não é alternativa ao ResouceQuota, é o complemento que o torna usável no dia a dia.

Pontos de atenção​

  • A cota só age na admissão. Se você aplicar um ResourceQuota em um namespace que já está acima do teto, os Pods existentes continuam rodando - apenas novos são bloqueados.
  • Quota não é garantia de recurso. Ela impede que se peça demais, mas não reserva nada no nó. Quem garante alocação é o requests de cada Pod, no agendamento.
  • O erro de cota aparece no controlador, não no Deployment. Quando um Deployment não consegue criar réplicas por causa da quota, a mensagem fica nos eventos do ReplicaSet - é lá que se deve olhar.

Benefícios​

  • Controle preciso de recursos por namespace
  • Prevenção contra uso excessivo, acidental ou malicioso
  • Melhor gestão de custos em clusters multiusuário
  • Base para políticas de fairness entre workloads

Prática: aplicando ResouceQuota​

Neste laboratório você vai:

  • Criar um namespace isolado
  • Aplicar um ResourceQuota limitando Pods, CPU, memória e storage
  • Ver o Kubernetes bloqueando workloads que excedem os limites
  • Entender qual cota foi atingida primeiro e por quê

Pré-requisitos​

  1. Um cluster Kubernetes funcional
  2. kubectl configurado
  3. Conhecimento básico de Pods, requests e limits
  4. Para o cenário de storage: uma StorageClass disponível (neste lab usamos nfs-storage)

Cenário 1 — CPU e memória​

Etapa 1 - Criar o namespace​

kubectl create namespace lab-resource-quota

Etapa 2 - Criar o ResouceQuota​

Crie o arquivo resourcequota.yaml

apiVersion: v1
kind: ResourceQuota
metadata:
  name: lab-resource-quota
  namespace: lab-resource-quota
spec:
  hard:
    pods: "6"
    requests.cpu: "1"
    requests.memory: "512Mi"
    limits.cpu: "2"
    limits.memory: "2Gi"

Entendendo o manifesto:

ChaveValorSignificado
pods6No máximo 6 Pods no namespace
requests.cpu1Soma dos requests de CPU não passa de 1 core (1000m)
requests.memory512MiSoma dos requests de memória não passa de 512Mi
limits.cpu2Soma dos limits de CPU não passa de 2 cores (2000m)
limits.memory2GiSoma dos limits de memória não passa de 2Gi

Aplique:

kubectl apply -f resourcequota.yaml

Verifique o estado inicial:

kubectl describe resourcequotas lab-resource-quota -n lab-resource-quota

Saída esperada:

Name:            lab-resource-quota
Namespace:       lab-resource-quota
Resource         Used  Hard
--------         ----  ----
limits.cpu       0     2
limits.memory    0     2Gi
pods             0     6
requests.cpu     0     1
requests.memory  0     512Mi

A coluna Used zerada confirma que nada foi consumido ainda. É essa tabela Used vs Hard que vamos acompanhar durante todo o lab - ela é a forma mais direta de ver a cota trabalhando.

Etapa 3 - Criar um Deployment que estoura a cota​

Vamos subir um Deployment com 6 réplicas, onde a soma dos recursos ultrapassa o que a cota permite.

Crie o arquivo deployment-resourcequota.yaml.

apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: myapp
  name: myapp
  namespace: lab-resource-quota
spec:
  replicas: 6
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - image: nginx
        name: nginx
        resources:
          limits:
            cpu: "0.5"
            memory: "512Mi"
          requests:
            cpu: "0.2"
            memory: "64Mi"

Recursos declarados por Pod:

  • requests.cpu: 0.2 (200m)
  • requests.memory: 64Mi
  • limits.cpu: 0.5 (500m)
  • limits.memory: 512Mi

Aplique:

kubectl apply -f deployment-resourcequota.yaml

Verifique quantos Pods realmente subiram:

kubectl get deployment myapp -n lab-resource-quota

Saída esperada:

AME    READY   UP-TO-DATE   AVAILABLE   AGE
myapp   4/6     4            4           43s
kubectl get pods -n lab-resource-quota

Saída esperada:

NAME                     READY   STATUS    RESTARTS   AGE
myapp-74bf858c77-5x242   1/1     Running   0          66s
myapp-74bf858c77-675xx   1/1     Running   0          66s
myapp-74bf858c77-bncd6   1/1     Running   0          66s
myapp-74bf858c77-vzpqq   1/1     Running   0          65s

Pedimos 6 réplicas e só 4 subiram. Vamos entender exatamente por quê.

Etapa 4 - Descobrir qual cota travou primeiro​

Cada linha do ResourceQuota impõe um teto diferente. Dividindo o teto pelo consumo de um Pod, descobrimos quantos Pods cada cota permitiria:

CotaHardConsumo por PodPods que caberiam
pods616
requests.cpu1000m200m5
requests.memory512Mi64Mi8
limits.cpu2000m500m4
limits.memory2048Mi512Mi4

Quem manda é o menor número da última coluna. Como limits.cpu e limits.memory só comportam 4 Pods cada, o Deployment parou em 4 - mesmo que a cota de pods permitisse 6 e a de requests.cpu permitisse 5.

Confirme olhando a cota de novo:

kubectl describe resourcequota lab-resource-quota -n lab-resource-quota

Saída esperada:

Name:            lab-resource-quota
Namespace:       lab-resource-quota
Resource         Used   Hard
--------         ----   ----
limits.cpu       2      2
limits.memory    2Gi    2Gi
pods             4      6
requests.cpu     800m   1
requests.memory  256Mi  512Mi

Repare que limits.cpu e limits.memory estão com Used igual a Hard — esgotados. Já pods (4 de 6) e requests.cpu (800m de 1) ainda teriam folga. Isso prova que foram os limits que travaram, não os requests.

Etapa 5 - Ver a mensagem de erro do Kubernetes​

O Deployment não reclama diretamente. Quem registra a falha é o ReplicaSet:

kubectl describe replicaset -n lab-resource-quota | tail -20

Saída esperada:

Events:
  Type     Reason        Age   From       Message
  ----     ------        ----  ----       -------
  Normal   SuccessfulCreate  6m45s        replicaset-controller  Created pod: myapp-74bf858c77-675xx
  Warning  FailedCreate      6m44s        replicaset-controller  Error creating: pods "myapp-74bf858c77-bnd7p" is forbidden: exceeded quota: lab-resource-quota, requested: limits.cpu=500m,limits.memory=512Mi, used: limits.cpu=2,limits.memory=2Gi, limited: limits.cpu=2,limits.memory=2Gi

Essa mensagem é a prova definitiva do lab: o Kubernetes mostra o que foi pedido (requested), o que já estava em uso (used) e qual era o teto (limited).

Onde olhar quando "o Deployment não sobe"

kubectl describe deployment não mostra esse erro. Sempre que réplicas não aparecerem sem motivo aparente, vá direto no describe replicaset — é lá que o controlador registra a recusa da API.

Cenário 2 - Storage​

Etapa 1 - Criar um ResourceQuota para volumes​

Crie o arquivo resourcequota-storage.yaml

apiVersion: v1
kind: ResourceQuota
metadata:
  name: storage-quota
  namespace: lab-resource-quota
spec:
  hard:
    requests.storage: "10Gi"
    persistentvolumeclaims: "1"

Entendendo o manifesto:

  • requests.storage: "10Gi" → limita a soma do storage solicitado por todos os PVCs a 10Gi
  • persistentVolumeClaims: "1" → permite no máximo 1 PVC no namespace

Aplique:

kubectl apply -f resourcequota-storage.yaml

Etapa 2 - Criar o primeiro PVC​

Crie o arquivo pvc-quota.yaml

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-quota
  namespace: lab-resource-quota
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: "10Gi"
  storageClassName: nfs-storage

Aplique:

kubectl apply -f pvc-quota.yaml

Verifique o consumo:

kubectl describe resourcequota storage-quota -n lab-resource-quota

Saída esperada:

Name:                   storage-quota
Namespace:              lab-resource-quota
Resource                Used  Hard
--------                ----  ----
persistentvolumeclaims  1     1
requests.storage        10Gi  10Gi

As duas cotas foram esgotadas de uma vez: o PVC consumiu a única vaga de persistentvolumeclaims e os 10Gi inteiros de requests.storage.

Etapa 3 - Violar a cota com um segundo PVC​

Crie o arquivo pvc-quota-2.yaml, pedindo apenas 2Gi

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-quota-2
  namespace: lab-resource-quota
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: "2Gi"
  storageClassName: nfs-storage

Aplique:

kubectl apply -f pvc-quota-2.yaml

Saída esperada:

Error from server (Forbidden): error when creating "pvc-quota-2.yaml": persistentvolumeclaims "pvc-quota-2" is forbidden: exceeded quota: storage-quota, requested: persistentvolumeclaims=1,requests.storage=2Gi, used: persistentvolumeclaims=1,requests.storage=10Gi, limited: persistentvolumeclaims=1,requests.storage=10Gi

O que aconteceu:

  • O primeiro PVC já tinha consumido os 10Gi de requests.storage
  • E também a única vaga de persistentvolumeclaims
  • A mensagem cita as duas violações - bastaria uma para bloquear

Repare que o PVC é rejeitado na criação, antes mesmo de tentar provisionar volume. A cota age na admissão do objeto, não no momento em que o volume é usado.

Limpeza do laboratório​

kubectl delete namespace lab-resource-quota

Apagar o namespace remove de uma vez os ResourceQuotas, o Deployment, os Pods e os PVCs criados aqui.

aviso

Se o PVC estiver Bound a um PersistentVolume com reclaimPolicy: Retain, o PV continua existindo depois de apagar o namespace. Confira com kubectl get pv e remova manualmente se não for mais usar.

Conclusão​

Com o ResourceQuota aplicado:

  • O namespace ganha um teto agregado de CPU, memória, storage e contagem de objetos
  • Workloads que ultrapassam qualquer uma das cotas são bloqueados na criação
  • A cota que tava primeiro é sempre a mais restritiva - vale fazer a divisão hard + consumo por Pod para descobrir qual é
  • O describe resourcequota (Used vs Hard) e o describe replicaset (event FailedCreate) são as duas ferramentas para diagnosticar qualquer bloqueio por cota

O passo natural a partir daqui é o LimitRange, que preenche automaticamente os requests e Limits que a quota exige
