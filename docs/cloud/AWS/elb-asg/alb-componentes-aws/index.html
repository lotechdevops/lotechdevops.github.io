Componentes do Application Load Balancer (ALB)

Para dominar o Application Load Balancer, é essencial entender seus componentes fundamentais e como eles trabalham juntos. Cada componente tem uma função específica na arquitetura do ALB, formando um sistema coeso e flexível para distribuição de tráfego.

Visão Geral da Arquitetura​

O ALB é composto por quatro componentes principais que trabalham em conjunto:

Internet -> Load Balancer -> Listeners -> Rules -> Target Groups -> Targets

Vamos explorar cada um destes componentes em detalhes:

1. Load Balancer (O ALB em si)​

O Load Balancer é o componente principal - é literalmente o ALB que você cria na AWS. Ele funciona como o ponto de entrada central para todo o tráfego.

Características Principais​

Distribuição Geográfica

  • Automaticamente distribuído em múltiplas Availability Zones
  • Alta disponibilidade garantida pela AWS
  • Falha em uma AZ não afeta o funcionamento

Endereçamento

  • Recebe um DNS name único (ex: meu-alb-123456789.us-east-1.elb.amazonaws.com )
  • Não possui IP fixo (diferente do NLB)
  • DNS atualizado automaticamente quando há mudanças

Segurança

  • Integrado com Security Groups
  • Suporte a VPC e subnets
  • Configuração granular de acesso

Configurações do Load Balancer​

Scheme (Esquema)

  • Internet-facing: Recebe tráfego da internet
  • Internet: Apenas tráfego interno da VPC

IP Address Type

  • IPv4: Apenas endereços IPv4
  • Dualstack: IPv4 + IPv6 simultaneamente

2. Listeners - Os "Ouvintes" do ALB​

Listeners são processos que ficam "escutando" por conexões em uma porta e protocolo específicos. Eles são o primeiro ponto de contato quando uma requisição chega ao ALB.

Como Funcionam os Listeners​

Imagine um listeners como um recepcionista de hotel que:

  • Fica na porta principal aguardando clientes
  • Verifica o tipo de solicitação (HTTP ou HTTPS)
  • Consulta as regras para saber onde direcionar
  • Encaminha para o destino correto

Configurações dos Listeners​

Protocolo e Porta:​

HTTP:80   → Tráfego web não criptografado
HTTPS:443 → Tráfego web criptografado

Certificados SSL/TLS:​

  • Obrigatórios para listeners HTTPS
  • Suporte ao AWS Certificate Manager (ACM)
  • Possibilidade de múltiplos certificados (SNI)

Políticas de Segurança:​

  • Controla versões TLS suportadas
  • Define cipher suites permitidos
  • Configurações de Perfect Forward Secrecy (PFS)

Exemplo de Configuração de Listeners:​

Listener 1:
  Protocol: HTTP
  Port: 80
  Default Action: Redirect to HTTPS

Listener 2:
  Protocol: HTTPS
  Port: 443
  SSL Certificate: arn:aws:acm:region:account:certificate/cert-id
  Default Action: Forward to target-group-web

3. Rules - As Regras de Roteamento​

Rules são o cérebro do ALB - elas determinam para onde cada requisição deve ser enviada baseada em condições específicas. Cada listeners pode ter múltiplas regras avaliadas em ordem de prioridade.

Anatomia de uma Rule:​

IF (condições) THEN (ações)

Exemplo:

IF path-pattern = "/api/*" THEN forward to target-group-api
IF host-header = "admin.empresa.com" THEN forward to target-group-admin

Tipos de Condições​

Path-based Routing

/api/users/*     → User Service
/api/orders/*    → Order Service
/admin/*         → Admin Panel
/static/*        → Static Content

Host-based Routing

api.empresa.com     → API Backend
admin.empresa.com   → Admin Interface
blog.empresa.com    → Blog Application

Header-based Routing

User-Agent: Mobile    → Mobile-optimized servers
API-Version: v2       → Version 2 of API
Authorization: Bearer → Authenticated endpoints

Query String Routing

?version=beta    → Beta environment
?region=us-east  → US East servers
?debug=true      → Debug-enabled instances

Source IP Routing

10.0.0.0/8      → Internal network traffic
192.168.1.0/24  → Office network

Prioridades das Rules​

As rules são avaliadas em ordem de prioridade (menor número = maior prioridade)

Priority 1: IF host = "api.empresa.com" AND path = "/v2/*"
Priority 2: IF host = "api.empresa.com"
Priority 3: IF path = "/api/*"
Default:    Forward to default target group

Tipos de Ações:​

Forward

  • Encaminha para um ou mais target groups
  • Suporte a weighted routing (distribuição percentual)

Redirect

  • Redireciona para outra URL
  • Útil para HTTP -> HTTPS, www -> non-wwww

Fixed Responde

  • Retorna resposta fixa (ex: manutenção, erro customizado)
  • Códigos HTTP customizáveis

Authenticate

  • Integração com Amazon Cognito ou OIDC
  • Autenticação antes do forwarding

4. Target Groups - Grupos de Destinos​

Targets são os recursos finais que realmente processam as requisições. Eles podem ser de diferentes tipos dependendo do target group.

Tipos de Targets Groups:​

Instance Target Groups

Target Type: instance
Targets: EC2 instances
Port: 80, 8080, 3000, etc.
Protocol: HTTP, HTTPS

IP Target Groups

Target Type: ip
Targets: Endereços IP específicos
Use Case: On-premises, containers, outros ALBs

⚡ Lambda Target Groups

Target Type: lambda
Targets: Funções AWS Lambda
Protocol: HTTP (convertido para evento Lambda)

ALB Target Groups

Target Type: alb
Targets: Outros Application Load Balancers
Use Case: Arquiteturas hierárquicas

Configurações dos Target Groups:​

Health Check Settings

Path: /health
Port: traffic-port
Protocol: HTTP
Interval: 30 seconds
Timeout: 5 seconds
Healthy threshold: 2
Unhealthy threshold: 2
Success codes: 200

Advanced Settings

Deregistration delay: 300 seconds
Slow start duration: 0 seconds
Load balancing algorithm: round_robin
Stickiness: disabled

Algoritmos de Load Balancing:​

Round Robin (Padrão)​
  • Distribui requisições sequencialmente
  • Melhor para targets com capacidade similar
Least Outstanding Requests​
  • Envia para target com menos requisições pendentes
  • Ideal para targets com capacidades diferentes

5. Targets - Os Destinos Finais​

Targets são os recursos finais que realmente processam as requisições. Eles podem ser de diferentes tipos dependendo do target group.

Tipos de Targets:​

EC2 Instances

Instance ID: i-1234567890abcdef0
Port: 80
Availability Zone: us-east-1a
Health Status: healthy

IP Addresses

IP: 10.0.1.100
Port: 8080
Availability Zone: us-east-1b
Health Status: healthy

Lambda Functions

Function: arn:aws:lambda:region:account:function:my-function
Version: $LATEST
Health Status: N/A (sempre healthy se função existe)

Estados dos Targets:​

  • Initial -> Target sendo registrado.
  • Health -> Target respondendo aos health checks
  • Unhealthy -> Target falhando nos health checks
  • Unused -> Target registrado mas não recebendo tráfego
  • Draining -> Target sendo removido, finalizando conexões existentes

Como os Componentes Trabalham Juntos​

Vamos acompanhar o fluxo completo de uma requisição

Fluxo de Requisição Detalhado:​

1. Cliente → https://api.empresa.com/users/123
2. DNS → Resolve para ALB endpoint
3. ALB → Recebe requisição na porta 443
4. Listener → HTTPS:443 captura a requisição
5. Rules → Avalia regras por prioridade:
   - Rule 1: host = "api.empresa.com" ✅
   - Action: Forward to target-group-api
6. Target Group → Seleciona target healthy:
   - Algorithm: round_robin
   - Selected: EC2 instance i-abc123
7. Health Check → Confirma target está healthy
8. Forward → Envia requisição para EC2:8080
9. Response → Retorna resposta via ALB
10. Cliente → Recebe resposta final

Melhores Práticas para Componentes​

Load Balancer​

  • Use múltiplas AZs para alta disponibilidade
  • Configure security groups apropriados
  • Use naming conventions consistentes

Listeners​

  • Sempre redirecione HTTP para HTTPS em produção
  • Use certificados do ACM quando possível
  • Configure políticas de segurança modernas

Rules​

  • Use prioridades lógicas e bem organizadas
  • Documente o propósito de cada regra
  • Teste regras em ambiente de staging primeiro

Target Groups:​

  • Configure health checks apropriados para cada serviço
  • Use deregistration delay adequado para graceful shutdown
  • Monitore métricas de saúde regularmente

Targets:​

  • Distribua targets em múltiplas AZs
  • Implemente health check endpoints robustos
  • Use Auto Scaling Groups para gerenciamento automático
