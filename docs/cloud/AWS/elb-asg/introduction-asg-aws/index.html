O que é Auto Scaling Groups (ASG)

O Auto Scaling Group é um serviço fundamental da AWS que automatiza o gerenciamento de instâncias Amazon EC2, garantindo que suas aplicações tenham sempre a quantidade certa de recursos computacionais disponíveis. Diferentemente do gerenciamento manual de servidores, o ASG monitora continuamente suas aplicações e ajusta automaticamente a capacidade para manter performance estável pelo menor custo possível.

Por que ASG é diferente?​

Imagine que você administra uma equipe de desenvolvedores (suas instâncias EC2). Um gerente tradicional (infraestrutura estática) mantém sempre o mesmo número de pessoas, independentemente da carga de trabalho. Já o ASG é como um gerente inteligente que:

  • Monitora a carga de trabalho em tempo real
  • Contrata mais pessoas quando há picos de demanda
  • Dispensa temporariamente quando a demanda diminui
  • Substitui automaticamente pessoas que ficam doentes (instâncias falhas)
  • Distribui o trabalho entre diferentes escritórios (Availability Zones)

Essa é a diferença fundamental: o ASG adapta recursos automaticamente à demanda real.

Principais Características do ASG​

Gerenciamento Automático de Capacidade​

O ASG mantém sua aplicação sempre com o número ideal de instâncias:

  • Scale Out: Adiciona instâncias quando demanda aumenta
  • Scale In: Remove instâncias quando demanda diminui
  • Health Monitoring: Substitui instâncias falhas automaticamente
  • Cross-AZ Distribution: Distribui instâncias entre múltiplas zonas

Três Pilares de Capacidade​

  • Minimum: Número mínimo de instâncias sempre em execução
  • Desired: Número ideal para operação normal
  • Maximum: Limite máximo para controlar custos

Políticas de Scaling Inteligentes​

  • Target Tracking: Mantém métricas em valores alvo (ex: CPU em 50%)
  • Step Scaling: Escalabilidade baseada em alarmes do CloudWatch
  • Scheduled Scaling: Antecipa demanda baseada em padrões conhecidos

Integração Nativa com AWS​

  • Elastic Load Balancing: Registro/remoção automática de targets
  • CloudWatch: Monitoramento e métricas detalhadas
  • SNS: Notificações sobre eventos de scaling
  • Systems Manager: Gerenciamento avançado de configurações

Quando Usar Cada Abordagem​

🎯 Use ASG quando:

  • Aplicações rodando em EC2
  • Demanda varia ao longo do tempo
  • Precisa de alta disponibilidade
  • Quer integração nativa com ALB/NLB
  • Busca simplicidade de configuração

🎯 Use Scaling Manual quando:

  • Aplicações com carga muito previsível
  • Ambientes de desenvolvimento/teste
  • Controle total sobre timing de mudanças
  • Recursos computacionais específicos

🎯 Use Third-party Tools quando:

  • Ambiente multi-cloud
  • Necessidades muito específicas
  • Já tem investimento em ferramentas
  • Equipe especializada em determinada solução

🎯 Use Kubernetes HPA quando:

  • Aplicações containerizadas
  • Arquitetura cloud-native
  • Microserviços em Kubernetes
  • Scaling granular por container

Como ASG Funciona na Prática​

Fluxo Básico de Operação:​

1. Monitor → 2. Evaluate → 3. Decide → 4. Act → 5. Validate
     ↓            ↓           ↓         ↓          ↓
  Métricas    Políticas   Scale     Launch/    Health
  CloudWatch  de Scaling  Decision  Terminate  Checks

Exemplo de Scaling Out (Adicionar Instâncias):​

  1. CloudWatch detecta: CPU média > 70% por 5 minutos
  2. ASG avalia política: "Se CPU > 70%, adicionar 2 instâncias"
  3. ASG decide: Precisa escalar de 4 para 6 instâncias
  4. Launch Template cria: 2 novas instâncias EC2
  5. Health checks validam: Novas instâncias estão saudáveis
  6. ALB registra: Instâncias no Target Group automaticamente
  7. Tráfego distribui: Para todas as 6 instâncias

Exemplo de Scaling In (Remover Instâncias):​

  1. CloudWatch detecta: CPU média < 30% por 15 minutos
  2. ASG avalia política: "Se CPU < 30%, remover 1 instância"
  3. ASG seleciona: Instância para terminação (baseado em política)
  4. Connection draining: ALB para de enviar novas requisições
  5. Graceful shutdown: Aguarda conexões existentes finalizarem
  6. Instância termina: Após período de grace
  7. Capacidade ajustada: De 6 para 5 instâncias

Componentes Essenciais do ASG​

Entender os componentes do ASG é fundamental para aproveitar todo seu potencial:

Launch Template/Configuration​

  • Definição: "Molde" para criar novas instâncias
  • Contém: AMI, instance type, security groups, user data
  • Versionamento: Permite atualizações controladas

Auto Scaling Policies​

  • Purpose: Regras que determinam quando escalar
  • Tipos: Target tracking, step scaling, scheduled
  • Metrics: CPU, memory, custom metrics, SQS queue size

Health Checks​

  • EC2 Health Checks: Status da instância (running/stopped)
  • ELB Health Checks: Aplicação respondendo corretamente
  • Custom Health Checks: Via CloudWatch ou APIs

Availability Zones​

  • Distribution: Instâncias espalhadas automaticamente
  • Fault Tolerance: Falha de uma AZ não afeta o serviço
  • Rebalancing: ASG redistribui instâncias automaticamente

Limitações e Considerações​

Limitações Importantes:​

  • Cold start time: Novas instâncias levam tempo para ficar prontas
  • State management: Instâncias são efêmeras (stateless preferred)
  • Cost complexity: Pode ser complexo prever custos com scaling dinâmico
  • Over-scaling: Configurações inadequadas podem gerar custos altos

Quando NÃO Usar ASG:​

  • Aplicações stateful: Requerem persistência de dados local
  • Recursos únicos: Instâncias com configurações muito específicas
  • Baixa variabilidade: Carga sempre constante
  • Controle total: Necessidade de controle manual absoluto
