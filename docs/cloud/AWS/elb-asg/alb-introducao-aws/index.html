O que é Application Load Balancer (ALB)

O Application Load Balancer é a solução mais avançada e versátil de load balancing da AWS para aplicações web modernas. Diferentemente dos load balancers tradicionais que operam apenas com endereço IP e portas, o ALB funciona na camada 7 do modelo OSI (camada de aplicação), permitindo tomar decisões inteligentes de roteamento baseadas no conteúdo das requisições HTTP/HTTPS.

Por que ALB é diferente?​

Imagine que você administra um shopping center (sua aplicação). Um porteiro tradicional (load balancer básico) apenas conta quantas pessoas entram e direciona para lojas alternadamente. Já o ALB é como um concierge inteligente que:

  • Lê o que a pessoa está procurando.
  • Direciona clientes de eletrônicos para o 2º andar.
  • Encaminha quem busca roupas para o 1º andar.
  • Reconhece VIPs e os direciona para atendimento especializado.

Essa é a diferença fundamental: o ALB entende o conteúdo das requisições.

Principais Características do ALB​

Roteamento Baseado em Conteúdo​

O ALB pode analisar e rotear tráfego baseado em:

  • Path da URL: /api/usersvs /api/orders.
  • Headers HTTP: Tipo de dispositivo, versão da API.
  • Query string: Parâmetros específicos da requisição.
  • Host/Hostname: Múltiplos domínios no mesmo load balancer.

Suporte a Protocolos Modernos​

  • HTTP/2: Múltiplas requisições paralelas em uma conexão.
  • WebSockets: Comunicação bidirecional em tempo real.
  • gRPC: Protocol Buffers para comunicação entre microserviços.

Integração Nativa com AWS​

  • Target Types Flexíveis: EC2, containers ECS/EKS, Lambda, IPs.
  • SSL/TLS Gerenciado: Certificados do AWS Certificate Manager.
  • Segurança Integrada: AWS WAF para proteção contra ataques.

Quando Usar Cada Tipo:​

Use ALB quando:​

  • Aplicações web modernas (React, Angular, Vue).
  • APIs REST ou GraphQL.
  • Arquiteturas de microserviços.
  • Necessita roteamento baseado em conteúdo.
  • Integração com containers ou Lambda.

Use NLB quando:​

  • Ultra alta performance (milhões req/seg).
  • Protocolos não-HTTP (TCP/UDP).
  • Necessita IP estático.
  • Jogos online ou aplicações real-time.

Use GLB quando:​

  • Deploy de appliances virtuais (firewalls, IDS/IPS).
  • Necessita transparência de rede (preserva headers originais).
  • Inspeção de tráfego com third-party solutions.
  • Arquiteturas de segurança centralizadas.

Evite CLB:​

  • Considerado legado pela AWS.
  • Migre para ALB ou NLB.

Casos de Uso Ideais para ALB:​

1. Arquitetura de Microserviços​

ALB → /api/auth/*     → Authentication Service
    → /api/users/*    → User Management Service  
    → /api/payments/* → Payment Service
    → /api/orders/*   → Order Processing Service

2. Aplicações Multi-tenant​

ALB → empresa-a.api.com → Tenant A Infrastructure
    → empresa-b.api.com → Tenant B Infrastructure
    → *.api.com         → Default/Shared Services

3. Blue/Green Deployments​

ALB → 90% tráfego → Versão Atual (Blue)
    → 10% tráfego → Nova Versão (Green)

4. A/B Testing​

ALB → Header: experiment=true  → Versão Experimental
    → Header: experiment=false → Versão Estável

Componentes Principais do ALB​

Entender a arquitetura do ALB é fundamental para usar todo seu potencial:

Load Balancer​

  • O próprio ALB, distribuído em múltiplas AZs
  • Endereço DNS público para receber tráfego.
  • Configurações de segurança e rede.

Listeners​

  • "Ouvintes" que ficam aguardando conexões.
  • Definem protocolo e porta (HTTP:80, HTTPS:443).
  • Contêm regras de roteamento.

Target Groups​

  • Grupos de destinos que recebem tráfego.
  • Podem conter EC2, IPs, Lambda, ALBs.
  • Configurações de health check específicas.

Rules​

  • Regras que determinam para onde enviar cada requisição.
  • Baseadas em condições (path, host, headers).
  • Prioridades definem ordem de avaliação.

Fluxo de uma Requisição no ALB​

  1. Cliente faz requisição → https://api.empresa.com/api/users
  2. DNS resolve → Endereço do ALB
  3. ALB recebe → Listener HTTPS:443 captura
  4. Avalia regras → /api/users matches rule #2
  5. Seleciona target → Target Group "user-service"
  6. Health check → Apenas targets saudáveis
  7. Forwarding → Envia para instância específica
  8. Resposta → Retorna ao cliente via ALB

Benefícios do ALB​

Flexibilidade​

  • Roteamento baseado em conteúdo
  • Suporte a múltiplos tipos de target
  • Integração com toda stack AWS

Segurança​

  • Terminação SSL/TLS centralizada
  • Integração nativa com WAF
  • Security Groups granulares

Observabilidade​

  • Métricas detalhadas no CloudWatch
  • Access logs customizáveis
  • Integration com AWS X-Ray

Custo-benefício​

  • Paga apenas pelo que usa
  • Reduz complexidade de infraestrutura
  • Elimina necessidade de proxies adicionais

Limitações e Considerações​

Limitações Importantes:​

  • Latência adicional: ~1-2ms vs conexão direta
  • Complexidade: Mais configurações que load balancers simples
  • Custos: Pode ser mais caro que soluções básicas
  • Vendor lock-in: Específico da AWS

Quando NÃO Usar ALB:​

  • Aplicações que precisam de IP estático
  • Protocolos não-HTTP (TCP/UDP puros)
  • Requisitos de latência ultra-baixa (menor que 1ms)
  • Orçamento muito restrito

Preparando-se para a Configuração​

Antes de partir para a configuração prática do ALB, você precisa entender:

  1. Arquitetura de rede: VPC, subnets, security groups
  2. Targets disponíveis: Que aplicações/serviços você quer balancear
  3. Requisitos de roteamento: Como dividir o tráfego
  4. Certificados SSL: Se vai usar HTTPS
  5. Monitoramento: Que métricas são importantes
