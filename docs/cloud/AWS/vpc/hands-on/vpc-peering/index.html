VPC Peering

Objetivo​

Conectar a lab-vpc a uma segunda VPC usando VPC Peering, configurar as rotas nos dois lados e comprovar a comunicação por IP privado.

Veja a teoria em VPC Peering e Transit Gateway.

O que vamos criar​

RecursoNomeDetalhes
VPClab-vpc-b10.1.0.0/16 (não pode sobrepor a lab-vpc, que é 10.0.0.0/16)
Sub-redesub-b-1a10.1.1.0/24, na AZ a
Security Grouplab-b-sgICMP e SSH vindos de 10.0.0.0/8
Instânciaec2-bNa sub-b-1a, sem IP público
Peeringpeering-labEntre lab-vpc e lab-vpc-b

Pré-requisitos​

  • lab-vpc com a ec2-publica em execução e a rt-publica (EC2 pública e privada)
  • O mesmo par de chaves das outras instâncias

Etapas​

1. Criar a segunda VPC e a sub-rede​

  1. No console da VPC, crie uma VPC (Somente VPC): Nome lab-vpc-b, CIDR 10.1.0.0/16.
  2. Crie uma sub-rede: VPC lab-vpc-b, Nome sub-b-1a, AZ a mesma da ec2-publica, CIDR 10.1.1.0/24.

Não crie Internet Gateway: a lab-vpc-b não precisa de internet.

2. Criar o Security Group e a instância​

  1. Crie o Security Group: Nome lab-b-sg, VPC lab-vpc-b, com duas regras de entrada, ambas com origem 10.0.0.0/8:
    • Todos os ICMP - IPv4
    • SSH
  2. Lance a instância: Nome ec2-b, Amazon Linux 2023, t3.micro, mesmo par de chaves, VPC lab-vpc-b, Sub-rede sub-b-1a, IP público: Desabilitar, Security Group lab-b-sg.
  3. Anote o IP privado da ec2-b (começa com 10.1.1.).
observação

A origem 10.0.0.0/8 cobre as VPCs dos laboratórios (10.0, 10.1 e 10.2). Assim o mesmo Security Group serve também para o laboratório de Transit Gateway.

3. Testar antes do peering​

Conecte na ec2-publica (ssh -A) e rode:

ping -c 3 -W 2 IP_PRIVADO_EC2_B

O ping não responde. Não há rota entre as duas VPCs.

4. Criar a conexão de peering​

  1. No console da VPC, clique em Conexões de emparelhamento → Criar conexão de emparelhamento.
  2. Nome: peering-lab.
  3. VPC solicitante: lab-vpc.
  4. Conta: Esta conta. Região: Esta região.
  5. VPC aceitadora: lab-vpc-b.
  6. Clique em Criar conexão de emparelhamento. O status fica Pending acceptance.
  7. Selecione a conexão → Ações → Aceitar solicitação → confirme. O status muda para Active.

5. Criar as rotas nos dois lados​

Só criar o peering não faz nada funcionar. Cada lado precisa de uma rota.

Na lab-vpc:

  1. Abra a rt-publica → Editar rotas → Adicionar rota.
  2. Destino: 10.1.0.0/16. Alvo: Conexão de peering → peering-lab.

Na lab-vpc-b:

  1. Abra a route table principal da lab-vpc-b (a associada à sub-b-1a) → Editar rotas → Adicionar rota.
  2. Destino: 10.0.0.0/16. Alvo: Conexão de peering → peering-lab.
Route tableDestinoAlvo
rt-publica10.1.0.0/16peering-lab
Principal da lab-vpc-b10.0.0.0/16peering-lab

6. Testar depois do peering​

Na ec2-publica:

ping -c 3 IP_PRIVADO_EC2_B
ssh ec2-user@IP_PRIVADO_EC2_B

Agora o ping responde e o SSH funciona, tudo por IP privado, sem passar pela internet.

O que observar​

  • Foram necessárias rotas nos dois lados, além do Security Group liberando a origem.
  • Os CIDRs não se sobrepõem (10.0.0.0/16 e 10.1.0.0/16). Com CIDRs iguais, o peering não funcionaria.
  • A ec2-b não tem internet nem IP público, e mesmo assim é alcançada. O peering usa a rede privada da AWS.
  • O peering não é transitivo: se existisse uma terceira VPC ligada só à lab-vpc-b, ela não alcançaria a lab-vpc.
  • O peering não tem taxa, e a transferência de dados segue as regras de cobrança normais da AWS.

Limpeza​

Se for fazer o laboratório de Transit Gateway em seguida, mantenha a lab-vpc-b e a ec2-b, mas apague o peering e as rotas (passos 1 e 2 abaixo), para não conflitarem com o Transit Gateway.

  1. Apague a rota 10.1.0.0/16 da rt-publica e a rota 10.0.0.0/16 da route table da lab-vpc-b.
  2. Em Conexões de peering, selecione peering-lab → Ações → Excluir conexão de emparelhamento.
  3. Se não for continuar: encerre a ec2-b, exclua o lab-b-sg, a sub-rede sub-b-1a e a lab-vpc-b.
