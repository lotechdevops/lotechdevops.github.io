Security Groups em camadas

Objetivo​

Aplicar o padrão de Security Groups em camadas: cada camada só aceita tráfego vindo da camada imediatamente anterior, referenciando o Security Group de origem, e não endereços IP.

Veja a teoria em Security Groups e NACLs.

O que vamos montar​

CamadaInstânciaSecurity GroupAceita
Webec2-publicalab-publica-sg (já existe)SSH do seu IP
Aplicaçãoec2-privada-1alab-app-sg (novo)TCP 8080 e SSH, só de lab-publica-sg
Bancoec2-privada-1blab-db-sg (novo)TCP 3306 só de lab-app-sg, e SSH de lab-publica-sg

Como o objetivo é testar as regras, vamos simular os serviços com um servidor web simples do Python, nas portas 8080 (aplicação) e 3306 (banco).

Pré-requisitos​

  • Instâncias ec2-publica, ec2-privada-1a e ec2-privada-1b em execução (EC2 pública e privada)
  • Acesso SSH às instâncias privadas pela pública, com ssh -A

Etapas​

1. Criar o Security Group da aplicação​

  1. No EC2, vá em Security Groups → Criar grupo de segurança.
  2. Nome: lab-app-sg. VPC: lab-vpc.
  3. Regras de entrada:
    • TCP personalizado, porta 8080, origem o grupo lab-publica-sg
    • SSH, origem o grupo lab-publica-sg
  4. Mantenha a saída padrão e clique em Criar grupo de segurança.

2. Criar o Security Group do banco​

  1. Crie outro: Nome: lab-db-sg. VPC: lab-vpc.
  2. Regras de entrada:
    • TCP personalizado, porta 3306, origem o grupo lab-app-sg
    • SSH, origem o grupo lab-publica-sg
  3. Mantenha a saída padrão e clique em Criar grupo de segurança.
observação

Observe que o banco aceita a porta 3306 apenas de quem pertence ao lab-app-sg. Se você adicionar mais servidores de aplicação no futuro, basta usar o mesmo Security Group nas novas instâncias. Nenhuma regra muda.

3. Trocar os Security Groups das instâncias​

  1. Selecione a ec2-privada-1a → Ações → Segurança → Alterar grupos de segurança.
  2. Remova o lab-privada-sg e adicione lab-app-sg. Salve.
  3. Faça o mesmo na ec2-privada-1b, trocando pelo lab-db-sg.
observação

As mudanças valem imediatamente, sem reiniciar as instâncias.

4. Subir os serviços de teste​

Conecte na ec2-publica (ssh -A) e, a partir dela, na ec2-privada-1a. Rode o "serviço de aplicação":

sudo pkill -f http.server
mkdir -p ~/site && echo "app-1a ok" > ~/site/index.html
nohup python3 -m http.server 8080 --directory ~/site > ~/server.log 2>&1 &
sleep 1
curl -m 5 http://localhost:8080

Deve retornar app-1a ok. Saia (exit), conecte na ec2-privada-1b e rode o "serviço de banco":

sudo pkill -f http.server
mkdir -p ~/site && echo "db-1b ok" > ~/site/index.html
nohup python3 -m http.server 3306 --directory ~/site > ~/server.log 2>&1 &
sleep 1
curl -m 5 http://localhost:3306

Deve retornar db-1b ok.

Por que esses comandos?
  • pkill encerra servidores antigos: se a porta já estiver ocupada, o servidor novo morre e o curl retorna Empty reply from server.
  • nohup e > ~/server.log mantêm o servidor vivo mesmo se o terminal fechar. Em caso de erro, leia cat ~/server.log.
  • index.html faz cada instância responder com o próprio nome.

Os dois ficam rodando em segundo plano. Saia da ec2-privada-1b e volte para a ec2-publica.

5. Testar as camadas​

Anote o IP privado de cada instância privada.

a) Web → Aplicação (deve funcionar). Na ec2-publica:

curl -m 5 http://IP_PRIVADO_1A:8080

Retorna app-1a ok: o lab-app-sg aceita a porta 8080 de quem está no lab-publica-sg.

b) Web → Banco (deve falhar). Ainda na ec2-publica:

curl -m 5 http://IP_PRIVADO_1B:3306

Falha por tempo esgotado (Connection timed out). O banco só aceita a porta 3306 de lab-app-sg, e a camada web não faz parte dele.

c) Aplicação → Banco (deve funcionar). Conecte na ec2-privada-1a e rode:

curl -m 5 http://IP_PRIVADO_1B:3306

Retorna db-1b ok: a instância pertence ao lab-app-sg.

d) Banco → Aplicação (deve falhar). Saia, conecte na ec2-privada-1b e rode:

curl -m 5 http://IP_PRIVADO_1A:8080

Falha: o lab-app-sg só aceita a porta 8080 de lab-publica-sg, e o banco não está nele.

TesteOrigemDestinoResultado
aWebAplicação 8080Funciona
bWebBanco 3306Bloqueado
cAplicaçãoBanco 3306Funciona
dBancoAplicação 8080Bloqueado

O que observar​

  • O tipo de erro indica a camada do problema: timeout é bloqueio de rede (Security Group ou NACL); Connection refused ou Empty reply significa que a rede liberou, mas o serviço não está escutando ou falhou.
  • A origem das regras é um Security Group, e não um IP. As instâncias podem trocar de IP, e as regras continuam valendo.
  • O tráfego só flui no sentido permitido: a camada web não alcança o banco, nem o banco inicia conexão com a aplicação.
  • Cada camada expõe só a porta necessária.
  • A resposta de uma conexão permitida volta sem regra extra, pois Security Groups são stateful.

Limpeza​

Encerre os servidores de teste. Em cada instância privada, rode:

pkill -f http.server

Mantenha os Security Groups e as instâncias para os próximos laboratórios.
