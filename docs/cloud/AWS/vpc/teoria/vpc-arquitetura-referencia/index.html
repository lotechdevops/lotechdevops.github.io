Arquitetura de Referência

Objetivo​

Este artigo junta os conceitos da seção em uma arquitetura clássica: uma aplicação web em três camadas, distribuída em duas Availability Zones.

A arquitetura​

CamadaSub-redeO que rodaAcesso
ApresentaçãoPúblicaLoad Balancer, NAT GatewayInternet
AplicaçãoPrivadaInstâncias EC2 (Auto Scaling)Só pelo Load Balancer
DadosPrivada (isolada)Banco de dadosSó pela aplicação

Distribuição por AZ​

Em cada AZ, uma sub-rede de cada camada:

AZ AAZ B
Pública10.0.1.0/2410.0.2.0/24
Aplicação (privada)10.0.11.0/2410.0.12.0/24
Dados (privada)10.0.21.0/2410.0.22.0/24

A VPC usa, por exemplo, 10.0.0.0/16. Os números acima são apenas um exemplo de planejamento.

Como os componentes se encaixam​

Roteamento​

Route tableAssociada aRotas
PúblicaSub-redes públicas10.0.0.0/16 → local
0.0.0.0/0 → Internet Gateway
Privada AAplicação e dados da AZ A10.0.0.0/16 → local
0.0.0.0/0 → NAT Gateway da AZ A
Privada BAplicação e dados da AZ B10.0.0.0/16 → local
0.0.0.0/0 → NAT Gateway da AZ B
Dados (opcional)Sub-redes de dadosApenas local (sem saída para a internet)

Security Groups em cadeia​

Security GroupEntrada permitida
sg-albHTTPS 443 de 0.0.0.0/0
sg-appHTTP 8080 de sg-alb
sg-db3306 (ou a porta do banco) de sg-app

Ninguém na internet alcança a aplicação nem o banco diretamente. O tráfego só segue o caminho ALB → aplicação → banco.

Saída das instâncias privadas​

  • Para a internet (atualizações, APIs externas): NAT Gateway da própria AZ.
  • Para o S3 e DynamoDB: Gateway Endpoint (gratuito), que tira esse tráfego do NAT.
  • Para SSM, Secrets Manager, SQS: Interface Endpoints, se quiser evitar o NAT.

Acesso administrativo​

Em vez de bastion host com SSH aberto, prefira o SSM Session Manager, que não exige porta de entrada nem IP público (veja o hands-on de EC2).

Boas práticas​

Planejamento de CIDR​

  • Escolha uma faixa grande o bastante para crescer (um /16 é comum).
  • Não sobreponha com outras VPCs nem com a rede da empresa, pois isso impede peering, VPN e Transit Gateway.
  • Reserve espaço para novas camadas e novas AZs.
  • Documente os CIDRs em uma planilha central.

Alta disponibilidade​

  • Use no mínimo duas AZs e distribua as sub-redes.
  • Crie um NAT Gateway por AZ. Com um único NAT, a falha daquela AZ derruba a saída das outras (e o tráfego entre AZs é cobrado).
  • Ponha o Load Balancer em sub-redes de todas as AZs usadas.

Segurança​

  • Princípio do menor privilégio nos Security Groups: referencie outros SGs em vez de faixas de IP.
  • Banco de dados e aplicação em sub-redes privadas, sem IP público.
  • Use NACLs para bloqueios pontuais (por exemplo, um IP malicioso).
  • Habilite VPC Flow Logs (ao menos REJECT) para auditoria.
  • Use policies de endpoint para limitar o que sai pelos endpoints.

Custos​

ItemAtenção
NAT GatewayCobrado por hora e por GB. Use Gateway Endpoint para o S3
IPv4 públicoCobrado por hora, inclusive em uso
Interface EndpointsPor hora, por AZ
Transit GatewayPor attachment/hora e por GB
Tráfego entre AZsTem custo. Mantenha tráfego intenso na mesma AZ quando possível

Evoluindo a arquitetura​

NecessidadeComponente
Conectar outra VPC (outro ambiente)Peering ou Transit Gateway
Ligar o escritórioSite-to-Site VPN ou Direct Connect
Funcionários remotosClient VPN
Resolver nomes internosZona privada do Route 53 + Resolver Endpoints
Investigar bloqueiosReachability Analyzer + Flow Logs

Resumo rápido​

  • Arquitetura clássica: 3 camadas (pública, aplicação, dados) em 2 ou mais AZs.
  • Apenas o que precisa de internet fica em sub-rede pública (Load Balancer, NAT Gateway).
  • Aplicação e banco ficam em sub-redes privadas, protegidos por Security Groups em cadeia.
  • Um NAT Gateway por AZ, e Gateway Endpoint para o S3.
  • Planeje os CIDRs com folga e sem sobreposição desde o início.
  • Prefira SSM Session Manager a bastion hosts.
