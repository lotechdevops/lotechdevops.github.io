Políticas de Roteamento (Routing Policies)

O Amazon Route 53 permite controlar como o tráfego DNS será roteado para seus recursos usando diferentes políticas de roteamento. Essas políticas determinam como o Route 53 responde às consultas DNS, podendo levar em conta fatores como: geolocalização, latência, falhas, balanceamento de carga, entre outros.

Ao criar um registro DNS no Route 53, você escolhe uma dessas políticas, de acordo com o seu objetivo.

Tipos de Políticas​

1. Roteamento Simples (Simple Routing)​

Essa é a política mais básica e direta. Com ela, o Route 53 responde com um único valor, como um endereço IP ou um nome de recurso (por exemplo, um ALB ou S3).

Quando usar:

Use o Simple Routing quando você tiver um único recurso e não precisar de balancemento, failover ou qualquer lógica adicional.

Exemplo:

foo.example.com -> 11.22.33.44

2. Roteamento por peso (Weighted Routing)​

O Weighted Routing permite distribuir o tráfego entre múltiplos recursos com base em pesos definidos. Isso é útil em cenários como testes A/B, deploys progressivos (canary) ou ambientes blue/green.

Como funciona:

Você atribui uma porcentagem (ou peso) a cada destino. O Route 53 distribui as respostas de acordo com esses pesos.

Exemplo:

  • 70% do tráfego -> ALB na us-east-1
  • 20% do tráfego -> ALB na us-west-2
  • 10% do tráfego -> ALB na eu-central-1

Você também pode ativar health checks, assim o Route 53 redireciona automaticamente o tráfego para os destinos saudáveis.

3. Roteamento por Geolocalização (Geolocation Routing)​

Esse tipo de roteamento responde às consultas DNS com base na localização geográfica do usuário. Você pode definir regras por continente, país ou até estado (nos EUA).

Quando usar:

Quando quiser personalizar a experiência dos usuários de acordo com sua localização, como idiomas, ofertas locais ou servidores regionais.

Exemplo:

  • Usuários da França -> fr.example.com (55.66.77.88)
  • Usuários da Alemanha -> de.example.com (11.22.33.44)

Você também pode configurar um destino "default (99.11.22.33)" para qualquer região não coberta por regras específicas.

4. Roteamento por Geoproximidade (Geoproximity Routing)​

Esse tipo é semelhante ao anterior, mas funciona com base na proximidade física entre o usuário e os endpoints. A diferença é que aqui você pode aplicar um bias, um ajuste manual que permite expandir ou reduzir a área de influência de cada recurso.

Observação:

Essa política exige o uso do recurso Route 53 Traffic Flow.

Exemplo:

Você pode configurar para que usuários dos EUA sejam redirecionados preferencialmente para um servidor no Norte da Califórnia, mas com bias estendido até o Norte da Vírgina.

5. Roteamento por Latência (Latency Routing)​

Com essa política, o Route 53 envia o tráfego para o endpoint com menor latência de rede, baseado em medições feitas entre os resolvers DNS e os data centers da AWS.

Quando usar:

Quando você possui recursos em várias regiões da AWS e quer sempre entregar a melhor performance possível para o usuário final.

Exemplo:

  • Usuário da EUA, Europa e Africa -> recebe IP de um ALB na us-east-1.
  • Usuário da Asia -> é direcionado para um endpoint na ap-southeast-1.

Também pode ser combinado com health checks para garantir que a performance esteja associada à disponibilidade.

6. Respostas Múltiplas (Multivalue Answer Routing)​

Essa política retorna vários IPs como resposta DNS, simulando um round-robin com verificação de integridade.

Diferencial:

O Route 53 realiza health checks nos destinos e retorna apenas os IPs saudáveis.

Exemplo:

  • www.example.com -> [192.0.2.2, 198.51.100.2, 203.0.113.2]

Essa abordagem pode ser útil para balanceamento direto, sem uso de Load Balancer.

7. Roteamento com Failover (Failover Routing)​

Essa política cria um mecanismo de alta disponibilidade, com um endpoint primário e um secundário (de backup).

Como funciona:

O Route 53 realiza verificações de integridade (health checks) no endpoint primário. Se ele falhar, o tráfego é automaticamente redirecionado para o endpoint secundário.

Exemplo:

  • Primário: api.example.com -> ALB na us-east-1
  • Secundário: api.example.com -> ALB na us-west-2

Essa política exige health check ativo no recurso primário.

Conclusão​

Cada política de roteamento tem seu cenário ideal de uso. O segredo é entender como seu tráfego deve se comportar e escolher a política que melhor atende seus requisitos de disponibilidade, performance ou controle regional.
