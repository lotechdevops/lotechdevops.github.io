Deploy com Application Load Balancer (ALB) no Elastic Beanstalk

Objetivo​

Realizar o deploy com Application Load Balancer (ALB) de uma aplicação no Amazon Elastic Beanstalk, aplicando customizações de rede, capacidade e operações alinhadas a boas práticas de produção. Diferente do Lab 1, aqui você ajustará explicitamente os recursos do ambiente antes do provisionamento.

Etapas de Configuração​

Etapa 1 - Configurações do Ambiente​

  1. Abra o console do Amazon Elastic Beanstalk em https://console.aws.amazon.com/elasticbeanstalk/

  2. Clique em Criar aplicação

  3. Na etapa Configurar ambiente, selecione:

    • Ambiente de servidor Web -> Usado para sites, APIs ou aplicações web acessíveis via HTTP.

  4. Em Informações da aplicação, informe o nome da aplicação

  5. Em Informações do ambiente, preencha:

    • Nome do Ambiente -> Esse nome será utilizado para identificar e acessar a aplicação.

  6. Em Plataforma, selecione:

    • Python (versão mais recente disponível)

  7. Em Código da aplicação, escolha Fazer upload do seu código e preencha:

    • Rótulo da versão -> identificador da versão do código.
    • Arquivo local -> Selecione o pacote .zip da sua aplicação.

  8. Em Predefinições, escolha:

    • Configuração personalizada -> Permite ajustar manualmente parâmetros como rede, segurança, escalabilidade e banco de dados.

  9. Clique em Próximo para seguir para a etapa 2.

Etapa 2 - Configuração de acesso ao serviço​

Nesta etapa, configure os perfis do IAM que o Elastic Beanstalk utilizará para gerenciar os recursos do ambiente.

2.1 - Perfil de serviço (Obrigatório): Ao clicar em Criar perfil, a tela de criação da Role do IAM é exibida. Nela você deve selecionar o serviço que usará essa Role e o caso de uso específico.

  • Elastic Beanstalk - Compute -> Esse caso de uso é voltado para o perfil de instância EC2. Ele concede permissões para que as instâncias criadas no ambiente possam executar ações necessárias para a aplicação, como acessar o Amazon S3 ou enviar métricas para o CloudWatch.

  • Elastic Beanstalk - Environment -> Esse caso de uso é o correto para o Perfil de serviço, pois permite que o Elastic Beanstalk tenha acesso a outros recursos da AWS necessários para criar e gerenciar ambientes.

  • Para o Perfil de serviço, selecione Elastic Beanstalk - Environment e continue a criação da Role.

  • Geralmente, ao final da criação, o console gera automaticamente uma Role chamada aws-elasticbeanstalk-service-role, que será utilizada para esse propósito.

2.2 - Perfil da Instância EC2 (Obrigatório): Ao clicar em Criar perfil, a tela de criação da Role do IAM é exibida com as mesmas opções de caso de uso vistas no Perfil de serviço.

A diferença está na escolha correta do caso de uso: Elastic Beanstalk - Compute

  • Ela concede permissões para que as instâncias do ambiente consigam executar ações necessárias, como:
    • Enviar logs e métricas para o Amazon CloudWatch.
    • Acessar arquivos armazenados no Amazon S3.
    • Interagir com outros serviços de suporte dentro da AWS.

  • Para o Perfil da instância EC2, selecione Elastic Beanstalk - Compute e continue a criação da Role.

  • Normalmente, o console cria uma Role com o nome aws-elasticbeanstalk-ec2-role, que será associada automaticamente às instâncias EC2 do ambiente.

2.3 - Par de chaves EC2 (opcional):

  • Selecione um par de chaves existente ou crie um novo caso queira acessar as instâncias via SSH.
  • Essa configuração é opcional: se não precisar de acesso remoto às instâncias, pode deixar em branco.

Boas práticas de Produção:

  • "Revise as permissões padrão das roles criadas automaticamente"
  • "Sempre utilize o Princípio do Menor Privilégio
  • "Considere armazenar credenciais sensíveis no AWS Secrets Manager"

Etapa 3 - Definir redes, banco de dados e etiquetas​

Nesta etapa, você pode configurar como o ambiente do Elastic Beanstalk será provisionado em termos de rede, banco de dados e organização com etiquetas.

3.1 - Configurações de instâncias:

  • VPC, selecione VPC personalizada criada por você.

  • Endereço IP público -> Marque essa opção apenas se quiser que as instâncias EC2 recebam IP público diretamente.

  • Sub-redes -> Selecione ao menos uma sub-rede privada criada por você.

3.2 - Banco de dados:

  • Essa opção permite integrar um RDS ao ambiente, criando um banco de dados gerenciado junto à aplicação.

Atenção: Se você habilitar o banco de dados, lembre-se que o RDS não é excluído automaticamente quando o ambiente do Beanstalk for encerrado. É necessário removê-lo manualmente para evitar custos extras.

3.3 - Etiquetas (tags):

  • As tags permitem identificar, organizar e gerenciar seus recursos dentro da AWS.
  • Cada tag é formada por um par chave/valor
  • O uso de tags é opcional

Etapa 4 - Configurar o tráfego e a escalabilidade da instância (Opcional)​

Nesta etapa, o Elastic Beanstalk ajuste as configurações avançadas como relacionadas às instâncias EC2 e ao Auto Scaling do ambiente.

4.1 - Instâncias:

  • Em Volume raiz (dispositivo de inicialização), define o tipo, tamanho e performance do volume EBS associado às instâncias.

  • Em Monitoramento do Amazon CloudWatch, define o intervalo de coleta de métricas. Pode ser de 5 minutos (padrão) ou 1 minuto (para maior granularidade).

  • Em Serviço de metadados da instância (IMDS), por padrão, o Beanstalk habilita apenas o IMDSv2 por questões de segurança.

  • Em Grupos de segurança do EC2, escolhe os Security Groups que irão controlar o tráfego de rede das instâncias.

4.2 - Capacidade (Auto Scaling):

  • Em Tipo de ambiente, selecione Carga balanceada para utilizar múltiplas instâncias EC2 atrás de um balanceador de carga.

  • Em Mínimo e Máximo, define a quantidade de instâncias mínima e máxima que o Auto Scaling poderá manter.

  • Em Composição da frota, escolha entre instâncias sob demanda (garantem disponibilidade) ou instâncias Spot (mais baratas, porém sem garantia de permanência).

  • Em Arquitetura, selecione x86_64 (mais compatível) ou arm64 (mais econômico, se sua aplicação suportar).

  • Em Tipos de instâncias, selecione os tipos de máquinas EC2 que poderão ser utilizados. Por padrão já aparecem t3.micro e t3.small, mas você pode adicionar ou remover conforme necessário.

  • Em ID da AMI, mantenha a opção padrão (selecionada automaticamente pelo Beanstalk) ou escolha uma AMI personalizada, caso precise de um ambiente pré-configurado.

  • Em Resfriamento da escalabilidade, defina o tempo mínimo (em segundos) que o Auto Scaling aguardará entre uma ação de escala e outra (scale in/ scale out). O valor padrão é 360 segundos (6 minutos).

  • Em Acionadores de Escalabilidade -> Aqui você define as regras automáticas para aumentar ou reduzir as instâncias com base em métricas do CloudWatch

    • Métrica -> métrica do CloudWatch usada como referência. (Ex: NetworkOut, CPUUtilization).
    • Estatística -> como a métrica será interpretada: Average (média), Minimum (mínimo), Maximum (máximo) ou Sum (soma).
    • Unidade -> a unidade da métrica (ex: Bytes, Percent).
    • Período -> intervalo entre avaliações da métrica (em minutos). (ex: a cada 5 minutos).
    • Duração da ruptura -> tempo que a métrica precisa permanecer acima ou abaixo do limite para disparar a ação. (ex: 5 minutos).
    • Limite superior -> valor da métrica que, quando ultrapassado, aciona scale out (adicionar instância).
    • Incremento para aumentar -> quantas instâncias EC2 serão adicionadas quando o limite superior for ultrapassado.
    • Limite inferior -> valor da métrica que, quando ficar abaixo, aciona scale in (remover instância).
    • Incremento para diminuir -> quantas instâncias EC2 serão removidas quando o limite inferior for atingido.

4.3 - Configurações de rede do balanceador de carga

  • Em Visibilidade, defina se o Load Balancer será:

    • Pública -> acessível pela Internet (usado para aplicações web).
    • Interna -> acessível apenas dentro da VPC (usado para sistemas internos/microsserviços).

  • Em Sub-redes do balanceador de carga, selecione:

    • Sub-redes públicas se a visibilidade for Pública

    • Sub-redes privadas se a visibilidade for Interna

    • Para alta disponibilidade, escolha duas ou mais sub-redes em diferentes zonas de disponibilidade (AZs)

4.4 - Tipo de balanceador de carga

  • Application Load Balancer (ALB) -> recomenado para aplicações web, trabalha na camada 7 (HTTP/HTTPS).

    • Ao escolher ALB, é necessário definir se ele será:

      • Dedicado -> o Elastic Beanstalk cria um Load Balancer exclusivo para esse ambiente.

      • Compartilhado -> permite usar um Load Balancer já existente na sua conta, podendo ser compartilhado entre vários ambientes.

  • Network Load Balancer (NLB) -> trabalha na camada 4 (TCP/UDP), indicado para tráfego de baixa latência e suporte a endereços IP estáticos.

    • Ao escolher NLB, não é necessário definir se será dedicado ou compartilhado.

4.5 - Receptores, Processos e Regras

  • Em Receptores -> definem em qual porta/protocolo o Load Balancer vai receber as conexões.

    • Porta 80 por padrão já vem habilitada.
    • Se quiser HTTPS, é necessário adicionar um receptor na porta 443 e associar um certificado SSL (ACM).

  • Em Processos -> definem como o tráfego recebido pelo receptor será encaminhado para as instâncias EC2.

    • Padrão: porta 80 (HTTP)
    • Aqui também é configurado o caminho de verificação de integridade (health check).
    • Perdurabilidade (Stickiness) -> controla se a sessão do usuário sempre será direcionado para mesma instância. Por padrão vem Desabilitado.

  • Em Regras -> permitem criar condições personalizadas para rotear o tráfego.

    • Por padrão, existe apenas a regra default, que encaminha todo o tráfego para o processo principal.

4.6 - Acesso aos arquivos de Log

  • Em Armazenar logs -> habilita o envio dos logs de acesso do Elastic Load Balancer (ALB ou NLB) para um bucket do Amazon S3
    • Esse logs contêm informações detalhadas de cada requisição: IP de origem, caminho solicitado, latência, status de resposta, entre outros.
    • Útil para auditoria, análise de tráfego e troubleshooting

Ao habilitar, você deve escolher um bucket S3 ou permitir que o Beanstalk crie um automaticamente.

Etapa 5 - Configurar atualizações, monitoramento e registros em log​

5.1 - Monitoramento

  • Em Relatórios de integridade, selecione uma das opções:

    • Básico -> fornece apenas informações gerais do ambiente (ex: status "Ok", "Warning" ou "Severe").

    • Aprimorado -> coleta métricas detalhadas em tempo real de instâncias e recursos, exibindo diagnósticos mais completos.

      • Ao selecionar essa opção, você pode configurar métricas personalizadas do CloudWatch para instâncias e para o ambiente, além das métricas padrão já habilitadas.

  • Em Personalização de regra de monitoramento de integridade, marque as opções:

    • Ignorar aplicação 4xx -> para desconsiderar erros 4xx (como 404 ou 403) retornados pela aplicação durante a verificação de integridade.

    • Ignorar balanceador de carga 4xx -> para desconsiderar erros 4xx originados no Load Balancer.

      • Útil para evitar falsos positivos em apps que retornam muitos 404 ou 403, mas não necessariamente indicam falha real.

  • Em Streaming de eventos de integridade para o CloudWatch Logs -> por padrão a opção vem desabilitada.

    • Ao habilita, os eventos de integridade são enviados para o CloudWatch Logs, permitindo armazenamento de longo prazo, criação de dashboards personalizados e configuração de políticas de retenção.

5.2 - Atualizações gerenciadas da plataforma

  • Quando habilitada, o Elastic Beanstalk aplica automaticamente atualizações da plataforma durante a janela de manutenção configurada.

  • Em Janela de atualização semanal -> define o dia e horário (UTC) em que as atualizações serão aplicadas.

    • Durante esse período, o Beanstalk realiza updates de forma controlada, mantendo a aplicação disponível.

  • Em Nível da atualização, selecione umas das opções:

    • Patch e secundária -> aplica atualizações de segurança, correções de bugs e pequenas melhorias.
    • Somente Patch -> aplica atualizações de segurança e correções de bugs.

  • Em Substituição de instâncias

    • Se habilitada, força a recriação das instâncias mesmo quando não há novas atualizações disponíveis.
    • Útil para garantir que instâncias antigas sejam renovadas periodicamente.

5.3 - Notificações por e-mail

  • Em E-mail, insira um endereço de e-mail válido para receber notificações automáticas do Elastic Beanstalk.
    • Essas notificações incluem eventos importantes do ambiente, como:
      • Falhas na implantação
      • Problemas de integridade
      • Atualizações da plataforma
    • Permite acompanhar o status do ambiente sem precisar acessar o console constantemente.

5.4 - Atualizações e implantações contínuas

  • Em Implantações da aplicação, selecione como o Beanstalk vai atualizar as instâncias:

    • Todas de uma vez -> substitui todas as instâncias ao mesmo tempo. Mais rápido, mas pode causar indisponibilidade durante o deploy.
    • Contínua (Rolling) -> atualiza grupos de instâncias em lotes. Mantém parte do ambiente ativo enquanto o restante é atualizado.
    • Contínua com lote adicional -> cria um lote extra temporário para manter a capacidade total do ambiente durante o deploy.
    • Imutável -> cria novas instâncias com a nova versão e substitui as antigas apenas quando estiver tudo validado. Evita downtime, mas consome mais recursos.
    • Divisão de tráfego (Blue/Green) -> cria um ambiente paralelo com a nova versão e, após validação, redireciona o tráfego para ele. Requer configuração manual de DNS/Route53.

  • Em Tipo de tamanho de lote, defina como os grupos de instâncias serão atualizados:

    • Porcentagem -> define a porcentagem de instâncias que serão atualizadas por vez.
    • Corrigido -> define um número fixo de instâncias por lote.

    As opções Tamanho do lote de implantação, Divisão de tráfego e Tempo de avaliação de divisão de tráfego ficam disponíveis apenas se a opção de Implantação da aplicação não for Todas de uma vez.

    • Tamanho do lote de implantação -> quantidade (em % ou número fixo) de instâncias que receberão a atualização em cada etapa.
    • Divisão de tráfego -> permite enviar parte do tráfego para a nova versão da aplicação durante a implantação.
    • Tempo de avaliação de divisão de tráfego -> período (em minutos) que o Elastic Beanstalk vai manter a divisão de tráfego antes de finalizar a migração para a nova versão.

  • Em Atualizações da configuração:

    • Tipo da atualização contínua, escolha como as instâncias serão substituídas quando houver alterações de configuração:

      • Desabilitado -> nenhuma atualização automática é feita. Alterações só são aplicadas manualmente.

      • Contínua com base no tempo -> substitui instâncias em lotes a cada intervalo de tempo definido. Útil para ambientes previsíveis.

      • Contínua com base na integridade -> substitui instâncias em lotes, mas somente avança se o lote anterior estiver íntegro (sem falhas). Reduz risco de indisponibilidade.

      • Imutável -> cria novas instâncias com a configuração atualizada e substitui as antigas somente após validação. Mais seguro, mas consome mais recursos.

      As opções Tamanho do lote, Capacidade mínima e Tempo de pausa ficam disponíveis apenas se o tipo de atualização contínua não for Desabilitado ou Imutável.

      • Tamanho do lote -> número máximo de instâncias substituidas por vez durante a atualização.

      • Capacidade mínima -> número mínimo de instâncias que devem permanecer ativas em serviço em todas as fases da atualização.

      • Tempo de pausa -> intervalo de tempo (máx. 1 hora) que o Beanstalk aguarda antes de iniciar a próxima atualização de lote.

  • Em Preferências de implantação:

    • Ignorar verificação de integridade, escolhe as opções:

      • Verdadeiro -> o Beanstalk não reprova a implantação mesmo que ocorram falhas nas verificações de integridade. Útil em ambientes de teste, mas arriscado em produção.
      • Falso -> o Beanstalk interrompe a implantação se detectar falhas de integridade. Recomenadado para ambientes críticos/produção.

    • Limite de integridade -> define qual nível de integridade mínimo é aceito para considerar a implantação válida:

      • OK -> exige que todas as instâncias estejam saudáveis (sem falhas).
      • Aviso -> aceita pequenas falhas ou degradações, desde que não comprometam o ambiente.
      • Reduzido -> tolerar um número maior de falhas nas instâncias durante a implantação.
      • Grave -> mesmo em estado crítico o Beanstalk continua a implantação. Usado apenas para cenários de teste.

    • Tempo limite de comando -> define, em segundos, quanto tempo o Beanstalk aguardará para que cada instância conclua os comandos de implantação.

      • O valor padrão é 600 segundos (10 minutos), mas pode ser ajustado conforme a complexidade da aplicação.

5.5 - Software de plataforma

  • Em Opções de contêiner - Servidor de proxy -> define o servidor web/proxy que ficará na frente da aplicação:

    • Nginx -> padrão em ambientes Linux/Node.js/Python.
    • Apache -> dependendo da plataforma escolhida (ex: PHP).

  • Em Amazon X-Ray -> se Habilitado, ativa o daemon do X-Ray dentro das instâncias, permitindo capturar detalhes de requisições, rastrear latência e identificar gargalos.

  • Em Armazenamento de logs do S3 -> se Habilitado, envia os logs das instâncias para um bucket no Amazon S3. Útil para retenção de longo prazo, auditoria ou conformidade.

  • Em Streaming de logs de instâncias para o CloudWatch -> se Habilitado, envia os logs em tempo real para o CloudWatch Logs, permitindo monitoramento contínuo, criação de métricas e alarmes

  • Em Propriedades do ambiente (variáveis de ambiente) -> define variáveis que serão injetadas na aplicação.

    • Tipos de origem:
      • Texto simples -> valor direto no console (ex: PYTHONPATH, ENV=prod).
      • ARN de Secrets Manager/SSM -> referências seguras para senhas, tokens e parâmetros sensíveis.

Etapa 6 - Revisão e Criação​

Depois de configurar as etapas anteriores, o Elastic Beanstalk exibirá um resumo com todas as opções selecionadas para a aplicação e o ambiente.

6.1 - Revise as informações exibidas:

  • Nome da aplicação e nome do ambiente
  • Plataforma escolhida
  • Código da aplicação (aplicação de amostra ou código enviado)
  • Configuração de rede (VPC e sub-rede selecionada)
  • Perfis do IAM criados (perfil de serviço e perfil da instância EC2)
  • Predefinição escolhida (ex: Instância única)
  • Outras informações opcionais mantidas como padrão.

6.2 - Se tudo estiver correto, clique em Criar

Esse processo pode levar alguns minutos, pois o Beanstalk irá:

  • Provisionar automaticamente os recursos de infraestrutura.
  • Configurar monitoramento com CloudWatch
  • Subir a aplicação no ambiente criado.

6.3 - Ao final, será exibida uma URL pública no formato

http://<nome-do-ambiente>.<regiao>.elasticbeanstalk.com

6.4 - Clique na URL para validar que a aplicação está funcionando

  • Caso tenha usado a opção Aplicação de amostra, a página exibirá o exemplo padrão do Elastic Beanstalk.
  • Caso tenha feito upload do seu código, a aplicação definida será carregada.
