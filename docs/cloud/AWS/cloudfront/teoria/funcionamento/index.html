Como o CloudFront Funciona

Fluxo de Entrega de Conteúdo​

Quando um usuário solicita conteúdo através do CloudFront, três etapas principais acontecem automaticamente.

1. Roteamento DNS Inteligente​

O DNS do CloudFront analisa a localização do usuário e direciona a requisição para o POP (Ponto de Presença) mais próximo em termos de latência. Um usuário em São Paulo vai para um POP brasileiro, um usuário em Londres vai para um POP Europeu. Essa seleção leva apenas milisegundos.

2. Verificação de Cache no POP​

O POP verifica se possui o arquivo solicitado em cache e se ele ainda está válido (dentro do TTL).

Cache Hit (arquivo está em cache):

Usuário → POP [tem em cache!] → Entrega imediata
Tempo: 10-50ms

O melhor cenário. O arquivo é entregue instantaneamente do servidor local.

Cache Miss (arquivo não está em cache):

Usuário → POP → Cache Regional → Origem
                    ↓
              Armazena e entrega
Tempo: 200-500ms (primeira vez)

O POP primeiro consulta o cache regional antes de ir à origem. Se nem o cache regional tiver, busca na origem, armazena em ambos os níveis de cache e entrega ao usuário.

3. Streaming Progressivo​

Quando o CloudFront busca um arquivo da origem, ele não espera o download completo. Assim que o primeiro byte chega, já começa a enviar para o usuário. Isso é especialmente importante para arquivos grandes como vídeos, o usuário vẽ o conteúdo carregando progressivamente.

Arquitetura de Duas Camadas​

O CloudFront usa dois níveis de cache para otimizar entrega e reduzir carga na origem.

POPs (Edge Locations)​

São os servidores mais próximos dos usuários finais. Existem mais de 400 POPs globalmente. Sua função é entregar conteúdo muito popular com latência mínima. Porém, têm capacidade limitada e precisam remover conteúdo menos acessado constantemente para dar espaço a novos arquivos.

Caches Regionais​

Ficam entre os POPs e sua origem. Há cerca de uma dúzia distribuídos em grandes regiões geográficas (América do Sul, América do Norte, Europa, Ásia, etc.). Têm capacidade muito maior que POPs individuais e retêm conteúdo por mais tempo.

Por que dois níveis?

Conteúdo de popularidade moderada pode ser removido dos POPs mais ainda estar no cache regional. Quando um POP precisa desse conteúdo, busca do cache regional (rápido) em vez da origem (lento). Isso é especialmente valioso para conteúdo que tem acessos regulares mas não é extremamente popular.

Fluxo com Duas Camadas​

Origem (ex: S3 em São Paulo)
    ↑
Cache Regional (América do Sul)
    ↑
┌───┴────┬─────┬─────┬──────┐
POP-SP  POP-RJ POP-BSB POP-POA
  ↑       ↑      ↑       ↑
Usuários em diferentes locais

Quando múltiplos POPs de uma região precisam do mesmo arquivo, apenas um precisa buscar da origem, os demais pegam do cache regional compartilhado. Isso reduz drasticamente requisições à origem.

Casos Especiais​

Nem todo tráfego segue o fluxo padrão. Existem exceções importantes:

Requisições de Escrita: Métodos PUT, POST, PATCH, DELETE e OPTIONS vão direto do POP para a origem, pulando o cache regional. Faz sentido, essas operações modificam dados e precisam chegar imediatamente ao servidor principal.

Requisições Dinâmicas: Conteúdo que varia por usuário ou sessão não passa pelos caches regionais. O CloudFront detecta essas características e vai direto à origem.

Otimização S3: Se sua origem é um bucket S3 e o cache regional está na mesma região AWS que o bucket, o POP vai direto no S3. Não faz sentido adicionar uma camada extra quando estão no mesmo datacenter.

Exemplo Prático​

Site de e-commerce com origem em São Paulo:

Cliente → POP-SP → Cache Regional SA → S3
Tempo: 300ms

Cache vazio, precisa buscar da origem

08:10 - Segundo acesso (SP):

Cliente → POP-SP [cache hit!] → Cliente
Tempo: 15ms

Agora está em cache local, entrega instantânea.

09h00 - Primeiro acesso (RJ):

Cliente → POP-RJ → Cache Regional SA [tem!] → Cliente
Tempo: 45ms

POP do Rio não tem, mas cache regional já foi populado por SP.

10h00 - Primeiro acesso (Miami):

Cliente → POP-Miami → Cache Regional NA → S3
Tempo: 280ms

Região diferente, precisa buscar da origem novamente.

10h15 - Segundo acesso (Miami):

Cliente → POP-Miami [cache hit!] → Cliente
Tempo: 18ms

Resultado do dia:

  • Arquivo requisitado 500+ vezes
  • Origem recebeu apenas 2 requisições (SP e Miami)
  • Taxa de cache hit: 99%+
  • Economia de banda e performance excelente

Invalidação de Cache​

Quando você precisa forçar atualização antes do TTL expirar, pode invalidar o cache. A invalidação remove o objeto de todos os POPs e caches regionais simultaneamente. Na próxima requisição, o CloudFront busca a versão atualizada da origem.

Importante: As primeiras 1000 invalidações/mês são gratuitas, depois você paga por path. Para conteúdo que muda frequentemente, é melhor usar versionamento de arquivos em vez de invalidar constantemente.

Otimizações Automáticas​

O CloudFront implementa várias otimizações sem você precisar configurar:

Conexões Persistentes: Mantém conexões abertas com origens frequentemente acessadas, evitando overhead de estabelecer novas conexões TCP/TLS.

Compressão: Pode comprimir arquivos automaticamente antes de enviar ao usuário, reduzindo tamanho da transferência.

Streaming Progressivo: Começa a enviar dados assim que o primeiro byte chega, não espera o arquivo completo.

Monitoramento​

Acompanhe métricas importantes no CloudWatch:

Cache Hit Rate: Porcentagem de requisições atendidas do cache. Acima de 85% é excelente, acima de 70% é bom. Abaixo de 70% pode indicar necessidade de ajustar TLS.

Origin Requests: Número de requisições que chegam à origem. Quanto menor, melhor, siginifica que o cache está funcionando bem.

4xx/5xx Error Rate: Taxa de erros. Monitore para identificar problemas rapidamente.

Bytes Downloaded/Uploaded: Volume total de tráfego processado

Performance

Configure TTLs apropriados para cada tipo de conteúdo: imagens e CSS podem ter TTL de dias, APIs de listagem podem ter minutos, conteúdo personalizado usa TTL zero mas ainda se beneficia de otimizações de rede.
