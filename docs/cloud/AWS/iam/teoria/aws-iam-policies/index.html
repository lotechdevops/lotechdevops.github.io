Políticas e Permissões no IAM

Conceito Fundamental​

No IAM, as políticas são documentos em formato JSON que definem quais ações uma identidade ou recurso pode realizar dentro da AWS. Elas são avaliadas toda vez que uma entidade principal (usuário ou função) realiza uma solicitação.

As políticas se aplicam independentemente do método de acesso: Console, CLI ou API.

Tipos de Políticas no IAM​

A AWS oferece sete tipos principais de políticas, listadas da mais comum para a menos usada:

1. Políticas Baseadas em Identidade​

Controlam as ações que usuários, grupos ou funções (roles) podem executar.

Tipos:​

  • Políticas gerenciadas pela AWS: Prontas para uso, ex: AmazonEC2ReadOnlyAccess
  • Políticas gerenciadas pelo cliente: Criadas e mantidas por você
  • Políticas inline: Vinculadas diretamente a uma única identidade

2. Políticas Baseadas em Recursos​

Anexadas diretamente a recursos (ex: bucket S3, fila SQS), definem quem pode acessar e em quais condições.

Exemplo:​

  • Permitir que uma role de outra conta acesse um bucket S3
{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::123456789012:role/CrossAccountRole"
  },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::meu-bucket/*"
}

3. Limites de Permissões (Permission Boundaries)​

Restringem as permissões máximas que uma identidade pode exercer, mesmo que ela tenha políticas permissivas.

  • Não concedem acesso, apenas restringem
  • São ideais para delegação segura de criação de usuários

4. SCPs (Service Control Policies)​

Políticas aplicadas a contas dentro de AWS Organizations.

  • Controlam o que toda a conta pode ou não pode fazer
  • Afetam inclusive o usuário raiz
  • Não concedem permissões, apenas restringem

5. RCPs (Resource Control Policies)​

Usadas com AWS Organizations para restringir acesso a recursos de forma centralizada, sem alterar a política de cada recurso.

6. ACLs (Access Control Lists)​

Antigo modelo usado em serviços como Amazon S3, WAF, VPC.

  • Permitem controle simples entre contas
  • Não utilizam JSON

7. Políticas de Sessão​

Políticas temporárias anexadas a sessões criadas via sts:AssumeRole, AssumeRoleWithSAML, ou AssumeRoleWithWebIdentity.

  • Combinam com a política da role assumida
  • Podem impor condições extras durante o tempo da sessão

Políticas e o Usuário-Raiz​

O usuário-raiz não pode receber políticas de identidade ou limites de permissões. No entanto:

  • Pode ser afetado por SCPs e RCPs
  • Pode ser especificado em políticas baseadas em recurso (como Principal)

Estrutura de uma Política JSON​

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowListBuckets",
      "Effect": "Allow",
      "Action": "s3:ListAllMyBuckets",
      "Resource": "*"
    }
  ]
}

Elementos da Política​

CampoObrigatórioDescrição
Version✅Versão do idioma de política (use sempre "2012-10-17")
Id❌Identificador da política
Statement✅Bloco principal com as instruções
Sid❌ID opcional de cada instrução
Effect✅Allow ou Deny
Action✅Ações permitidas ou negadas
ResourceCondicionalRecursos afetados pela ação
Condition❌Condições opcionais para a instrução
PrincipalCondicionalQuem está autorizado (somente para políticas baseadas em recurso)

Exemplo Avançado com Condições​

{
  "Sid": "AllowGetObjectWithCondition",
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::meu-bucket/*",
  "Condition": {
    "Bool": { "aws:SecureTransport": "true" },
    "StringEquals": { "aws:RequestedRegion": "us-east-1" }
  }
}

Privilégio Mínimo​

Princípio básico de segurança: conceda apenas as permissões mínimas necessárias.

  • Comece com uma política restrita e expanda conforme a necessidade
  • Evite usar * em Action e Resource sem motivo claro

Boas Práticas​

  • Use políticas gerenciadas pela AWS como ponto de partida
  • Para personalização, use políticas gerenciadas pelo cliente
  • Evite políticas inline sempre que possível
  • Utilize IAM Access Analyzer para validar políticas
  • Nomeie políticas e Sid de forma descritiva

Conclusão​

As políticas do IAM são a base da segurança e do controle de acesso na AWS. Dominar sua estrutura, tipos e lógica de avaliação é essencial para proteger recursos com precisão, escalabilidade e conformidade.
