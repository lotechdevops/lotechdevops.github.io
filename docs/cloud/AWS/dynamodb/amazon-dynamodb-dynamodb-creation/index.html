Criação de Tabela no DynamoDB

Criando uma tabela no Amazon DynamoDB​

Ao criar uma tabela no DynamoDB, o primeiro passo essecial é definir um nome para a tabela, pois ele será utilizado para identificar e gerenciar a tabela em todas as consultas, integrações e operações futuras.

Nome da tabela​

  • Este campo é obrigatório
  • Escolha um nome que represente claramente o propósito da tabela ou o tipo de dados que ela armazenará.
  • É recomendado utilizar nomes significativos, por exemplo: Usuários, Pedidos, ProdutosEstoque.

Dica: Evite nomes genéricos ou abreviações díficis de entender, pois isso facilita a manutenção e a colaboração em equipe.

Chave de partição​

Após definir o nome da tabela, o próximo passo fundamental é configurar a chave de partição, que compõe a chave primária da tabela.

  • A chave de partição é um identificador único ou atributo que determina como os dados são distribuídos nos bastidores do DynamoDB, garantindo escalabilidade e alta disponibilidade
  • Este valor é usado como base para o hash interno do DynamoDB, permitindo acesso rápido e eficiente aos itens.

Exemplo prático: Em uma tabela Usuarios, a chave de partição pode ser UserID

Chave de classificação (opcional)​

Além da chave de partição, você pode adicionar uma chave de classificação, formando uma chave primária composta.

  • Essa segunda parte da chave permite armazenar múltiplos itens com o mesmo valor de chave de partição, mas diferenciados pela chave de classificação.
  • Isso possibilita organizar, consultar e filtrar dados relecionados de forma hierárquica ou por categoria.

Exemplo prático: Em uma tabela de Pedidos, a chave de classificação pode ser ClienteID e a chave de classificação pode ser DataPedido. Assim, é possível buscar todos os pedidos de um cliente ordenados por data.

Configurações da Tabela​

Na etapa de criação da tabela no DynamoDB, você pode escolher entre duas abordagens principais para definir as configurações iniciais:

  • Configurações padrão
  • Configurações personalizadas

Configurações padrão​

Esta opção é recomendada para quem deseja criar a tabela rapidamente com as definições básicas sugeridas pela AWS.

  • É ideal para projetos iniciais, protótipos ou quando você quer explorar o DynamoDB sem se preocupar, neste momento, com ajustes detalhados.
  • Mesmo escolhendo as configurações padrão, a maioria das opções pode ser modificada depois, garantindo flexibilidade para evoluir o design da tabela conforme as necessidades crescem.

Configurações personalizadas​

Ao selecionar Personalizar configurações, você terá acesso a recursos avançados que permitem ajustar o comportamento da tabela para casos de uso específicos. Entre as configurações avançadas que podem ser definidas nesta opção estão:

  • Classe da tabela (DynamoDB Standard ou DynamoDB Standard-IA)
  • Calculadora de Capacidade
  • Configurações de capacidade de leitura/gravação
  • Throughput a quente
  • Índices secundários
  • Criptografia em repouso
  • Proteção contra exclusão

Observação: Essa abordagem é recomendada quando já existe um entendimento claro sobre o volume esperado de dados, padrões de acesso ou requisitos especiais de disponibilidade e recuperação.

1. Classe da Tabela​

Classe da tabela determina como os custos serão otimizados de acordo com o padrão de acesso aos dados. Existe duas opções de configuração:

  • DynamoDB Standard
  • DynamoDB Standard-IA

- DynamoDB Standard:

É a classe padrão e mais utilizada

  • Indicada para workloads em que os dados armazenados são acessados com frequência.
  • A maior parte do custo costuma vir do throughput (operações de leitura e gravação).
  • Excelente escolha para aplicações ativas, como sistemas de pedidos, carrinhos de compras, aplicações web e APIs em tempo real.

- DynamoDB Standard-IA (Infrequent Access):

Recomendado para tabelas cujos dados são pouco acessados, mas que ainda precisam estar disponíveis com latência de milessegundos quando necessário.

  • Nessa classe, o custo do armazenamento é mais barato, mas as operações de leitura e gravação são mais caras em comparação com a classe padrão.
  • Ideal para casos como arquivamento de dados históricos, logs antigos ou tabelas de consulta eventual, em que o custo principal é o armazenamento, não o acesso frequente

💡 Resumo prático:

  • "Se a tabela precisa responder rapidamente e será consultada ou atualizada com frequência, escolha DynamoDB Standard."
  • "Se o volume de dados é grande, mas raramente consultado, Standard-IA pode reduzir custos significativos de armazenamento.

2. Calculadora de Capacidade​

Na etapa de configuração personalizda, o DynamoDB oferece uma calculadora de capacidade para estimar automaticamente as unidades de capacidade de leitura (RCU) e unidades de capacidade de gravação (WCU) que sua tabela precisará, com base nas características esperadas da workload. Abaixo, o detalhamento de cada campo:

  • Tamanho médio do item (KB): Representa o tamanho médio, em kilobytes, dos itens que serão armazenados na tabela.
    • Por padrão, vem preenchido como 1 KB, adequado para tabelas com registros pequenos, como IDs ou descrições breves.
  • Leitura de itens/segundo: Estimativa do número de leituras que a aplicação fará por segundo.
    • Padrão inicial 1, que simula uma carga muito baixa. É recomendável ajustar conforme a expectativa real de uso.
  • Gravação de itens/segundo: Quantidade estimada de operações de gravação por segundo.
    • Também vem como 1 por padrão. Ajustar conforme a previsão de inserções ou atualizações.
  • Consistência da leitura: Define o modelo de consistência desejado:
    • Eventualmente consistente (padrão): mais econômico, pois cada leitura consome metade de uma RCU.
    • Fortemente consistente: garante que a leitura sempre retorne o dados mais recente, mas consome o dobro de RCUs.
  • Consistência da gravação: Mantém como padrão, pois todas as gravações no DynamoDB já têm comportamento transacional robusto.

3. Configurações de Capacidade de Leitura/Gravação​

Nesta etapa, você define como o DynamoDB gerenciará e cobrará pelo throughput de leituras e gravações da tabela, de acordo com o perfil da sua aplicação. As opções são:

  • Sob demanda:

    Ao optar por este modo, o DynamoDB gerencia automaticamente o ajuste de escala, acomodando variações do tráfego sem que você precise definir limites fixos de capacidade.

    Por padrão, a tabela usará as cotas padrão do DynamoDB para throughput, permitindo atender a grandes volumes de solicitações caso o tráfego cresça repentinamente.

    No entanto, você pode configurar opcionalmente um throughput máximo da tabela, definindo:

    • Máximo de unidades de solicitação de leitura
    • Máximo de unidades de solicitação de gravação

    Essa configuração ajuda a limitar o uso e os custos da tabela, protegendo a aplicação contre aumentos inesperados ou uso excessivo de recursos. É especialmente útil em ambientes de teste, contas compartilhadas ou aplicações onde se deseja maior previsibilidade de custo.

    Importante: Mesmo configurando o throughput máximo, o DynamoDB continua ajustando automaticamente a escala de acordo com a demanda - apenas respeitando o limite superior que você definiu.

    Observação: É a opção recomendada para começar projetos novos, aplicações serverless ou situações em que o tráfego pode crescer rapidamente sem previsão.

  • Provisionado:

    Ao escolher o modo Provisionado, você define previamente a quantidade de capacidade de leitura e gravação que sua tabela terá. Essa abordagem garante previsibilidade de custos e controle sobre o throughput, pois você paga pela capacisade reservada independentemente de ser consumida ou não.

    Para tornar a operação mais flexível, o DynamoDB oferece a funcionalidade de Auto Scaling tanto para leitura quanto para gravação. Quando o Auto Scaling está ativado, o serviço ajusta automaticamente a capacidade provisionada da tabela conforme o volume real de tráfego. Isso permite acompanhar variações de demanda sem intervenção manual, mantendo o equilíbrio entre desempenho e custo.

    Na configuração do Auto Scaling, você define três parâmetros importantes para leitura e gravação separadamente:

    • Unidades de capacidade mínima: representa o limite inferior, ou seja, o valor mínimo de capacidade que sua tabela nunca ficará abaixo, mesmo em períodos de baixa demanda.
    • Máximo de unidades de capacidade: define o limite superior que o Auto Scaling pode alocar, evitando consumo excessivo e controlando os custos.
    • Utilização pretendida (%): indica a porcentagem média de uso que o Auto Scaling tentará manter em relação ao limite configurado. Por exemplo, se for definido como 70%, o serviço ajustará dinamicamente para manter o consumo próximo a esse valor, aumentando ou reduzindo a capacidade conforme necessário.

    Essa configuração garante que sua tabela provisionada continue atendendo picos de tráfego sem desperdício durante períodos de menor demanda, ao mesmo tempo que protege contra custos inesperados ao impor limites máximos de capacidade.

4. Throughput a Quente​

Na configuração avançanda da tabela, existe a opção de Throughput a quente, que permite pré-aquecer a tabela para lidar com picos planejados de tráfego sem sofrer atrasos de escalonamento ou controle de utilização. Ao aumentar manualmente o valor de throughput a quente, você informa ao DynamoDB que sua aplicação poderá atingir picos superiores ao padrão de consumo recente, evitando limitações temporárias quando houver crescimento repentino.

Por padrão, o DynamoDB ajusta automaticamente esses valores de throughput a quante de acordo com o histórico de consumo, tanto em tabelas no modo sob demanda quanto no modo provisionado, sem custo adicional. Essa adaptação automática considera o pico anterior e dobra a capacidade para suportar novas demandas.

Contudo, quando você já sabe que haverá um evento especial ou grande volume de requisições (como promoções, campanhas de marketing ou lançamento), é possível aumentar manualmente o throughput a quente. Essa configuração envolve definir valores mais altos para unidades de leitura por segundo e unidades de gravação por segundo, garantindo que a tabela esteja preparada para suportar esses picos desde o ínicio. Vale destacar que, ao definir esses limites manualmente, podem ser aplicadas cobranças adicionais conforme a política de preços do DynamoDB.

Essa estratégia de pré-aquecimento é especialmente útil para workloads previsíveis e eventos críticos, onde a continuidade e o desempenho da aplicação não podem ser comprometidos.

5. Índices Secundários​

Na configuração avançanda da tabela, também é possível definir índices secundários, que são estruturas opcionais mas extremamente poderosas no DynamoDB. Eles permitem que sua aplicação consulte dados de formas adicionais além da chave primária definida na tabela.

Existem dois tipos de índices secundários:

  • Índice Secundário Global (GSI): permite criar consultas usando uma chave de partição e/ou chave de classificação diferentes das chaves primárias da tabela. Os GSIs são ideais quando sua aplicação precisa de múltiplas formas de acesso aos dados ou quando é necessário atender a novos requisitos de consulta sem alterar a estrutura principal da tabela.

  • Índice Secundário Local (LSI): usa a mesma chave de partição da tabela, mas adiciona uma chave de classificação alternativa. Isso é útil quando você precisa consultar itens que compartilham a mesma chave de partição, mas deseja classificá-los ou filtrá-los de diferentes maneiras.

Na prática, os índices secundários funcionam como visões alternativas dos dados, otimizadas para diferentes padrões de acesso, sem a necessidade de duplicar informações em tabelas separadas. É importante lembrar que a criação de índices secundários gera custos adicionais, pois o DynamoDB precisa manter e atualizar esses índices sempre que os dados correspondentes na tabela principal são modificados.

Durante a criação da tabela, você pode adicionar esses índices antecipadamente, ou então criá-los posteriormente conforme a evolução das necessidades da aplicação. Essa flexibilidade é um dos pontos fortes do DynamoDB, pois permite que o design do banco de dados acompanhe o crescimento e as mudanças no uso real.

6. Criptografia em repouso​

Na configuração avançada do DynamoDB, há a opção Criptografia em repouso, que garante que todos os dados armazenados sejam protegidos automaticamente.

Por padrão, o DynamoDB aplica criptografia em repouso a todos os dados do usuário, sem a necessidade de qualquer ação adicional por parte do administrador ou desenvolvedor. Essa criptografia protege os dados contra acessos não autorizados ao nível do armazenamento físico.

O serviço utiliza o AWS Key Management Service (AWS KMS) para gerenciar as chaves de criptografia, sendo que, por padrão, o próprio DynamoDB administra essas chaves sem custo adicional. Caso seja necessario atender a requisitos mais rigorosos de segurança e compliance, você pode optar por gerenciar suas próprias chaves de criptografia no KMS (Customer Managed Keys), o que oferece maior controle sobre políticas, rotação e auditoria de uso das chaves.

Essa abordagem reforça a segurança de dados confidenciais ou sensíveis, sendo especialmente importante em aplicações corporativas ou sujeitas a normas de conformidade, como LGPD ou GDPR. Mesmo que você opte por não personalizar essa configuração, todos os dados permanecem criptografados em repouso de forma transparente.

7. Proteção contra exclusão​

No processo de criação ou ajuste de tabelas no DynamoDB, existe a opção de ativar a Proteção contra exclusão.

Essa configuração tem como objetivo proteger a tabela contra exclusões acidentais ou não autorizadas. Quando habilitada, ela impede que a tabela seja removida até que essa proteção seja manualmente desativa.

Essa funcionalidade é recomendada especialmente para tabelas que armazenam dados críticos ou que suportam workloads de produção, pois adiciona uma camada extra de segurança operacional. Com isso, mesmo que alguém com permissões administrativas tente excluir a tabela por engano ou sem o devido processo de validação, a exclusão não será permitida enquanto a proteção estiver ativa.

Essa proteção pode ser ativada ou desativada posteriormente, conforme as necessidades do ambiente, mantendo a flexibilidade na administração do banco de dados, mas garantindo maior segurança para evitar perdas de dados irreversíveis.

8. Políticas baseadas em recursos​

Na configuração de uma tabela do DynamoDB, você pode definir uma Política baseada em Recursos, que é um documento JSON utilizado para controlar quem pode acessar a tabela e de que forma esse acesso ocorre.

Essas políticas permitem aplicar regras diretamente no recurso - no caso, na tabela - tornando possível definir permisões detalhadas, como quais usuários, funções ou serviços da AWS podem realizar ações específicas (por exemplo: GetItem, PutItem, DeleteItem, entre outras).

A própria AWS fornece exemplos de políticas para facilitar a criação, cobrindo casos comuns como:

  • Permitir que uma aplicação específica leia dados de uma tabela.
  • Restringir a exclusão de itens apenas a determinados perfis.
  • Permitir que serviços integrados (como Lambda ou API Gateway) tenham acesso controlado à tabela.

Essas políticas são parte essencial do modelo de segurança do DynamoDB, alinhadas ao princípio de menor privilegio, e ajudam a garantir que os dados sejam acessados somente por entidades autorizadas, reforçando a segurança e a governança do ambiente.
