Usuários, Grupos e Permissões

O Linux é um sistema multiusuário por design. Toda ação (abrir um arquivo, iniciar um serviço, ler um log) é executada por alguém e autorizada ou negada com base em quem esse alguém é. Entender esse modelo é a base para administrar servidores, proteger dados e, mais adiante, entender containers e Pods isolam processos.

Este material está dividido em três partes:

  1. Usuários e grupos: identidade, arquivos de contas e gerenciamento
  2. Permissões: leitura, escrita, execução, chmod, chowne umask
  3. Recursos avançados: SUID/SGID/sticky bit, ACL, atributos, sudo e boas práticas.
Pré-requisito

Recomenda-se ter lido o post sobre o FHS. Os arquivos de conta ficam em /etc, e as pastas pessoais, em /home.

Parte 1 - Usuários e Grupos

1.1 O modelo de identidade​

Para o kernel, usuários e grupos não são nomes, e sim números:

  • UID (User ID): identifica o usuário
  • GID (Group ID): identifica o grupo

Os nomes (maria, devs) existem apenas para facilitar a leitura humana. O mapeamento entre nome e número fica nos arquivos de conta (seção 1.3).

Na operação: quando você restaura um backup em outra máquina e os donos dos arquivos aparecem como números (1001) em vez de nomes, é porque o UID existe nos arquivos, mas não há usuário com esse número no sistema novo.

1.2 Tipos de usuário​

TipoUID (faixa típica)Característica
root0Superusuário. O kernel ignora a maioria das restrições de permissão
Usuários de sistema1 a 999Contas de serviço (nginx, postgres, sshd). Normalmente sem login interativo
Usuários regulares1000 em diantePessoas. Possuem home e shell
nobody65534Conta sem privilégios, usada para processos que não devem possuir nada
observação

A faixa de 1000 em diante é o padrão do Debian, Ubuntu e RHEL 7+. Em sistemas mais antigos, a faixa regular começava em 500. Os limites ficam em /etc/login.defs (UID_MIN, UID_MAX, SYS_UID_MIN).

Contas de serviço devem ter shell /usr/sbin/nologin (ou /bin/false), impedindo login interativo. Se o serviço for comprometido, o invasor não ganha um shell pronto.

1.3 Os arquivos de contas​

Quatro arquivos em /etc sustentam todo o modelo:

ArquivoConteúdoPermissão típica
/etc/passwdContas de usuário644 (legível por todos)
/etc/shadowHashes de senha e políticas de expiração640 ou 000 (apenas root)
/etc/groupGrupos e seus membros644
/etc/gshadowSenhas e administradores de grupos640 ou 000

Estrutura do /etc/passwd​

maria:$y$j9T$...hash...:20400:0:90:7:14::
  1          2            3   4  5  6  7 8
CampoSignificado
1Nome de login
2Hash da senha (! ou * indica conta bloqueada ou sem senha)
3Último troca de senha (dias desde 01/01/1970)
4Mínimo de dias entre trocas
5Máximo de dias de validade da senha
6Dias de aviso antes de expirar
7Dias de tolerância após expirar
8Data de expiração da conta

O prefixo do hash indica o algoritmo: $6$ (SHA-512), $y6 (yescrypt, padrão em distribuições recentes).

Por que a senha não fica no passwd?

O /etc/passwd precisa ser legível por todos (programas consultam nome e UID o tempo todo). Se os hashes ficassem ali, qualquer usuário poderia copiá-los e tentar quebrá-los offline. Por isso existe o shadow, restrito ao root.

Estrutura do /etc/group​

devs:x:2000:maria,joao
  1  2   3       4

Campos: nome do grupo, senha (x), GID e lista de membros suplementares.

1.4 Grupos primário e suplementares​

Todo usuário possui:

  • Um grupo primário: definido no /etc/passwd. É o grupo atribuído aos arquivos que o usuário cria
  • Zero ou mais grupos suplementares: definidos no /etc/group. Concedem acessos adicionais

Muitas distribuições usam o modelo User Private Group: cada usuário recebe um grupo próprio com o mesmo nome (maria:maria). Isso facilita o compartilhamento controlado, porque o grupo primário não dá acesso a ninguém além do próprio usuário.

id maria
# uid=1001(maria) gid=1001(maria) groups=1001(maria),2000(devs),27(sudo)

1.5 Consultando identidade​

ComandoFunção
whoamiUsuário efetivo atual
idUID, GID e todos os grupos
id usuarioMesmas informações de outro usuário
groupsLista os grupos do usuário atual
who / wQuem está logado agora
lastHistórico de logins
lastlogÚltimo login de cada conta
getent passwd usuarioConsulta a conta em todas as fontes (arquivos, LDAP, AD via SSSD)
getent vs. cat /etc/passwd

Em ambientes integrados ao Active Directory ou LDAP (via SSSD ou Winbind), os usuários de domínio não aparecem no /etc/passwd. Use getent passwd e getent group, que consultam todas as fontes configuradas no nsswitch.conf.

1.6 Gerenciando usuários​

Criar Usuário useradd​

sudo useradd -m -s /bin/bash -c "Maria Souza" -G devs maria
sudo passwd maria
OpçãoFunção
-mCria o diretório home (copiando o conteúdo de /etc/skel)
-sDefine o shell
-cComentário (nome completo)
-GGrupos suplementares
-gGrupo primário
-uUID específico
-dHome personalizado
-rCria conta de sistema
-eData de expiração da conta
useradd vs. adduser

No Debian/Ubuntu existe também o adduser, um wrapper interativo e amigável (cria home, pede senha e dados). O useradd é o comando de baixo nível, disponível em qualquer distribuição e o ideal para scripts e automação.

Valores padrão ficam em /etc/default/useradd e /etc/login.defs. O /etc/skel é o molde copiado para todo novo home (.bashrc, .profile).

Modificar Usuário usermod​

sudo usermod -aG docker maria       # adiciona ao grupo docker (MANTÉM os outros)
sudo usermod -s /bin/zsh maria      # troca o shell
sudo usermod -L maria               # bloqueia a conta (lock)
sudo usermod -U maria               # desbloqueia
sudo usermod -e 2026-12-31 maria    # define expiração da conta
Cuidado com o -a

usermod -G devs maria substitui todos os grupos suplementares de maria por devs. Sempre use -aG (append) para adicionar sem remover os existentes. É um dos erros mais comuns em produção, e pode tirar o usuário do grupo sudo.

Remover Usuário userdel​

sudo userdel maria      # remove a conta, mantém o home
sudo userdel -r maria   # remove a conta e o home/mail spool

Antes de remover, verifique se há processos ou arquivos do usuário: ps -u maria e find / -user maria 2>/dev/null.

Senhas e políticas: passwd e chage​

sudo passwd maria                   # define ou troca a senha
sudo passwd -l maria                # bloqueia a senha
sudo passwd -e maria                # força troca no próximo login
sudo chage -l maria                 # exibe a política de expiração
sudo chage -M 90 -m 1 -W 7 maria    # máx 90 dias, mín 1, aviso 7
sudo chage -d 0 maria               # força troca no próximo login
sudo chage -E 2026-12-31 maria      # expira a conta nessa data

1.7 Gerenciando grupos​

sudo groupadd devs                      # cria o grupo
sudo groupadd -g 2000 devs              # com GID específico
sudo groupmod -n desenvolvedores devs   # renomeia
sudo groupdel devs                      # remove (não pode ser o primário de alguém)
sudo gpasswd -a maria devs              # adiciona maria ao grupo
sudo gpasswd -d maria devs              # remove maria do grupo
A mudança de grupo não é imediata

Os grupos de um usuário são carregados no login. Depois de adicionar maria a um grupo, ela precisa sair e entrar de novo (ou executar newgrp devs) para que a sessão enxergue o novo grupo. Use id para confirmar.

PARTE 2 - Permissões

2.1 O modelo de permissões​

Cada arquivo e diretório possui:

  • Um dono (usuário)
  • Um grupo
  • Três conjuntos de permissões: para o dono (u), para o grupo (g) e para outros (o)
ls -l /opt/app/config.yml
# -rw-r----- 1 maria devs 1240 Nov 28 10:00 config.yml

Lendo a primeira coluna:

-  rw-  r--  ---
│   │    │    └── outros (o): nenhuma permissão
│   │    └─────── grupo  (g): leitura
│   └──────────── dono   (u): leitura e escrita
└──────────────── tipo: - arquivo, d diretório, l link simbólico

Ordem de avaliação: o kernel verifica em sequência e para na primeira correspondência:

  1. Se o usuário é o dono, vale a permissão do dono
  2. Senão, se pertence ao grupo, vale a do grupo
  3. Senão, vale a de outros

Isso significa que o dono pode ter menos acesso ao grupo (ex.: ---rwx---): ele é barrado na etapa 1, mesmo pertencendo ao grupo.

2.2 O significado de rwx​

PermissãoEm um arquivoEm um diretório
r (read)Ler o conteúdoListar os nomes dos itens (ls)
w (write)Modificar o conteúdoCriar, renomear e apagar itens dentro dele
x (execute)Executar como programaAtravessar o diretório (acessar o que está dentro, cd)

Pontos que geram confusão:

  • Para apagar um arquivo, o que importa é a permissão w no diretório, não no arquivo
  • Um diretório com r mas sem x permite ver os nomes, mas não acessar os arquivos
  • Um diretório com x mas sem r permite acessar um arquivo se você souber o nome, mas não listar
  • Para alcançar /a/b/c, é preciso ter x em todos os diretórios do caminho

2.3 Notação octal​

Cada permissão tem um valor, e a soma forma um dígito:

PermissãoValor
r4
w2
x1
OctalBinárioSímbolosSignificado
7111rwxTudo
6110rw-Leitura e escrita
5101r-xLeitura e execução
4100r--Somente leitura
0000---Nada

Combinações do dia a dia:

ModoSímbolosUso típico
644rw-r--r--Arquivos comuns, públicos para leitura
600rw-------Arquivos privados (chaves SSH, segredos)
640rw-r-----Config com acesso do grupo (ex.: /etc/shadow)
755rwxr-xr-xExecutáveis e diretórios públicos
700rwx------Diretórios privados (~/.ssh)
750rwxr-x---Diretórios restritos ao grupo
Evite o chmod 777

chmod 777 concede escrita a qualquer usuário do sistema. É a "solução" mais comum para um Permission denied, e quase sempre esconde a causa real (dono ou grupo errado). Corrija o dono/grupo, não abra tudo.

2.4 Alterando permissões: chmod​

Modo octal (define tudo de uma vez):

chmod 640 config.yml
chmod 750 /opt/app

Modo simbólico (altera apenas o que for indicado):

chmod u+x script.sh         # dono ganha execução
chmod g-w arquivo           # grupo perde escrita
chmod o-rwx segredo.txt     # outros perdem tudo
chmod a+r arquivo           # todos ganham leitura
chmod u=rwx,g=rx,o= pasta   # define cada conjunto explicitamente

Sintaxe: [ugoa][+-=][rwxXst].

Recursivo:

chmod -R 750 /opt/app
chmod -R u+rwX,go-rwx /opt/app  # X = execução só em diretórios (e arquivos já executáveis)
O X maiúsculo

Com -R, usar x aplica execução em todos os arquivos. O X aplica execução somente a diretórios (e a arquivos que já eram executáveis), evitando transformar arquivos de texto em executáveis.

2.5 Alterando dono e grupo: chown e chgrp​

sudo chown maria arquivo        # troca o dono
sudo chown maria:devs arquivo   # dono e grupo
sudo chown :devs arquivo        # somente o grupo
sudo chown -R app:app /opt/app  # recursivo
sudo chgrp devs arquivo         # alternativa para o grupo

Somente o root pode mudar o dono de um arquivo. O dono pode alterar o grupo para outro grupo do qual ele faça parte.

2.6 Permissão padrão: umask​

O umask define quais permissões são removidas de novos arquivos e diretórios

  • Base para arquivos: 666 (O Linux não cria arquivos executáveis por padrão)
  • Baee para diretórios: 777
umaskArquivosDiretóriosUso
022644755Padrão clássico
002664775Colaboração em grupo
027640750Mais restritivo
077600700Privado ao dono
umask       # exibe o valor atual
umask 027   # altera para a sessão atual

O valor é herdado do shell e configurado em /etc/profile, /etc/login.defs, ~/.bashrc ou no PAM. Para serviços systemd, use UMask= na unit.

observação

Em distribuições com User Private Group, usuários comuns costumam ter umask 002, porque o grupo primário é exclusivo do usuário. Confira o valor no seu sistema com umask.

Parte 3 - Recursos Avançados

3.1 Permissões especiais: SUID, SGID e Stick Bit​

Além dos três dígitos, existe um quarto dígito à esquerda (ex.: 4775).

BitValorEm arquivo executávelEm diretório
SUID4Executa com os privilégios do dono do arquivoSem efeito
SGID2Executa com os privilégios do grupo do arquivoNovos itens herdam o grupo do diretório
Sticky1Sem efeito atualSó o dono do item (ou root) pode apagá-lo

SUID: o exemplo do passwd​

ls -l /usr/bin/passwd
# -rwsr-xr-x 1 root root 59976 ... /usr/bin/passwd
#    ^
#    s no lugar do x do dono = SUID ativo

Qualquer usuário precisa trocar a própria senha, o que exige escrever no /etc/passwd (restrito ao root). O SUID resolve: o passwd roda como root durante a execução, só para esse programa.

SGID: pasta de colaboração​

sudo mkdir /srv/projeto
sudo chown root:devs /srv/projeto
sudo chmod 2775 /srv/projeto

Com o SGID, todo arquivo criado ali pertence ao grupo devs, independentemente do grupo primário de quem criou. Combinado com umask 002, é a base para pastas compartilhadas.

Sticky bit: o caso do /tmp​

ls -ld /tmp
# drwxrwxrwt 12 root root 4096 ... /tmp
#          ^
#          t = sticky bit

O /tmp é gravável por todos, mas graças ao sticky bit cada usuário só apaga os próprios arquivos.

Como ler a notação​

SímboloSignificado
s minúsculoBit especial ativo e x ativo
S maiúsculoBit especial ativo, mas sem x (geralmente indica configuração incorreta)
t / TO mesmo para o sticky bit
chmod u+s arquivo    # ou chmod 4755 arquivo
chmod g+s pasta      # ou chmod 2775 pasta
chmod +t pasta       # ou chmod 1777 pasta
Segurança: SUID é alvo de ataque

Um binário SUID-root com falha pode virar escalação de privilégios. Auditar periodicamente é uma boa prática:

find / -perm -4000 -type f 2>/dev/null     # SUID
find / -perm -2000 -type f 2>/dev/null     # SGID
find / -perm -0002 -type f 2>/dev/null     # arquivos graváveis por todos

Compare a lista com uma linha de base. Qualquer binário SUID novo e desconhecido merece investigação.

3.2 ACL (Access Control Lists)​

O modelo ugo é limitado: só permite um dono e um grupo por arquivo. E se a Maria (dona) e o grupo devs precisarem de acesso, e o João (de fora do grupo) também?

As ACLs permitem conceder permissões a usuários e grupos adicionais, de forma individual.

getfacl arquivo                         # exibe as ACLs
setfacl -m u:joao:rw arquivo            # joao: leitura e escrita
setfacl -m g:auditoria:r arquivo        # grupo auditoria: leitura
setfacl -x u:joao arquivo               # remove a entrada do joao
setfacl -b arquivo                      # remove todas as ACLs
setfacl -R -m u:joao:rX /opt/app        # recursivo

ACL padrão (default): em diretórios, define a ACL que será herdada por novos itens.

setfacl -d -m g:devs:rwx /srv/projeto

Pontos importantes:

  • Um + ao final das permissões no ls -l indica que há ACL (drwxrwxr-x+)
  • A máscara (mask) limita as permissões efetivas de todas as entradas de ACL (exceto o dono). Se uma ACL "não funciona", confira a linha mask:: no getfacl
  • O filesystem precisa suportar ACL (ext4 e XFS suportam por padrão nas distribuições atuais)

3.3 Atributos de arquivo​

Além das permissões, o filesystem (ext4, XFS) suporta atributos que valem até para o root.

sudo chattr +i arquivo    # imutável: não pode ser alterado, apagado ou renomeado
sudo chattr +a arquivo    # append-only: só aceita acréscimo (ideal para logs)
sudo chattr -i arquivo    # remove o atributo
lsattr arquivo            # lista os atributos

Quando usar: proteger arquivos críticos contra remoção acidental ou alteração indevida (ex.: um /etc/resolv.conf que não pode ser sobrescrito).

Pegadinha clássica: o arquivo está com rw correto, o dono certo, e mesmo assim dá Operation not permitted até para o root. Rode lsattr: provavelmente há um i ativo.

3.4 Escalação de privilégios: su e sudo​

ComandoComportamento
suTroca de usuário sem carregar o ambiente dele. Pede a senha do usuário de destino
su -Troca de usuário com o ambiente de login completo
sudo comandoExecuta um comando com privilégios de outro usuário (padrão root). Pede a senha do próprio usuário
sudo -iShell de login como root
sudo -lLista o que o usuário atual pode executar

Por que sudo é preferível a logar como root:

  • Auditoria: cada comando fica registrado, associado a quem o executou
  • Menor privilégio: é possível liberar apenas comandos específicos
  • Sem compartilhar a senha do root

Quem tem acesso ao sudo​

Depende da distribuição, pelo grupo:

DistribuiçãoGrupo administrativo
Debian / Ubuntusudo
RHEL / Rocky / Alma / Fedorawheel
sudo usermod -aG sudo maria     # Debian/Ubuntu
sudo usermod -aG wheel maria    # RHEL e derivadas

Configurando o sudoers​

Sempre edite com visudo, que valida a sintaxe antes de salvar. Um erro no /etc/sudoers pode bloquear todo o acesso administrativo.

sudo visudo                          # edita /etc/sudoers
sudo visudo -f /etc/sudoers.d/devops # edita um arquivo em sudoers.d
sudo visudo -c                       # apenas valida a sintaxe

Sintaxe de uma regra:

quem   onde=(como_quem)   o_quê

%wheel   ALL=(ALL)       ALL
maria    ALL=(root)      /usr/bin/systemctl restart nginx
%devops  ALL=(ALL)       NOPASSWD: /usr/bin/systemctl status *
ElementoSignificado
maria / %devopsUsuário ou grupo (o % indica grupo)
ALL (primeiro)Em quais hosts a regra vale
(root)Como qual usuário pode executar
Último campoQuais comandos (use caminho completo)
NOPASSWD:Dispensa a senha (use com critério)

Boa prática: não edite o /etc/sudoers principal. Crie arquivos individuais em /etc/sudoers.d/, com permissão 0440, um por função ou equipe. Fica organizado, versionável e fácil de remover.

Cuidado com comandos "liberados" que dão shell

Liberar sudo vim, sudo less ou sudo find equivale a liberar root completo, pois esses programas permitem abrir um shell interno (:!sh). Libere somente comandos específicos e, quando possível, com argumentos fixos.

3.5 Quando o acesso é negado por outra camada​

Se as permissões ugo e ACLs estão corretas e ainda assim há Permission denied, investigue as camadas adicionais:

CamadaComo verificar
SELinux (RHEL e derivadas)getenforce, ls -Z, ausearch -m avc -ts recent
AppArmor (Ubuntu, SUSE)aa-status, dmesg | grep -i apparmor
Atributos do filesystemlsattr
Filesystem somente leituramount | grep ro,
Opções de montagemnoexec, nosuid, nodev no fstab

Conexão com Containers e Kubernetes

O modelo de UID/GID é o mesmo dentro dos containers, porque eles compartilham o kernel do host. Isso tem consequências diretas:

  • Rodar como root no container significa UID 0, que é o mesmo UID 0 do host (a menos que se use user namespaces). Por isso a boa prática é usar USER no Dockerfile
  • No Kubernetes, o securityContext do Pod controla essa identidade:
securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  runAsGroup: 3000
  fsGroup: 2000
  • fsGroup aplica um GID aos volumes montados, resolvendo o clássico Permission denied quando a aplicação não-root precisa gravar em um volume persistente
  • No systemd, as diretivas User= e Group= (post anterior) seguem a mesma lógica: processo sem privilégios, com o mínimo de acesso
Gancho para o próximo conteúdo

Este tema é o alicerce para Namespaces e cgroups (user namespace) e para Segurança em Kubernetes (securityContext, Pod Security Standards).

Boas Práticas

  • Princípio do menor privilégio: conceda apenas o acesso necessário
  • Nunca trabalhe como root. Use contas nominais e sudo
  • Uma conta por pessoa. Evite contas compartilhadas (perde a rastreabilidade)
  • Use grupos por função (devops, dba, suporte) em vez de permissões por usuário
  • Contas de serviço: usuário dedicado, nologin, sem senha utilizável
  • Políticas de senha e expiração com chage, ou autenticação por chave SSH
  • Revise contas periodicamente: remova ou bloqueie contas de quem saiu da empresa (usermod -L, chage -E 0)
  • Evite 777. Corrija dono e grupo
  • Proteja chaves e segredos: chmod 600 em chaves privadas, 700 em ~/.ssh
  • Audite SUID/SGID e arquivos graváveis por todos periodicamente
  • Em ambientes com AD/LDAP, use getent e valide o mapeamento de UID/GID

Troubleshooting: "Permission denied"

Roteiro de diagnóstico, nesta ordem:

# 1. Quem sou eu e a quais grupos pertenço?
id

# 2. Qual é a permissão do arquivo?
ls -l /caminho/arquivo

# 3. E de TODOS os diretórios do caminho? (falta de x é causa comum)
namei -l /caminho/completo/arquivo

# 4. Existe ACL?
getfacl /caminho/arquivo

# 5. Existe atributo imutável?
lsattr /caminho/arquivo

# 6. SELinux ou AppArmor?
ls -Z /caminho/arquivo
getenforce

# 7. O filesystem está somente leitura?
findmnt -T /caminho/arquivo

Erros comuns:

SintomaCausa provável
Adicionou ao grupo, mas continua sem acessoA sessão não recarregou os grupos. Faça logout/login ou use newgrp
Perdeu o acesso ao sudo após usermod -GFaltou o -a: os grupos suplementares foram substituídos
Arquivo com rw, mas não consegue abrirFalta x em algum diretório do caminho (use namei -l)
Não consegue apagar um arquivo que é seuA permissão w é do diretório, ou há sticky bit/atributo i
user is not in the sudoers fileUsuário fora do grupo sudo/wheel ou sem regra no sudoers
Erro de sintaxe no sudoersEditou sem visudo. Recupere com pkexec visudo ou modo de resgate
Script não executaFalta x, ou o filesystem está montado com noexec
Root recebe Operation not permittedAtributo imutável (chattr +i) ou SELinux
Donos aparecem como números após restoreO UID não existe no sistema de destino

Boas práticas

  • Menor privilégio, sudo nominal e grupos por função
  • Sempre usermod -aG (nunca só -G)
  • Nunca chmod 777: corrija dono e grupo
  • Edite o sudoers apenas com visudo e use /etc/sudoers.d/
  • Audite SUID/SGID e contas inativas
